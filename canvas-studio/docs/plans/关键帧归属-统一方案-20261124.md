> **⚠️ 状态：已拍板不采用（2026-11-24，用户决定）。** 保持现状——**允许分镜没有关键帧**，这是设计上的选择，不是缺陷。本文整篇（含「归属改必填」「堵绕过口子」「三条修复通道」「与布局侧同批验收」）**不执行、不排期**，仅作过程留档；下一个人请勿据此改代码。同日的布局侧方案（`历程视图-分镜一行一镜`）**已单独落地**，与本文解绑。

> **一句话：归属就是「这张图引用了哪张分镜卡」这一条血缘。方案不新增字段、不拆工具，只做四件事——把这条血缘变成必填、堵住绕过它的口子、给已有的断链补三条修复通道、删掉两处「以为有兜底」的假承诺。**

- `关键帧判镜-sourceIds归属-方案-20261124.md`（根因证据链，保留不动）
- `历程视图-分镜一行一镜-方案-20261124.md`（布局侧，与本方案**必须同批验收**）

## 1 问题：三种「对不上」，只有一种能机械化防

| 形态 | 表现 | 本项目实测 | 能否机械化 |
|---|---|---|---|
| **① 漏绑** | 图出了，`sourceIds` 里没有分镜卡 | **9 / 9 张全中** | **能** — 产生侧强校验 |
| ② 绑错 | 卡绑上了，但绑的不是画的那一镜 | 视频侧 4/4 正确，图片无从判断 | **不能** — 工具层看不见画面，只能靠 `qc_shot` 事后核对 |
| ③ 悬空 | 分镜卡被取代 / 重建后，引用失效 | 未观测到 | 部分 — 本期不覆盖（见 §7） |

用户说的「不知道图片是否归属分镜」，指的是 ①。**本方案只解决 ①，并明确承认 ②③ 的边界** —— 不把 ① 的修法包装成「归属问题已被彻底解决」。

## 2 现状盘点：判定链已经完整，缺口只有一个

一条图从生成到判镜，现有链路是这样的：

```
模型调 image_generate(shotRefs: [...])
  → resolveShotRefs()            reference-resolve.ts:291
  → params.shotNodeIds
  → sourceIds（并入分镜卡 id）     generate.ts:3100+
  → deriveShotSemantics()          canvas-view.ts:429   ← 判镜在此
  → laneOfNode / computeWaterfallLayout（分栏、托盘）
```

已具备的能力（**不需要重做**）：

| 已有能力 | 位置 | 说明 |
|---|---|---|
| 卡找不到时报可操作错误 | `reference-resolve.ts:291` | 抛 `CS-USER-ERR`，带候选卡标题 + "未落地就停手"的出路。质量很高 |
| 镜位锚点集的权威口径 | `shot-versions.ts:195` `shotAnchorCardsOf` | 显式声明优先、血缘唯一时回退、多卡拒绝 —— CV-277 已修好 |
| 判镜唯一实现 | `canvas-view.ts:429` `deriveShotSemantics` | 三趟传播：卡→镜号、视频→继承、图引用卡→关键帧 |
| 意图→操作类型 | `generate.ts:1635` `operationTypeOf` | `shotNodeIds` 非空 = 关键帧；空 = `look` |
| 绑镜时自动编组 | `generate.ts:1816` `attachShotGroup` | 并入「分镜 N · 素材」组 |

**唯一的缺口：`shotRefs` 是可选参数。**

`host-tools.ts:2255` 只写了 `if (Array.isArray(a.shotRefs) && a.shotRefs.length > 0)` —— 不传就跳过，`shotNodeIds` 为空，`operationTypeOf` 静默返回 `look`，图正常落盘。**没有任何一处会因为"该绑却没绑"而拒收。**

所以这不是「缺能力」，是「缺必填」。

## 3 方案：四层，缺一层都不闭环

### L1 · 产生侧强制（治本）

给 `image_generate` / `image_generate_withtxt` 加**必填**参数 `intent`：

| `intent` | 校验（全部在 `execute` 内、`runGeneration` 之前抛） | 落盘 `operationType` |
|---|---|---|
| `'shot'` | ① `shotRefs` 必填且**恰好 1 张卡**<br>② `aspectRatio` 必填<br>③ 卡必须是分镜卡（交给 `resolveShotRefs` 已有守卫） | `text-to-image` / `image-to-image` |
| `'look'` | ① `shotRefs` 必须为空（传了就报错，防"两头都填"的模糊态） | `look` |

要点：

1. **`intent` 不进 `operationType` 枚举**，只进 `generationPrompt` 落盘。`operationTypeOf` 的判据仍看 `shotNodeIds` —— 少改一处枚举，0 迁移。
2. **「恰好 1 张」只约束模型的 `shotRefs` 入参，不约束 `sourceIds`。** 后者可能因 CV-031 继承而带多张卡（`shot-versions.ts:55` 已注明），强行要求 `sourceIds` 恰好 1 张会撞上 CV-277 的既有保守口径。
3. 报错文案必须给候选卡标题（复用 `resolveShotRefs` 的 `suggestRefCandidates`）—— 只说「缺参数」模型会换参数绕道，这是 2026-10-22 的真机教训。
4. `character_generate` 同样加 `intent`：它的 `operationTypeOf` 分支（`generate.ts:1645`）已经按 `shotBound` 二分，只是没有必填约束。

**这一层解决 ① 的"以后不再发生"。**

### L2 · 阶段闸（防"用 look 绕过"）

L1 有一个天然漏洞：模型想省事，直接传 `intent:'look'`，参数完全合法，图照样出，`operationType` 还正确地标成 `look`。**漏传从「错误」变成「合法的选择」，反而更难查。**

所以必须有阶段闸。规则：

| `state` | `intent='look'` | 依据 |
|---|---|---|
| `storyboarding`（落地前） | **允许**，仍受 `lookBudget` 3 张/周期限制 | 澄清期出样张/定妆照/概念图是合法动作 |
| `keyframe_review` | **禁止** | 分镜已落地，此时出样张等于绕过关键帧审批 |
| `executing`（单向终点） | **禁止**，除非持有一次性令牌 | 产线已开，改风格必须用户发起 |

现状体检（这是真漏洞，不是理论风险）：

| `state` | 现在 look 出图 |
|---|---|
| `storyboarding` | 放行，3 张/周期（`look-budget.ts:34`） |
| `keyframe_review` | 拦（`approval-gate.ts:102` `PRODUCING_TOOLS`），**但 auto 模式放行** |
| `executing` | **完全无人管** — `approval-gate.ts:155` 直接 `return null`，`lookBudget` 不适用 |

两个结构性事实：

- `approval-gate.ts:153` `if (mode !== 'confirm') return null` —— **auto 模式下整道审批门失效**，`keyframe_review` 也拦不住。所以新闸**不能塞进 `approvalGateMessage`**，必须独立成 `assertLookAllowed(workflow, intent)`，否则在 auto 下就是个摆设。
- `executing` 是单向终点，永不回退，项目一旦落地就永远停在这 —— 令牌是唯一能表达「临时放宽」的手段。

**「用户要求修改风格」的机械化实现**（零新增 UI，复用现有交互）：

```
1. 模型调 intent='look'，state=executing
2. assertLookAllowed 抛 CS-USER-ERR：
   「已进入分镜制作阶段，不允许自动生成效果图。若用户明确要求调整风格，
     请先 ask_user_choice 征得确认；不要换参数绕道。」
3. 模型 ask_user_choice("是否进入风格调整？")
4. 用户答「是」→ answerPendingQuestion 成功
   → workflow.lookRevisionUntil = now + 2h（一次性令牌）
5. 模型重调 look → 通过 → 成功后清空令牌
```

报错文案本身就是模型的行为指南，与 `assertLookBudget` 的既有范式一致（`look-budget.ts:40`）。令牌置位挂在 `routes.ts` 已有的 `resetLookBudget(projectId)` 同一处接线。

新闸（仅非 `storyboarding` 生效）与 `lookBudget`（仅 `storyboarding` 生效）**零重叠、恰好互补**，不需要重构 `lookBudgetApplies`。

### L3 · 读侧反查（救历史，只读不写盘）

`sourceIds` 已经空的存量图，靠视频的完整血缘倒推。**精确规则**：

> 对每个分镜卡 → 找 `sourceIds` 含该卡、且 `toolName !== 'compose'` 的视频 → 取该视频 `sourceIds` 中**第一个** `kind === 'image'` 且 `toolName === 'image_generate'`、并且未被取代（`supersededBy === undefined`）的元素 = 该镜关键帧。

实测命中（本项目 4 镜视频的真实 `sourceIds` 位序）：

| 镜 | 视频 | `sourceIds` 位序 | 反查结果 |
|---|---|---|---|
| 1 | `2134a198` | `[0]` character_sheet, `[1]` image_generate `90e8ec96`, `[2]` 卡 | `90e8ec96` ✓ |
| 2 | `14523ffc` | `[0]` character_sheet, `[1]` image_generate `6403940c`, `[2]` 卡 | `6403940c` ✓ |
| 3 | `28341673` | `[0]` image_generate `1adf21ea`, `[1]` character_sheet, `[2]` 卡 | `1adf21ea` ✓ |
| 4 | `13e522cc` | `[0]` image_generate `86492b1c`, `[1]` character_sheet, `[2]` image_generate `2475df87`（旧版）, `[3]` 卡 | `86492b1c` ✓ |

**注意：不是「第一个画面位」。** 镜 1/2 的第 0 位是 `character_sheet`，按「第一个 image」会取到角色四视图。必须同时排除 `character_sheet` 和已被取代的版本 —— 镜 4 第 2 位就是一张被取代的旧图。

排除项（四条，缺一条就会误判）：

1. `toolName === 'character_sheet'` —— 镜 1/2 的第 0 位
2. `supersededBy !== undefined` —— 镜 4 的第 2 位
3. `origin === 'manual'` —— 用户上传的参考图不该被判成关键帧
4. **被任一 `character_sheet` 引用的图** —— 角色设计图（本项目 `94bf511c`，768×1424 竖幅）也是 `image_generate` 产物，`toolName` 排除不掉它；靠「它被 `54ea815e` 这条四视图引用」这一条挡住。虽然当前它没被视频引用、反查天然不会命中，但一旦某镜视频把角色图放在第 0 位就会误判，这条守卫是便宜的保险。

- 落点：`deriveShotSemantics` 加**第四趟**（`canvas-view.ts:447` 之后），纯函数、不写盘
- 先到先得：一张图已归属某镜就不再改判

本项目的 9 张 `image_generate` 产物构成（反查会被拿来做回归基线）：

| 类别 | 张数 | 节点 | 反查是否采纳 |
|---|---|---|---|
| 现行关键帧 | 4 | `90e8ec96` / `6403940c` / `1adf21ea` / `86492b1c` | **采纳**（各归其镜） |
| 被取代的历史版本 | 4 | `854587f9` / `a83ea8cd` / `2475df87` / `62b2c1ac` | 否（排除项 2） |
| 角色设计图 | 1 | `94bf511c`（被 `54ea815e` 引用） | 否（排除项 4） |

**局限（必须在文档里说清，不能夸大）**：

1. 该镜**还没出视频**时，反查完全失效 —— 本项目能命中 4/4 是因为 4 镜都有视频，属于幸运而非普遍规律。
2. 一镜若用「多图融合参考」出视频，第 0 位不一定是构图基准帧。
3. 镜 4 有两条视频（`944a7684` 旧版 → `13e522cc` 现行），两条的第 0 位都指向 `86492b1c`，结果幂等。但规则上应**优先取未被取代的视频**，避免旧版视频的参考组合污染判断。

所以 L3 是**有限的补救**，不能当通解。

与 `shotAnchorCardsOf`（`shot-versions.ts:195`）的关系：那一个回答「**这条视频**属于哪一镜」（供版本取代判重），本层回答「**这张图**属于哪一镜」。思路同构（显式优先、血缘兜底），但输入和消费方都不同，**不要合并成一个函数** —— 合并会让版本判重的 CV-277 保守口径被反查规则污染。

副作用评估：`deriveShotSemantics` 同时被 `arrangeCanvas`（整理布局）和 `computeWaterfallLayout`（历程视图）消费，命中后这些图会从「创意」栏移到「关键帧」栏 —— **这正是期望效果**，也是本方案必须与布局方案同批验收的原因：布局改完若图还在创意节，4 格行只有 3 格，会被误判成布局没做对。

### L4 · 手动归镜（人工兜底，唯一写盘通道）

反查认不出的图（该镜无视频 / 多图融合 / 历史上被挪动过），只能人工指定。

- 位置：节点详情面板加「归属到第 N 镜」
- 实现：往 `sourceIds` 追加分镜卡 id + 走 `attachShotGroup`（`generate.ts:1816`）并入「分镜 N · 素材」组
- 不引入新字段：**归属仍只有一个事实源 `sourceIds`**

这是历史数据唯一的确定修复手段。也是 L1/L2 上线后，用户纠正模型偶发错误的唯一入口。

## 4 一并删掉两处假承诺

模型之所以连续 9 次漏传而不自查，是因为两处文档告诉它"有兜底"。**改 L1 之前必须先删这两条，否则模型会继续依赖不存在的校验。**

| # | 位置 | 原文 | 实际 |
|---|---|---|---|
| 1 | `skills/drama-episode-executor/SKILL.md:45` | 「角色镜全带 `shotRefs` 定妆句柄（绑镜纪律，**Host 会拒收缺省调用**）」 | 代码里**没有**这条校验，`host-tools.ts:2255` 只是 `if (length > 0)` 才设置 |
| 2 | `host-tools.ts:2235 / 2288 / 2319`（三个工具各一处） | 「**传了 `shotRefs` 时必传** aspectRatio——Host 会拒收缺省调用」 | `generate.ts:2331` 是 `params.aspectRatio ?? runtime().defaultAspectRatio()`，**只回退不拒收** |

第 2 条在 L1 里正好变成真的（`intent='shot'` 时强制校验 `aspectRatio`），届时文案不用改。但第 1 条必须删/改，因为 L1 的校验点是 `intent` 而非 `shotRefs`。

另有一处结构性不一致（不是假承诺，但会在 L1 之后暴露）：`host-tools.ts:2258` 的 `shotBound` 把 `storyboardRef` 的 shot id 形态也算作绑镜（门禁用），而 `operationTypeOf` 只看 `shotNodeIds`（标签用）—— 两条路各算一次。shot 形态已停用，L1 落地时顺手收敛成单一来源。

## 7 明确不做

| 不做 | 理由 |
|---|---|
| 新增 `shotId` / `frame` 字段 | `sourceIds` 已是唯一事实源，加字段就是第二份真相。帧位（首帧/末帧）语义本期不做 —— 一镜多 take 的帧位绑定是独立设计 |
| 拆成 `keyframe_generate` / `look_generate` 两个工具 | 拆完模型多了一条"选错工具"的合法路径，比"漏参数"更难查；工具数已 37 个。`intent` 参数拿到同等校验强度，零迁移 |
| 改 `operationType` 枚举 | `look` / `text-to-image` / `character-sheet` 的语义已够用，动枚举牵动 `OPERATION_STAGE`、`OPERATION_PRODUCT`、连线色、标签四处 |
| 覆盖形态 ②（绑错镜） | 工具层看不见画面，无法判断"这张图画的是不是镜 2"。只能靠 `qc_shot` 事后核对 |
| 覆盖形态 ③（卡重建后悬空） | 分镜卡被重新落地取代时，引用它的图如何迁移，是独立问题，本期不碰 |
| 回填历史 `sourceIds` | 开发阶段只修产生路径。历史画布靠 L3 读侧投影 + L4 手动归镜 |
