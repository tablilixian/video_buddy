## 0. 结论与边界

桌面端支付遵循一条固定边界：**渲染层不碰 token、不碰金额、不判成功**。

1. client 只请求 Host 的同源业务路由 `/canvas-studio/billing*`；
2. Host 用自己缓存的 access token 请求 DramaServer `/v1/billing/*`；
3. 商品、金额、币种、积分全部由服务端从已发布商品版本读取，**请求体不含任何金额字段**；
4. 拿到 `checkout_url` 后用 `window.open` 交系统浏览器，应用内不嵌 Stripe；
5. 支付成功与否以服务端 Webhook 履约结果为准，client 只靠刷新 `overview` 观察。

**本轮做**：订阅/套餐/积分包展示、购买、Stripe Customer Portal 管理、支付后到账刷新、余额门禁（G1）。
**本轮不做**：退款/拒付入口（服务端无桌面 API）、套餐升降级与按比例换购（一期不支持）、精确计费（G2，需后端价格表 + 冻结/结算接口）。

### 0.3 实测暴露的两个契约坑（会直接影响实现）

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| **409 的 code 无法区分原因** | `409` 的 `code` 恒为 `conflict`，真实原因只在 `message`：`idempotency key conflict` / `subscription checkout already pending` / `checkout expired` / `checkout failed` / `checkout already complete` | 新增纯函数 `classifyCheckoutConflict(message)`，**唯一实现点**，单测覆盖 5 条 message；禁止在 UI 层 `includes('pending')` 散落判断。`portal_unavailable` 有独立 code，不受此影响 |
| **`GET` 失败仍返回 200 + 体内 `error`** | 上游 overview 读失败时不是非 2xx | Host 侧统一包成 `BillingSnapshot.error`；client 的 `ok` 判断必须看 `error` 字段，不能只看 `res.ok` |

> token 一律走 `~/.cache/cs-probe-token`（0600）+ 环境变量，不落日志、不进文档、不写进仓库。探测产物见 `docs/api-probe/billing-20261102/`（`checkout_url` 已脱敏）。

## 2. 服务端契约（桌面端只用三条）

| 方法 | Host 路由（本方案） | 上游 | 用途 |
| --- | --- | --- | --- |
| `GET` | `/canvas-studio/billing` | `/v1/billing/overview` | 订阅 + 余额 + 待支付 + 商品目录 |
| `POST` | `/canvas-studio/billing/checkout` | `/v1/billing/checkout-sessions` | 创建套餐 / 积分包 Checkout |
| `POST` | `/canvas-studio/billing/portal-sessions` | `/v1/billing/portal-sessions` | 打开 Stripe Customer Portal |

与上游文档的**唯一偏离**：路径前缀用 `/canvas-studio/billing`（本插件全部路由同前缀），语义与载荷完全一致。

必须遵守的硬规则（摘自上游文档，实现时逐条对照）：

1. `POST /checkout` 必带 `Idempotency-Key`（1–200 字节、可打印 ASCII），请求体**只允许** `kind` + `product_code`，未知字段被拒；
2. 同一 key + 同 kind/product + Session 未过期 → 返回同一 `checkout_url`（仍 201）；key 相同但商品变了 → `409`；Session 过期/已支付/创建失败 → `409`；
3. 商品 code 必须来自 `overview`，**不得硬编码**；
4. 所有 billing 响应 `Cache-Control: no-store`；
5. `GET` 读失败时上游返回 200 + 体内 `error`；`POST` 失败才是非 2xx + `{error:{code,message}}`；
6. 限流：认证接口 600/min/用户，checkout 与 portal 额外 30/min，超限 `429` + `Retry-After`。

### 4.3 状态矩阵（7 态，与 `CreditsCard` 同精神）

| 态 | 判据 | 渲染 |
| --- | --- | --- |
| 未配置账号体系 | `businessApiBase` 或 `supabaseUrl` 为空 | 入口不渲染（整块隐藏，与登录入口一致） |
| 未登录 | `signedIn === false` | 页面内空态 + 「登录后查看订阅」，按钮调 `requestLoginPrompt()` |

| 待支付 | `pending_checkout !== null` | 顶部横幅 + 对应卡片按钮「继续支付」 |

### 5.2 购买流（核心）

```
点击购买
  → 生成/复用幂等键（见 5.3）
  → POST /canvas-studio/billing/checkout  { kind, product_code }
  → 201 { checkout_url, order_id }
  → 本地登记 pending（用返回值构造临时 pending_checkout）
  → window.open(checkout_url, '_blank', 'noopener')   // 交系统浏览器
  → 进入 pending 态：横幅 + 5s 轮询（见 6.4）
```

硬约束：

1. **不内嵌 Stripe 表单、不加载 Stripe.js、不判定成功页**；
2. 打开前 Host 侧校验 URL：只放行 `https://stripe.com`、`https://*.stripe.com`，Portal 只放行 `https://billing.stripe.com`，否则 `502`；
3. 套餐请求在飞时**禁用全部套餐按钮**；积分包只禁用当前这张卡（多买互不影响）；
4. 失败不自动重试（幂等键语义要求「同一次购买意图」才复用，自动重试必须复用同 key，本轮不做自动重试，交给用户点击）。

### 5.3 幂等键策略（比参考实现更严）

参考实现每次点击都生成新 key，上游文档自己承认「网络层自动重试换新 key 会导致积分包重复下单」。本方案改成**按购买意图复用**：

```
keyOf(kind, product_code) → Map 内查
  有且未过期(10min) 且上次结果不是终态  → 复用
  无 / 终态（checkout expired | failed | already complete）→ crypto.randomUUID() 新建
```

- key 只存在 client 内存（`Map`），不落盘、不进日志；
- 终态判定：HTTP 409 且 `classifyCheckoutConflict(message) ∈ {expired, failed, already_complete}` → 换新 key 后允许用户再点一次（**实测 409 的 code 恒为 `conflict`，只能靠 message 细分，见 §0.3**）；
- `409 already_pending` 不换 key，改为刷新 overview 让 UI 看到 pending。

### 5.4 管理订阅流

```
当前订阅 provider==='stripe' 且 status ∉ {canceled, expired}
  → POST /canvas-studio/billing/portal-sessions
  → 201 { portal_url } → window.open → 记录subscriptionKey（plan_code|status|cancel_at_period_end|current_period_end）
  → focus 刷新 + 5s 轮询，key 变化即停并提示「订阅状态已更新」；2min 未变停轮询提示手刷
```

`manual` 订阅不显示「管理订阅」；Portal 不可用（`409 portal_unavailable`）→ 提示「当前订阅不支持在线管理，请联系客服」，不弹重试。

### 5.5 错误分派表（client 唯一实现点）

| code / status | UI 行为 | 文案 |
| --- | --- | --- |
| `unauthenticated` / 401 | 触发一次 `pushSession` 重试；仍失败则提示重新登录 | 登录状态已失效，请重新登录。 |
| `permission_denied` / 403 | 页面级受限态，停请求 | 账号当前不可用，请联系客服。 |
| `forbidden` / 403 | 内部集成错误，仅 toast + 日志 | 请求被本地拒绝，请重试或重启应用。 |
| `invalid_argument` / 400 | 刷新 overview（商品 code 可能过期） | 商品信息已更新，请重试。 |
| `not_found` / 404 | 刷新 overview | 该商品已下架。 |
| `conflict` / 409 | **先过 `classifyCheckoutConflict(message)`**：`already_pending` → 刷新 overview 显示待支付横幅；`expired`/`failed`/`already_complete` → 换幂等键 + 刷新 overview；`idem_mismatch` → 换键后允许重试一次 | 按分支给文案，不统一说「已有订阅」（见 §0.3） |
| `portal_unavailable` / 409 | 隐藏管理入口 + 提示 | 当前订阅不支持在线管理。 |
| `rate_limited` / 429 | 按 `Retry-After` 禁用按钮倒计时 | 请求过于频繁，请 N 秒后再试。 |
| `unavailable` / 503 | 可重试提示，不清旧数据 | 支付服务暂时不可用，请稍后重试。 |
| `invalid_response` / 502 | 提示 + 日志 | 支付返回异常，请稍后重试。 |
| `transport_error` / `status=0` | 保留快照 + 顶部细条 | 无法连接支付服务，稍后自动重试。 |

### 5.6 边界场景

| 场景 | 处理 |
| --- | --- |
| 用户重复点同一商品 | 幂等键复用 → 服务端返回同一 URL，不产生第二单 |
| 已有 pending 套餐还点另一套餐 | 服务端 409 → 刷新 overview → 横幅显示「待支付」+「继续支付」 |
| 已订阅用户买积分包 | 允许（`purchasable` 不受订阅影响） |
| 打开 Stripe 后直接关浏览器 | Session 过期或 `checkout.session.expired` → pending 消失 → 按钮恢复；轮询 2min 后停 |
| 支付完成但 Webhook 慢 | 轮询期间保持 pending 横幅，超时后提示「支付结果确认中，请稍后手动刷新」 |
| 面板打开期间 token 过期 | 401 → pushSession 一次重试；不许静默失败 |

## 6. 数据刷新设计（**现状不全面的根因在这里**）

### 6.1 现有刷新触发源清单

| 数据 | 权威源 | 现有触发 | 位置 |
| --- | --- | --- | --- |
| access token | client（supabase-js） | boot / `SIGNED_IN` / `TOKEN_REFRESHED` / `SIGNED_OUT` + `visibilitychange` 补推 | `auth-store.ts:306-314` |
| 余额 | Host 缓存 30s TTL | 卡片挂载、登录后预取、一次生成彻底结束（立刻 + 6s 复检）、`visibilitychange` | `credits-store.ts:96-108`、`index.ts:295/1492`、`account-state.ts:38` |
| 生成队列 | Host | 2s 轮询（有在途任务才跑） | `index.ts:1448/1503` |
| 渲染任务 | Host | 1s 轮询 | `index.ts:1520/1693` |
| 技能广场 | Host | 3s 轮询（打开才跑） | `SkillMarket.tsx:48` |
| text 模型目录 | Host 缓存 5min | **只在会话推送时重拉** | `account-state.ts:30` |
| 项目 / 资产库 / 画布 | Host | 打开与操作后即刷 | `StudioFrame` 各 action |

### 6.2 五个缺口（本方案要补的）

| # | 缺口 | 后果 | 修法 |
| --- | --- | --- | --- |
| **R-1** | 只有 `visibilitychange`，**没有 `window.focus`** | Electron 里切到系统浏览器付款，页面始终 `visible` ⇒ 回来**一次都不刷新**；所有「付款后到账」都看不到 | 新增 `refresh-signal.ts`：`focus` + `visibilitychange` 双通道，1s 内去重，auth / credits / billing 三层共用 |
| **R-2** | 没有 pending checkout 轮询 | 支付是 Webhook 异步履约，客户端无任何观察手段，只能靠用户手点刷新 | billing-store 内 pending 轮询：5s / 2min 上限 / focus 立即一次 / pending 消失即停 |
| **R-3** | 订阅状态变化（`cancel_at_period_end`、`past_due`）无入口无轮询 | Portal 改完续费状态回来仍是旧文案 | Portal pending 态同款轮询，判据是「订阅状态 key 变化」 |
| **R-4** | 登出只清余额，不清订阅/商品 | 换账号后短暂看到上一个账号的订阅（正确性 + 隐私） | `notifyAuthCleared()` 旁加 `resetBilling()`；`billing-store` 订阅 auth 变化自行 reset |
| **R-5** | 商品目录 5min TTL 仅由会话推送触发 | 后台上下架商品后，用户不重登看不到 | billing 快照 15s TTL 自带目录，focus 时按 TTL 重取即可（不动 account-state 的目录链路） |

### 6.3 刷新矩阵（本方案的完整口径）

| 数据 | 触发源 | 频率 / TTL | 停止条件 |
| --- | --- | --- | --- |
| billing 快照 | 打开面板（force）、回到前台（TTL 15s）、pending 轮询、支付/Portal 回来后 | 打开必刷；focus 按 TTL | 面板关闭即停轮询 |
| 余额（左栏卡） | 登录预取、卡片挂载、回到前台、一次生成结束（+6s 复检）、**支付成功后**、billing 轮询命中变化 | Host TTL 30s | 常驻（低频） |
| 登录态补推 | 回到前台（focus/visibility） | 1s 去重 | 常驻 |
| text 模型目录 | 会话推送（不变） | Host TTL 5min | 常驻 |
| pending 轮询 | 购买成功后 / 进入面板时已有 pending | 5s，最长 2min | pending 消失、面板关闭、超时 |
| Portal 轮询 | 打开 Portal 后 | 5s，最长 2min | 订阅状态 key 变化、面板关闭、超时 |

### 6.4 pending 轮询实现纪律

1. **单例**：`billing-store` 内一个 `timer`，重复进入只重置不叠加；
2. **面板关闭即停**：`BillingPage` 卸载调 `stopPendingPoll()`（不做「后台常驻轮询」）；
3. **focus 抢占**：轮询期间用户切回来，立刻打一拍，计时器重置（不额外加一次）；
4. **只在 pending 时轮询**：`pending_checkout === null` 且无本地 waiting 订单 → 不起定时器；
5. **超时文案**：2min 后停并显示「支付结果确认中，可手动刷新」；
6. **变化判定**（命中任一条即认为履约完成）：
   - `pending_checkout` 由非空变 null；
   - `subscription.plan_code` / `status` / `cancel_at_period_end` 变化；
   - `credits.available_balance` 变化（超过 0.0001）。
7. **连锁刷新**：命中后 `refreshCredits(true)`（左栏卡同步变），并 toast「支付状态已更新」。

### 6.5 明确**不做**的刷新

| 不做 | 原因 |
| --- | --- |
| 常驻轮询 billing（面板关闭后继续跑） | 白烧请求；用户不看页面时 `no-store` 数据没有意义 |
| 回到前台时全量重拉项目/资产/画布 | 与支付无关，放大抖动面；沿用各自现有触发 |
| 把 billing 响应写进 localStorage / sessionStorage | 上游要求 `no-store`，且订阅是隐私数据 |
| 支付成功页回跳 deep link | 上游契约就是「系统浏览器 + Webhook 履约」，不引入回调协议 |
| 在 `wrapStudioToolDefinition` 里做计费门禁 | 那里是「脏参数」语义，混入计费会连本地 ffmpeg 工具一起拦（见 §7） |

## 7. 余额门禁 G1（预检）

### 7.1 位置与会话

单点实现：`src/billing-gate.ts` 导出 `assertCreditsAvailable()`。
调用点：`generate.ts:396` 现有鉴权 fail-fast 的**紧邻处**（`if (isDramaAuthRequired() && getAuthSession() === null) throw CS-AUTH-001`）。那里是全部消耗型请求的唯一汇聚点，且语义同族（「这类请求需要账号」）。

### 7.2 判据

| 条件 | 行为 |
| --- | --- |
| 未启用（`businessApiBase` 空 / 未配置 Supabase） | 放行（本地模式，与现有 fail-open 一致） |
| 未登录 | 已在 `CS-AUTH-001` 拦下，不重复 |
| `balance === null`（从未读到） | **放行**（fail-open：网络抖动不该锁死生成） |
| `available_balance <= 0` | 拒：`CS-BILL-003`，`uiKind: 'config'`（重试无意义，需去充值） |
| 账号受限（`creditsDisabled`） | 拒：沿用 403 受限语义 |

**绝不本地预扣、绝不估算单价**——没有单价接口（`/v1/pricing` 404），任何估算都是假数据。

### 7.3 G1 与 G2 的分界

| 级别 | 能力 | 依赖 |
| --- | --- | --- |
| **G1（本轮）** | 余额 ≤ 0 时拒发消耗型请求，引导去订阅页 | 只用 `/v1/credits/balance` |
| **G2（另立需求）** | 生成前冻结、生成后结算、失败退还、扣费可解释 | 后端需提供：① 每模型/档位单价；② 按用户 freeze/settle 接口（现有 `frozen_balance` 字段说明后端已有钱包概念，但未开放给桌面端） |

> 现状提醒：生成链路走 `dramaApiKey` + `/api/v1/generate/*`，那条路径**不按用户扣费**。所以 G1 只能拦住「余额是 0 还在烧后端」，**不代表真实计费已打通**。

## 附录 B · 落地回填（2026-11-02，P1–P3 全部完成 = CV-396）

### B.1 与设计不同的四处

| # | 设计原文 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 1 | 积分「最多 4 位小数去尾随 0」 | **一律整数截断**（`Math.trunc`） | 用户 2026-11-02 拍板，与 WorkBuddy 一致：小数位只让用户困惑「余额为什么一直不变」 |
| 2 | 刷新触发源补 `visibilitychange` 之外若干处 | 抽成独立模块 `client/refresh-signal.ts`（`window.focus` + `visibilitychange` 双源、1s 去重），账号 / 余额 / 订阅三处共用 | 三处各写一份必然漂移；且真因只有一个 —— Electron 里跳系统浏览器时主窗口从未 hidden |
| 3 | 幂等键「每次点击生成，失败换新」 | **按购买意图复用**（`kind:code → key`，10min 保活），只在 `expired` / `idem_mismatch` 换键 | 每次点击换新键 ⇒ 网络超时后重点一次会重复下单，积分包是真金白银 |
| 4 | 待支付横幅给「继续支付」 | 只在**本地还留着该商品的键**时才出现 | 无键去点只会在服务端撞 `409 already pending`，是死路，不如不给这个按钮 |

### B.2 上线必须知道的四条不变量（改这块之前先读）

1. **路由尾段必须两端去斜杠**：`pathname.slice(prefix.length).replace(/^\/+/, '').replace(/\/+$/, '')`。只写 `^\/+$` 会得出 `/checkout`，所有写动作静默 404（`tests/billing-routes.test.mjs` 钉住）。
2. **GET 永不抛**：`refreshBilling()` 把失败写进快照的 `error` 字段并**保留上次数字**；抛错只在写动作。UI 要能区分「读不到」与「没有订阅」。
3. **G1 余额闸在 `dramaPost`，不在 `requireDramaAuth`**：后者被上传等不扣费路径共用；余额未知（null / 非有限）一律 fail-open，只在 `available_balance <= 0` 时抛 `CS-BILL-001`。
4. **金额与积分的格式化是两套**：`formatCredits`（整数截断）/ `formatPrice`（2 位 + Intl 币种）。混用会让钱变成整数或让积分出现小数。
