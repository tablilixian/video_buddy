## 0. 判定四档与清理规则

| 档 | 含义 | 后续动作 |
|---|---|---|
| 【可清】 | 该会话有**正向行为证据**且代码在生效边界内，或 `cv-details` 已判通过而 STATUS 未同步 | 批量确认后转「已完成·桌面验收通过」 |
| 【部分】 | 主判据过了、次判据缺一条，或只验到机制未触发 | 保留待验收，记「已达标子项」，等补一条证据再清 |
| 【无证据】 | 会话没调用相关路径 / 代码不在生效边界内 | 保留待验收，明确写「下一场该采什么」 |
| 【反证】 | 会话暴露修复未生效或新缺陷 | **绝不许清**；登记新缺陷，回到产生路径修 |

### 17.5 640×360 专项结论（用户第 4 问）

**不是硬编码常量，是 `quality:"draft"` 把 manifest 的 1280×720 乘 0.5 得到的。**

| 环节 | 事实 | 代码位置 |
|---|---|---|
| 定义 | `RENDER_QUALITY_SCALE = { draft: 0.5, standard: 1, high: 1 }` —— 唯一来源，注释明写「864×480 素材进 **640×360** 的草稿也会被误报成糊片」 | `src/remotion/manifest.ts:102-106`（注释 `:95-97`） |
| 计算 | 出片与 spot 两处都 `width: Math.round(width * preset.scale)`；draft preset = scale 0.5 + `videoBitrate:'low'` + `keyframeIntervalInSeconds:10` | `src/client/remotion-render.ts:66-70,337-338,432-433` |
| 触发 | **仅** `render_composition({ quality:'draft' })`；`probe:true` / `spotFrames` 只渲静帧不编码，与分辨率无关 | `src/host-tools.ts:3786-3787,3807-3812,3610,3626-3629` |
| 1280×720 真值 | 永远取 manifest `meta.width/height`，不是布局表；standard/high scale=1 即原尺寸 | `src/layout-table.ts:20`、`src/remotion/resolution-check.ts:27` `DELIVERY_BASELINE` |
| 产物去向 | **会落盘成 mp4 资产并落成画布节点**（带 `draft:true`），就地替换上一版草稿、**不进版本链留档**；交付档 standard/high 才 append + 写版本链。本场 draft 调用 5 次（2 次成功出片 640×360）+ probe 2 次，最终以 high 档 `cd891847` 交付 1280×720 | `src/host-tools.ts:3821-3832`、`src/compose.ts:800-807,816-818,829-859,881,896-897` |
| 与「分辨率三档」的关系 | **两套互不相干的体系**：三档（480p=864×480 / 720p=1376×768 / 1080p=1920×1088）管 **AI 生成素材的推理规格**（`resolution-tiers.ts`）；draft scale 管 **Remotion 输出画布缩放**。宿主「素材是否被上采样」判定必须复用同一个 scale，否则会把低分辨率素材进草稿误报成糊片 | `src/resolution-tiers.ts:102-105`、`src/remotion/manifest.ts:95-97` |
| 风险 | 回执模板 `已生成产物: ${url} (${width}x${height}…)` 与 `renderComposeResult` **不标 quality / 不写「草稿」**，模型只能靠数字区分；`compose.ts:800-807` 自述「必须一眼能和交付档区分开，否则用户会把粗片当最终成片交付」。本场模型没误用，但草稿节点若被当片段引用，代码层无 `draft` 过滤 | `src/host-tools.ts:669,701-719`、`src/compose.ts:800-807` ⇒ 修法见 P1-4 |

**本场 640×360 出现在事件 270 / 460（draft 两次），1280×720 出现在 540 / 577 / 619（standard×2 + high×1）** —— 是同一份 manifest 换 quality 重渲，不是两个项目、也不是降级 Bug。

**P1-3｜故事板与执行脱节，时长账反复告警**
- 证据：t2:s3 写 §04 两镜各 7.5s；t3:s6/s7 H3 各出 8.00s；t3:s16 `compose_video` 回执「分镜表 15s，实际 16s，相差 1.000s」「成片 16.020s 与目标 15s 相差 1.020s」；t4 用户要求一镜到底后，模型只改 `video_composite duration:15`、**没回写故事板**，t4:s3/s6 两次回执都报「素材 15.08s 比分镜窗口 7.50s 长 7.58s」。
- 判断：数据一致性缺陷。`resolution-check.ts` 那句「分镜窗口是规划值」只解释了差异，没有推动回写；用户中途改结构时缺「先改分镜表再审」的约束。
- 修复：合成类工具在「单段素材 > 任一 shot 窗口且 shot 数 >1」时，回执升级为「先 `write_storyboard` 回写 §04 再继续」；总纲补一句「中途改镜头结构 = 回写分镜表，不只是改生成参数」。验收：同类改动后 §04 与最终帧窗一致、0 条时长告警。

**P1-4｜视觉样张「只能看到一张」+ 候选无状态（用户第二问）**
- 证据：见 §21.2 更正 1；用户 00:04:36 主动插话「生成一个效果图我看看。或者生成一个品牌页面，包括商品图，logo，广告词，等等」→ 模型才 t1:s25 手写 `board.sh` 拼 `brand-board.png`、t1:s31 用 `write_note` 贴到画布。实际出了 5 张图，但 §02 语义上只认一张 `lookRef`，其余散落；6 个平级 image 节点分不出定稿锚点与废候选（`replaces` 用了 2 次、没用 3 次）。`look-budget.ts` 软预算按全局 3 张计数，t1:s19 拦截 → t1:s20 `ask_user_choice`（225.3s）→ t1:s21 放行第 4 张。
- 判断：**不是「出图太少」，是同批候选没有一等公民的展示容器**。用户要的是「看得见、选得出」，不是多出几张。
- 修复（先做便宜的）：① 品牌板产品化——把本场手写的 `brand-board.png` 做成 Host 自动生成的画布节点（产品图 + Logo + 字标 + 广告词 + 色板 + 香调），`look_card` 落卡时同步落板；② 出图节点打 `candidate / approved` 状态并按批次分组折叠；③ 软预算按资产类别分桶或把「用户显式要求的多类品牌资产」识别为一次授权整批放行。**不建议**现在给 `image_generate` 加 `count` 多 seed（成本 ×N、单张 24–104s、后端批量未确认）。验收：用户不插话也能看到 ≥1 张汇总板并能指出定稿锚点。**需拍板 D**。

**P2-1｜22 分钟花在 5 次全量 H3 合成，没有低成本试错档**
- 证据：`video_composite` 5 次 00:22:01（均值 264.3s / max 432.0s），t3:s6 与 s7、t4:s3 与 s6 都是同参数重出；t3:s5 还被 IR 预检拒收 1 次。

**P2-2｜H3 IR 预检模式判据冲突（工具自认的已知债）**
- 证据：t3:s5 拒收回执原文「本预检的模式是**按素材数量**推出来的（2 图 = FL2VA），而 `h3-prompt-writing` 是按**素材角色**判模式。两者不一致时，上面这些段名 / 对齐行 ERROR 多半只是派生症状」。
- 判断：同一 prompt 被两套判据解释成不同模式，产生假阳性拒收。
- 修复：预检与 `h3-prompt-writing` 共用同一个 `resolveH3Mode()` 纯函数；不一致时给 WARN 而非 ERROR。验收：两处判模式结果一致 + 反向变异验红。

**P2-3｜`upload_image` 契约含糊 + 幻觉工具**

**P2-4｜音频时间轴越界不可观测**
