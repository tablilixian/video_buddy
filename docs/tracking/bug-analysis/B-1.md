# B-1 ｜ 删除元素后文件仍残留（重开）——.trash 语义之争 + 清理闭环缺口

> 优先级 P2（重开条目，含**两个拍板点**）｜ 风险 T2/T3 ｜ 依赖：无
> 截图要点：资料库原描述「Windows 上废弃的文件进入了 .trash 目录里，没有实际从文件系统删除。期望彻底删除之」。

## 现象与定性（2026-10-02 代码复核，结论不变）
`.trash` 是 CV-243 的**设计语义**（两段式回收站：rename 进 `assets/.trash/`，不物理删——防误删/共享引用/生成竞态），不是「应该删但没删成」的主链路 bug。真实缺口三个：
1. **历史保护名单无限滞留**：`asset-gc.ts:133,159-161,184-192` + `asset-history.ts:10-11,141-148`——history.json 里无 `deletedAt` 的条目永不物理清；而**画布删节点不写 deletedAt**（只有历史面板显式删除才写，routes.ts:1249）→ 画布删掉的生成产物只要还在历史面板里就永远留在 .trash。
2. **GC 只在打开项目时触发**：`client/index.ts:1624` fire-and-forget + 手动路由 `routes.ts:1195-1222`——不再打开的项目删除即永久滞留。
3. **Windows 静默 rename 失败**：`asset-gc.ts:92-97` 失败 continue 无感知——文件被占用（播放器/ffmpeg）时连 .trash 都进不了；POSIX rename 静默覆盖同名、Windows 目标已存在即 EPERM，同名二次删除在 Windows 会失败。

## 修复方案（按拍板结果二选一，共同前置先行）
**共同前置（无论拍板结果都该做）**：
- a. 画布删节点时给 history 对应条目补 `deletedAt`（`trashAssetsForRemovedNodes` 处，routes.ts:1401-1416）——堵缺口 1 的主源。
- b. GC 触发点补「项目关闭时」或定期（挂 project close / 每日首启）——堵缺口 2。
- c. Windows rename 失败改为可感知：失败时记 warning + 重试一次（EPERM 延迟重试），仍失败保留原位并在结果里提示——堵缺口 3。

**拍板点 ①：滞留策略**——A. 老化（.trash 内 >N 天且无历史保护 → GC 物理清）；B. 暴露 .trash 入口让用户自己清；C. 维持现状（历史面板删除即清）。推荐 A+C 组合。
**拍板点 ②：删除语义**——用户原话要「彻底删除」；但 CV-246 历史保护（undo/回溯）是既有产品决策。若拍板「画布删除=彻底删」，直接跳过 .trash 硬 unlink（与 B-4 force 删除共用确认 UI）；若维持回收站，则 a/b/c 落地后滞留问题已解，向用户说明语义即可。

## 改动风险
- 硬删与 undo/竞态保护冲突（CV-243 的设计初衷）——拍板前勿动手改语义。
- deletedAt 补写会改变 GC 保护名单行为：已删除条目的文件在下次 GC 被物理清——需在发布说明注明。
- Windows 重试逻辑要防与播放器长占用竞态（重试也失败就保留原位，不阻塞保存）。

## 验收
无头：asset-gc 单测（画布删除→deletedAt 补写→GC 物理清；rename 失败重试路径）。桌面：Windows 上删节点 → 关开项目 → .trash 清空；macOS 行为不变。
