## 〇、结论速览（决策版）

| 问题 | 结论 |
|---|---|
| 是什么 | Python 写的**视频逆向拆解工具**：逐镜判断"画面是怎么做出来的"（实拍/AI/3D/代码/录屏/静图…10 类），再按做法给出复刻路线。**只拆不产**——生成要外挂 capsule-cinema，渲染要 agent 自己写 Remotion |
| 能不能整包引入 | **不能**。① Python/OpenCV 栈，我们是 TS/Node ② 它只拆不产，接不上我们的生成与渲染链 ③ 产物形态是 `breakdown.json + report.html`，不是我们的 CompositionManifest DSL |
| 对我们有没有用 | **有，而且补的正是我们的短板**。它最强的三块（确定性取证、制作方式判定、生成单元规划）恰好是我们 REQ-036 复刻链路最弱的三块 |
| 复刻部分能借鉴吗 | **能，且是本次最大价值点**：`production.py` 的"生成单元规划"（同场景合并 + DP 分组 + S01–S07 规则）直接对应我们的 `video_composite` 能力，我们缺的只是**规划层** |
| 风险 | 项目仅 7 天历史（2026-10-29 创建）；准确率是自评且开发集为主；OpenCV 算法移植与本仓"刻意朴素、不引视觉库"铁律冲突（**最大决策点 D1**） |
| 许可 | **Apache-2.0 干净**（有 NOTICE，声明 JuneYaooo 版权）；但其**评测视频与案例视频有版权，不可取用** |
| 下一步 | 跑 S0（0.5 天零代码观察，见 §五），门槛过了再进 S1 |

## 一、调研：rea-video 是什么

### 1.1 仓库事实（2026-11-05 GitHub API 实测）

| 项 | 实测值 |
|---|---|
| 仓库 | `JuneYaooo/rea-video`，公开、未归档 |
| 热度 | **989 ★ / 141 forks** / 1 open issue / 2 subscribers |
| 时间线 | **创建 2026-10-29**，最近推送 2026-11-04（调研当日仍在更新） |
| 许可 | **Apache-2.0**（`LICENSE` + `NOTICE` 声明 `Copyright 2026 JuneYaooo`） |
| 语言 | Python（`requires-python >= 3.10`） |
| 体量 | `rea_video/*.py` **8,748 行**（最大 `packaging.py` 1,463、`pipeline.py` 603、`classify.py` 469）；`tests/` 79 项 pytest |
| 主题 | `agent-skills`、`aigc-detection`、`shot-detection`、`video-breakdown`、`remotion`、`vlm` |

⚠️ **项目只有 7 天历史**，但增速快、社区活跃（7 天 989★）。这意味着：**方法论已经成熟可学，但代码 API 与产物格式还会变——所以只吸收方法与算法，不依赖其代码版本**。

### 1.2 它做什么（能力面）

一句话：**给 AI 助手用的视频逆向工程工具**。输入一条视频，输出：

1. **逐镜判定底层画面制作方式**——10 类：实拍 / AI 生成视频 / 数字人 / 3D 渲染 / 2D 动画 / 定格动画 / 代码模板渲染 / 录屏截图 / 静态图推拉 / 静帧；实拍再看有没有被 AI 二次加工（换脸、对口型、风格化、换装…）
2. **剪辑包装层**——逐句字幕时间轴（导出 SRT/ASS）、花字样式（字色/描边/底框/入场）、贴纸/GIF/画中画、音效卡点
3. **声音三轨**——人声（真人 vs TTS）、BGM（BPM/调性/AI 还是曲库）、音效时间点
4. **拍法**——景别、机位、12 种布光方案附器材、调色风格、剪辑节奏
5. **复刻方案**——按做法分流：实拍给**拍摄场次**（场景聚类 + 机位分组）、AI 镜头给**生成单元**（几次调用、每镜提示词中英、参考素材打标）、代码段给 Remotion 规格、静图推拉给**本地 ffmpeg 参数**

**它不出片**：生成外挂 [capsule-cinema](https://github.com/JuneYaooo/cheap-claude-video)（另一个仓库），代码渲染要 agent 自己写 Remotion 工程，实拍要用户自己拍。

### 1.3 架构与产物

```
rea_video/
├── shots.py        切镜检测（硬切/黑场淡入淡出/交叉溶解/MG 节拍）
├── features.py     确定性取证（帧率指纹、冻结帧、平坦块、噪声、光流…）
├── classify.py     融合判定（确定性概率 × VLM 概率 + 硬约束 + 多数规则）
├── packaging.py    剪辑包装层（OCR 字幕时间轴、花字样式、贴纸）
├── audio.py / stems.py / sound_source.py   声音三轨
├── aspects/        拍法可插拔维度（framing/camera/lighting/editing/grade/subject）
├── plan.py         单镜 → 路由规则 + 候选模型
├── production.py   ★ 整片 → 生成单元 / 拍摄场次（复刻方案核心）
├── remake.py       ★ 拼回原时间线 + compare.mp4 并排对比
├── evaluate.py     评测（labels/holdout 集、按时长加权准确率）
└── capabilities/   ★ 能力地图：routing.yaml（R01–R20）+ primitives + models/*.yaml

skills/rea-video/   SKILL.md + 8 个 references —— agent 工作流（本仓 skill 同构）
eval/               4 组标注集 + RESULTS.md（准确率与回归记录）
```

**三层能力地图**（值得单独看）：

```
signals（镜头特征，拉片时检测）
   │  routing.yaml
   ▼
primitives（43 个与厂商无关的能力原语）
   │  models/*.yaml 的 primitives 字段
   ▼
models（具体模型：limits / cost.usd_per_s / license / verified.basis / 90 天过期校验）
```

路由规则只认原语不认厂商，换模型时规则不改；`scripts/validate_capabilities.py` 校验引用完整性与"首选模型是否真支持该原语"。

### 1.4 它准不准（`eval/RESULTS.md`，自评）

| 项 | 结果 | 证据强度 |
|---|---|---|
| 制作方式（8 类，时长加权） | 调参集 **98.3%** / holdout **99.6%** / holdout2 **98.9%** / 公众号转码 **88.6%** | 调参集规则在这批样本上设计；转码集是开发集 |
| + Gemini VLM | 转码集 88.6% → **99.6%** | 真实 Gemini 跑过 |
| + agent 看图复核 | 转码集 **100%**；抖音带货两条 46.4% → **97.5%** | zcode / Claude 盲测 |
| **切点 F1** | **1.00**（两条真值片，含 14 处 0.25s 交叉溶解） | 有真值 |
| 真实素材识别 | 97–99% | — |
| 字幕时间轴 | 召回 0.975–1.0 / 精确 0.933–1.0 / 起止误差中位 ≈0.06s | 3 条真值（开发集） |
| 音效 | **精度约 0.2（≈随机）** —— 自认短板，改交 VLM 听 | 真值 110 处对照 |

**必须一起看的局限（README 不显眼处 + RESULTS.md「已知局限」）**：

1. **labels 集从头解码后 0.999 → 0.983**（2026-11-02 回归），此前多次"与改前一致"是复用缓存特征得到的——**它的数字有过自我修正史**。
2. **2D 动画、定格动画、数字人的评测视频数 = 0**（`what-it-detects.md` 表格直书）；实拍样本只有 3 条。
3. 只开 VLM 不做 agent 复核时，留出集反而**变差**（0.998→0.965），靠加"看图来源必须在工具前两名里"等闸门修回。
4. VLM 会**编造证据**（"挂钟数字乱码"实为清晰），流程里专门留了 `disputed` 必看列表。
5. 音乐来源判断"普通配乐一律写倾向曲库、待确认"。

> **对我们的含义**：它的准确率可信度**中等偏上**（有真值、有留出集、有自我修正记录），但**不能照单全收**——尤其是 2D/定格/数字人这些零样本类别。吸收时按"方法可信、数字存疑"处理。

## 二、评估：与我们逐维对照

### 2.1 我们的现状（REQ-036 爆款复刻链路）

本仓 grep `rea-video` = **0 命中**——此前从未评估过它。

已有的复刻链路（`skills/viral-remake/SKILL.md` + 配套工具）：

```
download_video → media_probe（真值）+ evidence_grid（网格+实测切点）+ video2vl（逐镜语义）
   → 拆解六列表（镜序/起止秒/内容类型/元素与动效/转场入/字幕落点 + 素材需求）
   → verify_teardown（回核）→ teardown_store（落库）→ write_note（画布便签）
   → 映射 CompositionManifest 轨道 → render_composition 出片
   → 五项对照验收（节奏≤0.2s / 转场 / 字幕 / 信息卡 / 整体）+ 响度≤2dB
   → 批量换装裂变
```

工具 **46 个**（`tests/tool-registry.test.mjs:44` 钉死）、skill **31 个**、视频模型**只有 MiniMax H3**（drama + fal 双通道），`seedance2` 占坑未接（`src/generate.ts:177`）。

### 2.3 关键差异：两条产品路线的根本不同

| | rea-video | 我们（canvas-studio） |
|---|---|---|
| 定位 | **逆向工程工具**：把别人的片子拆明白，告诉你怎么做、花多少钱 | **生产工作台**：从创意到成片的完整链路 |
| 对"复刻"的理解 | 按原片做法**分别重做**：实拍去拍、AI 生成、代码写工程，最后拼回原时间线 | **结构复刻**：复用节奏/镜头/转场/字幕形态，素材与文案换成自己的（`viral-remake/SKILL.md:15`"复刻结构，不复刻素材本身"） |
| 判定制作方式的目的 | 决定**用哪条技术路线**复刻（省钱、可控） | 目前不判定——直接把内容映射到 manifest 轨道 |
| 产物 | `breakdown.json` + `report.html` + 复刻计划 | CompositionManifest + 成片 + 画布 |
| 边界 | 不出片 | 不做逐镜像素级还原（产品原则，`viral-remake/SKILL.md:27-28`） |

**结论：互补而非竞争。** 它最强的（取证、判定、规划）正是我们最弱的；我们最强的（生成、渲染、画布、批量）它完全没有。所以——**吸收方法论与算法，不吸收产物形态与执行器**。

## 三、能不能集成？——正反论证

### 不整包引入的五个理由

| # | 理由 | 说明 |
|---|---|---|
| 1 | **栈不通** | Python + OpenCV + numpy + onnxruntime；本仓是 TS/Node/Electron。没有"复制目录就能用"的路径，只能移植算法 |
| 2 | **只拆不产** | 它的复刻要外挂 capsule-cinema、要 agent 自己写 Remotion、要用户自己拍。这三样我们**都有**——引入它反而多一条并行链路 |
| 3 | **产物形态不通** | 它的产物是 `breakdown.json` + `report.html`；我们的复刻入口是 **CompositionManifest DSL**（`tracks[]` + 白名单组件，确定性 + 可校验 + 无任意代码执行）。这是刻意架构，不能为复用放弃——**与 shotcraft 卡在同一条上**（它写 TSX、我们是 manifest） |
| 4 | **证据强度中等** | 准确率是自评、开发集为主、有回归史（0.999→0.983）；2D/定格/数字人零样本；音效精度≈随机。**方法可信，数字不能当采购依据** |
| 5 | **项目太年轻** | 7 天历史，API 与产物格式必然变。绑定其代码版本 = 追一个移动靶 |

### 值得吸收的六个理由

| # | 价值点 | 对应我们的实证痛点 |
|---|---|---|
| 1 | **制作方式分类学**：10 类 + 叠加层 + AI 加工 + "真实素材 vs 参考素材"两分 | 我们的六类内容类型不回答"怎么做的"——实拍段该给拍摄方案还是 AI 近似？静图推拉能不能零成本本地复刻？现在没依据 |

#### A2 · 确定性取证层（**依赖决策点 D1**）

- **落点**：扩展 `src/evidence-grid.ts` 或新 `src/method-evidence.ts`（**建议扩展，避免工具数 46 变动**——`tool-registry.test.mjs` 钉死名单）
- **按性价比排序的可测项**：

  | 序 | 项 | 算法来源 | 价值 | 实现依赖 |
  |---|---|---|---|---|
  | a | **AIGC 元数据** | `probe.py`：GB 45438 隐式标识（Label 1/2/3 + 服务方编码）、C2PA、编辑器签名 | **出现时极强**（一票定案）；平台常清除，但查一次很便宜 | 纯 ffmpeg/文件解析，**零视觉库** |
  | b | **重复帧 / 原生帧率指纹** | `features.py`：24→30 转码约 20% 重复帧、周期 4–6；原生 ≥48fps 无重复帧 | 判"转码过的实拍 vs 生成视频"——正是我们抖音样片的失分区 | ffmpeg 逐帧，**零视觉库** |
  | c | **冻结帧比例 + 静图推拉检测** | `shots.py` `_mg_beats`（`changed < 0.004` 连续 ≥0.4s = 冻结）+ `features.py` LK 光流拟合相似变换（RANSAC 内点率/残差） | 冻结帧判静帧/代码画面；**光流拟合直接产出 `zoom_per_s`/`pan_px_per_s` → 静图推拉本地零成本复刻**（`remake.py render_still_motion`） | 冻结帧：ffmpeg 可做；**光流：需 OpenCV（D1）** |
  | d | **渲染 vs 拍摄纹理** | `features.py`：平坦 8×8 块比例、覆盖 95% 像素所需颜色数、横竖直边比例、Immerkær 噪声 | 区分 3D/代码渲染与实拍 | 需像素运算（D1） |

- **⚠️ 这是本次最大决策点**：本仓铁律"刻意朴素，不引入视觉库"（`src/teardown-verify.ts:9`）。**建议先做 a + b + 冻结帧（纯 ffmpeg），c 的光流与 d 的纹理放 D1 拍板后**。
- **成本**：a+b+冻结 1d；含 c+d 2–2.5d

#### A3 · 切点检测算法升级

- **落点**：新 `src/shot-detect.ts`（纯函数层）+ 适配进 `src/teardown-verify.ts`（**保持回核三态语义不变**）
- **从 `shots.py` 移植**（约 237 行，算法清晰、有注释）：
  1. 分数 = `0.6 × HSV 直方图 Bhattacharyya + 0.4 × clip(像素差分×4)`
  2. **局部自适应阈值**（0.5s 窗口局部中位数的 2.5 倍 + 0.06）——比我们的固定阈值抗光照闪烁
  3. **变化面积门限** `changed > 0.25`——"标题在静态版式上弹出"只变局部，不算切镜（我们现在会误报）
  4. **交叉溶解检测**：中间帧是否为两端帧的线性混合（α∈[0.2,0.8]、残差 <0.20），并用 Farneback 光流排除"是运动不是溶解"
  5. 黑场/白场淡入淡出（亮度掉到极值又回来）
- **验收**：拿本仓已有拆解真值的参考片测 **切点 F1 ≥ 0.95**（rea-video 自称 1.00，我们不追平，但要显著优于现状）
- **成本**：1–1.5d（含测试）
- **风险**：光流部分依赖 D1；若 D1 否决，只移 1/2/3/5（无光流），溶解检测降级为"标疑似"

#### A4 · **生成单元规划**（本次最高价值项）

- **落点**：新 host 工具 `plan_generation_units`（输入：拆解表 JSON；输出：单元分组 + 提示词 + 调用次数估算）。**先只出计划，不自动执行**（决策点 D4）
- **从 `production.py` 移植**（439 行，纯算法、**零视觉库依赖**——场景相似度用首尾帧 HSV 直方图，可由 ffmpeg 抽帧后算）：
  1. `_runs`：同场景 + 硬切相连的 AI 镜头归一个 run；**中间插入的代码/录屏/静图不打断 run**（"口播+UI"类片子的常见做法）
  2. `_split_run`：**动态规划求最少单元数**，代价函数 `1.0 + 0.4×(超 prefer 8s) + 0.2×(低于最短 4s)`
  3. 规则 S01–S07：同场景合并 / 超长在动作停顿处切（后段用前段尾帧作首帧）/ 遮挡转场单独切 / 文字抽代码层 / 提示词写"动作过程+结束状态" / 单元内连续硬切 ≤8s（最多 10s）/ 长视频按叙事段落分段
  4. `_unit`：多镜头提示词拼装（`镜头i（a–b s）：…`）+ 全片统一风格句 + 参考素材打标（`@图片1` 产品、`@图片2` 人物、`@视频1` 原片片段）+ S05 尾帧衔接说明
- **对齐我们的能力**：`video_composite` 参考图 1–9 张 + `videoRefs` ≤3 段（`docs/canvas-studio-tools.md:318`）——**规划时必须按这个上限分组**，rea-video 的 `CAPSULE_ENGINES = {"seedance2.0": (4,15), "minimax-h3": (4,15)}` 换成我们的 H3 实际规格
- **验收**：拿 README 案例口径自测——榨汁杯 11 镜应组出 ≤3 单元；混合片 5 镜应组出 1 单元；**每单元提示词能直接贴进 `video_composite`**
- **成本**：1d（纯函数 + 单测）
- **注意**：`production.py` 的场景相似度"只看颜色分布，MV 类会切得偏碎"（RESULTS.md 自认局限）——保留其局限说明，别当成已解决

#### A5 · 能力地图

## 六、风险与边界清单

1. **D1 视觉库铁律冲突**——本仓 `teardown-verify.ts:9` 明写"刻意朴素，不引入视觉库"。rea-video 的光流/纹理检测依赖 OpenCV。**默认走零视觉库路径**，要开缺口须单独拍板。
2. **它的准确率不能当采购依据**——自评 + 开发集为主 + 有回归史（0.999→0.983）+ 2D/定格/数字人零样本。吸收方法，不吸收结论。
3. **项目 7 天历史**——只吸收算法与方法论，**不 pin 其代码版本、不依赖其 `breakdown.json` schema**。
4. **许可**：Apache-2.0 干净（有 NOTICE，移植代码须保留版权声明）；**其评测视频/案例视频有版权，一律不取**。
5. **产品原则边界**：判定制作方式是**为选路径**，不改变"结构复刻、不复刻素材本身"与"不做逐镜像素还原"的承诺（`viral-remake/SKILL.md` §0/§6）。
6. **渲染预算墙不因此消失**：CSR 每帧 7.9–19s（shotcraft 评估 §三）——A1 的"代码渲染复刻"路线吸收过来，仍受此约束；**两条线不混账**。
7. **工具数量闸门**：`tests/tool-registry.test.mjs` 钉死 46 个——A2/A4 落地方式优先"扩展既有工具"，确要新增须同步改 `EXPECTED_TOOL_COUNT / EXPECTED_TOOL_NAMES`。
8. **不碰上游**：本文所有落点均在 `canvas-studio/`，不涉及 `deepseek-harness/` 子模块。
