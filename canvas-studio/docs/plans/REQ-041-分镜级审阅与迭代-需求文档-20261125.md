# REQ-041 · 分镜级审阅与迭代闭环（需求文档）

> **日期**：2026-11-25（同日四轮修订）　**状态**：D1–D4 全部已拍；§9.7 数据通路已定；第 1–3 批可直接开工
> **一句话**：把「渲完整片才发现哪里不对」改成「每张分镜卡上就能看这一屏的画面和旁白，引用到对话里说一句，只改这一屏」。
> **水位**：REQ-040 已用，本需求占 REQ-041；实现取 CV 号时按 STATUS §4.1 重新复核。
> **主交互**：右键「引用到对话」+ 一句人话 → `patch_spec_section(shotNodeId)` → 单段重渲。无审阅状态、无闸门、无新 surface。

---

## 一、需求场景（用户视角，不含具体片例）

用户对 agent 说「帮我做一段讲 X 的视频，给 Y 看」，此后期望经历这样的过程：

1. **看到第一版分镜**——不是等到成片，而是每一屏都有画面可看。
2. **逐屏看（画面 + 旁白）**——第 1 屏、第 2 屏……按顺序过，每屏看到的是最终会出现在成片里的那一屏（同样的字、同样版式、同样动），并且**能听到这一屏的旁白**。
3. **对某一屏说一句**——「这屏不够直观，换成图+标注」「这里数字挤了」「这句旁白太赶」。说的是**这一屏**，不是「整片再改改」。
4. **agent 只改这一屏**——别的屏不动，已经看过的屏不用重看。
5. **再看这一屏**——改完立刻换成新版，等待以秒计，不以分钟计。
6. **循环若干轮**，直到你觉得可以。不想再改就停——**停下来的那一版就是最终版**。
7. **交付**——你说「出片」，整片一次渲染，音画同步、转场连续。

**关键约束**：这套交互不得打断自动模式。用户没空逐屏看时，流程照旧一路跑到成片；逐屏审阅是「有人愿意看时才出现」的加速通道，不是必经关卡。

> 说明：本需求与任何具体选题、具体版式（轨道示意、括号标注、图表选型）无关。那些只是「用户会对某一屏提出什么意见」的示例，属于内容层，不进本需求范围。

---

## 二、现状盘点：缺的不是渲染能力，是用户的入口

R11（REQ-038，2026-11-16 已落地）已经解决了「改一段不动全片」的底层问题，判据原文是「改一段的代价 = 1 段渲染 + 1 次确认」。逐项核对：

| 能力 | 现有实现 | 用户现在能用到吗 |
|---|---|---|
| 段表（段的真实内容窗，对齐转场预卷） | `manifest.meta.segments`，`planFromSpec` 唯一写入 | 否，只在 manifest 里 |
| 段级独立渲染 | `deliver/segments/<id>.mp4`，每段一个文件 | **否**，产物在磁盘上，界面无入口 |
| 段级静帧 | `build/qc/seg-<id>.png`，每段一张 | **否**，只回灌给 agent 的回执 |
| 段级原子改 | `patch_spec_section`（第 54 号工具）：一次改一处、整份复校、一步重编、一行 diff | **否**，只有 agent 能调 |
| 改一段只脏一段 | 段 hash 缓存，实测「1 复用 / 2 重渲」 | **否**，用户看不到「只有这段重渲了」 |
| 整片汇合 | 一条时间轴一次渲染，本来就是完整成片 | 是（但有前提，见 §四.2） |

**结论**：链路的下半段（渲染、隔离、修改）是通的；断点在**最后一步接线**——段产物已经躺在磁盘上，但客户端完全不认识 `segmentRef`，所以分镜卡上出不来视频。而「说话的位置」其实已经有了：右键「引用到对话」→ chip → `patch_spec_section(shotNodeId)`。上表五个「否」，本质是同一个原因——**段产物没接到卡上**。

这决定了本需求的工程量重心：**不是渲染架构，也不是新建审阅面，而是把段产物接到已有的分镜卡上，让它能被「引用着一句话改掉」**。

## 三、需求条目

### R1 · 分镜可逐屏呈现（视频为主形态）

**解决**：用户第一次看到画面的时点，从「成片渲完」提前到「分镜成形」。

- 每一屏的**主形态是渲出来的视频片段**（`deliver/segments/<id>.mp4`），不是文案表；文案降为副信息。
- 视频旁必须**同期可听旁白**。画面与声音是同一屏的两个部分，缺一个就判断不了「这屏能不能看」。段产物本身是 `muted:true`（拼片不重复音轨），所以审阅播放要按段帧窗把 `audio.voiceOver` 叠上去。
- 呈现位置 = 画布上**已经带 `segmentRef` 的那张分镜卡**（R11-B3 已对位），不新建审阅页、不新增 surface。
- 呈现顺序与成片顺序一致，用户能连续过屏，也能直接跳到任意一屏。

**判据**：任取一屏卡上的视频，与该屏在成片中的对应帧窗逐帧一致；播放时能听到该屏旁白。

**边界**：不要求一次渲出全部屏的片段；按需出、出的成本以秒计。

### R2 · 意见必须能准确落到某一屏

**解决**：用户说「这屏不行」，系统必须知道是哪一屏，而不是靠 agent 猜。

- 用户在**正看着某一屏**的状态下提意见，该意见默认归属这一屏。
- 意见可以是纯自然语言（「换成图+标注更直观」），不需要用户懂任何字段。
- 落不到屏的意见（比如「整体节奏太快」「换个风格」）必须能升格为**全片级意见**，不得被硬塞进某一屏。

**判据**：用户对第 N 屏提意见后，被修改的 spec 段 id 必须是第 N 屏；对全片级意见，不产生任何单屏修改。

**边界**：意见的语义理解仍由 agent 承担；本需求只保证「归属正确」，不保证「理解正确」。

### R3 · 一次修改只影响一屏

**解决**：改一屏不能把别的屏带坏，也不能让用户重看已经认可的内容。含三层，但**三层的强度不同**，必须分开承诺：

| 层 | 要求 | 现状 | 强度 |
|---|---|---|---|
| 数据层 | 改第 N 屏只改第 N 屏的 spec 字段，其他段字段逐字节不变 | `patch_spec_section` 已保证（一次一处 + 一行 diff） | **硬承诺**，任何时候成立 |
| 呈现层 | 别的屏的**画面一个像素都不动**，用户不必回去确认「没被带坏」 | **新增**：段产物按段幂等，其余卡指向的 mp4 不变 | **硬承诺**，任何时候成立 |
| 渲染层 | 只有第 N 屏重渲，其余段复用 | 段 hash 含段窗 `start`/`end` ⇒ **内容改则只脏本段；时长改则后续段全部重渲** | **软承诺**，有条件 |

**为什么渲染层只能是软承诺**：`segmentHash` 的输入是 `{start, end, quality, globals, tracks}`（`shot-cache.ts:89`）。改文案、换卡 ⇒ 段窗不变 ⇒ 只脏本段（已实测 1 复用 / 2 重渲）。但一旦改动**屏时长**（加词、拆屏、插入一屏），后续所有屏的 `start`/`end` 都平移 ⇒ **全部重渲**。这是切片几何的必然结果，不是缺陷。

**这个区分是需求的核心口径之一**：机器重渲 ≠ 用户重审。用户不需要知道哪几段在后台重渲，他需要知道**哪些屏的画面真的变了**。所以交付承诺应当是：

> 改一屏，用户只需要重看这一屏。后台可能重渲更多屏，但那是机器成本，不转化为用户成本。

**判据**：改第 N 屏后，第 1..N-1 屏的 spec 字段不变、卡上播放的段产物不变；段产物 hash 在「仅内容改动」时也不变。

**边界**：用户主动要求「整体重排」「换全片风格」时，允许全段失效；但必须**明示**「这次会动到 X 屏，之前看过的画面都会变」，不得静默全废。

### R4 · 改完立刻能再看这一屏

**解决**：反馈环的长度决定用户愿意改几轮。等 5 分钟看一次，用户只会改一轮就妥协。

- 修改完成后，重渲的**只有这一屏**，用户拿到的等待时间应与单屏时长成正比。
- 重渲完成后，用户回到的仍是这一屏，而不是被扔回开头。
- 需要同时给出「改前 / 改后」的对照能力（同一屏、同一时刻），否则用户无法判断是否真的改对了。

**判据**：改一屏的端到端时间（说意见 → 看到新版这一屏）不随全片长度线性增长，只随该屏时长增长。

### R5 · 没有审阅状态

**2026-11-25 用户拍板：分镜的视频上不挂任何状态。**

- 不设「未审 / 已通过 / 已打回」。只要有成品就能看，任何时候停下来就是最终版。
- 「通过」由**行为**表达：这一段不再提意见，就是认可。不点按钮，也就不需要状态同步。
- 因此不存在「全部通过才能交付」的判据 —— 交付由用户说「出片」触发，不由系统统计。
- agent 也不需要状态：它只处理用户实际发出的那一条意见。

**判据**：产品里不存在段级审阅状态的存储与读取路径。

**为什么删**：状态是给「有阶段的流程」用的。这套交互没有阶段——出过一次片之后，任何时候都能改、也能停。加状态只会多出第二处真相（状态说通过、用户还在改）。

### R6 · 汇合与交付

**解决**：用户认为可以了，就出一版完整成片。

- 交付物是**整片一次渲染**的结果，不是把段产物拼起来。
- 理由不变（已核实）：段产物 `muted:true` 无音轨；段窗含转场预卷，拼接会在接缝处重复/丢失转场帧。
- 交付由用户主动触发（「出片」），系统不判断「是否审完」——没有状态，也就无从判断。
- 终版必须**音画齐**：段审阅里的旁白是客户端叠的，终版是渲染进 mp4 的。

**判据**：交付成片音轨完整、接缝处转场连续、时长等于各屏之和（含转场预卷的账）。

### R7 · 自动模式不受影响

**解决**：这套交互不能变成新的必经关卡（历史上已有「加一道审批 → 100 分钟零出片」的教训）。

- 无审阅订阅者时，流程直接放行，与今天完全一致。
- 逐屏审阅只在「用户在场并且愿意看」时出现。
- 自动模式下仍必须留下可查阅的审阅产物（每屏静帧 + 段产物 + 屏表），供事后回查。
- 等待不得无限：有订阅者但长时间无操作，按既定超时放行并在未决项中记一条「分镜未确认」。

**判据**：关闭审阅交互后，一条片子的端到端行为与今日逐帧一致。

## 四、口径与关键判断

### 4.1 「分镜」在本需求里指段（section），不是 StoryboardShot

- `StoryboardShot`（`src/contracts/storyboard.ts:62`）是叙事单元，带 `camera` / `visual` / `promptEn` / `refImage`，用于 AI 生成画面的叙事片。
- 科普/信息类片子的视觉由 `content-spec` 的 `sections[]` 决定，一屏 = 一个 section = 一个讲点。
- 两者当前**没有映射关系**。若按 shot 审，必须先建 shot→section 映射表，属于额外负担且会造出两套「分镜」事实。
- **本需求统一取 section 口径**：用户看到的「一屏」= 段表里的一个 `id` = spec 的一个 `section.id`。

### 4.2 「整合成一段完整视频」= 整片渲染，不是拼接

用户心智里「最后把它们拼起来」是合理的，但落到实现上恰好相反，且**相反的方向更好**：

| | 物理拼接段产物 | 整片一次渲染 |
|---|---|---|
| 音轨 | 段产物无音轨，需另行拼接，接缝处易断 | 天然连续 |
| 转场 | 段窗含预卷，接缝处重复或丢失 | 天然连续 |
| 拼接缝 | 需要额外验证（关键帧对齐、时间基） | 不存在 |
| 一致性 | 需要验证段间字号/色板/版式是否漂移 | 同一份 manifest，天然一致 |

所以「整合」在产品语义上是**收口动作**（用户说「出片」→ 整片一次渲染），不是一道拼接工序，也不是「全部通过」的统计结果。

### 4.3 「不影响别的分镜」的三层含义（易被含糊掉）

1. **数据不被改**：改 A 屏不改 B 屏的字段。
2. **呈现不重来**：A 屏改了，B 屏卡上放的还是同一段 mp4，不用重新打开确认。
3. **认知不重看**：用户改完 A 屏，不需要为了确认没坏而把前面重看一遍。

第 1 层已有实现；第 2、3 层是本需求的新增价值，也是最容易被实现成「每次改动全片重出」的地方。

### 4.4 「通过」不等于「好看」

本需求交付的是**更短的反馈环**，不是审美自动化。它让用户在「改一屏只花几秒」的时点发现问题；真正把片子做好看的仍是内容与版式的决策。需求验收时不得用「成片质量是否提升」作为判据，只能用「反馈环是否变短」。

## 五、交互契约

| 环节 | 用户看到 | 用户能做 | 系统必须保证 |
|---|---|---|---|
| 出片 | 每张分镜卡挂上该屏视频 + 同期旁白 | 逐卡看、听、重播 | 视频与旁白来自真实渲染 |
| 提意见 | 右键「引用到对话」→ chip 进输入框 + 一句话 | 说人话，不需要懂字段 | chip 带节点 id，宿主按 `segmentRef` 落段 |
| 修改中 | 该卡的处理中状态 | 继续看别屏 | 只重渲该段 |
| 改完 | 该卡换成新版视频 | 再提意见 / 就此不管 | 其余卡内容与播放不受影响 |
| 收口 | 没有收口动作 | 说「出片」 | 整片一次渲染，音画齐 |

**主交互是「引用到对话 + 说意见」，不是「逐屏批准」。** 依据：`@ref` chip 链路与 `patch_spec_section(shotNodeId)` 都已存在（见 §9.1），用户不需要学一套新的审阅 UI。

**轮次**：一句话 → 一处改 → 一段重渲。D1 的「一轮一屏」保留，但语义降级：它约束的是**一次意见只改一处**（归因清晰），不是「一次批准一屏」。屏多时也该一次只提一屏的问题，否则改完分不清是理解错了还是只改了一半。

两个派生规则：

1. **全片级意见不占段**：「整体节奏太快」「换个风格」这类不落到某一段，走全片意见通道（否则会被误当成某一屏的要求）。
2. **停在哪儿都算定稿**：用户随时可以说「就这样，出片」。系统不追问「还有几屏没看」。

## 六、非目标

1. **不做叙事片的 AI 生成画面审阅**——叙事片已有 `keyframe_review` 审「这一镜长得对不对」，判据不同，本期不合流（合并会让一个状态承载两套判据）。
2. **不新建审批状态机**——沿用既有「用户在等一个决策」的判定，不新增第四种 review 状态。
3. **不承诺「首轮即达满意」**——轮次多少取决于内容难度与用户要求，本需求只保证每轮便宜。
4. **不做外部协作/分享**（发给客户看、留评论）——本期只解决「用户自己在项目里审」。
5. **不做内容层能力**（新卡型、新图元、新动效）——用户可能借这条通道提出「我要一张示意图」，那属于卡库缺口，另立需求。

## 七、验收方式

| 编号 | 验什么 | 怎么证明（可观测事实） |
|---|---|---|
| A1 | 段视频即成片 | 同分辨率下，某屏卡上视频与该屏在成片中的对应帧窗逐帧一致（中点帧可 pixel-diff） |
| A2 | 意见归属正确 | 对第 N 屏提意见后，被改的 spec 段 id = 第 N 屏 |
| A3 | 隔离性（数据） | 改第 N 屏后，其余段 spec 字段 diff 为空 |
| A4 | 隔离性（渲染） | 改第 N 屏后，其余段产物 hash 不变，仅第 N 段重渲 |
| A5 | 隔离性（呈现） | 改第 N 屏后，其余卡指向的段产物路径与内容不变，用户不需要重看 |
| A6 | 反馈环不随片长膨胀 | 6 屏片与 20 屏片，改一屏的端到端时间处于同一量级 |
| A7 | 自动模式零回归 | 关闭审阅交互，端到端行为与今日一致（逐帧对比或等价断言） |
| A8 | 交付完整性 | 成片有音轨、转场连续、时长为各段之和 + 预卷 |
| A9 | 旁白可听 | 播放某屏卡，能听到该屏 `audio.voiceOver`，起点按段帧窗裁剪（不从 0 起算） |

## 八、与既有体系的关系

- **R11（REQ-038）**：本需求消费其能力，不改其契约。段表、段产物、`segmentRef`、`patch_spec_section`、段 hash 均为既有资产；本需求只补「客户端把段产物接到卡上」这一层。
- **`render-preview`（CV-334）**：现有渲染前预览是**整片播放器 + 帧步进**，本需求把它**降为单段细看播放器**（点卡打开），复用其播放内核与安全区，不改其「渲染前确认」的原语义。
- **`keyframe_review`**：只服务叙事片画面确认，本期不动。
- **`patch_spec_section`**：作为唯一修改入口被复用。若实现中发现它缺字段（例如某类意见没有对应可改字段），**扩展白名单**，不另开第二个写入口。

## 九、开工条件评估（2026-11-25 逐项核实）

### 9.1 已具备，不必做（可直接消费）

| 能力 | 落点 | 核实结论 |
|---|---|---|
| 段表（段窗对齐转场预卷） | `manifest.meta.segments`，`planFromSpec` 唯一写入 | 可用 |
| 段级静帧 | `build/qc/seg-<id>.png`（宿主抽帧，段中点） | 可用，每段已有一张 |
| 客户端单帧渲染 | `renderSpotFramesOnWeb(manifest, frames[])`，1–8 帧 | 可用，与线上渲染同源 |

### 9.6 三条实现硬约束（2026-11-25 开工前查证）

**① 段产物没有 URL 出口（已定：发布时复制进 `assets/`，见 §9.7）。** `ROUTE_ASSETS`（`routes.ts:1369`）只接受 `<projectId>/<file>` **两段**、且必须落在 `assetsDir(projectId)` 下；`deliver/segments/<id>.mp4` 既带子目录、又不在 assets 里 ⇒ 现有路由取不到它。

**结论：复制，不新开媒体路由。** `publishSegmentArtifacts` 已经每段 `copyFileSync` 一次（`shot-render.ts:177`），再加一次复制到 `assets/seg-<id>.mp4` 即可；`<video>` 拖进度所需的 Range 由 assets 路由原样承继，不必复刻 stat / Range。

两条不许做的简化：

- **不走 `saveLocalAssetBytes`**：它用 `newAssetId()` 随机命名（`generate.ts:1483`），重渲一次换一个文件名 ⇒ URL 漂移、缓存与引用全废。段副本必须**确定性命名**、覆盖写。
- **不新开 `/segments` 媒体路由**：要么复制一套 stat / Range（30–40 行），要么与 assets 各维护一份缓存头；段产物总量 = 屏数，双份磁盘不是问题。

**副作用（接受）**：`assets/` 里会出现不被任何画布节点引用的孤儿文件。`asset-gc` 对根目录孤儿**只登记不删**（模块头 ③ / F-08），且 `candidates` 只从「被删节点的 url」取（`asset-gc.ts:78`）⇒ 段副本不会被 GC 误删。诊断面的孤儿清单会多几条，记一笔即可。

**② hover 播放是静音的。** CV-082 的判据是 `canHoverPreview = node.kind === 'video' && node.url !== undefined`，且播放走 `muted + loop`。更硬的约束是浏览器：**hover 不是用户手势，不允许触发带声的自动播放**。⇒ **画面可以 hover 预览，听旁白必须点击**。这不是设计选择。

**③ 客户端不知道某段渲过没有。** `segmentRef` 只说「你是哪一段」（`spec:s2`），不含「有没有 mp4」。⇒ **由 §9.7 的 L1 只读清单路由回答**：它同时给出 url 与存在性，客户端不盲拼 URL、不会一次刷出 6 个 404。清单拉取失败时才回退到「卡不显示视频」（静默，不报错）。

### 9.7 段产物上卡：数据通路（2026-11-25 定案，待开发）

目标一句话：**让磁盘上已有的 `deliver/segments/<id>.mp4` 出现在那张已经带 `segmentRef` 的分镜卡上。** 四层，自下而上：

| 层 | 落点 | 改什么 | 量 |
|---|---|---|---|
| L0 发布 | `publishSegmentArtifacts`（`shot-render.ts:157`） | 增 `assetsDir`；每段多复制一份到 `assets/seg-<id>.mp4`（确定性名，覆盖写）；`SegmentPointer` 加可选 `assetFile` 与 `ref`（对不齐则不给 `ref`） | 小 |
| L1 查询 | 新只读路由 `GET /canvas-studio/remotion/segments?projectId=` | 读 `deliver/card.json` 的**顶层 `segments`**（`DeliveryCard.segments`；文档早先误写为 `pointers.segments`，实现两种都认、顶层优先），按 `id` stat `assets/seg-<id>.mp4`，回 `{id, ref, url, startFrame, frames, durationSec, v}`；`ref` 缺省则不回 | 小（无状态） |
| L2 取数 | 新 `src/client/use-segment-media.ts` | 画布就绪 + 渲染完成各拉一次；按 **`ref`** 建索引 `Map<segmentRef, url>` | 小 |
| L3 卡面 | `CanvasNode.tsx` 的 text 分支 | `node.segmentRef` 在 L2 索引里命中时渲 `<video muted loop playsInline preload="metadata">`；否则维持现状文案 | 中（本需求主体） |

**为什么不让客户端自己拼 URL。** 拼法（`/canvas-studio/assets/<pid>/seg-<id>.mp4`）一旦成为跨端隐式契约，宿主改一次命名规则，客户端只会静默 404；而且「这段渲过没有」仍然答不了（§9.6 ③）。一条只读清单路由把两件事一起解决，**不改 `canvas.json`、不加持久字段**。

**为什么不把 url 写回分镜卡。** 写画布 = 触发画布保存与版本（`projects.ts` 的 `keepSegmentRef` 正是在防客户端把 `segmentRef` 冲掉）。把「一次渲染的产物地址」塞进用户文档，等于每次重渲都要改文档 → 脏版本、脏 undo 栈。产物地址属于渲染态，不属于文档。

**载荷形态**（6 段约 1KB）：

```json
{"projectId":"<pid>","segments":[
  {"id":"s1","ref":"spec:s1","url":"/canvas-studio/assets/<pid>/seg-s1.mp4",
   "startFrame":0,"frames":190,"durationSec":6.333,"v":1732512345678}
]}
```

`v` = 段文件 mtimeMs。客户端拼 `?v=` 即可破缓存 —— 这直接把 §十 的待实测 4 变成不需要实测的定论（覆盖写 + 同名文件 + `no-store` 仍可能被已解码的媒体元素持有旧帧，加版本串是零成本保险）。

**匹配键必须是 `ref`，不是 `id`（这条错了会静默坏）。** 卡上 `segmentRef` 存的是 **spec 原文 id**（`segment-binding.ts:29` 明确标注），而段产物 id 是**清洗过**的：白名单 `[A-Za-z0-9_-]`，其余折 `-`、空则兜底、且**段表整表不对齐时直接退回 `seg-1..seg-N`**（`segment-artifacts.ts` 模块头）。两个分叉场景都会让 id 对不上：

| 场景 | 会发生什么 |
|---|---|
| spec 段 id 含中文 / 点号（如 `第一屏`） | 清洗后变 `seg-1`，与 `segmentRef` 里的原文对不上 |
| 段表过期 / 手写 manifest / 改过没重建 | 全线退成 `seg-N`，与任何 spec id 都对不上 |

后果都是**卡上没视频且不报错**，排查时看不出所以然。处置：

- 清单**同时返回 `ref`**（`segmentRefOf(specSectionId)`），客户端拿 `node.segmentRef` 做**字符串等值比对**，不复刻清洗规则；
- `ref` **只在段表对齐时生成**（`planSegmentArtifacts` 里已有 `aligned` 判据，`segment-artifacts.ts:123`）。对不齐就**不给 ref**——卡不显示视频，属于诚实失败；
- **禁止按序号瞎配**（「第 2 个 artifact 配第 2 张卡」）。名字错了比没有名字更糟，这条纪律 R11 已经立过，这里沿用。


**回退**：清单里没有该 id、或 stat 不到、或 `<video onError>` ⇒ 卡显示文案（即今天的形态），**不报错、不显示破图**。这是 §9.6 ③ 的落地。

**本期不做**（三条都是「看起来更彻底、实际引入新债」）：

- 不把段产物建成画布节点：会同时进版本、undo、GC 三条既有链；
- 不给卡加 `segmentUrl` 持久字段（理由同上）；
- 不做多卡同播（hover 单例已定，§十 2）。

#### 第 1 批四步（可直接照排，每步单独可验）

| 步 | 改什么 | 怎么验 |
|---|---|---|
| 1 | `publishSegmentArtifacts` 复制到 `assets/seg-<id>.mp4`，指针带上 `ref` | 文件存在；`card.json` 顶层 `segments[].ref` 与卡上 `segmentRef` 对得上 |
| 2 | `/remotion/segments` 只读路由 | curl 返回 6 条、`ref` 全为 `spec:sN`、url 全 200；未渲过的项目回空数组 |
| 3 | `use-segment-media`（按 `ref` 索引）+ text 分支挂 `<video>` | 6 张卡出现画面、hover 静音播；无段项目卡不变、控制台无红 |
| 4 | 右键菜单按 §9.5 收窄 | 分镜卡上不再出现「修改提示词 / 重试」 |

#### 一个必须先改的开关：draft 不发段

`shot-render.ts:335` 是 `const publish = deps.publishSegments ?? deps.quality !== 'draft'` —— **draft 档压根不发布段产物**。

这会在真实路径上打死整个功能：用户最常做的是先点「草稿快渲一版」看一版（draft），而 draft 不产段 ⇒ 卡上永远没视频，用户会认为功能没做。

**处置**：`render_composition` 调 `runShotRender` 时显式传 `publishSegments: true`（`host-tools.ts:3986` 的调用点加一行），不改 `shot-render.ts` 的缺省语义。代价 = draft 也复制一份段到 `deliver/segments` + `assets/`（每段 1.3–1.9MB，十几段量级，可接受）。合规性上也是对的：用户要审的就是「刚渲出来的那一版」，draft 版正是它。

#### 第 3 批（N3）旁白怎么接

段 mp4 无音轨（R11-C3 刻意为之），旁白在 `manifest.audio.voiceOver`。hover 不能带声（§9.6 ②，浏览器硬限制），所以分工是：

- **hover = 静音画面**（复用 CV-082 单例）；
- **点开细看 = `<video>` + 一个 `<audio>`**，`audio.currentTime` 起于 `startFrame / fps`，play / pause / seek 双向同步。

对齐全在客户端按段帧窗裁，不需要新机制（§十 3）。
