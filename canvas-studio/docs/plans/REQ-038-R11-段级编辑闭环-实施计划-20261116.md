# REQ-038 R11 · 段级编辑闭环 实施计划

> 2026-11-16 11:21 起。目标不是「分镜渲得更快」，是**改一段不动全片**。
> 判据：改一段的代价 = 1 段渲染 + 1 次确认，且不触碰其他段产物与其他分镜卡。
> 依据：`REQ-038-R11-代码review-20261116.md` §6（真机实测）/ §7（四问答疑）/ §8（优先级）。

## 0. 为什么契约先行

O-1（可寻址）和 O-2（可隔离）看起来是两件事，实际缺同一个东西：**段表**。

- 段渲染现在靠 `boundariesFromSpec` → `planStages` 的等分起点（200 / 400）；
- 而内容轨被 `applyStageTransitions` 左移 10 帧（190 / 390）。

两者错位 10 帧，于是每段末尾都含下一段的入场画面 ⇒ 改 s2 必脏 s1（实测 `1 复用 / 2 重渲`）。
段表把「段的真实内容窗」变成 manifest 里的一等数据，段渲染、段挂载、段级 patch 读同一份，
**C1 与 C3 一次性解决**，不用靠轨 id 前缀（`s2-` / `u0-s2-`）猜归属。

## 1. 契约定义

```jsonc
// manifest.meta.segments（可选；缺省 = 旧 manifest，走现有回退，逐帧不变）
"segments": [
  { "id": "s1", "startFrame": 0,   "frames": 190 },
  { "id": "s2", "startFrame": 190, "frames": 200 },
  { "id": "s3", "startFrame": 390, "frames": 210 }
]
```

| 项 | 规定 |
|---|---|
| 谁写 | `planFromSpec`（唯一），在 `applyStageTransitions` **之后**聚合 `screenTracks` 每桶的最早 `startFrame` |
| 谁读 | `resolveShotBoundaries`（段窗）、段挂载、段级 patch、验收脚本 |
| 语义 | `startFrame` = 该段首轨的**实际**起点（含转场预卷）；`frames` = 到下一段起点（末段到片尾）；**首尾相接、无重叠、Σ = durationInFrames** |
| 空屏 | 该段无轨 ⇒ 起点取 `timeline[i].startFrame`，段仍保留（保持段序与 sections 一一对应） |
| 兼容 | 字段可选，不影响 `MANIFEST_CONTRACT_VERSION`；旧 manifest 无此字段 ⇒ 回退 `spec` 边界 ⇒ 现有测试与产物不变 |
| 登记 | `KNOWN_META_KEYS` 必须加 `segments`，否则每份 manifest 刷「契约外字段」警告 |
| **指纹** | `manifestGlobalsFingerprint` **必须排除 `segments`**：它是派生数据，不是渲染输入；不排除 ⇒ 任何段表改动让全段 dirty，缓存直接失效 |

### B4 落地口径（四处，全部来自真机会话 6f8ba13c 的代价）

1. **probe 返抽帧**：`sampleFrames` 原写 `probe || spot ? [] : pickSampleFrames()`。批注预算的
   铁律是「额度只在对图片有产出时扣」，而 probe 扣掉唯一一次批注额度却一张图都不给 ——
   会话里 step41 的 `probe:true` 吃掉额度、step43 想看画面直接被拒，之后 4 次全量渲染盲改。
   现在 probe 也抽样（spot 仍空，它的画面走 spotFrames 静帧通道）。
2. **units 型段 `copy` 可缺省**：旧校验逼模型给拼合文案，它顺手把 `-60°C` 写成 `-64°C`
   —— 一个纯格式校验污染了成片里唯一的数值。缺省时配方切分用各单元文案拼合（只作权重，
   不上屏）；给了非字符串仍然拒收（「能过就行」会一路带到上屏）。
3. **超时按帧窗收窄**：`renderTimeoutMs` 的分母改成 `plannedFrameCount()`，段渲染从
   600 帧预算降到段窗帧数（200 帧 ⇒ 108s，原来是 204s）。3 段合计 612s → 324s。
4. **Q2 时序回核接线**：分镜路径合成 outcome 时绕过 `commitRenderJob`，`verifyTeardown`
   不跑 ⇒ 用户传了 `timingSegments` 也永远没有 `report.timingCheck`（界面像回核过）。
   现在 `shot-render` 注入 `verifyTiming`（缺省 `verifyShotTiming`，与整片同一算法同一组
   常量），≥2 段才跑，失败只记一行不吞成片。

### B3 落地口径（五处，全部来自真机会话的「改不了」）

1. **对位规则 = 数量相等 + `createdAt` 序**，不用时间窗。段时长由 `planStages`（6.5s）或
   spec 的 `durationSec` 定，而 `shot.duration` 是故事板自己写的 —— 两个时钟从来不同源，
   按「落在哪一段的时间窗里」对位会在段长改动后**静默错位**，比不对位更坏。
   真机 3 屏 vs 6 卡（含 3 张备份）正是「不等就一个都不绑」的第一次实况：回执明说
   「屏 3 ≠ 分镜卡 6，要按段改请直接给 segmentId」。
2. **段指针写两处**：结构化 `segmentRef`（`patch_spec_section` 读它）+ 正文
   `【段】spec:s2 · B1 · 「−60°C 的冰芯」`（人读得到、模型也能看见）。正文走**幂等替换**
   而不是重建整份 —— 保住模型手改过的 `【视觉】/【运镜】` 那些行。
3. **回填点在 scaffold 之后，不在 seed**：分镜卡落地在前、spec 写在后面，两条平行数据
   唯一的交汇点是「spec 编译成 manifest」这一刻。dry（无 `writeTo`）不碰画布；
   写画布失败只回一行警告（spec 已落盘，manifest 已可渲）。
4. **备份拍跳过、不折叠**：它们的 `visual` 往往与主镜几乎同字（真机里唯一能区分的
   「备份：」前缀是模型自己写的），折叠只会撑长卡面。回执说清「跳过了几条 + 怎么保留」
   比塞进卡里有用；镜号也一起不铸，否则镜号与卡面不符（镜号同时是产物命名的锚）。
5. **`patch_spec_section` 是六字段白名单**（`copy` / `label` / `unitCopy` / `unitCard` /
   `unitIndex` / `dataSource`），一次只改一个内容字段，`dataSource` 只作附加（单独给它
   不构成一次改动 —— 它不上屏）。units 型屏改 `copy` **拒收并列出各单元文案**：
   真机会话里正是「为过校验编一句拼合文案」这个口子，把 `−60` 顺手写成 `−64`。

### B5 落地口径（六处，含一处测试跟着行为改）

1. **密度只报两个可解释指标**（字/秒、屏均信息点）+ 一条版面观察，**不阻断渲染**。
   §7.4 的第三项「文本面积占比」没做：它要从 manifest 反算 `textCard` 面积占比，口径一歪
   就会给出「已经很密」的错觉；前两个指标已能复现真机的 2 字/秒与屏均 1 点。
2. **`targetStageSec` 必须与 sections 段数同改**：两处都是「屏数」的事实来源。屏数不符时
   错误信息直接算出「`targetStageSec: 4` ⇒ 5 屏」—— 模型自己复刻 clamp + 可行带算不准，
   算错一次就是一轮「改 → 再拒收」。
3. **`cornerMark` 直接去掉文字**，不是换成段 id：段 id 是内部命名，放屏上等于泄漏；
   换成 `label` 则与眉标重复。它是装饰，就只做装饰（accent 短横）。
4. **多单元 chrome 是「提升到整屏」而不是「裁掉」**：只裁不提升会让第二个格位露出全片
   底色 —— 双底板难看，**漏底更糟**。所以 `liftChrome`：只有首单元出，且**不投影进 cell**。
5. **`generatedBy` 白名单与配方覆盖率是两个问题**：前者问「走没走正路」（builder + 三种
   声明式都算），后者问「是不是配方生成」（手写 builder 不算）。混用一个函数会让其中一边
   失真，所以 `isMarkedGeneratedBy` 独立于 `deriveRecipeDensity` 的 `isRecipe`。
6. **`req038-r9-stagger` 的两条断言跟着行为改了**（如实登记）：原断言「两个单元的基底轨
   必须都在」正好把 P2-9 的双底板钉死；现改为「两个单元的**内容轨** + 只有一块整屏底板」。
   这是产品行为变更后测试同步，不是为了让代码过 —— 反向变异（把 chrome 裁掉又不提升）
   已实测变红。

### B2 落地口径（与计划的三处偏差，如实登记）

1. **编排外提**：`host-tools.ts` 里那 105 行装配（真的零测试、P0 就出在这里）搬进
   `shot-render.ts`，宿主服务（渲染 / 存盘 / 探测 / 拼接 / 抽帧 / spec 读取）全部注入。
   理由两个：装配错只有集成测试能挡（纯函数挡不住）；`host-tools.ts` 已顶到体积棘轮
   （注册值 + 余量 ≈ 15 行），B2 无处落脚。文件从 5412 → 5355 行（首次下降）。
2. **抽帧落 `assets/` 不是 `build/qc/`**：抽帧图走 `saveLocalAssetBytes` 落资产目录，
   回执按既有 `frames[]` 通道给磁盘路径。改口径的原因是 `build/qc/` 的图没有同源 URL、
   不进资产历史、画布也引用不到，而 `frames[]` 下游（回执文案 / `read_image`）要的是
   资产路径。文件名 `qc-<id>.png` 仍可辨认。
3. **报告改为按段产物真值构造**：`report` 不再是 `undefined as unknown as RenderJobReport`
   的 cast（下游自检行因此几乎空），现在给帧数（Σ 段帧）/ 字节 / 实测分辨率 / 码率 /
   抽帧数；`prepareMs` 等拆分项如实填 0（分镜路径没有独立准备阶段，不虚报）。

## 5. 风险与红线

| 风险 | 处置 |
|---|---|
| 段表进 meta 导致全段 hash 失效 | 指纹显式排除（B0 的硬性验收项） |
| 段窗变化让全部缓存一次性失效 | 接受：一次性重渲，换回后续「改一段只重渲这段」 |
| 段窗与 `sliceByShots` 半开区间语义不一致 | 单元测试锁 `[start,end)`，末段 `end = durationInFrames` 不进区间 |
| 旧 manifest 无段表 | 回退 `spec` 边界，行为逐帧不变（回归纪律） |
| 分镜卡加字段破坏 `adopt` 往返 | `segmentRef` 只新增、不参与 `04_storyboard` 解析；adopt 忽略未知字段 |
| 段级 patch 误改其他 section | patch 只接受 `sectionId` + 白名单字段，写回前 diff 回显 |

## 6. 不做

- 段级 UI 编辑器（C1/C2 契约未稳）
- ref2va 镜头视频混入 spec 通道（「一段」语义会含混）
- 把 `build/shot-cache` 当交付（hash 名 + 静音轨 + 过期回收）
- 给 spec 加 DSL（先证明用户真会按段改）
