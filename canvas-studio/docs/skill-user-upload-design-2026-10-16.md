## 2. 技术前提复核（这决定了实施成本）

### 2.1 上游已经现成的能力（无需开发）

| 能力 | 机制 | 出处 |
|---|---|---|
| 目录发现 | 按 rank 扫 5 类根目录，支持 `<name>/SKILL.md` 目录包与 `<name>.md` 扁平文件 | `deepseek-harness/packages/skill/skill-filesystem/README.md`、`docs/subsystems/skills.zh.md:64-90` |
| 热更新 | Chokidar 监听增/删/改；**目录整体删除再重建仍可观测**；首方 `write`/`edit` 工具同步失效 | 同上 |
| 正文改动免重启 | catalog 与正文生命周期分离：每次 `skill(name)` 重读文件 | `skills.zh.md:194` |
| 调用控制 | frontmatter `disable-model-invocation` / `user-invocable`（**fail closed**：非法值整条丢弃） | `skill-filesystem/README.md` |
| 额外路由 | frontmatter `whenToUse`（不受 description 长度限制）、`metadata` | `skills.zh.md:96-101` |
| 分层注册 | `ctx.skills.registerProvider()`（插件 apply 时同步注册，`list()` 内可异步发现）；按 scope 分层 | `skills.zh.md:249-304` |
| 变更事件 | `skills/change` —— 提供方变更时通知，消费方重新 `snapshot()` | `skills.zh.md:311-328` |
| **已挂载** | desktop 用的 `standard` / `code` preset **已包含 `skill-filesystem` 行** | `~/.videobuddy/profiles/node_modules/@deepseek-ai/dsh/config/agent-presets/standard/agent.cordis.yml:83` |

**结论**：把一份用户 skill 放进 `<DSH_HOME>/skills/<name>/SKILL.md`，它**今天就会被发现、进模型 catalog、且热更新**。本机 `~/.videobuddy/skills` 与 `~/.agents/skills` 目前都**不存在**，但 provider 会从最近存在的祖先逐段跟踪 —— 目录一创建即被发现。

### 2.2 canvas-studio 现状与差距

| 环节 | 现状 | 差距 |
|---|---|---|
| 注册 | 自研 `registerMinimaxSkills` 只读**包内** `skills/`（`src/skills/minimax-skills.ts:153-178`），走 `ctx.skills.register()` | 用户目录不在扫描面内 ⇒ 用户 skill 进不了 catalog |
| 依赖 | `package.json:68` 声明 `@deepseek-ai/dsh-skill-filesystem` | **源码零引用**（装了没用） |
| 广场列表 | `SkillMarket.tsx:49` 直接用模块常量 `VISIBLE_CATALOG`；client 端无 fs ⇒ 实际是编译期 `BUNDLED_CATALOG` | 用户 skill **不可能出现在广场**，除非加一条 Host→Client 的动态列表通路 |
| 装载 | `skills.json` + `ActiveSkillChips` + CV-323 注入（order 154） | ✅ 已通 —— 这是用户 skill「生效」的现成通道 |
| 槽位绑定 | `toolchain.md` 表格在**插件包内**（随包发布，用户改不了） | 用户 skill 无法进入绑定表；需要「用户槽位表」或换策略 |

### 2.3 三个反直觉点（不先讲清会踩坑）

1. **「内置优先」在项目级目录下是反的。** 单层内优先级：project(100) > project-agents(200) > custom(300) > user(400) > agents(500) > bundled(600)；且 `register()` 的 runtime 条目排序为「project > runtime > user」。⇒ 用户把 skill 放**用户级**（400）会输给内置 runtime（符合「内置优先」），放**项目级**（100）会**赢过内置**（违背「内置优先」）。**存放位置的选择直接决定冲突语义。**
2. **`<projectRoot>` 不等于 canvas-studio 的「项目」。** 上游 project root = 最近含 `.git` 的祖先目录，找不到才是 cwd。canvas-studio 的项目目录通常在 `~/Desktop/job/VideoOut/...`；若其祖先存在 `.git`，`<项目>/.dsh/skills` 会落到那个仓库根 ⇒ **跨项目串味**。项目级方案要先解决这个语义。
3. **description 可见长度有两套口径。** 上游 `tool-skill` 的 `catalogDescriptionMaxLength` 默认 **500**（`skills.zh.md:231`）；canvas-studio 自研注册控制 `DESCRIPTION_LIMIT = 1024`（最长 skill 914 字符）。⇒ 同一份内容走两条路径，模型看到的长度不同。用户 skill 若走上游 provider，契约里的 `description ≤1024` 是**够不到的**。

## 3. 需要拍板的六个问题

### P1 · 支持什么形式的用户 skill

| 选项 | 含义 | 代价 |
|---|---|---|
| **A（建议）** | 第一阶段：**知识型，且扩一个「用户可占」的槽位** | 需新增槽位概念或放开 `general` |
| B | 只开放现有 6 个能力槽位（= 现行契约） | **死锁**：6 个全被内置占用 ⇒ 永不生效（§5.1） |
| C | 也允许决策型上传 | 与 D1 拍板相反；多决策型打架，且总纲无法预判 |

**我的建议**：走 A，但**分两步**：先让它「能生效」（见 P3 的路径 B），再决定是否给风格型一个正式槽位。理由是用户最可能想上传的就是「我自己的风格」，而现在没有任何落点；同时风格型在分型上属于知识型（CV-321 已让 11 个风格 skill 交出工作流、只留风格知识），语义上并不违反 D1。

### P2 · 存放位置与作用域

| 选项 | 优先级后果 | 适用 |
|---|---|---|
| **用户级 `<DSH_HOME>/skills/`（建议默认）** | rank 400，输给内置 runtime ⇒ **天然满足「内置优先」** | 跨项目复用；一个用户装一次 |
| 项目级 `<项目>/.dsh/skills/` | rank 100，**赢过内置** | 需要「本项目专用且允许覆盖内置」时才用；且要先解决 §2.3-2 |
| 两者都给 | 用户级兜底 + 项目级覆盖 | 第二阶段再考虑 |

**建议**：第一阶段**只做用户级**，并在 UI 上明确写「此技能对你所有项目可用」。项目级延后到「project root 语义」被明确之后再谈 —— 否则会出现「我把 skill 放进项目里，结果它跑到了别的项目」这类难解释的问题。

### P3 · 用户 skill 怎样才算「生效」

三条可用路径，成本与确定性差别很大：

| 路径 | 机制 | 确定性 | 成本 |
|---|---|---|---|
| **A 进 catalog 自动** | 上游 provider 发现 → 进 `<available_skills>` → 模型按 description 自主选 | **低**（模型可能不选） | 0（已通） |
| **B 装载进激活集** | 用户点「装载」→ 写项目 `skills.json` → CV-323 注入（「用户选定即视为已确认」） | **高** | 0（已通） |
| **C 进槽位绑定表** | 总纲路由按绑定表加载 | 中（模型要按表加载） | **高**：`toolchain.md` 在包内只读，要生效必须新增一份**可写的用户槽位表** —— 与 CV-324「消灭第二事实源」方向相反 |

**建议**：第一阶段**只用 A + B，明确不做 C**。理由：① B 已经能保证「用户选了就一定用」（注入文案明确写了「命中清单直接加载使用，不要再问」）；② C 需要一个可写的第二事实源，收益（确定性从"高"到"更高"）远小于代价；③ 不给用户 skill 槽位，就同时绕开了 §5.1 的死锁 —— 这是**最低成本的自洽解法**。

### P4 · UI 与交互设计

**入口**：`SkillMarket` 顶部那个现在禁用 + 「待接入」的按钮，改为 **「导入技能」**（先例：`lobby-skill-marketplace-plan.md:217` 的预留位本来就是给它留的）。

**导入方式**（按推荐度）：

1. **选择技能目录 / 文件**（主打）—— 目录包 `<name>/SKILL.md` 或单个 `<name>.md`；选完先**预览 + 校验 + 冲突提示**，用户确认后才落盘。
2. **打开技能目录**（兜底，成本最低）—— 直接 `shell.openPath(<DSH_HOME>/skills)`，让用户自己拖文件进去。上游热更新会自动接住。
3. **在应用内新建**（进阶，可延后）—— 表单填 `name` / `description` / 类别 / role / slot + 正文，生成 `SKILL.md`。适合小 skill，但表单会诱导用户写出低质量描述。

> 不建议第一阶段做 **zip 导入**：需要解包、路径穿越防护、覆盖确认三件事，而收益仅「传输方便」—— 单人桌面产品里用不上。

**广场展示**：

- 列表数据源必须改成**动态**：Host 侧在 `skills/change` 事件触发时 `ctx.skills.snapshot({ cwd })`，把结果推给 client（现有 `VISIBLE_CATALOG` 是编译期常量，见 §2.2）。
- 卡片加**来源角标**：「内置」/「我的」；「我的」可删除，内置不可删。
- 新增分组 **「我的技能」**（空态给一句引导 + 上面第 2 种导入方式）。

**详情卡新增「生效状态」三态** —— 这是本次交互设计的核心，因为用户最常问的就是「我传了为什么没用」：

| 状态 | 展示 | 含义 |
|---|---|---|
| ✅ 已生效 | 「已进入模型可用列表」 | 上游 provider 已发现，catalog 里有它 |
| ⚠️ 未装载 | 「已导入，尚未在本项目装载」+ 一键装载 | 在 catalog 里，但模型不一定会用 ⇒ 引导走路径 B |
| ⛔ 有冲突 | 「与内置 `X` 同名，内置优先」 | 同名 skill 被内置覆盖（用户级 rank 400 的必然结果） |

**装载**：完全复用 `ActiveSkillChips`（工作流条下的 chip + 点击取消），零新增机制。

**删除**：删目录 + 从所有项目的 `skills.json` 清理该名；删除前提示「已装载它的项目会失去该规范」。⚠️ 落盘删除要走 OS 废纸篓（本仓安全删除约束，见 `MEMORY.md`），不要直接 `rm`。

### P5 · 支持什么格式

| 项 | 建议 | 理由 |
|---|---|---|
| 载体 | **目录包 `<name>/SKILL.md` + 可选 `references/`**（主打）；扁平 `<name>.md`（兼容） | 上游原生支持这两种；目录包才能承载渐进披露 |
| 命名 | 目录名 = frontmatter `name`，kebab-case | 上游硬校验，非法整条丢弃（fail closed） |
| frontmatter | 必需 `name` + `description`；**canvas-studio 附加 `role: knowledge`**（可选 `slot`） | 上游把 frontmatter 解析为**开放 YAML 对象**，额外字段被忽略 ⇒ `role` 放这里安全（这也是现行 CV-325 契约的写法） |
| `description` 长度 | 契约里**改标注为 ≤500 字符**（不是 1024） | 上游 `catalogDescriptionMaxLength` 默认 500（§2.3-3）；写 1024 会让用户以为可以，实际被截断 |
| `references/` | 允许，且正文用相对路径引用 | 与内置格式一致；读取时 Host `read` 工具直达 |
| `platform.yaml` | **用户的 skill 不需要** | 那是平台展示元数据；用户 skill 的展示字段直接从 frontmatter 派生（缺 `category` 时落「我的技能」分组） |
| `meta.yaml` | 不需要（上游署名载体，与用户无关） | 现行契约已如此 |

### P6 · 校验与安全

**先把信任模型说清楚**：这是**单用户桌面产品** —— 用户上传自己的 skill，等于用户改自己的东西，不是多租户内容分发 ⇒ 安全边界是「**防误操作 + 防自伤**」，不是「防敌手」。过度设计（沙箱、签名、权限）在这里没有收益，本仓一贯反对 over-engineering。

因此校验只做三件事：

1. **结构校验**（放行前）：`name` 合法且与目录名一致、`description` 非空、`role` 缺失或非 `knowledge` → **拒绝**（现行 `validateUpload` 已实现，规则不重写第二遍）。
2. **冲突提示**（落盘前）：与内置或已存在的用户 skill 同名 → 明确告知「内置优先，你的不会生效」，让用户改名前再传（**不要静默接受**）。
3. **约定提示**（非拒绝）：用户 skill 正文若出现「自设审批门」表述（CV-322 已对内禁，门禁正则可复用），给**警告文案**而不是拒绝 —— 拒绝会让用户困惑（他不知道总纲在哪、为什么不能写），而这类措辞本来就不会生效（总纲安全协议第 5 条已预写死）。

**必须修掉的 fail-open**：`validateUpload` 的 `owners` 默认 `{}` ⇒ 拿不到占用表时视为「未占用」⇒ fail-open。既然 P3 建议**不给用户 skill 槽位**，最干净的修法是**让 `slot` 变成可选**：只声明 `role: knowledge` 即可入库，`slot` 若声明了则仅作展示/未来用，**不参与绑定**。这样默认行为就是安全的（不存在「静默顶替内置」这条路径）。

## 4. 建议的分批路线（编号开工时取；此处只按批次）

| 批 | 内容 | 需要宿主改动 | 前置 |
|---|---|---|---|
| **批次 1** | 修 §5.1 的三处缺陷（激活集一轮空窗 / validateUpload fail-closed / `slot` 改可选 + 契约与验收表勘误） | 是（小改） | 无 —— **这批应该先做，与上传无关** |
| **批次 2** | 广场动态列表（Host `skills/change` → `snapshot()` → client）+ 「我的技能」分组 + 来源角标 + 生效状态三态 | 是（新路由/推送） | 批次 1 |
| **批次 3** | 导入入口：「选择目录/文件 + 预览校验 + 冲突提示 + 落盘」；启用顶部按钮 | 是 | 批次 2 |
| 批次 4（可选） | 应用内新建表单；项目级 skill 目录（需先定 project root 语义） | 是 | 批次 3 |

> 顺序理由：批次 1 是纯修复且与上传解耦，先做能立刻消掉「上传了也不生效」的坑；批次 2 先把「看得见」做出来（不落盘也能验，手工放文件即可走通全链路）；批次 3 才是写入面。

### 7.1 P1~P6（设计取向，冻结）

| 编号 | 结论 | 冻结内容 |
|---|---|---|
| **P1** | 第一阶段**只支持知识型**用户 skill | 风格型的正式槽位留第二阶段；用户 skill 默认按 `role: knowledge` 处理 |
| **P2** | **只做用户级**，落盘 `<DSH_HOME>/skills/<name>/` | 天然「内置优先」（rank 400 > bundled 600 的优先级语义），且绕开上游 `<projectRoot>` 语义问题 |
