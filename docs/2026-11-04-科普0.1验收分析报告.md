## 一、A4 失败的根因：不是渲染 bug，是**契约没读懂 + 自检失效**

这是本批最该记的一条。

### 现象
`build/manifest.json` 里 callout 轨写得很完整：

```json
{"id":"s2_callout","type":"callout","anchor":{"x":58.5,"y":39},
 "text":"黄赤交角 23.5°","box":{"x":22,"y":24,"w":24,"h":7.5},
 "line":"elbow","startFrame":384,"durationInFrames":32,
 "animate":{"from":{"opacity":0},"to":{"opacity":1},
            "startFrame":31,"durationInFrames":1,"easing":"easeOutCubic"}}
```

字段齐、anchor 合法、`line:"elbow"` 合法。**但成片里它一帧都没出现。**

### 根因（渲染器源码 + 逐帧复算定位）

`animated-style.ts` 里 opacity 是**两个因子相乘**：

```ts
const opacity = clampUnit(fade * (exitState?.opacity ?? state.opacity ?? 1))
```

- `fade` = `fadeInOnlyOpacity`（本轨无 exit）→ 轨内帧 ≥6 后恒为 1
- `state.opacity` = `animateStateAt` 读 `animate` 段

而 `animate` 段写的是 `startFrame: 31, durationInFrames: 1`，轨长 32 帧。
`animateStateAt` 的窗口命中条件是 `localFrame >= start && localFrame < start + dur`，
**唯一命中帧是 localFrame 31**——即轨的最后一帧，且该帧 progress = 0，opacity 仍为 0。

复算结果（轨内帧 → 合成 opacity）：

```
localFrame  0: animate.opacity=0.000 → 合成 0.000
localFrame 14: animate.opacity=0.000 → 合成 0.000   ← 标签淡入期，整层不可见
localFrame 20: animate.opacity=0.000 → 合成 0.000   ← 引线描边期，整层不可见
localFrame 26: animate.opacity=0.000 → 合成 0.000   ← 圆点弹出期，整层不可见
localFrame 31: animate.opacity=0.000 → 合成 0.000   ← 唯一命中帧，progress=0 仍为 0
```

**整条轨 32 帧，合成 opacity 恒为 0。** callout 组件自己那套内建动画（引线 0–20 帧描边、标签 14–26 帧淡入、圆点 18–26 帧弹出）全部在跑，但整层被 animate 段钉死为透明——**动画在动，东西看不见**。

这是一次**语义误用**：Agent 把 `animate.startFrame` 当成了"绝对帧号"来写（31 ≈ 想让它在最后出现），
而契约规定它是**轨内相对帧**。同一批的 `s5_chart`、`s5_kpi` 都正确用了轨内相对帧，只有 callout 这条踩了。

### 实帧验证（不靠 manifest 自证）

- 480×270 逐帧扫描 380–413 帧：引线几何区（水平段 x163–281 @ y65、垂直段 x281 @ y65–105）**橙像素恒为 0**
- 全分辨率裁切 180,200 起 700×250：标签盒区域**纯背景，无文字、无引线、无锚点圆点**
- 对照组 300/340/370 帧同样为 0，排除探针打偏

### 为什么没被自查发现

最后一条助手消息原话：

> **引线标注**：锚点落在倾斜地轴上，elbow 折线引到「黄赤交角 23.5°」

**这句话是凭 manifest 字段写的，不是看画面写的。** 它描述的是"manifest 里 anchor/line/text 都填了"，
而不是"片子里能看到引线"。会话里 `inspect_image` 用了 11 次，但**没有一次覆盖 callout 应在的 384–416 帧**。

这正是本次最需要修的**方法论缺陷**：验收项的核对必须**以成片像素为准**，manifest 只能用来定位怀疑点。

## 二、A5 失败：wipe 方向语义反了 + 时序错位

用户要求是"**左 wipe 进、右 wipe 出**"。实际两个面板都是 `direction:"right"`：

```json
s4_lPanel: reveal {kind:"wipe", direction:"right", durationInFrames:24, startFrame:0}
s4_rPanel: reveal {kind:"wipe", direction:"right", durationInFrames:26, startFrame:0}
```

`reveal.ts` 的语义：

```ts
case 'left':  return `inset(0 0 0 ${remaining}%)`  // 从右往左揭开：可见区收在右侧
case 'right': return `inset(0 ${remaining}% 0 0)` // 从左往右揭开：可见区收在左侧
```

即 `direction` 描述的是**揭示行进方向**。两个面板都写 `right` ⇒ **都是"从左往右揭开"**。

像素实测（与基准帧差分，取变化区右边界）：

```
右面板 f666 → 54.8%   f668 → 67.1%   f670 → 76.5%   f674 → 90.8%   f680 → 96.5%
```

右面板可见区**自左向右扩张**，是从左边推出来的，不是"右 wipe 出"。**判据要求的"两段 wipe 方向正确"不成立。**

另有**时序错位**：左面板 556 帧起、右面板 660 帧起，相差 104 帧（3.5 秒），
而两块面板是"直射 / 斜射"的**并置对比**。用户描述的"切换"语义暗示两者应**同时**进出，
现实现却是左面板先独占画面 3.5 秒，右面板才擦进来——这期间左面板的信息在讲"直射"，
但画面还是旧的，双语义对不上。

**正确写法**：右面板应写 `direction:"left"`（从右往左揭开 = 视觉上从右侧擦出），
或用 `direction:"right"` + `exit` 组合表达"右 wipe 出"，并把两块面板的 reveal 起点对齐。

## 三、A1 失败：编排壳整条链路缺失

判据原文："回复中**显式声明**走 `explainer-format-director` → `code-driven-explainer` 链"。

实测：

- 全会话 `explainer-format-director` 出现 5 次，但**没有一次是回复中的路由声明**：3 次 skill 目录快照、1 次 tool result（引用文件内容）、1 次助手 reasoning
- **关键新证据（第 2 步 reasoning）——这是权衡后的主动跳过，不是没看见**：

  > The 科普讲解体裁 format director exists but user named code-driven-explainer directly.
  > Per instructions: "If the user names a skill ... call the skill tool with the exact skill name before taking task actions."
  > Maybe also explainer-format-director? The routing says format directors route to executors.
  > User named the executor directly. I'll load code-driven-explainer and its references.

- 实际加载的 skill：`canvas-studio-creation` → `code-driven-explainer` → `voiceover-writing` → `music-prompt-writing`
- 而 `explainer-format-director` **在会话第 11 帧的 skill 目录里就已存在**（三次目录快照均包含它），
  其触发词明确覆盖"科普 / 讲解 / 知识视频 / 原理 / 科普短片 / explainer / science video"——**本片正中靶心**

助手第一轮的原话是：

> 已加载 `canvas-studio-creation` + `code-driven-explainer` … 先说明本轮的既定事实（不再询问）

它把"用户明确指定 code-driven-explainer"理解成了"直接用 executor、跳过 L2 壳"。
但 `explainer-format-director` 的定位恰恰是**用户点名下游时也要先做定向三问**（受众 / 记住哪一件事 / 时长画幅），
并显式声明路由链——这是**壳的职责，不是 executor 的**。

**根因定性修正**：这不是"没读懂契约"，而是**两条规则打架**——插件通用规则「用户点名 skill → 直接调用」
压过了体裁壳的「点名下游也要先过壳定向」。修法不能只靠会话行为约定，必须改
`explainer-format-director` 的 skill 描述/触发词，显式写明"**用户点名 executor 时本壳仍须先加载做定向**"，
让两条规则在描述层面消解冲突。

顺带：定向三问也确实没做。实际只问了 **2 个问题**（音色人格、数据口径），
而壳要求的三问（受众 / 记住哪一件事 / 时长画幅）**一项未问**——45s 科普片的受众（小学生 vs 航天爱好者）
直接决定了叙述密度，这正是该壳存在的价值。

## 五、其他发现（不在判据表内，但影响成片质量）

### 5.1 仪表盘段字幕卡与指针重叠（实帧可见）
Frame 450 全分辨率裁切：仪表盘中心那张 `0° 赤道` 字幕卡（box 中心 50,63）**被指针和轴心圆点直接穿过**，
文字被橙色指针切割成"小旭"状碎片。s3_center 与 s3_needle 抢同一坐标。

### 5.2 直射/斜射两段字幕卡文字叠字

### 5.3 片尾 9.5 秒无字幕、无配音
字幕轨最后一条 cap10 结束于 1065 帧，片长 1350 帧 ⇒ **285 帧（9.5s）纯裸画面**

### 5.4 19 条轨带"呼吸式"scale 微动
`s1_halo`/`s1_sun`/`s2_*`/`s3_*`/`s4_*`/`s5_chart` 等 19 条轨挂了 `scale 0.994 ↔ 1.006` 的往复动画。

**这是"为过 lint 而造动"，不是设计动效**，属于典型的判据驱动式返工。

### 第二层：补机制（让同类问题下次自动拦住）——已拍板：四条全部随本批处理，不单独立项

1. **加一条 manifest 静态校验**：`animate.startFrame + durationInFrames > track.durationInFrames` → error；
   尤其当 `animate` 段整轨只命中 1 帧且 `from.opacity === 0` 时直接判定"整层不可见"。
   *（这条能一劳永逸拦住 A4 这类错）*
2. **给 reveal 加语义断言**：`direction:"right"` + 面板位于画布右侧 ⇒ 警告"右 wipe 出请用 direction:left"，
   或提供 `reveal.out` 字段显式表达退场揭示（当前 `exit` 只支持 opacity/scale/rotation/x/y，**不支持 clip 退场**）。
3. **加"渲染产物自检"回路**：render 完成后按判据表自动抽帧检查——
   callout 检查引线区橙像素 > 0；reveal 检查边界推进方向；字幕检查净字密度；
   **禁止用 manifest 字段自证画面效果**。
4. **补 lint ML-10 的替代路径**：允许"设计性静物"豁免，而不是靠 0.6% 的 scale 呼吸刷动画帧占比，
   否则下一批还会长出一堆假动效。

### 第三层：验收机制本身——三条已落进六体裁验收材料（§〇.5–.7 总则 + 各判据表「取证」列）

1. **回填表里 A8 记"未执行"**，不勾选；
2. **验收必须有"负例必发"闸门**——正例跑完、正例成片交付后，若未见负例消息，本批**不予结案**；
3. **每条判据的"核对点"要标注取证方式**（像素 / 音频 / manifest / 溯源表），
   杜绝下一轮再出现"字段填了就算过"。

### 8.1 总账

### 8.3 三个结构性原因

1. **大头是模型推理，不是工具**。每步 20–70s 的生成间隔累计约 68 分钟；turn2 单 turn 57.9 min，中途两次 compaction（+30.7min、+62.4min）。**但步距实测与"compaction 后变慢"的假设相反**：turn1 平均 31.4s/步 → comp1 后 20.5s/步 → comp2 后 15.3s/步，**逐段递减**。即压缩后上下文变短，步进反而更快；上下文变长带来的"复利变慢"在本会话**没有出现**。真正的时延来自**步数本身（223 步）**，不是单步变慢。
2. **渲染不慢，慢在"改一次渲一次"的迭代**。render_composition 平均 15.6s；20 次里前 5 次（+44.6～+59.4min，即 11:43–11:58）是初版构建与首轮自检，后 15 次（+65.4～+81.3min，即 12:04–12:20）密集在修 4 个 bug 的重渲循环（每 bug 一轮 manifest 修改 + 25–42s 整片重渲）。**这正是 §六.2.3「渲染产物自检回路」要省的钱**——bug 早一轮定位，就少一轮渲染加中间的模型步。
3. **6.7 分钟在等人**，集中在音色选择题（375s）。数据口径题只等 28.5s（有推荐项答得快）。**验收提示词可以预置决策缺省**（"音色按推荐项，不用问我"），把这 6 分钟直接省掉。

澄清：按用户消息间隔粗算的"24.5 min / 31.6 min 空闲"是时间戳假象（系统消息同批打点）；逐事件核对后 turn1 结束到"继续"仅隔 63s，全会话除选择题外**无任何超过 70s 的人工空闲**；bash 170 次合计 57s（均 0.34s），不是瓶颈。
