# video-shotcraft 调研与适配评估（2026-10-25）

> 结论先说：**整包不引入；但它有三样东西正好补我们的短板**——镜头配方卡的「形式」、卡点剪辑的「方法论」、音效库的「品类」。另有一个姊妹 skill 可能比它更贴近我们的片型。

---

## 一、它是什么（事实）

| 项 | 内容 |
|---|---|
| 仓库 | `Vincentwei1021/video-shotcraft`（Apache-2.0，TypeScript，★ ~12k） |
| 定位 | 给 Claude Code / Codex 用的 **Agent Skill**，把 web/桌面产品做成**电影感宣传片** |
| 规模 | **157 张镜头配方卡 / 214 种样式 / 214 条动态样片**（README 与 SKILL.md 口径不一致，仓库实际另有 152/209 一版）；**已验收的 36.2 秒 Ink Press 模板**；**149 个音效 + 5 个 BGM** |
| 三种模式 | ① 直接套模板 ② Agent 自主自由创作 ③ 与用户逐阶段共同创作 |
| 生产链 | 最小只读检查 → 无头浏览器抓**真实页面 2x 全页纹理 + 元素级抠图** → 写 layout 坐标表 → 产品简报/分镜/Remotion 工程 → 复用 `demos/` 调校过的 TSX → 渲前 librosa 做**节拍分析** → 渲后**回测切点误差** → 出片 → 可选**剪映工程导出** / 浏览器「动效工作台」继续编辑 |
| 依赖 | Node + Remotion + Python 3 + `chrome-headless-shell`（低配 Linux 要 `--concurrency=1`） |
| 许可 | 仓库 Apache-2.0；音频逐条授权（另有 ATTRIBUTION）；**Remotion 自身许可按公司规模另算** |
| 第三方评估 | FSRS 61/100「推荐」，但**证据充分度低**（静态审查，未执行复现） |

**它的方法论内核**（比资产更有价值）：
真实截图 → 视觉语言从产品设计系统生长 → **卡点剪辑** → 确定性渲染 → **独立终检（subagent）**。

## 二、和我们比，差在哪（这才是重点）

| 维度 | video-shotcraft | 我们（canvas-studio + `code-driven-explainer`） |
|---|---|---|
| 片型 | 产品宣传片（launch / promo / demo） | **科普讲解片** + 图文/数据卡 |
| 素材来源 | 无头浏览器抓真实网页（元素级抠图 + 坐标表） | 用户上传 / 画布资产 / AI 生成；UI 由代码绘制 |
| **动画知识形态** | **157 张配方卡 + 214 样片 + 可复用 TSX** | `motion-patterns.md` 等**散文**（决策表 + 建议），模型自己翻译成 manifest |
| 模板 | Ink Press 36.2s 已验收 | **无模板**，每次从零组装 |
| 声音 | **149 SFX（16 类）+ 5 BGM + librosa 卡点 + 渲后切点回测** | TTS 旁白 + BGM 生成 + 音量闪避；**无 SFX、无卡点** |
| 交付后编辑 | 浏览器「动效工作台」时间线 + 剪映工程 | 节点式画布 + 故事板覆盖层 |
| 渲染 | Remotion 跑在 Node（CLI/SSR） | Remotion **CSR** 跑在 Electron 内置 Chromium |
| 额外依赖 | Node + Python3 + chrome-headless-shell | **无**（复用 Electron 自带 Chromium） |

### 三条能直接解释我们最近问题的事实

1. **我们把知识写成散文，它把知识写成组件**。
   这两天的会话显示：模型为了搞清 `textUnitProgress` / `ImageClip` / `shape-geometry`，去读了 24 次源码。
   它那边同一个问题的答案是「卡片 + demo 源码」——模型只要挑卡、填参数。
   **这正是 G6 的深层解法**：不是再加几段文字，而是把"可执行片段"给到模型。
2. **它没有"每次从零"**：一支已验收模板 + 卡库，等于给模型一个**起点**。我们是空 manifest。
3. **它的"高级感"有一半来自声音**：149 个 SFX 按 16 类组织。我们目前只有旁白和 BGM，**转场/文字/强调音效全缺**——这是"像不像专业片"的差距里最便宜可补的一块。

## 三、为什么**不建议整包引入**

| 理由 | 说明 |
|---|---|
| **片型错配** | 采集链是"抓真实网页"，我们的素材是画布资产/用户上传；核心资产（layout 坐标表、页面抠图）对科普片无用 |
| **运行时不通** | 它的 `demos/*.tsx` 是**直接写 React/Remotion 组件**；我们的产物是 **manifest DSL**（`tracks[]` + `animate`），TSX 不能直接复用，得逐个翻译 |
| **体量与依赖** | 157 卡 + 214 样片 + 149 音效 + 需要 `chrome-headless-shell`/Python；我们包体已 ~345MB（其中 onnxruntime 就 345M），再加一套等于翻倍 |
| **许可链** | 音频逐条授权 + Remotion 商用按公司规模（我们是个人/小团队，目前免费，但 Remotion 5.0 将改条款） |
| **证据强度** | 第三方评估证据充分度「低」：模板与卡片未被执行复现，剪映 Windows 路径作者自承未真机验证 |

## 四、建议吸收的四样（按性价比排序）

### ① 把「运动范式」改造成「卡片」—— **最该做，零依赖**

现在 `motion-patterns.md` 是散文；改成卡片结构（每张卡 ~20 行）：

```
卡名：text-as-mask（文字遮罩揭示）
适用：大标题 / 金句 / 数据揭示
参数：maskDirection(up|down) / revealFrames / stagger
最小片段：{ type:"textCard", anim:"maskReveal", animOptions:{...} }  ← 可直接粘进 tracks
观感要点：遮罩边缘要有 2px 羽化；揭示时不叠位移
```

- 收益：直接减少"读源码确认语义"（G6 的另一半答案）；模型从"翻译散文"变成"选卡填参"。
- 成本：纯文档 + 一条守卫（卡片必须能被 `validateManifest` 接受）。
- 数量建议：先做 **12–16 张**（覆盖我们已有的 5 种 anim + 形状/转场/图表组合），不追 157。

### ② 借它的**卡片分类与命名**做"词汇对照表"—— **零代码**

不搬资产，只搬**词汇**：把它的 157 张卡按类别（camera / typography / UI entrance / data emphasis / outro…）列出，
逐条标注「我们能不能做，用什么字段做」。产出一张对照表后，我们 skill 表达力从 5 种变 30+ 种，
而且**不需要新增渲染能力**（大部分是 manifest 已有能力的重新组合）。

### ③ 节拍卡点（beat sync）—— **中等收益，独立性强**

它用 librosa 算 beat → 按拍点切镜 → 渲后回测切点误差。
我们完全空白。落地形态建议：**先做"建议器"不动渲染**——离线算 beat map，输出 `cutFrames[]` 建议，
由 agent 排轨时参考；验证有收益后再考虑写进 manifest 的 `meta.beatMap`。

### ④ 音效（SFX）—— **最便宜的"高级感"**

只挑 10–20 个免费商用 SFX（whoosh / click / riser / impact），按 4 类进资产库，
在卡片里声明"这张卡配哪个音效"。体积小、见效快。

### 不建议吸收

动效工作台（时间线编辑器，产品级差异，成本极高）｜剪映工程导出（另一条交付形态）｜
puppeteer 采集链（片型不匹配）｜整包 vendor。

## 八、回答两个具体问题

### Q1：它对"我们慢 + 效果不稳定"帮助大吗？

**拆病因看，答案不一样。** 把我们最近实测的 6 类问题逐条对照：

| # | 我们的病因 | 证据 | shotcraft 帮助度 |
|---|---|---|---|
| 1 | **模型要"翻译散文 + 读源码"**：24 次源码探索、每步 reasoning 2.7–4 万字符 | 会话转录（A 级） | **高** —— 卡片 + demo 片段把"翻译"变成"选卡填参" |
| 2 | **每次从零组装 manifest**：没有起点，时长/结构靠试错 | 事故复盘（B 级） | **高** —— 已验收模板 = 起点 |
| 3 | **动效词汇贫乏**：只有 5 种 `anim`，表达力不足导致"要么死板要么乱动" | `manifest-contract` | **中高** —— 词汇对照表能把已有能力组合出 30+ 种 |
| 4 | **每步 ≈6s 固定 TTFT**（provider 侧） | 残差法（B 级） | **零** —— 与内容层无关 |
| 5 | **渲染链路不稳**：39 次超时 / 工单不派 / 素材被 GC 删 / 探针污染 | Phase 0（A 级） | **零** —— 它是内容工具，不碰运行时 |
| 6 | **声音单薄**：只有旁白 + BGM，无 SFX | 现状盘点 | **中** —— 149 个 SFX 里的 10–20 个就够用 |

**结论**：
- 对**慢**：帮助是**间接的**（少推理、少试错），不是决定性的。真正压时间的三件事是
  「减步数」「provider TTFT」「少读源码」，它只帮第三件，且不保证量。
- 对**效果不稳定**：帮助**明显，但只在内容/动效层**（#1/#2/#3/#6）。
  我们的核心事故（渲染出不了片）它**一点忙都帮不上** —— 那条线已经由 CV-363~365 在治。

> 换句话说：**它是"内容层的好教材"，不是"运行时层的解药"**。别把两件事混在一起期待。

### Q2：模板不能复用到咱们项目吗？

**能，但要分清"复用哪一层"。** 它的模板 = 一支完整 Remotion 工程；我们的产物 = **一份 manifest JSON**。
这两者之间不是"复制粘贴"，是"翻译"。分三层看：

| 层 | 能复用多少 | 怎么落 |
|---|---|---|
| **设计语言**（配色/构图/节奏/镜头语汇） | **100%** | 抽成我们的 **theme preset**：配色 + 字体 + `meta.look` 六项 + 动效基线（默认 duration/easing/stagger）+ 版式（左右分区等）。看到即能用，与实现无关 |
| **资产**（149 SFX / 5 BGM / 字体） | **大部分** | 音频逐条看 `ATTRIBUTION.md`（仓库 Apache-2.0，音频各自授权）；字体要看许可。挑 10–20 个进我们资产库 |
| **代码**（`demos/*.tsx`） | **不能直接复用** | 它是 React/Remotion 组件；我们的渲染是「manifest → 白名单组件」，模型只能产 JSON。只能做**能力映射**：把镜头卡翻译成我们已有的 `transform/animate/fx/textCard/shape/transition` 组合 |

**为什么不做"移植 TSX"这条路**：
1. 我们的架构刻意不让模型写代码（确定性 + 可校验 + 无任意代码执行），为了复用模板放弃这条，
   代价远大于收益；
2. 移植 157 张卡 = 157 次实现 + 157 条测试，且与我们 24 个组件的抽象重复。

**所以"模板复用"的正确形态是：**

```
模板 = theme preset（设计 token）+ 卡片序列（12–16 张映射好的镜头卡）
      ↑ 我们已有落点：meta.look（6 项）、global.fontFamily/theme/brandColor、look_card（5 tokens 视觉基调）
      ↑ 缺的是：动效默认值 + 版式 + "推荐卡片序列"
```

缺的那三样才是要做的事：给 manifest 加 `meta.themeId`（或 `select_theme` 工具），
它一次性展开成 look + 字体 + 动效基线，然后 agent 只在卡片库里挑镜头。
**这样"模板"是可复用的，而"TSX 代码"不需要被复用的。**
