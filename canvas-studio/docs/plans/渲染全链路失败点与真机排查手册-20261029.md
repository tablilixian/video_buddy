## B. 执行闭环 —— 反复循环，直到 §A DoD 达成

本文件是排查手册，**不是一次性审计**。每轮循环：

```
0. 通道体检  先确认会话能正常出工具调用——`11128 unapproved channel` / `TRANSPORT` /
             `余额读取失败` 会让 S6 根本发不出去（H8）。通道不通 ⇒ 通道修复升级为先行项，
             本轮先做沙箱内可做的部分（代码审 / 日志分析 / 探针 --check），不做无谓等待
     ↓
1. 建单   §3 S0-S5 前置确认 → S6 真机建单（先 draft / probe:true / 短时长走通，再换 high）
     ↓
2. 分类   结果落进 §5 决策树（先看耗时档，再看具体文案）
     ↓
3. 归因   对照 §4 假设表（H1-H8）拿证据定案；核对 §2 九条疑点是否复现
     ↓
4. 修复   按 §4「若成立的解决方向」实施；改码边界见文档头；
          每次修复单独 commit，commit 信息写明「修的是哪条假设」
     ↓
5. 回归   重跑失败场景 + §A D2 窗口矩阵；回归用例直接复用同目录
          REQ-035-真机验收清单-20261024.md 的 Z-1~Z-6
          （Z-1 冷启首单必须走隐藏窗口＝历史失败场景本体；Z-3 画布页卡住 20s 改派；Z-4 素材缺失自救）
     ↓
6. 记录   本轮证据（日志片段 + jobs[] 快照 + 耗时 + 产物 ffprobe）归档到
          docs/effect-tests/runs/（沿用 collect-effect-tests.mjs 惯例）
     ↓
    回到 1，直到 §A 全部打勾
```

**两条铁律**：
- ≈28.1s（8s 冷启 + 20s 判死，取不到单）与 ≈149s（取到单没开渲）是**两条不同断点**（疑点 7），修复与回归必须各自覆盖，不许合并治。
- 每轮循环的证据都归档，失败复现不丢单——历史 33 次失败就是丢在「老日志无 jobId/派单理由」上（疑点 3）。

## D. 自主执行授权 —— 不要停下来问，自己拍板，最后汇报

**执行模式**：拿到本文件后自主推进到底，**中途不要停下来向用户提问或请求确认**。需要拍板的地方，按下表规则自主决定并继续：

| 需要拍板的情形 | 自主决策规则 |
|---|---|
| 排查方向选择 | 按 §4 假设表的支持证据强度排序，先证伪可疑度最高的（当前即 H1/H2 → H3/H4） |
| 修复方案取舍 | 选对 DoD 最短路径、改动面最小的；优先复用项目既有机制，不引入新抽象 |
| 修隐藏窗口还是画布页 | 按 §3/§5 证据指向定；两边证据相当先修隐藏窗口（④ 层 403，历史根因嫌疑最大） |
| 测试要不要再多跑一轮 | DoD 未达成且还有未证伪的假设 ⇒ 继续跑，不请示 |
| 建单参数怎么选 | 先 `draft` + `probe:true` + 短时长走通，再换 `high`（§3 S6 既定顺序） |
| P0 后渲染全成功、新三档文案观测不到 | 允许**临时注入故障**验证观测面（临时移走 `render-host.js` 制造 503、用 `--windows=hidden-throttled` 档等）；结束后必须原样恢复（`git status` 干净 + bundle 重建），注入了什么、看到了什么写进汇报 |
| 归档命名 / commit 信息 / 报告格式 | 按本文档与项目惯例自行命名，不需要用户确认 |

**唯一的硬刹车**（除此之外一律自主，不停不问）：
- 操作**不可逆且会破坏用户数据/环境**：删项目数据、动 `deepseek-harness/` 子模块、force push 类操作
- 连续 3 轮闭环后 28s/149s 档仍复现，且 H1-H8 全部被证伪——此时停一次，带着全部证据汇报（这不算半路提问，是山穷水尽的兜底）

**需要用户配合的操作（S4/S6 真渲等）不算"提问"，不许因此停下等待**。正确姿势：
1. 沙箱内能做的先全部做完（日志分析、代码审、修复、单测、`--check`）；
2. 把需要用户跑的命令攒成**一张清单**（命令 + 在哪个目录跑 + 看什么 + 报告落哪），一次性给出；
3. 用户跑完后继续分析结果，闭环照常推进——等待期间不停工，转头做其他待办。

**最终汇报（每次收工必交，缺一不可）**：
- **做了什么**：每步动作 + 结论（跑了哪些步骤、审了哪些代码、修了哪些文件 + commit 号）
- **发现了什么**：根因链条——对应 §4 哪条假设、§5 哪一档、§2 哪条疑点
- **验证结果**：对照 §A DoD 逐条打勾（D1-D5），没达成的写清差在哪
- **自主拍板记录**：所有替用户做的决定 + 依据（用户只 review 决定，不需补答任何问题）
- **剩余风险与下一步**：未覆盖的场景、建议的后续动作

## 5. 失败分类决策树（真机复现后按耗时+文案走）

```
render_composition 返回
│
├─ 秒级失败（<5s）
│   ├─ 「manifest 校验失败…」            → ②-7，改 manifest（历史 2 次，10-28）
│   ├─ 「成片素材缺失或不可用…」          → ②-10，查 <project>/assets 是否存在、URL 白名单
│   ├─ 「渲染队列已满（最多 4 单等待）」   → ③ 队列，等前单结算
│   ├─ 「projectId / 工作区未绑定」       → ①/②-2，绑项目
│   └─ 「当前项目还在拍摄定稿阶段」        → ① 流程门（未落画布）
│
├─ ≈28.1s 失败（8s 冷启 + 20s 判死）      ← 历史 33 次都是这档
│   ├─ 老文案「画布页取单后一直没开始渲染」（合并档）
│   ├─ 新文案「Ns 内从未取走它」           → ⑤ 画布页没取单：
│   │       · 看 S6 日志有没有「交给画布页（冷启…）」→ 有 = 窗口没起来（H1/H2）
│   │       · 看画布页是否前台、轮询是否在发（H3/H4）
│   ├─ 新文案「已取走这张单，但 Ns 内一帧都没有渲染」→ ⑥ 没开渲（H3 主线程被占）
│   └─ 「渲染窗口异常，已中止本次渲染」      → ③ 窗口心跳丢 >30s，查 renderer-gone/unresponsive
│
├─ ≈60s 失败（CLIENT_CLAIM_STALL_NO_HOST_MS 档）
│   └─ 「Ns 内从未取走它」 + 无窗口可接管   → 隐藏窗口不可用 + 画布页不在，双扑空最恶劣情形
│
├─ ≈90s~20min 失败 → CS-RENDER-TIMEOUT
│   ├─ 「画布页已取单但 Ns 内一帧都没渲染」  → 取到单但没开渲（149s 实例，10-26 16:23:24）
│   ├─ 「渲染窗口心跳丢失」                 → 隐藏窗口执行者死了
