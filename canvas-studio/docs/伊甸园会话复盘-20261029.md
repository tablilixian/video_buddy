## 二、苹果 vs 石榴：不是画错，是设计选择（代码级铁证）

用户观感："故事是苹果，图看着像石榴"。结论：**在该项目设定里，禁果=石榴是主动决策，不是 bug。**

### 2.1 圣经原文与西方传统的分裂（背景）

- 《创世记》2–3 只用希伯来词 `peri`（פְּרִי，泛称"果子"），**从未指定种类**。
- "苹果"是后起西方传统：耶柔米《武加大译本》把 `peri` 译成拉丁 `malum`（既指"苹果"也指"恶"，文字游戏）+ 文艺复兴绘画 + 弥尔顿《失乐园》(1667) 固化。
- 美术史里禁果本来就不止苹果：凡·艾克画香橼、费拉里画杏、**鲁本斯《人类的堕落》画石榴**、米开朗琪罗画无花果树。石榴是古近东/地中海原生水果，在犹太文献与东正教圣像里常象征"多籽=丰饶/知识"。

### 2.2 代码/技能层面的硬证据

1. **`bible-story-director` 故事索引**（`skills/bible-story-director/references/story-index.md`）把这一条就叫 **"人类的堕落｜禁果"** —— 用的是"禁果"，**不是"苹果"**。技能本身就不钉苹果。
2. **`bible-story-director` SKILL.md §08 硬约束**明令：禁中世纪欧洲元素、禁金发碧眼白肤默认脸、要求古近东/中东相貌与器物（原文："AI 生成圣经题材的默认失败模式就是出一堆中世纪骑士和文艺复兴天使"）。**"苹果"恰恰是这个约束要压制的欧化表现。**
3. **会话剧本 §02 视觉规范**原文（代理手写的 storyboard.json）：
   > the ONLY high-saturation element is the **pomegranate-red fruit**（唯一的高饱和元素就是石榴红果实）
   > 人物表夏娃配色：「亚麻米白 / **石榴红**」
4. **7 条 `image_generate` 出图提示词**里，水果全部是石榴：
   - #1 `one pomegranate tree with deep red fruit`
   - #4 `the right one bearing a few deep crimson pomegranate-red fruit`
   - #7 `a single ripe pomegranate-red fruit hanging on a branch`

### 2.3 结论

代理从大都会博物馆近东考古藏品（"亚述象牙石榴，前 9–8 世纪"）取了专业素材依据，并依 §08 反欧化约束，把禁果设为石榴。用户心里的"苹果"来自西方大众传统，与这套"历史忠实"设定直接冲突。**要改成苹果必须反向覆盖 §08 与历史考据**——这属于产品决策，不是渲染缺陷。

## 三、问题清单（按严重度，含代码根因）

### 🔴 P0 · 渲染反复卡死 —— 已知 REQ-035，会话是其实例

**现象（会话）**：`画布页取单后一直没开始渲染，已中止本次渲染` 出现 **11+ 次**；会话结尾仍在排查「渲染工单反复取不到，可能因为此前取消的 720P 重出和探针在队列里残留」。**成片大概率卡在这没干净跑完。**

**代码根因**（详见 `docs/plans/REQ-035-Phase0-取证报告-20261024.md`）：渲染有两执行者——隐藏窗口（`render-host`）与用户画布页（`client`）。取证报告锁定五个死角 + 客户端单无看门狗：

| 死角 | 代码位置 | 机制 |
|---|---|---|
| **D-1** 派单闸与改派闸是同一闸 | `render-job.ts:387-401` / `routes.ts:2985-2993` | `renderHostReady()` 为 false 时：新单派给 client，**同时**改派也被禁 → 结构性死锁 |
| **D-2** "看过一眼"=永久归客户端 | `render-job.ts:227` 打点 `clientClaimedAt`；改派条件 `clientClaimedAt !== undefined → continue` | claim ≠ 正在渲染；画布页取走后卡死/崩溃，单永远回不到隐藏窗口 |
| **D-3** client 单没有看门狗 | `render-job.ts:413`（`armHostWatchdog` 只给 render-host 单装） | client 单唯一结局是等工具固定超时（90–420s） |
| **D-4** 冷启 3 秒竞态 | `render-job.ts:389` | 窗口要 创建→loadURL→下载 bundle→自检→首次自报，远超 3s；**每个新会话首单几乎必走 client** |
| **D-5** 超时后不 abort，页面自锁 | `render-host/main.ts:156` `if (polling \|\| currentJobId !== null) return` | 工具超时只是宿主放弃，**不通知页面**；页面若还在渲，`currentJobId` 一直非空 ⇒ 后续每单必超时 |

**判定分档已修但未根治**（会话代码现状，`render-job.ts:731-744`）：此前"从未取单"与"取单后没动"共用一句「画布页取单后一直没开始渲染」，P0-2 已把它们拆成两档（前者要用户把画布页摆前台/开对应项目；后者是页面主线程被占），并注释"34 次失败全是第一档，模型却按第二档去重试，白烧 28 分钟 37 次"。但 D-1~D-5 的结构性死角仍在。

**修复清单（REQ-035 / F-02a~e，尚未全部落地）**：
- F-02a 改派闸与派单闸解耦（改派只要求窗口存活，不要求 `renderHostReady`）
- F-02b `clientClaimedAt` 语义改"取单即计时"，N 秒无首帧即允许改派
- F-02c 给 client 单也装看门狗
- F-02d 冷启预算 3s→8s，booting 时排队等而非直接判 client
- F-02e 工具超时时向页面下发 abort，清 `currentJobId`

**关联记忆**：本机 `memory` 已记「CSR 渲染依赖画布页可见（rAF+paint）；Electron 未设 `backgroundThrottling:false`；真后台方案=自建 RenderHost 隐藏窗口（v2 文档）」。这与 D-3/D-5 互为印证——client 渲染链路本身脆弱，正是 REQ-035 要解决的。

## 五、下一步建议（给相关人）

1. **P0 是头号债**：推动 REQ-035 的 F-02a~e 落地（集中在 `render-job.ts` + `render-host/main.ts`），尤其 F-02c（client 单看门狗）与 F-02e（超时下发 abort 解页面自锁）。这是本次"越试越死"的根。
2. **显式切换渲染执行者**：auto 模式下优先走隐藏窗口（`render-host`），避免 client 链路在后台被节流（呼应 `backgroundThrottling:false` 遗漏）。
3. **manifest 手写路径补校验**：代理手写的 `build/manifest*.json` 应走 `scaffold_manifest` 或复用 `host-tools.ts:4109` 的 id 兜底，别再漏 `id`。
4. **模型无视觉护栏**：会话仍撞了 CV-068，说明护栏在 auto 模式下被绕过；考虑在工具层对 deepseek-flash 直接读图做硬拒（而非只靠 skill 文本禁令）。
5. **产品决策**：若用户预期"苹果"，需反向覆盖 `bible-story-director` §08 与历史考据——这是选题取向，应在需求澄清阶段与用户确认"禁果画成什么"，而不是出图后才发现不一致。
