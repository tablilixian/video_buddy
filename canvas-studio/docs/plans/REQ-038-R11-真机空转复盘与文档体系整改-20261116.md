## §0 摘要（结论先行）

两轮真机共 **153 分钟**、**210 次工具调用**，产出 **3 个文件、0 帧视频**。两次都不是"卡在渲染/等待"，而是**模型在信息不足的前提下反复自我确认**。

结论三条：

1. **主因不是"没告诉它有什么能力"，而是"告诉它的那份东西坐标系错了"。**
   `references/shot-cards.md` 里 24 个编号只有 **7 个**是真实注册卡号（覆盖率 **7/58 = 12%**），另 17 个是 manifest 参数或上游手法名。模型查不到卡，只能去源码枚举 —— 这是它读源码的**起点**，不是越界。

2. **第二层是"假信息"造成的信任崩塌。**
   一旦它发现文档里的编号在注册表里不存在，此后所有问题一律回源码确认，包括本来能从文档得到答案的（45 分钟里 18 次在读几何与字段语义）。

3. **修法不是"多写文档"，而是"把可以机械推导的事实全部改成生成 + 漂移闸"。**
   仓里已经有成熟先例（`manifest-fields.generated.md` / `component-contract.generated.md` / 两个 `*-drift.test.mjs` / `yarn check` 里的 `--check`）。模型读 `manifest-fields.generated.md` 那两次**零错误、零返工** —— 这是唯一被它当权威用的文档。

一句话方案：**先补三份生成文档（卡目录 / 表达力边界 / 几何换算），再补行为闸（禁读源码做能力发现 + 降级阶梯），最后补真能力缺口（`carry` 支持文字）。**

## §2 归因：为什么它总是去读源码

### 2.1 三层因果 + 一个放大器

```
用户需求（自然语言设计稿）
   │
   ▼
① 能力清单缺失 ────→ 只能去源码枚举「有什么卡」      ← 文档覆盖率 12%
   │
   ▼
② 撞见编号不一致 ──→ 判定「文档不可信」             ← 信任崩塌拐点
   │
   ▼
③ 几何/语义无文档 ─→ 投影、字号、行高只能从源码拼   ← 推导链从未被写过
   │
   ▼
④ 表达力边界无文档 → 撞到"做不到"，没有合法出口     ← 死锁 → 幻影搜索
   │
   ▼
放大器：每步推理重写全案（45 万字符），无决策预算
```

**这四层里，①②④是"我们没告诉他"，③是"结构上没人写过"。** 所以答案是两种原因都有，但比例约 2:1，且②是让①③恶化的关键。

### 2.2 定量：卡目录覆盖率 12%

| 项 | 数量 |
|---|---|
| 注册卡总数 | **58** |
| `shot-cards.md` 里的编号 | 24 |
| 其中是真实注册卡 | **7**（A1 A2 A4 A5 B1 C2 E1） |
| 其中不是卡号（是 manifest 参数 / 上游手法） | **17**（A3 B2 C1 D1 D2 E2 E3 F1–F10） |
| **注册了但文档完全没写** | **51**（A6 + CAM/DAT/FX/INT/OPN/OUT/P/RHY/TRN/TYP/UI 全部） |

另外 `shotcraft-catalog.md`（159KB / 152 张）是**上游 video-shotcraft 的手法库**，与本仓注册卡零重叠（`grep DAT6|UI5|TYP1` = 0 命中）。所以"我们有一份 159KB 的大目录"是错觉。

### 2.3 为什么"假编号"比"没写"更致命

`shot-cards.md` 的 24 个编号混了两套坐标系：

- **卡号**（A1/A2/A4/A5/B1/C2/E1）→ 写进 `section.card` 就能用
- **参数 / 轨型 / 手法**（A3 = `subtitle` variant、B2 = `chartBars`、D1 = `transition:wipeLeft`、F1–F10 = 上游手法映射）→ **不是卡号，写进 `card` 会被拒收**

模型在第 3 次 bash 就撞上这个不一致（`grep -rn "id: 'A2'"` 找不到 A3/B2/C1），结论是「文档和实现对不上」。此后它把文档降级为"参考"，把源码升格为"事实"——**45 分钟里有 18 次读源码，本来只要文档写清就能免掉。**

### 2.4 有一条确实只能来自源码（但要承认是我们的锅）

用户给的格位是 `cell h:24`。要判断"标题会不会被裁"，必须走完这条链：

```
cell.h 24%  ×  卡内 title box h 30%  =  7.2%
7.2% × 1920px（竖屏画布高） = 138px
字号 = 84px 设计值 × 1.778（1920/1080）= 149px
149px × 行高 1.15 = 171px  >  138px  ⇒  必被 overflow 裁掉
```

这四个常数分别住在 `content-spec.ts`（投影）、`recipe-cards.ts`（卡内 box）、`type-scale.ts`（基准换算）、`text-fit-plan.ts`（缩号策略）。**文档里一处都没有。**

这不是"文档漏写"，而是**这类推导链从来没被当成文档来写**——它是"能不能出好片"的决定因素，却只存在于源码注释里。

## §4 解决方案

### S-0 总原则：可机械推导的事实一律生成，手写文档只留判断

**做什么**：把"事实类"文档（有哪些卡、有哪些字段、怎么换算）改为脚本生成 + 漂移闸；"判断类"文档（怎么选卡、什么题材配什么节奏）保持手写。

**理由**：
- 事实类文档的手写版本**必然与代码漂移**，且漂移后没有任何机制发现 —— 本轮 12% 覆盖率就是漂移 6 个版本的累积结果。
- 仓内已有三次成功先例：`manifest-fields.generated.md`、`component-contract.generated.md`、`shotcraft-catalog.md`（装配器）。它们都有生成器 + 漂移闸，**从来没出过"文档说 A 实际是 B"的问题**。
- 模型对生成文档的信任度明显更高：第二轮它读 `manifest-fields.generated.md` 两次，零错误、零返工。

**为什么不选"再多写几份手写文档"**：手写文档解决的是"这一版有"，解决不了"下一版还在"。写 58 张卡的表格，一个 `registerCard` 调用就可能让两行过期，而没有任何测试会红。

**验收判据**：三份生成文档各有 `--check` 模式，进 `yarn check`；人为改一行源码不同步文档，`yarn check` 必红。

### S-1 `card-catalog.generated.md`（58 张卡目录）

**做什么**：从注册表导出，每张卡一行：

| 字段 | 来源 | 为什么需要 |
|---|---|---|
| `id` | `registeredCardIds()` | 写进 `section.card` / `unit.card` 的唯一合法值 |
| `title` | `getCard(id).title` | 一句话形态（"折线 + 峰谷标注"） |
| 类目 | id 前缀 | 按 A/B/C/DAT/UI/TYP… 分组，便于"我要一个图表"时定位 |
| 需素材数 | `getCard(id).assets.length` | **决定"零素材任务能不能用"** —— 本轮 58 张里 28 张要素材，30 张可零素材 |
| 需要什么素材 | `assets[].kind/source` | 同上；免去读 `assets` 声明 |
| 内部主 box | 生成器从 `generate()` 的返回常量提取 | 配合 S-3 算投影，回答"放进这个 cell 会不会挤" |

**理由**：
- 直接消掉 P-1（~14 次 bash/轮）与 P-2（编号歧义：表里出现的才叫卡号，其余是参数）。
- `assets.length` 这一列是**本轮最值钱的发现**：任务是"零素材、全代码绘制"，而 28 张卡要素材。模型当时只能靠读每张卡的 `assets` 声明来筛，读了 11 次 `recipe-cards*.ts`。一列数字能替代 11 次文件读取。
- `title` 与 `id` 都是**已经在内存里的事实**，导出成本几乎为零，没有"越导越错"的风险。

**为什么不选"让模型自己枚举"**（即现在这样）：
- 模型枚举一次要 `grep` + 读文件 + 人工去重，还容易漏（本轮它先算出 11 张，第三次才算出 58 张）。
- 枚举是**确定性任务**，交给脚本一次生成、永久使用，比每次让模型重算便宜两个数量级。

**为什么不选"把目录写进 SKILL.md"**：SKILL.md 有 40KB 硬闸 + 指针覆盖率要求，58 行表格会挤掉判断类内容。放 `references/` 由 skill 指针引用，符合既有结构。

**验收判据**：
- 生成文件 ≤ 8KB；`yarn gen:card-catalog --check` 干净。
- 真机提示"零素材、只能用不需要素材的卡"，模型**0 次** `grep src/remotion` 就给出卡号清单。

**风险与缓解**：登记闸（skill 体积、references 白名单、指针覆盖率）需要同批更新，否则 `yarn check` 会红 —— 这是登记成本，不是设计风险。

### S-2 `spec-capability.generated.md`（表达力边界）

**做什么**：一张"能 / 不能"的事实表，从类型定义 + `validateContentSpec` 的规则导出：

| 能力 | 结论 | 依据 |
|---|---|---|
| `carry`（跨屏常驻层） | **只能画形状**（rect + color + radius）；**不能放文字、不能描边** | `SpecCarry` 字段表 |
| `units` 上限 | **4 个/屏**（校验文案："一屏塞 5 个东西谁也不读"） | `validateContentSpec` |
| `section.label` | 渲染为 eyebrow：`${nn} / ${NN} · ${label}`，**不能自由排版** | 卡内 `eyebrow()` |
| 屏级 chrome（base/dots/glow/eyebrow） | 多单元时**只首单元出**且不投影（`liftChrome`） | `dropRepeatedUnitChrome` |
| 卡内 box | 卡自己定（如 title box 固定在 `h:30%`），spec 无法逐轨指定 | `recipe-cards.ts` |
| 每屏元素预算 | 2 units + carry 形状 + 卡自身 chrome ≈ 实际 4–5 个视觉元素 | 由上述推导 |

外加一节「**常见不可表达清单**」：跨屏固定文字、卡内细描边、逐单元字号、任意自定义图形 —— 每条给出**替代做法**（见 S-4 的降级阶梯）。

**理由**：
- P-4 是本轮死锁的直接来源。模型在 +46.7m 才发现 `carry` 不能放文字，**这个事实一条类型声明就能说清**。
- 表达力边界是**"负面清单"**，最容易被手写文档遗漏——因为写文档的人在描述"能做什么"时心情好，不会系统列"不能做什么"。生成则天然完整。
- 有了它，模型在**设计阶段**就能判断"这个设计表达不了"，而不是写到一半才发现。

**为什么不选"直接补 `carry` 的能力"**（即先做 S-5）：能力缺口确实要补（S-5），但**补完仍会有别的缺口**。边界文档是**每个缺口都不再撞 45 分钟**的通用止血；S-5 只补一个具体缺口。先止血，再治病。

**验收判据**：
- 文档里每一行都能在 `validateContentSpec` / 类型定义里找到对应；生成器 `--check` 干净。
- 真机给一个"表达不了"的需求，模型在 **≤ 2 分钟**内指出边界 + 给出替代方案，而不是读源码 20 次。

### S-3 `spec-geometry.generated.md`（几何与换算）

**做什么**：

1. **投影公式**：`cell` → 卡内 100×100 坐标系 → 画布像素，含三段换算（画布百分比 / 盒子百分比 / 像素）。
2. **1080 基准换算表**：`designPx × (canvasHeight / 1080)`，给 480p / 720p / 1080p / 竖屏 1080×1920 四档的实测值（字号、盒高、行高各一行）。
3. **字号与行高规则**：`title` / `bullets` / `subtitle` / `dataCard` 各自的基准号、行高、最大行数、缩号下限。
4. **四个已实测的算例**（直接抄自今日真机与单元测试）：

| 算例 | 输入 | 结果 |
|---|---|---|
| 竖屏 title 盒被压 | `cell.h:24` | 盒高 138px，字号 149→115，一行不裁 |
| 竖屏 bullets 4 条 | `cell.h:56` | 字号 85→79，4 条全在 |
| 1080p 标准 title | `cell.h:30` | 84px / 2 行，零变化 |
| 多单元只首单元出 chrome | `units×2` | 第二格位不会露出 `#111827` 全屏底色 |

**理由**：
- P-3 的 18 次读源码，本质是在**反推这四张表**。把结论直接给出来，等于把这 18 次省掉。
- **算例比公式有用**：模型会用"竖屏 title 盒 138px 装不下 149px 一行"这个结论直接做设计决策，而不需要自己推公式。今日我就是靠这两条算例定位到裁字根因的。
- 几何是**最容易漂移**的（改一个常量全表变），所以必须生成 + 漂移闸。也是我建议它**晚于 S-1/S-2 做**的原因（见 §5）。

**为什么不选"写一份几何教程"**：教程会解释"为什么这么设计"，而模型要的是"这个 cell 里能放几个字"。教程读起来舒服，做决策不方便。

**验收判据**：
- 四档画幅 × 五种 variant 的实测数值与 `planTextFit` 实际输出逐字段一致（用测试比对，不靠人眼）。
- 真机场景：用户给 `cell.h:24`，模型**不读源码**就能回答"标题会被压到 115px，想保 149px 请给 h≥30"。

### S-4 行为闸：三禁 + 一预算 + 三级降级

**做什么**：写进 `SKILL.md` 与**工具描述**（工具描述每步都在上下文里，比 skill 只读一次更硬）：

1. **禁读源码做能力发现**：卡清单只以 `card-catalog.generated.md` 为准；"能不能表达"只以 `spec-capability.generated.md` 为准。`src/remotion/**` 是实现，不是规格。
2. **禁幻影搜索**：文档说"没有"就是没有。再 `grep` 三遍也不会出现。若怀疑文档过期 → 报告"疑似文档漂移"，**继续出片**。
3. **禁手搓 manifest / 后处理注入**（沿用现有纪律，但补上"那么该怎么做"）。
4. **决策预算**：每屏选卡最多查 2 次；每轮最多读 2 份参考之外的文档；**到达预算就必须落笔**（先写 storyboard，再写 spec，再出 draft）。
5. **三级降级阶梯**（表达不了时的唯一合法路径）：

```
① 加 unit（上限 4 —— 用户说"2 个单元"是下限不是上限）
② 用 carry 形状层补装饰（S-5 落地后：carry 文字）
③ 仍不行 → write_note 记一句「这条做不到：<原因>，替代方案：<方案>」，然后继续出片
```

**理由**：
- P-5 的根因不是"模型不守纪律"，而是**纪律只写了禁止、没写替代**。一个只有红线的规则系统会让人停在原地；给出口才会前进。
- **工具描述 > skill**：skill 只在开头读一次，随后被 890 行源码挤到 context 边缘；工具描述在每次调用时都在。M1 护栏就是写在工具描述里的，虽然本轮没生效（因为没到 scaffold），但位置是对的。
- **决策预算是唯一能压住 P-8 的东西**。文档解决"信息不足"，预算解决"信息足够也不敢决策"。两者缺一不可。

**为什么不选"强制先写 storyboard 再允许读源码"**：想过，否决了。它会把"查证"变成"违规"，模型会选择**跳过查证直接编**——那比空转更糟（编出来的卡号会被拒收，但不一定每次都拒收）。

**为什么不选"在工具层硬拦 `read src/`"**：宿主没有这个权限面，且开发期我自己也要读源码。用"纪律 + 目录"约束比加一层拦截器便宜。

**验收判据**（真机可量化，见 §6）：`grep src/remotion` 次数 ≤ 3；幻影 `grep` 0 次；首产物（storyboard.json）≤ 8 分钟。

### S-5 `carry` 支持文字（真能力缺口）

**做什么**：`SpecCarry` 增加可选 `text` / `variant` / `fontPx` / `color` / `border`；`buildCarryTracks` 在 `text` 存在时输出 `textCard` 轨（`fadeFrames: 0`，跨段并集时长），否则维持现状输出 `shape rect`。

**理由**：
- 用户这类需求（"全片统一的左上角小字 + 右上角标签 + 底部结论"）是**小红书图文卡的标准骨架**，不是一次性怪需求。它现在**根本无法表达**：`SpecCarry` 只有 `id/box/color/radius`，而 `units` 被用户钉死为 2 个。
- `textCard` 轨最小字段只有 8 个（`id/type/variant/text/box/startFrame/durationInFrames/fadeFrames`），`carry` 的时间窗逻辑已经在 `buildCarryTracks` 里写好 —— **这是"接到现有管线"，不是"造新管线"**。
- 落地后，用户那条提示词 **100% 可表达，且仍然只要 2 个 units** —— 所以它也**反证了 P-7 的修法不必改用户的设计意图**。

**为什么不选"让用户改成 3 个 units"**：能绕，但把设计约束推给用户；而且 `units` 是卡（每张卡自带 chrome 与入场），拿它来放"一行灰色小字"会带进不需要的动效与底板。`carry` 语义本来就是"常驻层"，文字属于它的自然延伸。

**为什么不选"手写 manifest 后处理"**：那是一旦允许就再也回不去的口子 —— 本轮模型在 +45m~+53m 之间反复想走这条路，正说明它有多诱人。它会让所有版式问题绕过 spec，最终既不可校验也不可复用。

**验收判据**：
- 只传旧字段时输出**逐字段不变**（零回归）。
- 传 `text` 时输出 `textCard` 轨，`fadeFrames: 0`、`startFrame` 与 `durationInFrames` 覆盖 `fromSection..toSection` 并集。
- `fromSection/toSection` 指向不存在屏仍拒收（沿用现有校验）。
- 三处反向变异必须各红：① 不传 `text` 却出 `textCard`；② 时间窗不并集（只覆盖首段）；③ 校验放过非法 `variant`。

### S-6 输入侧：提示词重写 + 意图卡前置

**做什么**：

1. **重写 `docs/plans/REQ-038-R11-复刻参考片-能力对照与测试输入-20261116.md` 的输入 A**：删掉"每屏 2 个单元 + 格位钉死"与"另加 3 处固定 chrome"的矛盾；改为二选一：

2. **单元太矮会被「0–1 比例值」启发式误判**：卡内小元素（A6 结论文字占卡高 10%、眉标 6%）
   投影进矮 cell 时绝对百分比掉到 ≤1，`validateBoxRegion` 把它当成"写了 0–1 单位"直接拒收。
   单卡 / 屏首单元的 `cell.h` 必须 **≥17**（`spec-geometry.generated.md` §6 自动搜出）。
   **本轮的处置是把它写进文档，不改校验器** —— 那条启发式拦的是真实心算单位错
   （`w:0.58` / `h:1`），收紧阈值会放开一整类历史事故；而这个坑只在极小格位出现，
   文档写清 + 测试守住变体 A 的格位即可。
