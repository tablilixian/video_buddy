# 分镜审阅闸门 · 字段定义与改动清单

> 2026-11-24 · 状态：设计定稿，待实现。目标编号 **CV-469**（实现前按铁律 `git log` + `STATUS §4.1` 复核）。
> 已拍板：超时 30 分钟放行并记未决项；本期不覆盖叙事片；`claim` 为 section 级；**G1 面板只读 + 打回批注**（不开放直接编辑，避免第二套写入口）。

## 0 一句话

科普片在 confirm 模式下增加两次**阻塞式**审阅：**G1 信息审**（spec 编译前，纯文本表）与 **G2 版面审**（首版 draft 成片渲完之后，拿成片逐屏判定）。auto 模式两处全放行，靠 `claim` 校验告警与只读分镜板兜底。

两处闸门都排在 **R0 出片之后**：R0 的 spec 文案是占位，审它没有意义；这也是保住 M1 硬线（骨架落盘后必须先出片）的前提。

## 1 三轮修正（每轮都有实测依据）

### 1.1 第一次修正：G2 不出静帧 PNG

原设想用 `renderSpotFramesOnWeb` 为每屏出一张静态图。放弃：帧的选取与真实成片会差一档，且要动 `render-job.ts`。

### 1.2 第二次修正：G2 不传 manifest，改看已渲好的 draft 成片

上一版设计打算把 manifest 传给客户端内嵌 `@remotion/player`。**这条在实测数据面前不成立。**

| 实测对象 | 数值 |
|---|---|
| 真实科普片 `build/manifest.json` | 21KB / 30KB / 33KB / **87KB** |
| `~/.videobuddy/canvas-studio/projects.json` | **2.1KB**，4 个项目，单条记录 307 字节 |

`setPendingQuestion` / `answerPendingQuestion` 走 `commitRegistry`，**全量读整表再全量写回**（`projects.ts:1191`）。把 87KB 塞进一条 307 字节的记录，注册表膨胀 42 倍，每次问答重写一遍。

三条路都否掉：

| 方案 | 结论 |
|---|---|
| 内联进 `pendingQuestion` | **否**。注册表膨胀 42 倍 |
| 新开只读文件路由 + `manifestPath` | 可行但不必要。现行资产路由只认 `/<projectId>/<file>` 且限制在 `assetsDir`（`routes.ts:1369`），`build/` 不在内，需新开约 40 行 prefix 路由 |
| 复用渲染工单通道 | **否**。工单挂着 claim-stall 看门狗（按 `msPerFrame` 判活性），审阅混进队列会被误判成卡死 |

**采用的方案：G2 看 draft 成片，不内嵌播放器。**

依据是时序本来就自洽 —— `review_board(phase:'layout')` 发生在 R1 之后，而 R1 **必须**渲一版 draft（M1 硬线）。成片已经在磁盘上，URL 就是普通的 `/canvas-studio/assets/<pid>/<file>`，原生 `<video>` 直接播。

`board` 载荷因此只剩 **`draftUrl` + 每屏起止秒数**，8 屏约 2.4KB，注册表从 2.1KB 到 4.5KB，无压力。

四个附带收益：

1. **`StoryboardBoard.tsx` 不再需要 `@remotion/player`** —— 原生 `<video>` + `currentTime` 跳转，省掉一条重依赖惰性加载的纪律；
2. **审的就是成片**，不是"同源模拟"，像素 / 字幕位置 / 字号与交付一字不差；
3. **能审节奏** —— 静态屏永远看不出"第 3 屏停 2 秒太赶"；
4. **能听旁白对位** —— draft 带音轨，字幕与语音错位一耳可辨。

屏的起止秒由宿主调**与编译同一份 `planStages`** 算出（`content-spec.ts` 内已有），不会出现"面板说第 3 屏在 12s、成片里在 14s"的两套事实。

唯一代价：打回后要重渲一次 draft 才能再审。但 R1 每次改 spec 本来就要重渲，无新增成本。

### 1.3 「一个工具两个相位」改为「一个工具 + 一块组件」

G1 与 G2 共用**同一块客户端组件** `StoryboardBoard`：

| | G1 信息审 | G2 版面审 |
|---|---|---|
| 何时 | spec 落盘后、编译前 | 首版 draft 渲完之后 |
| 宿主工具 | `review_board({ phase: 'info' })` | `review_board({ phase: 'layout' })` |
| 组件内容 | 纯表格：主张 / 数据 / 来源 / 时长 / 卡名 | 表格 + 原生 `<video>`（`draftUrl`），点某行 `currentTime = startSec` |
| 需要渲染 | 否 | 是，但用的是 R1 必渲的那条 draft |
| 需要传 manifest | 否 | **否**（只传 `draftUrl`） |

两个相位都落 `pendingQuestion.board`，**不新建任何通道**。答案沿用意图卡 `fields` 的既有做法：以 JSON 字符串回流。

## 2 字段定义

### 2.1 `spec.sections[].claim`（唯一新增的持久化字段）

```ts
/** 本屏要让观众记住的一句话（一屏一个点）。units 是它的支撑证据。 */
claim?: string
```

- 位置：`src/remotion/content-spec.ts` 的 `sections[]` 元素类型（内联匿名类型，约 137 行起）。
- 粒度：**section 级，不是 unit 级**。一个 unit 一个主张意味着这屏讲了两个点，应该拆屏。
- 长度上限：**24 字**（含标点）。超限只告警，不拒收。
- 持久化：只存在于 spec，**不进 manifest**。manifest 是渲染契约，claim 是审阅元数据。

### 2.2 `StudioPendingQuestion.board`（审阅面板载荷）

```ts
/** 分镜板载荷。有值时客户端渲染审阅面板，答案以 JSON 字符串回流（与 fields 同款）。 */
interface StudioPendingQuestion {
  // …既有字段不变
  board?: StudioBoardPayload
}

export interface StudioBoardPayload {
  /** 相位：info = 纯文本；layout = 带成片播放器。 */
  kind: 'info' | 'layout'
  title: string
  /** 画幅（'16:9' / '9:16' …），播放容器按它占位。 */
  aspect: string
  /** 整片时长（秒）。layout 相位给出，info 相位可缺省。 */
  durationSec?: number
  /** layout 相位必填：已渲好的 draft 成片 URL（同源 /canvas-studio/assets/…）。 */
  draftUrl?: string
  /** G1 只读：面板不提供编辑入口，claim 的修改一律走打回批注。 */
  readonly: true
  rows: StudioBoardRow[]
}

export interface StudioBoardRow {
  sectionId: string
  index: number
  claim: string
  copy: string
  dataSource?: string
  card?: string
  durationSec: number
  /** 该屏在成片里的起止秒（由 planStages 同源算出）；info 相位可缺省。 */
  startSec?: number
  endSec?: number
}
```

**客户端分支优先级**：`board` > `fields` > `options`。挂在 `src/client/question-capture.tsx:236` 附近，与 `fields` 分支并列。

### 2.3 答案形状（`answer: string` 的 JSON 内容）

```ts
export interface StudioBoardAnswer {
  overall: 'approved' | 'rejected'
  decisions: Array<{
    sectionId: string
    status: 'pass' | 'reject'
    /** 打回时必填：问题类型，取自固定枚举，便于统计。 */
    issue?: 'missing-info' | 'wrong-info' | 'overcrowded' | 'overflow' | 'wrong-card' | 'off-topic' | 'pacing'
    /** 打回时用户可填的一句话。 */
    suggestion?: string
  }>
}
```

解析失败（用户直接关闭 / 旧客户端只回选项文本）**按 `rejected` 处理并保留原文**，绝不静默当通过。

### 2.4 `review_board` 工具签名

```
phase: 'info' | 'layout'          必填
specPath: string                  与 spec 二选一；推荐（spec 常 >10KB）
spec: string                      内联 JSON
draftUrl: string                  layout 相位必填；来自 render_composition 返回的成片 url
```

`layout` 相位**不接受 manifest / manifestPath** —— 不传渲染数据，只传成片地址。

返回（`renderTextResult`）：

```ts
{
  approved: boolean
  /** 逐屏批注摘要，直接进 agent 上下文改 spec。 */
  notes: Array<{ sectionId: string; issue?: string; suggestion?: string }>
  text: string   // 人读摘要：'3/8 屏通过，5 屏打回'
}
```

## 3 `claim` 校验规则（`validateContentSpec`）

四条，**全部为 warning**，不拒收。理由：存量 spec 没有该字段，设为 error 会让所有老项目瞬间编译失败。

| # | 判据 | 文案 |
|---|---|---|
| C1 | 缺失或空白 | `spec.sections[i] 未声明 claim（本屏要让观众记住的一句话）` |
| C2 | 长度 > 24 | `spec.sections[i].claim 有 N 字，超过 24 字——一屏讲不清一个点就该拆屏` |
| C3 | 与 `copy` 无共同 2-gram | `spec.sections[i].claim 与 copy 无共同关键词，可能跑题` |
| C4 | 与相邻屏 claim 的 2-gram Jaccard ≥ 0.6 | `spec.sections[i] 与 sections[i-1] 主张重复（相似度 0.NN）` |

C3/C4 用字符 2-gram 集合，纯函数、确定性、无分词依赖。C3 刻意宽松（只要有一个共同 2-gram 就通过），目标只是抓住"完全跑题"，不追求语义判断。

**auto 模式的价值就在这四条**：没有闸门时，它们是模型自我纠错的唯一信号，会随 `render_composition` 回执的体检告警行一起出现。

## 4 闸门行为矩阵

| | confirm 模式 | auto 模式 |
|---|---|---|
| **触发** | skill 规定顺序：R1 落盘后调 `review_board(phase:'info')` → 编译 → 渲 draft → 调 `(phase:'layout', draftUrl)` | 工具被调用时立即返回 `approved: true`，落一条 `write_note` 说明"分镜板已跳过" |
| **阻塞** | 阻塞到用户提交或超时 | 不阻塞（`studio-defaults.ts:194` 既有逻辑：auto 不落 pendingQuestion） |
| **超时** | **30 分钟**（新增 `BOARD_WAIT_MS = 1_800_000`，不复用 `QUESTION_WAIT_MS` 的 10 分钟）→ 放行 + 返回未决项标记 | 不适用 |
| **无订阅者** | 放行（沿用 `render-preview.ts` 纪律 2） | 同 |
| **打回** | 返回 `notes[]`，agent 改 spec 后重跑编译；**再次审阅只要求重审改动过的屏** | 不适用 |
| **重审判据** | spec 的 section 级 diff：`claim` / `copy` / `dataSource` / `card` / `durationSec` 任一变化即标脏 | 不适用 |

**重审 diff 的内存键**：`projectId + sectionId`，存最近一次通过的指纹（上述五字段拼接的哈希）。换项目清空。

## 6 测试清单

| 断言 | 能反向变红的方式 |
|---|---|
| C1–C4 各自触发 | 逐条删字段 / 加长 claim / 复制相邻 claim，断言 warnings 出现 |
| `startSec` 与编译同源 | 改 `targetStageSec`，断言 rows 的秒数随 `planStages` 变化而非按 `durationSec` 直加 |
| board 载荷体积护栏 | 8 屏 spec 生成的 payload < 8KB（防有人后续往里塞 manifest） |
| auto 模式不落 pendingQuestion | 强制 auto，断言 `projects.json` 无 `board` 字段且返回 `approved: true` |
| 30 分钟超时放行 | 缩短常量到 50ms，断言返回 `approved: true` 且带未决项标记 |
| 无订阅者放行 | 不挂载面板，断言立即返回 |
| diff 只重审脏屏 | 改 1 屏的 copy，断言 `rows` 只含该 sectionId |
| 答案解析失败按 rejected | 传 `answer: "好"`（非 JSON），断言 `approved: false` 且原文保留 |

守卫必须能反向变红（项目铁律）：每条断言都要有一个"故意改坏实现"的验证记录。

## 8 设计取舍备忘（已定，无需再议）

1. **manifest 不传输**：G2 只看 `draftUrl`。三条备选（内联 / 新路由 / 复用工单）的否决理由见 §1.2。
2. **G1 只读**：面板不提供编辑，claim 的修改一律走打回批注。理由是避免"面板写 spec 文件"与"模型写 spec 文件"两套写入口 —— 那会造出第二种事实源。
3. **`claim` 允许缺省**：C1 只告警。存量项目与 auto 模式都不能因为缺一个审阅元数据而渲不出片。
