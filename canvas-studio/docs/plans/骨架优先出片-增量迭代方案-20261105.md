## 1. 对「20 分钟出第一版」的三处必要修正

你的判断成立：有锚点 → 不重来；有产物 → 用户能纠偏。但要加三个约束，否则这条机制会被绕过：

### 1.1 「出了第一条视频」必须有质量门槛，不能是 4 张占位卡

`scaffold_manifest(recipe="explainer-cards")` 现在就能产出 5 条可渲轨（底色 + 4 段占位字幕），**3 分钟内就能渲出一条"视频"**。如果门槛定成「画布上有成片节点」，agent 会立刻达标然后继续空转，我们等于把失败点往后挪了 20 分钟。

**M1 合格线（三条全中才算）**：

| # | 判据 | 为什么 |
|---|---|---|
| ① | 字幕轨是**真实文案**（来自 §03 旁白或 §04 台词），不是 `【开场提问】把观众的问题原样问出来` | 占位卡没有信息量，用户看不出对不对，锚点没有校准价值 |
| ② | 段边界来自**旁白真值累计**（TTS 帧表 / `list_shots` 真值），不是按百分比权重估算 | 这是全文最重要的约束，见 1.2 |
| ③ | `quality:"draft"` 且**非 probe** —— 落画布节点，用户能点开看 | probe 不落节点 = 用户看不到 = 锚点不存在 |

### 1.2 「以这版为基础丰富」的技术前提：v1 的段边界必须一次算对

manifest 是声明式的，所以「丰富」在技术上只有两种操作：**追加轨**（append）和**替换单轨**（replace by id）。这两种操作能成立的前提是：**v1 的帧窗（每段 startFrame / durationInFrames）已经是终态**。

反过来说：如果 v1 用「4 段等权 15/25/35/25」估出来，后面拿到 8 句旁白真值（1326 帧、每句 90–220 帧不等），所有轨的 startFrame 全要重排 —— 就等于重写整片，**今天那 2h40m 的空转就是在这个循环里**："估算 → 发现不对 → 重排 → 又发现一条校验 → 再重排"。

**结论：v1 的价值不在"画面好看"，而在"帧窗不可变"。** 帧窗一旦钉死，后面每加一层都是一次 append，不需要重排，也就不会触发"整片重算"的思考雪崩。

这条要落成机器断言（见 T4）：v1 冻结后，脚本每次生成都断言段边界与 v1 一致，不一致直接报错，不允许模型自己"感觉差不多"。

### 1.3 锚点必须是**文件**，不能是对话记忆

今天 8 次压缩、摘要从 8,886 膨胀到 29,420 字符，模型仍然不信任摘要，回去重新读源码。**记忆层不解决问题，因为它本身是失真的。** 锚点要落成磁盘上的确定性产物：

```
<project>/build/PROGRESS.md          ← 唯一状态源（人读 + 模型读都靠它）
<project>/build/versions/v3.json     ← 每次成功渲染的 manifest 快照（机器读）
<project>/build/manifest.json        ← 当前工作副本
```

`PROGRESS.md` 由**宿主自动写**（T1），不靠模型自觉 —— 模型可以忘，宿主不会。

## 3. 增量迭代阶梯（每个 R 只推一个维度）

每一轮 = 一次可验证的增量 + 一次出片。这张表就是「怎么合理安排工具调用」的答案：

| 轮 | 推进维度 | 工具序列（按序） | 调用数 | 耗时预算 | 通过判据 |
|---|---|---|---|---|---|
| **R0** | 结构可渲 | `scaffold_manifest(recipe)` → `write(build/manifest.json)` → `render_composition({manifestPath, quality:"draft"})` | 3 | 3–5min | 返回 url + 时长 = 目标 ±1 帧 |
| **R1** | 信息（真文案） | `write(build/build-manifest.mjs)` → `bash(生成+自检)` → `render_composition(draft)` → `render_composition(spotFrames:[a,b,c])` → `read_image`×3 | 7 | 5–8min | 3 帧里字幕是真实句子、无溢出、无压边 |
| **R2** | 视觉（图表/数据卡） | 改脚本（+1 轨）→ `bash` → `render_composition(draft)` → `spotFrames(该轨首/中/末)` → `read_image`×2 | 6 | 5–8min | 数据卡不超框、数字与源数据一致 |
| **R3** | 视觉（形状/流程） | 同上 | 6 | 5–8min | 图元不出画布、遮挡关系对 |
| **R4** | 运动 | 改脚本（动画字段）→ `bash` → `render_composition(draft)` → `spotFrames`×4 → `read_image`×2 | 6 | 6–8min | 帧间有位移/透明度变化，无闪背景 |
| **R5** | 声音 | `tts_voiceover` 真值 → 改脚本（audio.voiceOver）→ `bash` → `render_composition(standard)` | 4 | 5–8min | 8 句起点误差 ≤1 帧 |
| **R6** | 定稿 | `render_composition({quality:"high"})` → `spotFrames` 全片 6 帧 → `read_image`×6 → `write_note` | 9 | 8–10min | 无未决项 / 已逐条复述 |

**每轮铁律**：

1. **单轮工具调用 ≤ 8 次**，超了就降级收尾（保住当前版本），不许"再做一点"。
2. **单轮只改 ≤3 轨**。改多了说明这一步没想清。
3. **每轮结束必须渲一次 draft**（`quality:"draft"` 会就地替换上一版草稿 → 画布只留一个节点，不堆卡）。
4. **每轮结束一句话汇报**：`R3 完成：data 段加了 30 点折线（帧 152–420），v3 draft 已落画布`。
5. **改单轨 → 只看目标帧**（`spotFrames`），不要整片重渲。今天 0 次 `spotFrames` 是明显反常。

## 4. 单轮标准作业流程（SOP，可直接写进 skill）

```
① 读锚点        read build/PROGRESS.md 尾部（≤80 行）
② 定位本次目标  只在「待办：下一步唯一动作」里挑一条；不要重排计划
③ 改脚本        write build/build-manifest.mjs（只改本轮那 1–3 轨）
④ 生成 + 自检   bash node build/build-manifest.mjs   → 打印 轨数/帧窗/断言结果
⑤ 出片          render_composition({ manifestPath, quality:"draft" })
⑥ 局部验帧      render_composition({ manifestPath, spotFrames:[…] }) → read_image
⑦ 更新锚点      宿主自动写 PROGRESS.md；模型只需回一句话 + write_note（阶段收尾时）
```

**为什么把「改脚本」放在「渲片」前，而不是「模型直接写 JSON」**：8 句旁白 + 30 点折线 + 引线标注 + 分区 wipe ≈ 60–90 轨 / 60–120KB JSON。手写超单步输出预算（今天是 32,768 token 打满两次），而脚本里排版是**代码算的**，模型只提供内容表（8 行文本 + 1 组数字）。这是把 token 从"排版"挪回"内容"。

### 6.1 `build/PROGRESS.md`（宿主自动写，唯一状态源）

```markdown

更新：2026-11-05 14:21:07

- v4 · draft · 45.00s · 1376×768 · 92.3 MB
- url: /canvas-studio/assets/render/xxx.mp4
- manifest: build/manifest.json（轨 78）
- 已验帧: 0, 152, 300, 420, 900

## 里程碑
- M0 骨架   14:00 ✅（scaffold recipe=explainer-cards）
- M1 首片   14:06 ✅（8 句真文案 · 1326 帧）
- M2 对齐   14:19 ✅（帧窗 = TTS 真值）
- M3 视觉   14:21 ⏳（data 段已加折线；body 段待做）

## 下一步唯一动作
- body 段加 3 个要点卡（帧 420–900），已有文案见 §04

- 末句字幕 2 行溢出（未修，M6 前处理）
```

**关键**：这份文件由宿主在每次 `render_composition` 成功后**追加/重写**，字段全部来自返回值（url / 时长 / 像素 / 轨数 / 帧号），零模型参与。模型要做的只是"读它"，而不是"记得它"。

### 6.2 `build/versions/vN.json`

每次成功渲染存一份 manifest 快照（含 meta + tracks + 渲染参数）。作用：
- 压缩后想回退，直接读 vN，不用重推；
- 定稿时对比 v1 ↔ vN 的帧窗，机器验证"只追加没重排"。

### 6.3 帧窗稳定性断言（脚本层）

```js
// build-manifest.mjs 内置
const v1 = JSON.parse(fs.readFileSync('build/versions/v1.json', 'utf8'))
const assertSegments = (manifest, v1) => {
  const a = segmentsOf(manifest), b = segmentsOf(v1)
  if (JSON.stringify(a) !== JSON.stringify(b)) {
    throw new Error(`段边界被改动（这是重排，不是追加）：\n v1: ${b}\n now: ${a}`)
  }
}
```

这条断言让「不许重排」从口头纪律变成**会失败的测试**。
