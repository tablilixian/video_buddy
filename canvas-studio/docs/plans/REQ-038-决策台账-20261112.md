## 2. 自拍决策（无人值守执行期间）

### 决策 1（SB-6）：P 类卡画面设计方向沿用 playsout 设计语言
- **问题**：RQ-11② P 类体裁卡 P1–P12 的画面设计方向（需求正本 §8.3 唯一待决项）。
- **选择**：沿用 playsout 的设计语言 —— 暗底 `#07070F` / 强调紫 `#98A3FF` / 呼吸字卡 / 胶片颗粒感。
- **原因**：RQ-11 验收判据 1 要求「P 卡重生成 playsout 规格 ⇒ 关键帧像素对拍 ≥40dB」。设计语言若不同源，「同规格可复现」这条判据连形式上都过不了（≥40dB 意味着画面几乎一致）。设计同源是判据可执行的前提；判据 4（不雷同 <25dB）由换内容变体保证，与设计语言同源不冲突 —— 同一套版式参数换内容后画面自然不同。此为需求文档 §5.2 给出的默认方向，证据链完整，采纳。
- **影响**：RQ-11②（P1–P12 卡的配色、字体、缓动基调）；`skills/code-driven-explainer/references/product-promo-cards.md` 的设计基调节。
- **可逆性**：仅影响 P 卡文档与生成器参数表的默认值；换方向 = 改默认参数表，代码结构不动（可逆）。

### 决策 2：RQ-03 主文本色的实现采用「旧硬编码色降为缺省值」而非引入主题变量
- **问题**：`textCard.color` 接入五个变体时，缺省值从哪来（主题 token / 每变体常量）。
- **选择**：每变体的旧硬编码色直接作为 `track.color` 的缺省（title/bullets/dataCard/timecode = `#e6edf3`，subtitle = `#f4f7fb`），不引入主题变量。
- **原因**：验收口径是「老 manifest 不写 color 逐像素不变」。`track.color ?? <旧值>` 的回退链最短、零间接层，review 时一眼可验；引入主题 token 会把「缺省色」变成第二事实源，任何 token 漂移都会破回归。subtitle 的旧色 `#f4f7fb` 与其他变体的 `#e6edf3` 不同，统一 token 反而要写特例。
- **影响**：`src/remotion/components/TextCard.tsx`（5 处 color 接线）；`src/remotion/manifest.ts`（TextCardTrack.color 注释）。
- **可逆性**：改为主题变量 = 改一处 `mainColor` 常量来源（可逆，1 个文件）。

### 决策 3：RQ-07 plate 仅限 title 变体，其他变体写 plate 收 warning 不收 error
- **问题**：`plate` 是 title 专属还是所有变体通用；非 title 变体写 plate 报 error 还是 warning。
- **选择**：仅 title 消费；subtitle/bullets/dataCard/timecode 写 plate 收 warning（「只在 variant:'title' 下生效（已忽略）」）。
- **原因**：与仓内既有惯例一致 —— `countUp` 非 dataCard 变体写时就是 warning（`manifest.ts` P2' 注释与校验分支同款处理）；subtitle 自带 `rgba(0,0,0,0.62)` 字幕条底（那是字幕条本体，不是可去的底板），`plate:'none'` 若报 error 会把「想去掉的是另一块底」的误用变成硬拒收。warning 足以让模型知道写了不生效。
- **影响**：`src/remotion/manifest.ts` 校验分支（TEXT_CARD_PLATES 白名单 + variant 检查）。
- **可逆性**：升级为 error = 删一处条件（可逆）。

### 决策 4：RQ-04/RQ-06 新描边宽字段用 `strokeWidthPx` 而非复用 `strokeWidth`
- **问题**：`shape:'path'` 已有 `strokeWidth`（百分比单位，相对 0-100 单位盒）；rect/circle 的 SVG 新路径需要 px 单位的描边宽，同名字段双单位必坑。
- **选择**：新字段名 `strokeWidthPx`（px）。
- **原因**：仓内先例 —— `fx` 刻意避开 `TransitionTrack.effect` 撞名（`manifest.ts` A2 节注释：「同名同层会同时污染类型、KNOWN_TRACK_KEYS 与工具描述」）。path 的旧语义不能动（老 manifest），双单位并存只能靠命名区分。
- **影响**：`Shape.tsx` SVG 新路径、`manifest-aggregates` 无关；KNOWN_TRACK_KEYS.shape 两键并存。
- **可逆性**：改名一处字段（可逆，1 文件）。

### 决策 5：RQ-06 radial 走 SVG `objectBoundingBox` + gradientTransform 双轴 scale
- **问题**：CSS `radial-gradient` 被 web-renderer 4.0.535 忽略（#16 实证）；SVG radialGradient 单 `r` 无法独立控制 x/y 半径。
- **选择**：`r=1` + `gradientTransform="translate(cx cy) scale(rx ry) translate(-cx -cy)"`（objectBoundingBox 单位坐标 0-1）。
- **原因**：objectBoundingBox 下坐标相对盒尺寸，映射天然随 box 缩放；translate-scale-translate 绕中心缩放数学等价「椭圆半径 rx/ry 独立」；与 dotGrid 的 SVG 路线同一结论（`timing.ts` fxStyles('metal') 注释实证链）。
- **影响**：`Shape.tsx` radial 分支；vignette 同构复用（批 3）。
- **可逆性**：换 ellipse+渐变方案 = 改一个分支（可逆）。

### 决策 6：RQ-09 轨级暗角做成 `shape:'vignette'` 专属原语（而非 fx 枚举或 meta.look 覆盖表）
- **问题**：暗角三选一：`fx:'vignette'` 枚举 / `shape:'vignette'` 新形状 / `meta.look` 按镜头覆盖表。
- **选择**：`shape:'vignette'` + `strength`（0-1，缺省 0.5），源工程口径（中心 50%/44%、透明环 38%、半径 118%/88%）硬编码进渲染层。
- **原因**：fx 是单值枚举且折算产物是 CSS 样式（暗角需要一个**叠加层**，不是样式）；meta.look 覆盖表要引入「按镜头 id 的第二事实源」（易漂移）；shape 是「一层 overlay」的自然表达（源工程 Vignette 就是一个 div），且直接复用批 2 的 SVG radialGradient 机制与 dotGrid/vignette 的「铺满画布」缺省惯例。
- **影响**：SHAPES 白名单 + ShapeTrack.strength + Shape.tsx 分支；playsout 11 镜头逐镜头强度可表达。
- **可逆性**：增枚举分支（可逆）。

### 决策 7：RQ-02 letterSpacing 双单位（px + em），em 优先；度量与渲染同源三处
- **问题**：源工程紧排是 em 口径（`-0.022em`）；折行预算需要 px 数值。
- **选择**：`letterSpacing`（px）+ `letterSpacingEm`（em，相对当前迭代字号）两字段；同时给 em 优先（warning）；`text-fit-plan.ts` 的折行预算、`text-fit-audit.ts` 体检、manifest 静态粗判**三处传同一份值**。
- **原因**：em 直接可写（贴近设计稿）；渲染层落 CSS `em` 串（浏览器相对最终字号换算）与折行循环「每轮 fontPx × em」口径一致 ⇒ 缩号迭代下折行=成片；三处同源是「体检说没溢出、成片却裁了」不可能再发生的机制保证（0B 不变量延续）。
- **影响**：TextCard.tsx / text-fit-plan.ts / text-fit-audit.ts / manifest 校验四处接线。
- **可逆性**：砍 em 字段 = 删一个分支（可逆，4 文件各一处）。

### 决策 8：聚合单元错峰字段命名 `unitStagger`/`unitFadeFrames`（避开 BaseTrack.fadeFrames）
- **问题**：聚合原语的「单元入场时长」若命名 `fadeFrames` 会与 BaseTrack.fadeFrames（整轨淡入淡出）同名同层冲突。
- **选择**：单元级加 `unit` 前缀。
- **原因**：两套动画（整轨级 + 单元级）语义正交且可叠加，命名必须让模型一眼分辨；KNOWN_BASE_TRACK_KEYS 的 fadeFrames 已被整轨消费。
- **影响**：manifest-aggregates.ts 五轨型 + Aggregates.tsx。
- **可逆性**：改名（可逆，2 文件）。

### 决策 9：RQ-01 双向兼容矩阵（新帧 + 裸 body + 旧 query 三路）
- **问题**：回执协议改造的兼容策略（SB-1 只拍「body 走帧、magic 判别」）。
- **选择**：服务端三路判定 —— ① body 前缀命中 `CSREND01` magic ⇒ 拆帧；② 未命中 ⇒ 整 body 按裸 mp4（老格式）；③ warnings/metrics 的 query 通道**保留读取**（旧客户端）。客户端有元数据时组帧、无元数据保留裸 body。
- **原因**：真机部署存在「宿主新、客户端旧」与「客户端新、宿主旧」两个过渡窗口；③ 是零成本兼容（几行 else 分支）；坏帧（metaLen 越界/截断）回落老格式判定而不是 4xx（与 D-15「渲染期 throw 代价远大于少一声响」同款取舍 —— 这里是「回落」而不是「断链」）。
- **影响**：`render-protocol.ts`（新）+ `client/api.ts` commit 函数 + `routes.ts` commit 端点。
- **可逆性**：砍 query 兼容 = 删 else 分支（可逆）。

### 决策 11：SB-2 的「再扩到 12 张」挂起 —— 落 3 张样卡 + 判据运行器，不盲扩

### 决策 12：RQ-19 的 `recipeCoverage` 以 `meta.generatedBy` 前缀为准
- **问题**：「由配方生成的轨占比」需要在渲染侧可判 —— manifest 没有逐轨来源标记。
- **选择**：约定 `meta.generatedBy` 以 `recipe:` / `spec:` / `template:` 开头 = 配方生成（coverage 1），手写 = 0；报告字段 `recipeDensity`（tracksPerSec / bytesPerTrack / textTracks / tracksByType / recipeCoverage）由宿主从 manifest 确定性推导，不信任客户端上报。
- **原因**：`generatedBy` 已在 KNOWN_META_KEYS（零新字段）；宿主有 manifest 全量（轨型分布/字节数都可算），客户端上报反而多一个伪造面；E10 的密度对比（0.04 vs 0.15 轨/秒）正是这两个数。
- **影响**：`render-report.ts`（deriveRecipeDensity）+ render-job 结算装配。
- **可逆性**：加逐轨标记 = 增字段（增量）。
