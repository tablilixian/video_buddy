## 1. 三个决定方案形态的引用事实

1. **粘贴共享文件**：`pasteNodes` 复制节点保留原 url——两个节点指同一磁盘文件。
   引用判定必须按**文件名（url basename）**计数，按节点 id 判会误删共享文件。
2. **undo 撤销栈是会话内的**：删除后马上 undo，节点带着原 url 回来——立即物理删除
   会让恢复的图片 404。
3. **资产卡**经 `anchorNodeIds` 挂节点，文件随节点走，不构成独立文件引用；
   export 成片文件挂在「成片」节点 url 上（同样进引用集合，删除成片节点后其
   export 文件按孤儿回收——BUG-006 的历史面板将来接管成片历史的显式保留）。

## 2. 方案：两段式回收（trash + GC）

```
删除节点（保存路由拿到 removedIds）
  └→ 对每个被删节点的文件：剩余节点引用集合不含其 basename
       └→ 文件移入 assets/.trash/（rename，不物理删）；不阻塞保存主链
undo 恢复节点
  └→ 资产路由 fallback：根目录未命中 → 查 .trash/（图片/视频不断链）
     promoteAssetFile 同样加 .trash fallback（undo 后再引用可自愈重传）
打开项目（自动）或 POST /canvas-studio/asset-gc（手动兜底）
  └→ GC：
      ① 引用集合内但落在 .trash 的文件 → 移回根目录（undo 恢复 + 已保存的场景）
      ② .trash 其余文件 → 物理删除（undo 不跨会话，绝对安全）
      ③ 根目录孤儿（历史遗留）→ 物理删除
      ④ reference-manifest 剪枝：指向已不存在文件的映射条目删除
```

### 判据与护栏
- 引用集合 = canvas.json 全部节点 `url` 的 basename 集合（纯函数，可直测）；
- GC 只扫 `assetsDir`：跳过 `.trash` 目录本身与 `reference-manifest.json`；
- trash 内同名冲突：POSIX `rename` 原子覆盖（同名 = 新产物顶替旧废料，可接受）；
- 生成中被删参考图的极端竞态：rename 原子不产生半截文件；`promoteAssetFile` 的
  `.trash` fallback 让 heal 仍可自愈；重试兜底。
- **不做**：磁盘用量统计 UI、回收站恢复 UI（BUG-006 历史面板接管）、jobs 台账清理。

## 4. 自测与验收
- 单测（真实 ProjectRegistry + 临时目录）：trash 移入 / 共享文件不误删 / 无文件节点不抛 /
  GC 回活 / trash 物理清 / 根孤儿清 / manifest 剪枝 / 引用集合纯函数。
- 真机验收清单：
  1. 删节点 → `assets/` 根目录对应文件消失（进 `.trash/`），画布正常；
  2. 删除 → undo → 图片照常显示（fallback 生效）→ 再保存 → 重开项目文件被 GC 移回；
  3. 重开项目 → `.trash/` 清空、历史孤儿（如 20MB mix 文件）被清；
  4. 复制节点 → 删原件 → 文件保留（粘贴件仍引用）；
  5. 正常项目打开：引用文件一个不动；GC 接口手动可调。
