# OpenMontage 三篇实测 · 地层论与生产线借鉴评估（2026-11-22）

**素材**（同一作者「AI天工造物」的连载，三篇构成一次完整实测）：

1. 《OpenMontage 实测：视频跑通，卡在声音上》（2026-10-19）
2. 《OpenMontage 视频制作-实测②：声音和画面都救回来了[VSCode VS. WorkBuddy]》（2026-10-22）
3. 《AI 视频制作-实测：WorkBuddy VS. Remotion，同一句提示词两条片》（2026-10-24）——提出「五层地层论」

**文档定位**：这是一份**借鉴评估**，不是需求、不是排期。文中条目不占 CV 号（按 STATUS §4.1，验收通过后才登记取号）。

**结论先行**：三篇里 60% 描述的能力我们已经做过、且做得更细；真正值得动手的是 **3 条立刻做 + 3 条低成本移植 + 1 条立项 + 5 条明确不借**。最值钱的不是任何一个技术点，而是它给的**定位语言**——它证明了我们把价值押在 L2/L3/L4 而不是 L1 是对的。

## 1. 三篇各自在说什么

| 篇 | 核心事件 | 对我们有效的结论 |
|---|---|---|
| ① | 装 OpenMontage，跑两条 15 秒同脚本片：零 API（Remotion/SVG 手绘）vs 接生成模型 | 零 API 版赢在准确与可控，API 版赢在质感；**准确和可控是可复用资产，质感只是这一条片子的观感** |
| ② | 换 edge-tts 修声音；抓到一个「自检全绿但响度低 7.8 LU」的坑；参考图打底做图生图 | **自动化自检能保证「跑完」，保证不了「好听」**；通用模型没有领域知识，别让它从零编 |
| ③ | 同一提示词分别交给编排型 agent 与 Remotion 工程，产出两条气质完全不同的片 | **五层地层**：模型造像素、渲染保准确、编排管流程、Agent 做取舍、FFmpeg 出文件 |

三篇的递进关系值得注意：①②是实测，③是**事后归纳**。③ 里那张「猜 vs 算」的对照，正是我们 2026-11-12 那份 remotion 路线文档得出的同一个结论（概率采样 vs 确定性计算），只是他们给它起了个更好讲的名字。

## 2. 事实基线：它是同类项，不是竞品

### 2.1 架构同构

| 维度 | OpenMontage | Canvas Studio | 判定 |
|---|---|---|---|
| 编排方式 | agent-first，无代码编排器，AI 编程助手即编排器 | 同：dsh agent + `skills/` + `platform.yaml` + `active-skills-prompt.ts` | **同构** |
| 流程声明 | YAML pipeline manifest（阶段/工具/成功闸门） | 状态机 + 工具层守卫（`approval-gate.ts`、`storyboard-gate.ts`、`wrapStudioToolDefinition`） | 我们更硬：闸在代码里抛错，不是 manifest 里声明 |
| 方法知识 | Markdown stage director skills + 三层知识架构 | `skills/` 分四层（project 100 > runtime > user 400 > bundled 600）+ 指针覆盖率闸 | 同构，我们层数更少但带硬性体积闸 |
| 状态记录 | JSON checkpoint（状态 + 决策日志 + 成本快照），随时恢复 | `canvas.json` + 节点状态 + `jobs.json` 视频任务续查 | **我们缺「随时恢复」** |
| 人工闸门 | 5 道（提案/脚本/分镜/素材/发布），代码级硬拦截 | 1 道（关键帧）+ 落地判据 | 我们主动收窄，见 D1 |
| 自检 | pre-compose 校验 + post-render（ffprobe/抽帧/音频/承诺校验） | `deliverable.ts` 交付卡 + 时长断言 ±1s；`media-probe.ts` ebur128 | 骨架齐，**缺阈值判定** |
| 交付 | publish 阶段 + 发布包 | `deliver/<project>/final.mp4` 权威路径 + `card.json` | 我们更细（治过 31 项目 6 个 final 的烂账） |

### 2.2 关键差异：他们无 UI，我们有画布

OpenMontage 的产物是「一个目录 + 一份发布包」，人通过终端看 checkpoint 做判断。我们的产物是**画布上的节点 + 一次 HITL 会话**。这条差异决定了后面所有取舍：

- 他们的「5 道闸门」是靠终端停下来实现的，成本低（作者自己说全程停 6 次）；
- 我们的闸门要靠 UI 拦住，每加一道都增加一次**确认疲劳**，而确认疲劳会直接导致用户无脑点「继续」——等于把闸门变成装饰。

**所以本文所有借鉴都要过一道筛：这个东西在「单人在桌面、连续创作、要看得见图」的场景下还成立吗。**

## 3. 地层论对我们意味着什么（这是三篇里最值钱的部分）

### 3.1 五层归位

| 层 | 职责 | 我们谁在干活 | 自研程度 |
|---|---|---|---|
| L1 生成模型 | 造现实拍不到的画面，产出**素材** | drama-api（Krea2 出图 / H3 出视频），`model-route.ts` 的 `imageEdit`→image2image 四槽位 | **租的** |
| L2 渲染 | 把每一帧**算**出来 | Remotion CSR 链路（`render-job.ts` → `/remotion/pending` → `/remotion/commit`）、`timing.ts` 纯函数插值、`animated-style.ts` 唯一接线点、`furniture.ts` / `chart-*` / `data-card-metrics` 叠加层 | **自研** |
| L3 编排 | 把一句话拆成工序并跑完 | dsh agent + skills 注入 + 画布状态机 | **自研** |
| L4 智能/取舍 | 不画一帧，决定调谁、花多少、过不过 | `approval-gate.ts`、预算台账（`budget-note.ts` / `look-budget.ts` / `billing-state.ts`）、`wrapStudioToolDefinition` 入参守卫 | **自研** |
| L5 交付 | 编码、响度、时长、命名 | `encoding.ts`、`deliverable.ts`、`media-probe.ts` | 自研但**判据不全** |

### 3.2 护城河判定：L1 是租的，值钱的只能在 L2/L3/L4

三篇文章里 OpenMontage 的所有收益都来自 L3（编排）而不是 L1（模型）。作者的原话是「OpenMontage 最值钱的地方，不是它接了多少模型，而是它把做视频拆成了一条能被检查、被干预、被复用的流程」。

把这条套到我们身上，得到一个**能反过来解释现有技术债的结论**：

> 我们的 L1 是租来的，质感上限由 drama-api 决定，永远追不上模型厂。
> 因此凡是「跟模型质量较劲」的需求都是亏本生意，凡是「把模型输出变成可复用资产」的需求都是赚的。

三条推论：

1. **BUG-056（Krea2 prompt 限 500 字符）不是产品缺陷，是租约条款**。正确解不是写更长的 prompt，而是把长意图**下沉到 L4 的结构化参数**（分镜字段、Look tokens、参考槽位），让 prompt 只承载剩余自由度。
2. **P2-7（voiceOverUrl 单轨）优先级要往上提**。声音是 L5 里唯一「用户一听就知道好坏」的维度，也是文章两轮实测的最大短板。单轨意味着无法做「旁白 + 环境音 + BGM」的有源混音，而混音是廉价的观感杠杆（不花 L1 的钱）。
3. **不要把「多接几个模型」当路线**。文章里智谱 CogVideoX 免费档连返 429、队列卡死 12 分钟，腾讯混元按量付费——两个都在 L1，接了也救不了交付。这与我们的单后端现实一致（见 D4）。

### 3.3 一个必须承认的对立面

文章作者的最终选择是「如果只能二选一，我选零 API 版：准确和可控可以复用，质感只是这一条片子的观感」。

**我们不能照抄这个结论**，因为我们没有「手绘矢量片」这个产品形态（我们是通用创作工具，不是医学插画生成器）。但它的**方法论**可以抄：**让确定性的一层去保证准确，让概率的一层只负责质感**。落到我们身上就是 A3。

### 档 A · 立刻做

#### A1 · 交付阈值闸

**现状证据**：`media-probe.ts:47-49` 已经在量 `lufs`（ITU-R BS.1770 integrated），量不到还分了两种人话原因（`'无音轨'` / `'ebur128 测量失败'`，见 :150-155）。但这个值在 `src` 里只有两个消费者：`storyboard-render.ts:454` 把它**写进拆解表**，`storyboard-diff.ts:216` 把它**做前后对比**。**没有任何一处拿它做阈值判断。**

**这不是理论风险，已经付过学费**：`docs/2026-11-04-科普0.1验收分析报告.md:263` 记录的同一次事故——TTS 素材仅 −27 LUFS → 成片 −22.0 LUFS → 整体 loudnorm 到 −16 后重混 → 最终 −14.0。整个过程自检全过。

**收益**：直接命中文章最硬的那条教训——「自检全绿但片子是废的，因为工具只报数不做阈值判断」。我们把测量写好了、把结果写进表了、把事故分析写完了，**唯一缺的就是一行 `if`**。这是全部十二条里「收益/成本」比值最高的。

**怎么做**（细节）：

| 项 | 判据 | 处置 |
|---|---|---|
| 整片综合响度 | −16 LUFS ± 2 | 超界 ⇒ `card.json` 标 `loudnessOutOfRange`，附实测值与建议命令 |
| 真峰 | ≤ −1.5 dBTP | 超标 ⇒ 拒收（削波不可逆） |
| 有无音轨 | 有旁白/有 BGM 时必须有音轨 | 无 ⇒ 拒收 |
| 首尾静音 | 首帧前 / 尾帧后 > 0.3s 静音 | 标注（不拒收） |

落点：扩 `deliverable.ts` 的交付卡，**不新增审批门**（与 D4 拍板的「不拒收已渲好的片子」保持同构）。

**取舍**：会一次性暴露一批存量成片不达标。按项目铁律「只修产生数据的路径，不动历史数据」，**这些存量只标注、不回填、不重渲**，修的是产生它们的路径（TTS 选型与 loudnorm 环节）。代价是短期内 `card.json` 会冒出一片 `loudnessOutOfRange`，看起来像退步，实际是把隐性缺陷变成可见。

**为什么现在做而不是等**：响度是**交付层唯一不需要碰任何算法就能改善的维度**。改一句 ffmpeg 参数（`loudnorm=I=-16:TP=-1.5:LRA=11`，`-c:v copy` 视频流不重编码，几秒跑完）就能把「听起来像半成品」变成「听起来像成品」。它也是我们唯一有机会**在 L5 上超过模型厂**的地方。

**验收判据**：造三个样本（−22 LUFS / −16 LUFS / 无音轨）跑交付，断言前两者分别标 `loudnessOutOfRange` 与原样通过，第三者拒收；并反向变异（把阈值改成 −30）必须变红。

#### A2 · 降级必须留痕

**现状证据**：我们有明确的「不许静默降级」纪律——`routes.ts:1842`（指名道姓失败，不静默降级成文生视频）、`canvas-asset-attach.ts:199-201`（「任何一步失败都抛 CS-USER-ERR……静默成功等于骗人」）。但纪律是**写在注释里的**，不是结构。所以它被绕过过：CV-180 就是「真波形其实一直是降级条」——Host 侧 PCM 字节上限把可解码时长锁死，客户端静默退回确定性降级公式，`routes.ts:2992` 至今还留着这条路。

**文章给的对照印证极狠**：第三篇作者自己发现，两个脚本的 `--engine` 默认值写死 `gemini`、README 标「推荐」，但拿不到 key 时**自动降级回 edge，只甩一行控制台提示**。他的原话是「你以为在跑旗舰，实际在跑兜底——它不报错、不中断，只是悄悄换了个引擎，出来的东西照样能交活」。这跟 CV-180 是同一个病灶。

**收益**：把已经存在但会腐烂的纪律，变成不会腐烂的结构。对一个「用户不知道自己在看兜底产物」的产品，这条直接关系信任；对排查，`data-provenance.ts` 已有基础设施，接入面很小。

**怎么做**：定义「降级事件」的封闭集合——换 provider、换模型、换分辨率档（`resolution-resolve.ts` 的回退）、换编码参数、换渲染路径（CSR 失败退静帧）、换波形/预览的降级实现。**每个集合成员的降级分支必须写一条 provenance 并带原因**，UI 在该产物上标「兜底」。反向闸：测试断言「若走了降级分支但无 provenance 记录 ⇒ 判红」。

**取舍**：短期报错与标注会变多，用户会看到以前看不见的「这台机器降级了」。这是**把隐性缺陷显性化的必要代价**。另一个取舍是**覆盖范围必须克制**——只登记真正影响交付的降级（上面那六类），不要把每个可选默认值都当降级事件，否则会变成噪音，用户再次学会忽略。

**为什么不是「加个日志」就完**：日志会丢、会滚、用户不看。provenance 是**跟着产物走的**，成片挪到别的目录、发给别人，那行「本片旁白走的是兜底引擎」还在。这是文章那个「决策日志」想法在我们这儿的正确落点——不是日志文件，是产物属性。

**验收判据**：构造六类降级各一次，断言每个产物都带 provenance；再构造一次「降级但不写 provenance」的变异，闸必须变红。

#### A3 · 硬信息不进 prompt，进确定性叠加层

**现状证据**：我们的 L2 已经有完整的确定性叠加能力——`furniture.ts`（版式家具）、`chart-*`（图表）、`data-card-metrics.ts`、`count-up.ts`、`text-guard.ts`（文字入参守卫）、`camera-motion.ts`（运动对齐）。这些都不是为了「画图」，是为了**画准**。

**文章那句可以直接搬**：「生成图负责质感，矢量层负责准确性」。他们的实证是：ImageGen 出的解剖图是「一整条连续腱袖」而不是四条分离肌腱，于是「在 Remotion 里叠加了四条半透明矢量带和四个中文标签」。**生成越快，验收越慢**——这句是他们的原话，也是我们 keyframe 环节的真实体感。

**收益**：中高。减少一整类返工——凡是要「一个字都不能错」的内容（品牌字、参数数字、字幕、结构标注），从「反复重抽直到蒙对」变成「一次生成 + 叠加层修正」。这直接降 keyframe 的重试次数，而重试次数就是 L1 的钱。

**怎么做**：落成一条规则，三处同时生效——① skill 层写明「硬信息清单」禁止进 prompt；② keyframe 的 prompt 组装处加禁用词检查（复用 `text-guard.ts` 的模式）；③ 合成层提供默认叠加件（字幕/角标/参数牌）。

**取舍**：合成复杂度上升，叠加层要跟镜头运动对齐（`camera-motion.ts` 已有能力，但每个新叠加件都要单独验）。另一个取舍是**观感上限**：叠加层是「贴上去的」，跟生成画面里的真实光影不融合，特写镜头会露馅。所以规则只覆盖**硬信息**，不覆盖风格性文字（墙上的招牌、书脊文字这类，必须让模型画，画歪了也符合真实感）。

**判断依据**：这条不是「抄一个功能」，是**把我们已经会做的事变成默认路径**。成本几乎为零，收益是让 keyframe 从「抽卡」变成「一次到位 + 修正」。

### 档 B · 低成本可移植

#### B1 · 返工判据：区分「底图不达标」和「叠加层缺失」

文章最有价值的隐性经验不是方法，是**归因**：同一张图返工两次，第一次是「结构不合格」（底图问题，得换参考图或换任务定义），第二次是「连续腱袖而非四条分离」（底图上限，改用叠加层补）。**这两种返工的正确处置完全相反，混在一起就会一边无限重抽、一边永远不补**。

**收益**：中。它省的是**决策时间**，不是代码。我们的 keyframe 返工目前没有归因分类，agent 和用户都在凭感觉重抽。

**取舍**：需要人工判断，不能自动化。所以它只能落成 skill 里的一个判据表 + 错误文案分层，不能做成闸。

#### B2 · 否决四分类，只用于文案与日志

文章把 6 次人工停下分成四类：结构错误（像素层面「看起来很正常」，机器发现不了）、审美判断、成本签字、合规策略。

**收益**：中。我们的错误系统（`routeError()` / `codeIsUserFacing()` / `error-kind.ts`）已经有分层，但**没有按「谁来判」分类**。这四类的价值在于：结构错误 ⇒ 必须给用户看截图并指出具体位置；审美 ⇒ 给对比图不给结论；成本 ⇒ 报数字等签字；合规 ⇒ 给条文不给建议。

**为什么不加成闸门**：见 D1。这四类只用来自动选择**错误卡片的形态**（`error-card-plan.ts` 已有这个抽象），不加审批步骤。

#### B3 · 决策日志最小形态

**收益**：中。它是 C1 的前置——不做这个，C1 做出来也只是「能恢复状态」而不能「解释为什么走到这儿」。

**怎么做**：append-only，一行一条，字段固定：`时间 / 阶段 / 决策 / 备选项 / 理由 / 成本`。**不碰状态机，不做可视化，不进 UI**（先进 `card.json` 同级的 `decisions.ndjson`）。

**取舍**：会写得很难看、会很啰嗦。但文章那句「每个决策都有备选项、理由、置信度，返工有记录」是他们敢说「可审计」的全部底气。**先能写，再谈好看。**

**为什么最小形态就够**：我们已经有 `manifest-audit.ts`、`data-provenance.ts`、`auto-test-checkpoints.ts` 三个「记录」类设施，各管一段。决策日志不该是第四个系统，应该是**把已有记录里「为什么」这一半补上**。

---

### 档 C · 中成本，值得单独立项

#### C1 · 阶段 checkpoint + 断点续跑

**现状证据**：`STATUS.md:629` 明确写着——「五步串行工作流：大部分已被更轻的实现覆盖……**「暂停/恢复/中断点续跑」仍零落地 | 仅设计**」。我们只有视频异步任务的 `jobs.json` 续查（`activeResumeJobCount`），那是**单任务**续查，不是**流程**续跑。

**收益**：最高。它一次覆盖三个已知痛点：P1-5（超时 + 不可见挂死）、零执行失败留红标节点、以及「同一题材第二条片子从零开始」。文章那句「随时可恢复」在桌面场景里价值比在他们 CLI 场景里更高——用户会关窗口、会重启、会隔天再来。

**成本**：高。这是清单里唯一需要动状态机的条目。

**取舍（这条最重要，必须写死边界）**：

1. **不做通用工作流引擎**。STATUS 里那套「五步串行工作流」已经被更轻的实现覆盖了大部分，**不要借 checkpoint 之名复活它**。
2. **`canvas.json` 仍是唯一状态源**。checkpoint 只在阶段收尾**读**主状态写一份不可变快照，**绝不反向写入主状态**——否则双写打架，一致性直接崩。
3. **resume 判据必须是「产物在不在」而不是「阶段标记到没到」**。这是我们从 `storyboard-gate.ts` 学到的：只看 `landed`，与 mode/state 无关。标了完成但产物不在，就是不可恢复。
4. **恢复目标只到「阶段边界」**，不做阶段内帧级恢复。渲染中途挂了就整段重渲——Remotion 的确定性让重渲是安全的（`timing.ts` 纯函数、无 CSS transition），这是我们的结构性优势，别浪费。

**为什么值得立项而不是不做**：因为它是唯一一个**把「已经付过的时间」变成资产**的机制。A1/A2/A3 都是「少出错」，C1 是「错了不用从头来」。在一条动辄十几分钟渲染、几十次 L1 调用的管线里，后者的复利更高。

**为什么排在 A 之后**：它成本最高、风险最大，而 A1 用一行 `if` 就能拿到同等量级的信任收益。**先修已经付过代价的漏洞，再补缺失的部件。**

---

### 档 D · 明确不借

#### D1 · 5 道人工闸门

**不借原因**：他们的场景是多题材铺量 + 终端交互，停 6 次成本可接受；我们是单人在画布上连续创作，每加一道闸都是一次确认疲劳。而且我们**已经用一道闸精确命中了他们四类否决里最难自动化的那一类**——结构错误。`approval-gate.ts:8-14` 记录过真实教训：旧门禁 `GATED_TOOLS` 只含 `video_generate`/`video_composite`，而最贵的逐镜出图走 `image_generate` 完全不设防，于是「14:25:46 提交分镜待批准，用户 14:29:44 才点批准，这 3 分 58 秒里 agent 把第 4~5 步跑完了」。他们的结论「靠提示词让模型自己停不可靠，真正的闸必须在代码里」跟我们这份记录是**同一个结论、同一类亏**——我们比他们更早吃过这个亏，也已经把闸做进代码了。

**照抄会亏什么**：多 4 次确认 = 用户学会无脑点继续 = 唯一那道关键帧门也被绕过。

#### D2 · 700+ 技能 / 12 条管线铺量

**不借原因**：他们的技能量是为了覆盖通用题材（科普/品牌/再利用/零成本四种形态）。我们是单垂类深打，且 skill 有 40KB 硬闸 + 指针覆盖率 ≥50%。**放宽闸值换技能数量是本末倒置**——技能多了，`active-skills-prompt.ts` 的注入会稀释，路由反而变差。

#### D3 · 水印遮罩、裁掉 AI 标识

**不借原因，且方向相反**。文章把水印当**生产障碍**（「合成时用角部渐变遮罩处理」），我们把水印当**取证证据**：`method-evidence.ts:9` 明确「框、GB 45438 隐式标识、各家生成器水印标签……出现时**一票定案**」。在国内合规语境下，裁掉 AI 标识是**风险**不是**优化**——文章自己也承认「AI 标识裁掉后要不要补合规标注：合规策略，必须人定」。我们已经有自动取证，别退回到人工赌。

#### D4 · provider 打分 registry

**不借原因**：他们有 60+ provider 集成，需要按「匹配度/质量/可控性/可靠性/成本/延迟/连续性」打分选路。我们是单后端（drama-api），视频侧只有两条真实路径（`image2videofl2va` / `image2videoref2va`，`msr`/`mkr` 已禁用）。**为两家 provider 写一个七维打分器是纯空转**，而且会诱导我们把精力花在 L1 的租约谈判上——而 3.2 已经论证过 L1 不是护城河。

#### D5 · 双 agent 同目录赛跑

**不借原因**：他们的「目录就是裁判」成立，是因为产物是**约定命名的文件集**，两个 agent 各写各的文件，冲突面小。我们的状态是 `canvas.json` 单写者 + 故事板唯一写入口 `mergeStoryboardWrite`，允许并发等于主动拆掉一致性保证。CV-461 那种「文字容量体检漏了就被静默丢掉」的坑，在并发下会从偶发变成常态。

**如果将来真要**：前置条件是 advisory lock + 产物命名空间隔离，成本远超收益。**先证明有这个需求再说。**

---

## 5. 三篇里要打折扣的说法

别把作者的乐观面一起抄过来。四处需要打折：

1. **「全自动」叙事与它自己的数据矛盾**。第二篇写得很老实：「前四版里有三版『渲染成功、规格达标、自检通过』，但人一看就是废的」。所以它给的诚实描述是「一句话启动，五道人工把关，产出稳定」——**不是全自动，是半自动**。我们对外表述也别用「全自动」。
2. **「零 API 版更值得选」不能照抄**（见 3.3）。作者是内容创作者，选的是「这一条片子」；我们是工具，选的是「一千条片子」。
3. **它的自检会报假阴性**。第一篇里「工具自带的音量检测在本机 FFmpeg 构建下跑不起来，报了『无旁白』的假阴性」，靠人用 numpy 重测才发现。对照我们：`media-probe.ts:150-155` 已经把「量不到」拆成 `'无音轨'` 和 `'测量失败'` 两种原因——**这一点我们比它细，别在 A1 的实现里退化成只返回 null**。
4. **它的「推荐方案」带静默降级**（第三篇自己揭穿的）。这一条恰好是我们 A2 的最佳论据，也是提醒：**任何带默认值的选型配置，都要问一句「降级路径在哪、有没有告警」。**

---

## 6. 落地顺序与理由

排序原则一句话：**先堵已经付过代价的漏，再补缺失的部件，最后才动状态机。**

| 顺序 | 条目 | 为什么是这个位置 | 前置 |
|---|---|---|---|
| 1 | A1 交付阈值闸 | 测量、写表、事故分析全做完了，只差判定；改一行拿最高信任收益 | 无 |
| 2 | A2 降级留痕 | 纪律已存在但会腐烂（CV-180 为证）；provenance 设施现成 | 无 |
| 3 | A3 硬信息叠加层 | 能力现成，落成规则即可；直接降 L1 重试成本 | 无 |
| 4 | B3 决策日志 | C1 的前置；不碰状态机，风险低 | 无 |
| 5 | B1 / B2 | 纯文档与文案分层，可随时插入 | 无 |
| 6 | C1 checkpoint | 收益最高但成本最高；依赖 B3 才有「为什么」，依赖 1-3 才有「恢复后不再出废片」 | B3 + A1/A2 |

**为什么 A1 排第一而不是收益最高的 C1**：A1 的成本是一行判定 + 一个断言，ROI 高两个数量级；而 C1 在 A1/A2 没做之前就上，等于「恢复了流程但恢复出来的还是没人验的废片」——恢复得越快，废片产得越多。

---

## 7. 一句话结论

三篇文章证明了我们选的路是对的（L3 编排 + L2 确定性渲染 + L4 硬闸），也顺手指出我们缺的只有一件半：**半个交付判据（A1）** 和一个**断点续跑（C1）**。剩下的都是「把已经写在注释里的纪律变成结构」（A2、A3、B3）。

最该带走的一句，不是任何技术点，是作者那句：**「把做视频拆成能被检查、被干预、被复用的流程，比多一个炫酷的生成模型更值钱。」** 我们的 L1 是租的，这句话就是我们唯一能赢的地方。
