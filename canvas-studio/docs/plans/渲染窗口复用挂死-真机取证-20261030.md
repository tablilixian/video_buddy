# 渲染窗口复用挂死 · 真机取证（2026-10-30）

> 议题来源：`session.v4 8.jsonl`（45 轮 / 97 次 `render_composition`：66 成功 / 31 失败，
> 其中 21 次是「隐藏渲染窗口已取单但 30.0–31.3s 内一帧都没渲染」）。
>
> 本文只记**真机实测**结论。宿主侧判死逻辑的台帐（不启浏览器那部分）在
> `tests/render-host-deadzone.test.mjs`。

## 一、结论（先看这段）

**同一个隐藏渲染窗口不能连续渲染第二单。** 第二单会在「首帧前后」把渲染页主线程按住，
心跳与进度同时停 ⇒ 宿主按「失联」在 30s 判死 —— 判死这个动作是**对的**（窗口确实已经没有
任何活性证据），错的是「窗口为什么会死」以及「死了之后怎么处置」。

**不是**「5415 帧超过窗口长度限制」，**也不是**「首帧前 30s 预算不够」。

## 二、实测数据

manifest = 会话里真实失败的那份：63 轨（26 段视频 + 37 张字幕卡）/ 5415 帧 /
1376×768 / 30fps / 24 个真素材（45MB），quality = `draft`，隐藏窗口 + 真 bundle + 真 WebCodecs。

| 场景 | 第 1 单 | 第 2 单 | 第 3 单 |
|---|---|---|---|
| **同窗口连续渲** | ✅ 102.8s 成交 · 首帧前 11.1s · 心跳空档 1.0s · 19.0ms/帧 | ❌ **取单后 11 拍心跳到 10s，随后心跳全停、139.1s 零帧** | ❌ 连单都取不走（页面已废） |
| **每单换新窗口** | ✅ 102.4s · 首帧前 10.9s · 18.9ms/帧 | ✅ 102.2s · 首帧前 10.8s · 18.9ms/帧 | ✅ 102.2s · 首帧前 10.8s · 18.9ms/帧 |

- 换窗组的成片字节数三次**完全相同**（9,512,139 B）⇒ 渲染是确定性的，挂死与内容无关。
- 冷启一扇新窗口只要 **404–684ms** ⇒ 「每单重建窗口」的成本远低于一次 30s 判死 + 人工重试。
- 首帧前耗时稳定在 **10.8–11.1s**（26 个 `<video>` 预取 + 首帧），距 30s 阈值有 3 倍余量
  ⇒ **给首帧前加规模预算救不了这个故障**。

## 三、机制

```
宿主派单（render-host） → 页面 claim → paint('rendering') + beat()
   → executeRenderJob → renderMediaOnWeb
        第 1 单：正常出帧（progress ≥ 0 后，min() 口径有进度兜着）
        第 2 单：约 10s 处主线程被按住 → 心跳停 → 无任何进度
   → 30s：render-job.ts 判死「渲染窗口异常」，dispose 窗口（dispatch.ts 30s 节流）
   → 第 3 单：30s 内再失败 ⇒ 节流命中、不再重建 ⇒ 继续在废窗上撞
```

`tests/render-host-deadzone.test.mjs` 的 S-5 钉住了最后那一环：判死才丢窗、且丢窗有 30s 节流。
会话里「19:31 之后同一份片 5/5 全死」「14:51–16:24 同尺寸 8/8 全活」就是「拿到新窗 / 拿到废窗」
的差别。

## 四、修法（按性价比）

1. **每单渲完就回收窗口（P0，最便宜的修法）**：`commit` / `cancel` / 失败结算后统一
   `disposeRenderHost` + 下次派单重建。实测重建 0.4–0.7s，换掉「第二单必挂 + 30s 判死」。
2. **去掉失败重建的 30s 节流（或只对「刚崩过的窗口」节流）**：现在第二次失败拿不到干净窗口，
   把「一次失败」放大成「连续失败」。
3. **错误文案分离（P1）**：`stall.detail` 已经是 `render host heartbeat lost for Ns`，但
   `userMessage` 一律「渲染窗口异常，请重试」。至少要分成「渲染器失去响应（已重启渲染窗口）」
   与「渲染慢（仍在进行）」两句 —— 模型现在只能对着同一句话反复重试。
4. **渲染页侧（P2，可选）**：把心跳搬到 Worker（主线程被按住也能报），这样宿主能区分
   「窗口活着但渲不动」与「窗口死了」。但注意：本故障里心跳停是**症状**，不是原因 ——
   搬 Worker 只会让判死变晚，不会让第二单渲出来。**不要用 4 替代 1。**

## 五、复现方式

```bash
cd canvas-studio
env -u ELECTRON_RUN_AS_NODE ELECTRON_DISABLE_SANDBOX=1 \
  ../dsh-plugin-desktop/node_modules/.bin/electron scripts/probe/render-host-stall.probe.mjs \
  --manifest="<project>/build/manifest-v35-poster.json" \
  --quality=draft --runs=3 [--freshWindow=1] [--runBudgetMs=150000]
# 报告：/tmp/cs-render-host-stall/report.json（每次 run 的首帧前耗时/心跳空档/总耗时/字节数）
```

`--runs=3`（不加 `--freshWindow`）= 复现挂死；`--runs=3 --freshWindow=1` = 对照组，应 3/3 成功。

## 六、探针局限

- 单机、单窗口、无其它负载；`draft` 档为主。会话里的失败集中在 draft/standard，`high` 未测。
- 素材走本地 HTTP（Range 支持），比真宿主的多项目资产路由快；**真机上首帧前可能更慢**，
  但本次实测已证明 30s 余量充足，慢不到 3 倍。
- 未覆盖「同时多张单 / 画布页与窗口抢单」的并发场景。

## 七、纠正一条此前结论

复盘初稿把 21 次归因为「首帧前无心跳死区（主线程被 `pageResponsiveness: 'disabled'` 按住，
30s 一刀切误杀健康渲染器）」。真机数据**否掉**了它：第 1 单在同一个 `disabled` 档下心跳稳在
1s 一拍、首帧前只有 11s。死区不是「首帧前」，而是「**复用窗口的第 2 单及以后**」——
主线程是被同一个渲染页里上一次渲染的残留状态按住/挂死的，与阈值无关。

## 八、修复（2026-10-31）：一扇窗只渲一单

按 §四 的第 1、2、3 条一起落地，**核心只有一条策略**：隐藏窗口的生命周期 = 一张单。

| 改动 | 位置 | 说明 |
|---|---|---|
| 结算打标 | `render-job.ts` `settleAndForget` | 窗口单（成功/失败/取消/超时都算）结算时 `markRenderHostServedJob()`，把窗口记为「脏」 |
| 回收（不节流） | `render-host/dispatch.ts` `recycleRenderHost` | 绕开失败重置的 30s 节流；顺手把 `lastWarmAt = 0`，让下一次派单**立刻**重建（否则会被 `warmRenderHost` 的 2s 防抖吞掉，单派给空气） |
| 派单前换新 | `render-job.ts` `runRenderJob` 开头 + `armTimeout`（拿到槽位那一刻） | 两处都要：前者让 `pickExecutor` 在干净状态上决定执行者；后者补「排队单」—— 前一张单可能在它建好**之后**才结束，窗口到那一刻才变脏 |
| 守卫 | `recycleServedRenderHost(exceptJobId)` | 窗口正被**另一张在飞的单**用着时不许回收（并发=1，最多只可能是「另一张还在跑」）；`exceptJobId` 排除刚拿到槽位的自己 |
| 文案分离 | `silenceOf` / `failRenderHostJobs` | 判死：`渲染窗口异常：隐藏窗口 Ns 内既没有心跳也没有进度（渲染器被卡住）…`；窗口没了：`渲染窗口异常：窗口已退出（reason）…` |

为什么把回收到派单侧而不是结算侧：结算发生在 `POST /remotion/commit` 的处理过程中，那一刻
渲染页正等着这个响应；同步销毁窗口会打断它的 fetch，凭空造出两条噪音日志。挪到派单侧，
没有任何人在等这个窗口。

**实测与门禁**

- `tests/render-host-deadzone.test.mjs` 12 条全绿（新增 S-7①~④ 四条守恒），
  13 组反向变异逐条验红（见文件末尾清单；M-A 因两处回收互相兜底而不变红，已注明）。
- 真机探针新增 `--recycle=1`：每单结束走**生产代码**（`markRenderHostServedJob` →
  `recycleRenderHostIfServed` → `disposeRenderHost` → `warmRenderHost`）再跑下一单 ——
  与 `--freshWindow=1` 的区别是「验的是修复后的真实链路」，不是探针自己 dispose。

**验收口径**

```bash
# 修复前：同一个窗口连渲 → 第 2 单取单后 139s 零帧
# 修复后：--recycle=1 连渲 3 次应 3/3 成交，且每轮 window:rebuilt bootMs ≈ 0.4–0.7s
... render-host-stall.probe.mjs --runs=3 --recycle=1 --quality=draft
```

若 3/3 成交且 `report.json` 里三次 `bytes` 相同（渲染确定性），则「复用必挂」这条被消掉；
GUI 侧的等价验收是「同一项目连渲 3 次不再出现『渲染窗口异常』」。
