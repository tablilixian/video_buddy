# 吸收 video-shotcraft：学习方案 + 拍板清单（2026-10-25）

> 目标不是"学会用它"，而是**把它的三样东西吸收成我们自己的能力**：镜头卡片的**形式**、主题模板的**形态**、声音与节奏的**品类**。
> 三条原则：**不 vendor 代码** ｜ **每阶段有可判定产出** ｜ **学完要能被数据验证**（不是"感觉懂了"）。

---

## 一、这套方案解决什么（对照我们实测的痛点）

| # | 我们的问题 | 现状证据 | 本方案哪一步解决 | 能到什么程度 |
|---|---|---|---|---|
| P1 | **模型要靠"读源码"才能确认引擎语义** | 最近会话 **24 次**源码探索，单步 reasoning 2.7–4 万字符 | S1 卡片化（把散文变成"可粘片段"） | 期望降到 ≤5 次/会话 |
| P2 | **每次从零组装 manifest**，时长/结构靠试错 | 事故复盘；manifest 校验反复失败 | S1 骨架卡 + S2 主题预设 | 首轮结构合法率 ≥80% |
| P3 | **动效词汇贫乏**（5 种 `anim` + 少量 fx） | `manifest-contract` | S1 卡片库（12→16 张） | 常用镜头 70% 能从卡里选 |
| P4 | **版式/节奏没有依据**，观感忽好忽坏 | 事故里 3 版被否 | S2 theme preset（含动效基线 + 版式） | 同一主题下节奏一致 |
| P5 | **声音单薄**：只有旁白 + BGM | 现状盘点 | S3 音效品类（10–20 个） | 转场/强调/文字有声音 |
| P6 | 到第一次提问 12.75 min | 会话转录 | 间接（少探索） | 目标 ≤5 min |
| — | **渲染链路不稳 / 每步 6s TTFT** | Phase 0 | **本方案不解决** | 已由 CV-363~365 与 provider 侧负责 |

> 写清"不解决"的部分，是为了不把内容层的收益记到运行时问题上——那会把账算错。

## 二、学习方案（四阶段，每阶段有产出与验收）

### S0 · 观察（约 2 小时，不改任何代码）

**做什么**
1. `git clone --depth 1` 到 `/tmp/shotcraft`（不进仓库、不装依赖）；
2. 打开在线 Gallery，**只挑 15 张**与我们能力相近的卡（文字揭示 / 数据强调 / 卡片入场 / 转场 / 收尾）；
3. 对这 15 张逐条填一张表：`卡名 | 它怎么实现 | 我们能不能做 | 用什么字段做 | 缺什么字段`。

**产出**：`docs/plans/shotcraft-能力对照表.md`（15 行）
**验收**：表里"能用现有字段复刻"的比例 ≥ **60%**。低于 60% 说明我们能力缺口比想象大，
要先补 manifest 字段而不是先做卡片。
**失败判据**：如果对照表里超过一半是"做不到"，**立即停止本方案**，改做能力补齐（那是另一条线）。

### S1 · 卡片化（0.5 天，纯文档 + 1 条测试）

**做什么**
1. 定卡片 schema（5 段）：`卡名 / 适用场景 / 参数 / 最小可粘片段 / 观感要点`；
2. 先写 **12 张**（覆盖：标题揭示、逐字打出、数据强调、卡片入场、图文分栏、转场×2、收尾、图表、进度条、高亮扫过、呼吸强调）；
3. 每张必须给**能被 `validateManifest` 直接接受的片段**；
4. 加一条守卫：卡片里的 JSON 片段逐个 `validateManifest` —— 错一个就红。

**产出**：`skills/code-driven-explainer/references/shot-cards.md` + `tests/shot-cards.test.mjs`
**验收**：12 张全过校验；SKILL.md 里加一行指引（注意：SKILL.md 已 11.8KB，**必须先腾 200 字节**再挂）。
**风险**：卡片写成"散文换皮"就白做 —— 判据是**片段能否直接粘进 tracks 跑通**。

### S2 · 主题预设（1 天，动 manifest 字段）

**做什么**
1. 定义 `theme preset` 的数据形状：配色 + 字体 + `meta.look` 六项 + **动效基线**（默认 duration/easing/stagger）+ **版式**（左右分区 / 上下分区 / 全屏卡）+ 推荐卡片序列；
2. 内置 **2 个**预设（不超过 2 个，多了没人用）：`ink-press`（借它的设计语言，冷色高对比）与 `warm-explainer`（我们科普片的暖色版）；
3. manifest 加 `meta.themeId`；展开时机在**校验前**（等价于默认值注入），并进 `warnings` 说明"已应用主题 X"。

**产出**：`src/remotion/themes.ts` + 展开逻辑 + 测试（含"未知 themeId 报错"与"显式字段优先于主题默认值"）
**验收**：同一份内容换 `themeId` 能出两种观感；显式写的字段不被主题覆盖。
**风险**：主题默认值与显式字段的**优先级**必须写死并测（否则又变成"两套事实"）。

### S3 · 声音品类（0.5 天）

**做什么**
1. 从它的 149 个 SFX 里挑 **10–20 个**（whoosh / click / riser / impact 各 3–5 个）；
2. **逐个核对 `assets/audio/ATTRIBUTION.md` 的授权**，登记到我们的资产说明；
3. 卡片声明"配哪个音效"（字段先只做**建议**，不参与渲染，避免动音频混音链）。

**产出**：资产目录 + `ATTRIBUTION` 记录 + 卡片字段 `sfx?`
**验收**：授权逐条可查；体积增量 < 2MB。
**风险**：授权不清的一个都不要用。

### S4 · 卡点（可选，1 天，先做建议器）

离线算 beat map → 输出 `cutFrames[]` 建议 → 由 agent 排轨时参考。
**不做**渲染层改动，也不进 manifest（先验证有收益再加字段）。

## 三、拍板清单（D14–D18）

| # | 决策 | 选项 | 我的建议 | 不拍的后果 |
|---|---|---|---|---|
| **D14** | 卡片以什么形式承载 | ① 纯 markdown 卡片 ② markdown + 校验测试 ③ 做成工具（`list_shot_cards` / `compose_from_cards`） | **②**：文档 + 守卫。③ 等卡片超过 30 张再说（现在做工具是过度设计） | ①会退化成长段说明文字（等于没做） |
| **D15** | 主题预设怎么进 manifest | ① `meta.themeId`（校验前展开）② 独立工具 `select_theme` ③ 写死在 skill 里 | **①**：manifest 自洽、可回放、可验签；③最差（又变成"skill 里有、manifest 里没有"） | 主题只在 skill 里 = 换个人就丢 |
| **D16** | 音效从哪来 | ① 用它的库挑 10–20 个 ② 自己生成 ③ 买商用库 | **①**，但必须逐条核对 ATTRIBUTION | 用了授权不清的音频 = 法务风险 |
| **D17** | 现在做不做卡点（S4） | ① 现在 ② 先做完 S1–S3 再看 | **②**：S4 收益最不确定，且要引入 Python/librosa | 现在做会拖慢主线 |
| **D18** | 要不要"部分移植"它的 TSX 组件（如 2.5D 运镜） | ① 一律不移植 ② 逐个评估，只移植"manifest 表达不了且价值高"的 | **② 但门槛极高**：必须同时满足「manifest 现有字段无法组合出」「至少 3 个镜头会用到」「有测试」 | 一律不移植可能错过 1–2 个高价值组件；一律移植会毁掉白名单架构 |

## 四、时间与顺序

```
S0 观察(2h)  ──→  D14 拍板  ──→  S1 卡片(0.5d)  ──→  S2 主题(1d)  ──→  S3 声音(0.5d)
                                   ↑                                    ↑
                            每步都要跑全量 smoke               D16 先核授权
S4 卡点 排到最后（D17 若选②）
```

总计约 **2.5 天**（不含 S4）。S0 是**门槛**：对照表不达标就不往下走。

## 五、怎么验证"学到了"（可量化，不看感觉）

| 指标 | 现在 | 目标 | 怎么测 |
|---|---|---|---|
| 单会话源码探索次数 | 24 | **≤5** | 会话转录里 grep `src/remotion` / `components` |
| 到第一次提问时间 | 12.75 min | **≤5 min** | 首个 `ask_user_choice` 时间 |
| manifest 首轮校验通过 | 未知（事故里反复失败） | **≥80%** | 渲染工具返回里无 `CS-USER-ERR` 结构错 |
| 镜头来自卡片的比例 | 0 | **≥70%** | 人工抽查 manifest 的 tracks 与卡片对照 |
| 同主题节奏一致性 | —— | 两版同主题片子节奏差 < 10% | 抽帧对比 |

> 这 5 个数下次会话就能测前两个；后三个要等有片子产出。

## 六、明确不做（防止跑偏）

- ❌ 不把 shotcraft 装进我们的 skills 目录（它是给 Claude Code/Codex 的，不是给我们的 host）
- ❌ 不 vendor 它的 157 张卡 / 214 样片 / 149 音效（只挑 10–20 个音效）
- ❌ 不引入 puppeteer / chrome-headless-shell / Python 依赖（我们的 CSR 路线没有浏览器依赖，这是优势）
- ❌ 不做动效工作台（时间线编辑器）、不做剪映导出
- ❌ 不为了"复用模板"改成让模型写 TSX（放弃确定性/可校验/无任意代码执行）

---

## 七、一句话建议

**先花 2 小时做 S0**（clone 到 /tmp 看 15 张卡，填对照表）。
如果"能用现有字段复刻" ≥60%，再投 2.5 天做 S1–S3；达不到就先补 manifest 能力，别做卡片。
**S0 花 2 小时能避免 2.5 天的错方向**，这是整份方案里性价比最高的一步。
