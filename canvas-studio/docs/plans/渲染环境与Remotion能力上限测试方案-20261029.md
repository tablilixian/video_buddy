## 0. 一句话结论

- 本项目的渲染路线是 **路线 B（CSR，客户端软编）**：`@remotion/web-renderer` 的 `renderMediaOnWeb`，**跑在 Electron 自带的 Chromium 里**，编码走 OpenH264/WASM。**不是** Remotion CLI，**不是** SSR（`@remotion/renderer`）。

### 4.2 铁律（写之前必读）

1. **必须用 Electron 启动脚本，不能用 `node`**：
   ```bash
   env -u ELECTRON_RUN_AS_NODE ELECTRON_DISABLE_SANDBOX=1 \
     ../dsh-plugin-desktop/node_modules/.bin/electron scripts/my-render-test.mjs
   ```
   `env -u ELECTRON_RUN_AS_NODE` 是必须的——否则 `electron` 会退化成裸 Node，拿不到 `app/BrowserWindow`。
2. **`NODE_OPTIONS=` 置空**再跑 node 侧脚本（verify/forensics 头注释都这么要求）。
3. **不要传 `browserExecutable`**（见 §1.1）。
4. **授权有两层 403**，写脚本时别踩（第 6 节详述）。
5. 页面里的渲染必须在 `app.whenReady()` 之后 `loadURL`；渲染结果通过 IPC 或 `/__save` 回写回主进程（verify.mjs 的做法）。
6. 真渲染需 GUI：agent/SSH/无窗口会话跑不了（除非 `S10_BUNDLE_ONLY=1` / `--check`）。

### 4.3 路线 A 最小骨架（照 verify.mjs 抽象）

```
1) @remotion/bundler bundle({ entryPoint: entry.tsx, webpackOverride }) → out/bundle
2) node:http 起静态服务：托管 bundle/ + assets/ + /__save 回写端点
3) Electron main：new BrowserWindow({ show:false }) + loadURL(`http://127.0.0.1:<port>/?manifest=...`)
4) 页面（渲染进程）：
     const cap = await canRenderMediaOnWeb({container:'mp4', videoCodec:'h264', width, height})
     if (!cap.canRender) → 记录 detail（这就是"能力上限"的直接证据）
     await renderMediaOnWeb({ composition, container:'mp4', videoCodec:'h264',
                              audioCodec:'aac', outputTarget:'arraybuffer',
                              quality 相关参数, onProgress })
5) 主进程拿 arraybuffer → 落盘 → ffprobe 校验流构成
```

> 关键参数来源：`QUALITY_PRESETS`（`src/client/remotion-render.ts:65-92`）——
> `draft{scale:0.5, bitrate:low, keyframe:10s, hw:prefer-hardware, cache:128MB}`、
> `standard{scale:1, bitrate:medium, keyframe:5s, hw:no-preference}`、
> `high{scale:1, bitrate:high, keyframe:2s, hw:prefer-hardware, cache:256MB}`。
> **要测上限就用 `high` 这一组。**

### 4.4 路线 B 最小骨架（照 e2e probe 抽象）

```
1) import 真 lib 产物：join(packageRoot,'lib','render-host/window.js') 等（loadLib 写法见 probe:36）
2) app.whenReady() → await ensureRenderHost(...) 拿到隐藏窗口 handle
3) 用真 runRenderJob 建一张单（可注入短 warmup/claim 阈值，render-job.ts:795 的 options）
4) 隐藏窗口轮询 GET /remotion/pending?owner=host → claim → 渲染 → commit
5) 断言产物字节 + 读 /canvas-studio/render-host/status 看自报
```

### 4.5 产物校验（每次必做）

```bash
ffprobe -v error -show_entries format=duration,size \
        -show_entries stream=codec_name,width,height,avg_frame_rate \
        -of default=nw=1 <产物.mp4>
```
判定：`h264` + `aac`、`avg_frame_rate=30/1`（或你设的 fps）、`duration ≈ durationInFrames/fps`、`size>0`。
（真实成功样本实测：`5764d91b-….mp4` = h264 1376×768 30fps 61.14s + aac，14.3MB。）

## 5. 怎样才算"体现 Remotion 的最高能力"（v2：标尺是"能做什么片子"）

> v1 的回答只有「1080p / 60fps / 30 分钟 / 8 轨」——那是**编码器没崩的证明**，不是**能力被用上的证明**。
> 一个 1080p60 的纯色渐变片，和一支有 3D 场景 / 着色器转场 / 词级字幕 / 音频驱动的片，跑的是同一个 `renderMediaOnWeb`。
> v2 把"最高能力"拆成四维（§5.0），并以 **Remotion 官方 `packages/example` 的 302 个 composition** 当外部标尺（§5.2）。

### 5.0 四维判据（"最高" = 四维同时到位，不是某一维拉满）

| 维度 | 问的问题 | 不达标的样子 | 本轮怎么判 |
|---|---|---|---|
| **1 题材广度** | 能拍出哪几类片子？ | 只会"图 + 字 + 推拉"的 PPT 片；片头、数据片、字幕流、3D 一个都不行 | §5.2 十项基准里 **≥7 项出片** |
| **2 视觉复杂度** | 用没用上 WebGL / Skia / 着色器 / 矢量变形 / 滤镜链？ | 画面平、没质感、转场只有淡入淡出 | 十项里"渲染器级能过"的项数 |
| **3 工程规模** | 分辨率 × fps × 时长 × 轨数 × 素材体积 | 60s 就超时、8 轨就掉帧 | §5.5 指标达标 |
| **4 稳定性/确定性** | 连渲一致、后台档不退化、同 manifest 逐帧可复现 | 两次出片不一样 / 隐藏窗口必挂 | §5.4 的 S2 |

⇒ v1 的"最高"只覆盖**第 3 维**。v2 的验收线 = 「十项基准 ≥7 项出片（第 1、2 维）」+「规模与稳定性达标（第 3、4 维）」。
**只报分辨率和时长，等于只交了四分之一的卷。**

### 5.1 先把 CSR 的硬边界划清楚（谈"上限"之前）

路线 B 的能力全受 `@remotion/web-renderer` 的**元素白名单 + CSS 白名单**约束——它不是"截图"，是把 DOM **仿真画到 canvas**（出处 `remotion.dev/docs/client-side-rendering/limitations`，2026-10-29 取原文）。

#### 5.1.1 组件白名单（决定"能不能用生态"）

| 官方明列**支持** | 官方明列**不支持** | 对我们的含义 |
|---|---|---|
| `<Video>`/`<Audio>`（`@remotion/media`）、`<Img>`（含 SVG data URI）、`<Gif>`、`<Rive>`、`<Lottie>`、`<ThreeCanvas>`、`<SkiaCanvas>`、`<AnimatedImage>`（仅 Chrome）、`<HtmlInCanvas>` | `<OffthreadVideo>`、`<Html5Video>`、`<Html5Audio>`、`<AnimatedEmoji>` | ① 我们已选 `@remotion/media`，**方向对**（devdoc R17）；② **3D / Skia / Lottie / GIF / Rive 在 CSR 里官方说"能"** ⇒ 天花板远高于"只能摆图叠字"，缺的是依赖与轨，不是路线；③ 表情包类素材没戏，改用 Lottie |

#### 5.1.2 CSS 白名单里对我们**最疼**的 8 条（+1 条官方未覆盖、必须自测的）

| 不支持 | 直接打死我们哪个已落地功能 | 出处 |
|---|---|---|

#### 5.1.3 三个"已实现、但 CSR 里疑似空转"的字段（本机静态核对，必测）

| 字段 | 我们写了什么 | 4.0.535 渲染器里有什么 | 判据 / 处置 |
|---|---|---|---|
| `blend`（`normal/screen/multiply/overlay/soft-light`） | `mixBlendMode` 逐组件下发（VideoClip`:47`、ImageClip`:38`、Shape`:24`、TextCard`:176`、AudioViz`:121`）+ look 颗粒层 `Root.tsx:190/203` | `@remotion/web-renderer/dist/esm/index.mjs` 里 `mixBlendMode` / `mix-blend-mode` / `multiply` / `soft-light` **命中 0 次**；`globalCompositeOperation` 只用于 `background-clip` 与 `destination-out/in/source-in` | 官方称 4.0.540 起支持 ⇒ **4.0.535 已实证整字段无效**（§10.2 有对照组：同一份 dist 里 `borderRadius` 命中 129、`transform` 140、`maskImage` 31，而这四个是 0）。⇒ 二选一：升版本 / 把字段从契约里下掉 |
| `clock` 转场 | `maskImage: conic-gradient(...)`（`timing.ts:401-402`） | 白名单只到 linear-gradient | 出片看是否像钟表扫开；若是硬切或整层突现 ⇒ 空转，改 `clip-path: polygon()` 逐帧近似 |

> 这三条与"能力上限"直接相关：**如果它们空转，说明我们对自家渲染器的认知还停在纸面**，那么任何"最高能力"结论都不可信。
> 它们也正好是"只修产生路径"的对象（`blend` 要么升级要么下掉），不涉历史数据。

#### 5.1.4 三个决定天花板高度的开关

1. **`allowHtmlInCanvas`（4.0.535 已有该 option，默认 `false`）**：开启后走 Chromium 实验 API `drawElementImage` 做**全帧截图** ⇒ **§5.1.2 整张 CSS 白名单失效**，浏览器能画的都能画。官方限制：需 Chromium 开启 `chrome://flags/#canvas-draw-element`；像素可能与 DOM 合成器**不一致**（`pixels may differ`）；不可用时**静默回落**（不报错，只在 console 打一行 warn）。⇒ 这是"CSR 天花板能否抬到 ≈ SSR"的唯一开关，见 §5.3 探针 Q13。
2. **编码/容器矩阵**（`@remotion/web-renderer/dist/mediabunny-mappings.d.ts`）：视频 `h264|h265|vp8|vp9|av1`；容器 `mp4|webm|mkv|mov|wav|mp3|aac|ogg|flac`；音频 `aac|opus|mp3|vorbis|pcm-s16|flac`。⇒ 透明视频（webm+vp9）、更小体积（h265/av1）**理论上可测**；实际取值以 `getEncodableVideoCodecs()` 为准，别照文档猜（§5.3 探针 Q14）。
3. **单并发**：CSR 无多线程（官方 `#Single concurrency`），后台页靠 Worker timer 顶替 rAF ⇒ 隐藏/后台档必然比前台慢，这是 §5.4 S2 的既有结论基础。

⇒ **"≥7 项出片"这条验收线的来历**：A(2) + B(4) = 6 项是"接线就能过"的存量；再拿下任意 1 个 C 级（探针 Q12/Q13 一通过，C 级至少能落 1 项）即达 7。七项是一个"能力面铺开"的门槛，不是一个凑数的数字。

三句话是本节的结论：

1. **"图 + 字 + 推拉"已经是 A 级基线，不再算能力**；
2. 待突破的是 **C 级三项（3D / Skia / 全量捕获）**，它们决定"能不能做片头、产品片、科幻感转场"——也就是客户眼里"贵的片子"；
3. **D 级为零**是这条路线的关键结论：**CSR 没有"根本做不了"的题材，只有"还没接线"的题材**（唯一例外是表情包类素材）。

### 5.3 四个 P0 探针（跑完才知道 C 能不能降成 B）

> 全部在 **Electron 渲染进程**里跑（`scripts/remotion-verify/electron/main.js:67` 已有打印 `chrome=` 的先例）。
> 建议直接加成 `scripts/render-forensics/run.mjs` 的 **Q12~Q15**，一次跑完落一份 `capability.json`。

| 探针 | 判据（渲染页 console 直跑） | 通过 ⇒ 结论 |
|---|---|---|
| **Q12 WebGL/GPU** | `const c=document.createElement('canvas'); const gl=c.getContext('webgl2') ?? c.getContext('webgl'); gl ? gl.getParameter(gl.VERSION)+' / '+gl.getParameter(gl.RENDERER) : 'no webgl'` | 有 `webgl2` 且 `RENDERER` 不含 `SwiftShader`/`Disabled` ⇒ 3D/Skia/shader 类可做。**可见窗口与隐藏窗口各跑一次**（后台窗口最容易退化成软渲） |
| **Q13 HTML-in-canvas** | `const c=document.createElement('canvas'); const x=c.getContext('2d'); ({draw:typeof x.drawElementImage, paint:typeof c.requestPaint, capture:typeof c.captureElementImage, off:'transferControlToOffscreen' in HTMLCanvasElement.prototype})`，再对照 `import {HtmlInCanvasSupported} from 'remotion'` | 四项齐 ⇒ 试 `allowHtmlInCanvas:true` 渲同一条片子做 A/B；不齐 ⇒ 先 `app.commandLine.appendSwitch('enable-canvas-draw-element')`（对应 `chrome://flags/#canvas-draw-element`，**switch 名以实测为准**）重启再测 |
| **Q14 编码矩阵** | `getEncodableVideoCodecs()` / `getEncodableAudioCodecs()`（`@remotion/web-renderer` 导出） | 输出实际可用集合。h264+aac 必备；h265/av1 可用 ⇒ "同画质更小体积"可谈；`vp9+webm` 可用 ⇒ 透明通道视频成立 |
| **Q15 SVG 元素** | 渲一份只含 SVG `path` / `polygon` 元素的短合成（我们的 `Shape` 就是这么写的），`ffprobe` + 抽帧目视 | 正常 ⇒ 4 种 shape 与 `path` 轨成立；异常（整块缺失/糊成一团）⇒ **二期 A1/A3 的全部自绘 shape 都要重做**，优先级最高 |

> **2026-10-29 已经真跑完了，结论在 §10**（别再当"待跑"读）。一句话：**Q12 绿**（Apple M3 真 GPU，不是 SwiftShader）/ **Q13 一个 flag + 两个 DOM 约束就能绿**（`--enable-features=CanvasDrawElement` + 元素必须是 canvas 子元素 + canvas 带 `layoutsubtree`，像素已验）/ **Q14 比预期富**（视频 h264+h265+vp8+vp9+av1，音频 aac+opus+mp3+flac+pcm-s16）/ **Q15 浏览器侧绿**（SVG path/polygon 光栅化正常，web-renderer 侧留给 B1）。

## 6. 403 授权：写脚本/自己 curl 时必踩的坑

本机 HTTP 面有**两道独立闸**，两道都回 403，但成因完全不同：

| 层 | 谁拦 | 判据 | 403 长什么样 | 出处 |
|---|---|---|---|---|
| **层 1：桌面壳** | `DesktopWebServer.register` 包一层 `permits()` | 必须带请求头 **`x-dsh-desktop-renderer: <本代 token>`**（timingSafeEqual 校验）；或 `ordinaryBrowserEnabled=true` 且 URL 无 `__dsh*` 标记 | 纯文本 **`forbidden`** | `dsh-plugin-desktop/src/webserver.ts:29-91`、`desktop-browser-access.ts:7,77`、token 注入 `electron-shell-generation.ts:89-122` |
| **层 2：canvas-studio** | 每条路由自己再判 | loopback + `Host` 端口 == expectedPort + `hostname===127.0.0.1` + `sec-fetch-site !== cross-site`；写操作还要 `Origin` 同源 | JSON `{"error":"canvas-studio request authority rejected"}` | `canvas-studio/src/routes.ts:388-433, 667-672` |

层 1 的 token 由 `webRequest.onBeforeSendHeaders` **按 webContents 注入**，且判据是
`requestBelongsToRenderer(details, webContentsId)`：`providedIds.every(id => id === 本窗口 id)`
（`electron-shell-generation.ts:64-71`）。⇒ **隐藏渲染窗口若 webContentsId 不同，就必须靠 `borrowHostSession`
（`src/render-host/window.ts:136-149`）拿到能带 token 的 session**；借不到时日志会明说「本窗口将一律 403」（`:191`）。

**这正是"curl 拿到 403 forbidden"的解释**：从 shell 裸 curl 拿不到 token 头 ⇒ 必然 403，
**这条本身不能证明页面坏了**。要判定隐藏窗口是否真被拒，看这两条：
- `GET /canvas-studio/render-host/status`（`routes.ts:322`）里 `report` 是否为 null；
- 日志里有没有 `RenderHost 建窗 8s 后仍不可接管：从未收到任何自报`（`window.ts:313-319`），
  以及 `渲染链路的请求被本机同源闸拒绝：…`（`dispatch.ts:89-100`，**这条是 403 的直接留痕**）。

A/B 探针（`scripts/probe/render-host-session.probe.mjs`，历史报告 `/tmp/cs-session-probe/report.json`）就是照这个思路设计的：
A 组默认 session ⇒ `forbidden`；B 组借宿主 session ⇒ `render-host-ok`。

|---|---|---|
| 单任务串行 | 后端同步单队列，**并发打过去只会排队**；10 条片一律串行 | `docs/api-probe/tts-capability-2026-10-26T09-37-35/report.md` |

### 9.4 自评闭环：怎么算"完美"，不完美就说是缺什么

#### 第一步：5 条硬检查（全自动，脚本判，不看感觉）

| # | 检查 | 命令 / 判据 | 判红意味着 |
|---|---|---|---|
| H1 | 有画面（非纯色/非黑场） | 逐帧 Y 跨度（YMAX−YMIN）**≤8 记为"平帧"**，**平帧占比 >20% 才判红**（实测：真渲成片 180 帧里只有 1 帧平帧 = 0.6%，那是合法淡入；用"全片最小值"判会把它误杀）；再跑 `blackdetect` 兜纯黑 | 合成没画出来（不是"效果不好"，是"没渲"） |
| H2 | 有运动 | 首帧 vs 末帧 SSIM **< 0.98** 视为有运动；中点帧 SSIM 必须落在两者之间（防"瞬间跳变"） | 动画纯函数没接上时间轴 |
| H3 | 时长与帧率精确 | `duration ≈ durationInFrames/fps`（±1 帧）；`avg_frame_rate` 精确命中设定值 | 编码器掉帧 / 帧数算错 |
| H4 | 可复现 | 同参数渲两次，逐帧 md5 全等；做不到就退一步 `ssim ≥ 0.999` 并记 `determinism:"near"` | 有非确定性（随机数 / `Date.now()`）混进渲染 |
| H5 | 编码合规 | `codec_name=h264` + 音轨 `aac`（或按 §5.1.4 矩阵声明的 codec），容器 `mp4` | 落盘参数没走到 `high` 档 |

命令（2026-10-29 本机实测过，直接抄）：

```bash
# H1 最小 Y 跨度（纯色=0，testsrc2=189 ⇒ 阈值 8 很安全）
ffmpeg -v error -i x.mp4 -vf "signalstats,metadata=print:file=-" -f null - \
  | grep -E "signalstats.Y(MAX|MIN)=" | paste - - \
  | awk -F'[=\t]' '{d=$4-$2; if(m==""||d<m)m=d} END{print "minYSpread="m}'
ffmpeg -v error -i x.mp4 -vf "blackdetect=d=0.1:pix_th=0.02" -f null -   # 有输出=有黑场

# H2 首末帧 SSIM（读 All: 值；实测 testsrc2 首末帧 0.755）
ffmpeg -v error -i x.mp4 -vf "select='eq(n\,0)'" -frames:v 1 f000.png -y
ffmpeg -v error -i x.mp4 -vf "select='eq(n\,FRAMES-1)'" -frames:v 1 f-last.png -y
ffmpeg -v error -i f000.png -i f-last.png -lavfi "ssim=stats_file=-" -f null -

# H3/H5 流构成
ffprobe -v error -show_entries format=duration,size,bit_rate \
        -show_entries stream=codec_name,width,height,avg_frame_rate \
        -of default=nw=1 x.mp4

# H4 逐帧哈希（两次渲染各跑一遍，diff 应无输出）
ffmpeg -v error -i x.mp4 -f framemd5 - | grep -v '^#' | awk '{print $6}' > h1.txt
```

#### 第二步：0–5 分（把"完美"量化成一句话一档）

| 分 | 含义（**必须同时满足**） |
|---|---|
| 5 | 5 条硬检查全绿 **且** 抽帧目视与官方示例的"视觉意图"等价（该有的元素都在、位置对、层级对） |
| 4 | 5 条全绿；有 1 处**非关键**视觉差异（颜色略偏、边缘 1px 抖、节奏略快） |
| 3 | 5 条全绿；但有 1 处**关键**退化（元素缺失一块 / 明显糊 / 转场像硬切） |
| 2 | 出片，但视觉意图未达成（例：`blend` 无效 = 图层是纯色叠加，看不出混合） |
| 1 | 出片，但几乎空白（只有背景 / 只有字） |
| 0 | 未出片（编译失败、超时、`canRenderMediaOnWeb=false`） |

> **画面"好不好看"不参与评分**：素材只是占位（§9.3），评审不看画质/构图/美感/锐度，只看「元素是否按意图出现、动作是否按时序发生、编码与时长是否正确」。这一条把评分从"审美"拉回"能力"，也是 10 项能横向比较的前提。

#### 第三步：目视复核（唯一允许"看"的环节）

抽 3 帧拼成 `contact.png`，用视觉模型看一遍，把**看到了什么**写进 `README.md` 一句话（"中景人物立绘从左侧滑入，右下角字幕逐词高亮，末帧整体放大 8%"）。
判据：**视觉描述必须能对上 5 分档的措辞**；描述与分数矛盾时，以视觉描述为准并把该项降分、标 `needs-human`。

#### 第四步：归因（写"缺什么能力"时只能从这张表里挑一行）

| 症状 | 缺的能力 | 证据来源 | 下一步（给二期） |
|---|---|---|---|
| 整块元素不出现 | 组件不在白名单 | §5.1.1 | 换实现（如表情包 → Lottie） |
| 颜色/混合明显不对 | `mix-blend-mode`（4.0.535 无） | §5.1.3 | 升 ≥4.0.540 或下掉字段 |
| 转场像硬切 / 整层突现 | `mask-image` 只认 linear-gradient | §5.1.3（`clock`） | 改 `clip-path: polygon()` 逐帧近似 |
| 翻面变成水平压扁 | `perspective` 不支持 | §5.1.3（`flipX`） | 改 `scaleX` 近似 |
| 3D 出片但极慢 / 花屏 | WebGL 退化成 SwiftShader | Q12（GPU 通道） | 换窗口档 / 沙箱外跑 |
| 全量捕获无效（无差别） | `drawElementImage` 缺失 | Q13 | 加 switch 或放弃该项 |
| 编码器 unsupported | 编码矩阵不含该 codec | Q14 | 换 h264/aac 基线 |
| SVG 元素缺失 / 糊成一团 | SVG 元素未支持 | Q15 | shape 轨重做（二期 A1/A3） |
| 超时 / 内存爆 | 规模上限 | S1 | 降分辨率 / 拆段渲染再拼 |
| 音画不同步 / 音频是空白 | `@remotion/media` 音频未注册 / TTS 占位 | `verdict.audio` | 补音轨注册 |

> 这条规矩是整套自评的**命门**：允许说"没做到"，但不允许说"差不多"。每个 <5 分必须能追到一行具体条目。

### 10.2 Q13 HTML-in-canvas —— **默认红；加一个 flag 就绿；而且真能画出白名单外的 CSS**

三段式结论（每一段都是实测，不是读文档）：

**第一段：默认不可用。** 四档窗口（hidden / visible / throttled / 带 flag）里，前三档 `drawElementImage`、`requestPaint`、`captureElementImage` **全部 undefined**（实例与原型上都没有）。

**第二段：一个 flag 就够。** `app.commandLine.appendSwitch('enable-features','CanvasDrawElement')` 之后，三个 API 全变 `function`。**不需要装任何依赖**。

**第三段：光有 API 还画不出来，还有两个结构性约束**（浏览器报错文案是唯一可信文档，逐条试出来的）：

| 试法 | 报错 | 结论 |
|---|---|---|
| 元素与 canvas 同级挂在 body | `Only immediate children of the <canvas> element can be passed to DrawElementImage.` | 被捕获元素必须是 **`<canvas>` 自己的直接子元素**（canvas 的 fallback content） |
| 元素变成 canvas 子元素 | `DrawElementImage requires the canvas to have the layoutsubtree attribute.` | canvas 必须带 **`layoutsubtree`** 属性 |
| 加 `layoutsubtree` 后再画 | 无报错 | **`drawElementImage(box,0,0,200,120)` + `requestPaint()` 都返回 ok** |

**最终像素证据**（两次独立运行完全一致）：把 `conic-gradient(红,绿,蓝,红)` 的 div 画进 200×120 的 canvas ⇒ **`nonEmptyPixels = 24000 / 24000`、`colorBuckets = 525`**。

而 `conic-gradient` 正好是 §5.1.2 里明确不支持的 CSS（`clock` 转场就栽在它上面）。⇒ **"抬天花板"这件事是真的，不是理论**：只要走 html-in-canvas，整张 CSS 黑名单一次性作废。

⚠️ 一个不稳定观察：带这个 flag 时 `loadURL` 偶发 `ERR_FAILED (-2)`（**2/9 次**，不带 flag 时 4/4 正常）。重试即可，但产品化前要评估——这可能是 flag 的实验性质量，也可能是我们探针页的加载竞态（n 太小，不下定论，B1 复现再看）。

### 10.3 依赖：项目里确实一个都没有，但"要不要集成"是另一个问题

三处 `node_modules`（根 / `canvas-studio` / `dsh-plugin-desktop`）逐个核过，**9 个候选包全部 NONE**（只有 `@remotion/paths` 有）。

先说清一件事：**"测试要装"和"产品要集成"是两回事。**
- 测试侧：全部装在独立子工程（D3），装坏了删目录，主包 lockfile 一行不动；
- 产品侧：看"每 MB 换多少能力"，不看"测试跑没跑通"。

逐包结论：

| 包 | 测试要不要 | 产品要不要 | 理由 |
|---|---|---|---|
| `three` + `@react-three/fiber` + `@remotion/three` | 要（#1 的 L0） | **暂不** | 漫剧/短剧主线是"图+字+转场+配音"，3D 的收益集中在片头/产品片；成本约 +1MB bundle 级别，且 R3F 与 React 19 的 peer 范围要先核。**先把能力证出来，等有真实片型需求再进** |
| `@remotion/skia` + `@shopify/react-native-skia` | **可选**（只做 4s 冒烟） | **暂不** | ⚠️ 这里原写"不要"，理由是我们以为有 React 19 冲突——**实测是 React 18.3.1，冲突不存在**（§11.2 R7）。真实成本 = 解包 9.6MB + CanvasKit wasm 随包；而我们真正缺的是"磨砂/噪点/光漏"，`filter` + 预渲染贴图能到 80% ⇒ **先做近似（§12.1 #2），Skia 冒烟可选、排最后** |

### 13.2 顺带证实/推翻的 4 件事

1. **1080p30 是便宜的**：12–13 ms/帧 ⇒ 一条 10s 片 3.6s 渲完。之前 §10.6 的"74 ms/帧"是 orbit 那种每帧几何重算的最坏情况，不代表 1080p 普遍成本。
2. **`<Video>` / `<Audio>`（`@remotion/media`）在 1080p + 5 段 `trimBefore` + `playbackRate` 0.5/1/1.5/2 下全部正常**，独立音轨 + 音量回调（ducking）也进了成片（有 aac 流且 md5 稳定）。

### 13.5 结论：这条路线可行，但有 3 个前提必须改

**可行**（依据是 13.1 的实测，不是判断）：

- 单条增量成本 ≈ **写 60–120 行 TSX + 20s 渲染**，10 条共用一个 bundle；
- 5 条硬检查纯机械，**不依赖执行者"眼力"**，所以不同会话跑出来的结论可比；
- 产物结构固定（`capNN.mp4` + `frames/contact.png` + `verdict.json` + `README.md` + `probe.mjs` + `source.json`），可逐个抽查。

**三个前提（不改就会翻车）**：

1. **一次只加一条，跑完立刻落 verdict**，禁止"写完 10 条再一起跑"。理由：**R3（clock/flipX）还没验**，其余 6 条的实现方式彼此独立，10 条一起写等于把 10 个未知叠在一起，红了你分不清是能力缺失还是自己写错。（R1 / R4 已在 §13.0 验绿，不再是未知。）
2. **C 级两项先过环境门**：#3 必须 `--flags=CanvasDrawElement`（且带 flag 时 `loadURL` 有约 2/9 的 `ERR_FAILED`，要重试——**这条已跑通，照抄即可**）；#1 必须先 `npm i --legacy-peer-deps --no-package-lock` 装 `three` + `react-three/fiber@^8.18`（§11.3 G1/G2）。
3. **先用素材索引挑素材，再写 composition**。样例里我踩过一次：trim 落在源片 21–24s 的暗场，contact sheet 那格几乎全黑，**看起来像渲染失败，其实是素材**。新会话请先跑一遍 `asset-index`（路径 / 宽高 / 时长 / 能否 `ffprobe` / 首中末帧亮度），从"有内容"的位置取 trim。
