# 复盘方法论（事故分析的纪律）

> 起因：2026-10-24 智能手表成片事故的复盘写了 **4 版**才收敛 —— v1 统计错（基于截断日志）、
> v2 把三个未证假设写成 P0 根因、v3 才纠数、v4 用独立实验台把三个 P0 全部证伪。
> 真正的代价不是"没人聪明"，而是**流程允许把猜测当结论**。以下四条是硬规则。

---

## 规则 1：每条结论必须标证据等级

| 等级 | 含义 | 可以拿它做什么 |
|---|---|---|
| **A** | 亲手复现（同条件跑出/跑不掉） | 可以直接当结论写进计划 |
| **B** | 日志/产物直证（原文可引） | 可以当结论，但要写清取证命令 |
| **C** | 源码直证（读实现推出来的） | 可以当结论，标注"实现层面" |
| **D** | 推断 / 类比 / 经验 | **只能当待验证假设**，不得进 P0 列表 |

反面教材：v2 把"素材预取死锁"（D 级）写成 P0，导致后续半天排错方向全歪。

## 规则 2：没有宿主日志，不下根因

客户端 `ctx.logger.warn` 不落文件日志，只有 Host 侧（route / registry / error-system）会写
`logs/dsh-*.log`。所以：

- 判"某接口有没有被调用"→ 回到**文件系统副作用**（目录是否被建）或客户端 devtools；
- 判"是不是超时"→ 必须先看到 `CS-RENDER-TIMEOUT` 那条日志与它的**次数**；
- 日志的行数要和会话里的失败次数**对上**（本次 39 = 39 才对上，这是最便宜的自证）。

## 规则 3：工具自报字段先做自洽校验

只要一个工具返回两个"应该互相关联"的字段，就先验它们是否互相矛盾：

- `warm=false` 恒不变 ⇒ 这个字段没在测东西（本次 `warm` 就是硬编码 false）；
- `encodeMs` 在一份 60s 的片子里报 20–34s，而 `msPerFrame × frames` 只有 1–2s ⇒ 两者必有一个在撒谎；
- 「总耗时 30s」而「每帧 50ms × 1800 帧 = 90s」⇒ 要么帧数错、要么耗时错。

**矛盾即不可信**。先别用它做决策，去看实现。

## 规则 4：每轮复盘必须有「被证伪的假设」一节

只写"我们做了什么"的复盘，等于没验证。合格的复盘要明确列出：

1. 曾经**以为**是什么（原话，别事后美化）；
2. 用什么实验/证据推翻的；
3. 推翻后，原计划里哪几条要跟着改。

本次被证伪的四条：素材预取死锁 / 窗口可见性节流 / 每单冷启动 40–60s / 中断后性能劣化 ——
四条都是 v2 的 P0 或 P1，实测全部不成立（见 `docs/archive/session-v4/session-v4-复盘-v4-实测结案.md`，2026-10-28 由 `docs/` 顶层迁入 `docs/archive/session-v4/`）。

## 附：取证最小闭环

```bash
# 1) 次数对不对
grep -c "CS-RENDER-TIMEOUT" ~/Library/Application\ Support/VideoBuddy/logs/dsh-$(date +%F).log
# 2) 关键分支有没有发生（本次：0 = 从未改派）
grep -c "滞留渲染工单" ~/Library/Application\ Support/VideoBuddy/logs/dsh-$(date +%F).log
# 3) 资源生命周期
grep -E "RenderHost (已创建|销毁)" ~/Library/Application\ Support/VideoBuddy/logs/dsh-$(date +%F).log
# 4) 重启次数
grep -c "^--- dsh-plugin-desktop" ~/Library/Application\ Support/VideoBuddy/logs/dsh-$(date +%F).log
```

> ⚠️ BSD grep 不认 `\|`（basic 模式），一律用 `grep -E`，否则零命中会被读成"没发生"。
