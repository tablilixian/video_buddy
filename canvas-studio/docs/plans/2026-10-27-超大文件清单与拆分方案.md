# 超大文件清单与拆分方案（2026-10-27）

> **定位**：代码侧「可维护性清单」—— 找出已经大到不好维护的文件，说清用途、结构、为什么难改，以及怎么拆。
> **配套**：文档与资产的位置治理见 [文档与散落资产归位方案](./2026-10-27-文档与散落资产归位方案.md)。
> **状态**：📋 清单（未动代码，无方案落地）。

## 0. 结论摘要

这个仓库的常态是「一个小模块一件事」：`canvas-studio/src/` 下有 **150+ 个 4–16KB 的单职责文件**。所以偏离这条基线的文件非常好认。

**真正的病不是「文件长」，是「一个函数吃掉整个文件」**：6 个 P0 文件里有 5 个是单函数 2,400–2,750 行，`styles.ts` 更极端 —— 整个文件就是一个模板字面量。

| 级别 | 文件数 | 合计行数 | 共同特征 |
| --- | --- | --- | --- |
| P0（单函数 >2,400 行） | 6 | 28,346 | 无法分段 review、无法并行改动、冲突恒定集中 |
| P1（1,000–2,100 行，函数尚可分） | 15 | ~21,000 | 定位成本高，但职责还算清楚 |
| 数据类（不建议拆） | 2 | 2,941 | 契约/码表，拆开反而难查 |

## 1. 尺子与统计方法

两个独立指标，缺一不可：

1. **文件行数** —— 反映「一次读不完 / git blame 稀碎」。
2. **最长函数行数** —— 反映「真正无法维护的单元」。一个 3,000 行文件里 30 个 100 行函数，和一个 3,000 行文件里 1 个 2,800 行函数，维护难度差一个量级。

```sh
# 文件行数
git ls-files 'canvas-studio/src/*' | xargs wc -l | sort -rn | head -30

# 最长函数（按顶层 function/组件声明切段）
python3 - <<'PY'
import re
f='canvas-studio/src/client/StudioFrame.tsx'
lines=open(f).read().split('\n')
starts=[(i,l) for i,l in enumerate(lines)
        if re.match(r'^(export )?(async )?function |^export const [A-Z]\w* = (forwardRef|\()', l)]
spans=[(starts[k+1][0] if k+1<len(starts) else len(lines))-i for k,(i,_) in enumerate(starts)]
print(f'{f}: {len(lines)} 行，最长函数 {max(spans)} 行')
PY

# 有多少测试按「源码文本」断言（决定拆分阻力的关键指标）
python3 - <<'PY'
import glob
files=sorted(glob.glob('canvas-studio/tests/*.mjs'))
for p in ['src/client/styles.ts','src/host-tools.ts','src/routes.ts',
          'src/generate.ts','src/client/StudioFrame.tsx','src/client/index.ts']:
    n=sum(p in open(f,encoding='utf8',errors='ignore').read() for f in files)
    print(f'{n:3d} 个测试读 {p}')
PY
```

## 3. P0 逐文件：为什么难维护 / 怎么拆

### 3.1 `host-tools.ts` —— 32 个工具挤在一个闭包里

**为什么难维护**

- 一个函数 2,437 行，任何工具改动都落在同一个函数体内 → `git blame` 无意义，冲突恒定集中在这一处。
- 32 个工具共享闭包里的 `registry` / `portOf` / `library`，**隐式依赖无法从签名看出**。
- 工具描述（中文长串，平均每个工具 1.5–3KB）与执行逻辑混在一起 —— `render_composition` 单块 251 行、`write_storyboard` 252 行、`inspect_image` 207 行，读一个工具要跨两个屏幕。
- 但**不能简单按文件切**：`withStoryboardGate` 是「故事板已落地」的**单一放行点**（L4394 起），`tests/storyboard-gate.test.mjs` 与 `tests/tool-registry.test.mjs` 钉死了「工具总数 + 名单」两件事。

**拆法（模式 C：父文件保留入口，子模块各管一域）**

```
src/host-tools/
├── index.ts            # 组装数组 + withStoryboardGate 唯一放行点（保持不变）
├── shared.ts           # resolveProjectId / renderResult / format* / clipCell 等 30 个 helper
├── image.ts            # image_generate / _withtxt / image_fix / character_* / look_card / qc_shot
├── video.ts            # video_generate / video_composite / video_rerender / image2vl / video2vl
├── storyboard.ts       # write_storyboard / list_shots / adopt_canvas_as_storyboard / submit_keyframes_for_approval
├── audio.ts            # music_generation / tts_voiceover / tts_narration / cut_audio
├── library.ts          # list_library_assets / add_to_library / upload_image / list_references
├── render.ts           # compose_video / render_composition / scaffold_manifest
└── inspect.ts          # inspect_image / layout_table / ask_user_choice / write_script
```

- **阻力最低**：12 个测试读 `src/host-tools.ts` 源码，但绝大多数断言的是「某个字符串/某段逻辑存在」，父文件保留 `export function createStudioTools` 后**测试零改动**。
- 顺序建议：**先搬 `inspect.ts`（3 个工具，最独立）验证模式**，再按域批量搬。

### 3.2 `routes.ts` —— 41 条路由塞进一个注册函数

**为什么难维护**

- `registerStudioRoutes` 2,834 行，39 个 `ROUTE_*` 常量与实现散落，读一条路由要先滚 2,000 行。
- 所有 handler 共享 `ctx` + `registry` + `library` + `port` 的**隐式闭包**；新增路由极易漏掉鉴权/loopback 校验这类横切逻辑。
- 里面有 8 条 Remotion 路由 + 3 条 render-host 路由（REQ-035 后加的），**新功能最后都往这个文件里塞**，属于结构性增长。

**拆法（按域切，`ctx` 显式传递）**

```
src/routes/
├── index.ts            # registerStudioRoutes：只做 dispatch + 横切装配
├── projects.ts         # projects / draft-landing / resolve-refs / groups / workflow
├── canvas.ts           # canvas / storyboard / layout / promote
├── assets.ts           # assets / library / asset-gc / asset-history / style-demos
├── skills.ts           # skills / active-skills / skill import / test-report
├── media.ts            # upload* / waveform / split-video / compose
├── remotion.ts         # remotion/{pending,jobs,progress,commit,cancel,sample,grain,fonts}
├── render-host.ts      # render-host / -js / -status
└── auth.ts             # auth + login 页
```

- **关键约束**：12 个测试读 `src/routes.ts` 源码做静态断言（如 `atomic-json-write.test.mjs:129` 断言 `['src/routes.ts', 1]` 的原子写次数）。父文件保留同名导出后，这些断言**仍然成立**；但**原子写计数这类「按文件数」的断言会因拆分而失效** → 必须逐个核对，必要时把断言路径改成目录。
- 建议先拆 `remotion.ts`（8 条路由，最新、最独立）。

### 3.3 `StudioFrame.tsx` —— 2,757 行的单组件

**为什么难维护**

- **22 个测试按源码文本断言它**（全仓最多），说明它就是 UI 契约的事实载体 —— 但也意味着任何结构性改动都可能一次红一片。
- 单组件里同时持有：布局三栏状态、项目列表、画布交互回调、对话流、设置抽屉、登录态、余额卡（`L599` 起两段 `// ──` 注释是仅有的分节标记）。
- 状态耦合是真难点，不是 JSX 长度：`props` 一个 `PropsRuntime<'root'>`，内部几十个 `useState` / `useEffect` 互相引用。

**拆法（两步走，不要一次到位）**

1. **纯展示外提**：`TopBar` / `LeftRail` / `CanvasPane` / `ChatPane` / `SettingsDrawer` / `LoginOverlay`，只搬 JSX + 收窄 props，`StudioFrame` 仍是唯一状态所有者。
2. **抽 hooks**：`useStudioLayout`（三栏开合/宽度）、`useStudioSelection`（选中/多选/焦点）、`useStudioChat`（对话事件订阅）—— 这一步才动状态，风险最高，放最后。

> 该文件与 `client/index.ts` 是**同一层的两半**（组件 ↔ 装配），建议同一批做，否则中间态很难自洽。

### 3.4 `client/index.ts` —— 2,720 行的装配函数

**为什么难维护**

- `studioClient()` 里混了 5 类职责：slot 注册、反射/服务接线（`ctx.reflect.provide('layout')`）、lobby 认领流程（含多次重试与 workspace 重建）、附件分流、事件订阅。
- lobby 认领那段（L830–L1100）本质是一个**带 5 个失败分支的状态机**，埋在装配函数里既不好读也不好测。
- 与 `StudioFrame` 共享 `project-store` 单例（注释里明确写了「不能把 store 交给框架，会创建两个实例」）—— 拆分时必须保住这条不变量。

**拆法**

```
src/client/
├── index.ts            # apply() + studioClient()：只做编排（保持导出名）
├── registration/
│   ├── slots.ts        # 主面板 / 侧栏 / 设置页注册
│   ├── services.ts     # layout / store / sessions 反射接线 + 自检日志
│   └── events.ts       # uiConversation / capture / 附件分流订阅
└── lobby-claim.ts      # 认领状态机（纯逻辑部分可单测）
```

### 3.5 `styles.ts` —— 10,730 行的单个模板字面量

**为什么难维护**

- 整个文件 = `const STUDIO_STYLES = \`` + 10,700 行 CSS + 反引号结尾。**注释里写一个反引号就会撕裂模板字符串**（`tests/visual-tokens.test.mjs` 头注释记录了两次真实事故）。
- 1,110 个唯一类名、11 个 `@keyframes`、13 个 `@media`，且**层叠顺序敏感**：文件里明确写着「`.csFrame[data-chat="strip"]` 与 `.csFrame[data-mode="lobby"]` 特异性相同，平手靠源码顺序取胜」。
- 拆分阻力全仓最高：**18 个测试按路径读 `src/client/styles.ts` 源码**，且 `scripts/preview-tokens.mjs:189` 用字符串标记 `const STUDIO_STYLES = \`` **解析**它，标记一变预览台全废。

**拆法（唯一可行：保留同名拼接入口）**

```
src/client/styles/
├── index.ts        # 按固定顺序 join 片段，导出 STUDIO_STYLES（保持 `const STUDIO_STYLES = ` 字面形态与路径）
├── shell.ts        # .csFrame / 三栏 / lobby / 收起态（顺序敏感区，保持原序）
├── canvas.ts       # 画布 / 网格 / 节点 / 连线
├── node.ts         # 节点卡内部 / 输入卡 / 时间轴
├── chat.ts         # 对话流 / 工具行 / 审批条
├── settings.ts     # 设置页 / 技能市场 / 登录
└── motion.ts       # @keyframes + 动效三语义
```

**先决条件**：`scripts/preview-tokens.mjs` 的解析器要改成「读目录后按顺序拼接」，`visual-tokens.test.mjs` 的 4 条静态守卫同步改为读拼接结果。**这一步必须先于拆分落地**，否则预览台和 18 个测试同时红。

### 3.6 `generate.ts` —— 66 个 export 的「薄客户端」变厚了

**为什么难维护**

- 名义上是「Drama 后端客户端」，实际塞进了 5 层职责：HTTP 调用、超时/重试、健康探测与队列深度、上传下载（含 SSRF 校验 `isBlockedIp`）、资产落库与引用清单（`promoteAssetFile` / `healReferenceFilename` / `pruneReferenceManifest`）。
- 66 个 export 意味着它已经变成「什么都往外给」的公用抽屉。
- `generateAsset()` 616 行是唯一真正的编排函数，其余是散装能力。

**拆法（三层 + barrel 过渡）**

```
src/drama/
├── client.ts       # dramaPost / callDrama / describeError / 超时与重试
├── health.ts       # ensureDramaReachable / queueDepthOf / 健康缓存
├── transfer.ts     # downloadBytes / assertSafeDownloadUrl / uploadBytesToDrama / isBlockedIp
└── index.ts        # 原 generate.ts 保留为 barrel（re-export），调用方零改动
src/assets/
└── persist.ts      # saveLocalAsset* / promoteAssetFile / healReferenceFilename / pruneReferenceManifest
```

- 保留 `src/generate.ts` 作为 barrel 是关键：11 个测试读它源码，直接删会红。

## 4. 拆分阻力矩阵（决定顺序的唯一依据）

| 文件 | 读源码的测试数 | 外部脚本解析 | 拆后能否「零测试改动」 | 建议模式 |
| --- | --- | --- | --- | --- |
| `host-tools.ts` | 12 | — | ✅ 能（保留 `createStudioTools` 导出） | 模式 C |
| `routes.ts` | 12 | — | ⚠️ 部分（原子写计数类断言需改路径） | 模式 C + 逐条核对 |
| `generate.ts` | 11 | — | ✅ 能（保留 barrel） | 模式 A |
| `client/index.ts` | 12 | — | ✅ 能（保留 `apply` / 导出名） | 模式 C |
| `StudioFrame.tsx` | **22** | — | ✅ 能（父组件保留） | 两步走 |
| `styles.ts` | **18** | `preview-tokens.mjs:189` 解析字面量 | ❌ 不能（须先改解析器） | 模式 A + 前置改造 |

**三种模式**：

- **A｜同名 barrel**：新目录承载实现，原路径文件改为 `export * from './xxx/index.js'`（或拼接常量）。测试与脚本零改动。
- **B｜直接改测试路径**：把 18–22 个测试改一遍。不推荐 —— 收益只是好看，代价是 20+ 处改动面。
- **C｜父文件保留入口，子模块分域**：父文件保留组装职责（如 `createStudioTools` 的数组与门禁），域逻辑下沉。最适合「有单一放行点」的文件。

## 7. 落地节奏建议

| 阶段 | 内容 | 为什么这个顺序 |
| --- | --- | --- |
| 0 | 立「文件大小守卫」测试（单文件 ≤1,200 行、单函数 ≤600 行，超阈白名单里只有现存 6 个） | 不立闸，拆完必回涨 |
| 1 | `host-tools.ts` 目录化（先搬 `inspect.ts` 验证模式） | 阻力最低、收益最大，作为拆分模式打样 |

| 4 | `generate.ts` 三层 + barrel | 独立于 UI，随时可做 |
| 5 | `styles.ts`（先改 `preview-tokens.mjs` 解析器 + 守卫） | 阻力最高，放最后 |

**每阶段一个 PR，一次只搬一个域。** 上一阶段 gate 全绿再开下一个。

## 8. 验收

拆分属于「行为不变」改造，验收标准是**零行为变化**：

```sh
# 包内四连（顺序不变，见 canvas-studio/AGENTS.md）
corepack yarn typecheck && corepack yarn build && corepack yarn verify:loader && corepack yarn test:smoke

# 根门禁
corepack yarn check
```

额外要求：

1. `tests/baseline-red.json` 必须维持空数组（当前已清零），任何新增红都视为回归；
2. `tests/tool-registry.test.mjs` 的工具总数/名单不变；
3. `tests/visual-tokens.test.mjs` 的 4 条静态守卫（反引号 / 幽灵令牌 / 空转令牌棘轮 / 动效语义）必须继续生效 —— **拆分不许让守卫失效**；
4. 每阶段结束后，本清单对应行标注「已拆」，并在 `STATUS.md §8` 追加一行变更记录（按 `DEV-WORKFLOW.md` 的收尾四步）。
