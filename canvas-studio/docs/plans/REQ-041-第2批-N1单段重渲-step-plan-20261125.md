## 1. 目标与边界

目标：分镜卡上「引用到对话 + 一句人话 → 只改这一段 → 这一段换新画面」形成最小闭环（需求 §9.4：1+2 批 = 最小可用闭环）。

非目标：结构性修改（D3）、替代整片出片（R6）、审阅状态（R5）、新 surface。

承诺口径按 R3 分三层，别混：数据层与呈现层是硬承诺（别的屏 spec 不变、卡上 mp4 不变）；渲染层是软承诺（内容改只脏本段；时长改会因帧窗平移重渲后续段）。用户遇到「拆成两屏」必须明示「要重排段表，之前看过的画面都会变」。

## 2. 触发形态：新宿主工具 `rerender_segment`

**职责单一**：它只做「把当前 manifest 重渲一遍并发布段产物」，**不改 spec**。改 spec 是 `patch_spec_section(shotNodeId)` 的活（`host-tools.ts:5409`，已支持 `shotNodeId` + `writeTo` 重编 manifest）。agent 处理一句意见时按序调两个工具；用户只是想重看某屏时直接调本工具。

- **注册位置**：`src/host-tools.ts`，紧随 `patch_spec_section` 之后。
- **入参**：`{ projectId?, shotNodeId?, segmentId? , quality? }`。`shotNodeId` / `segmentId` 二选一，同时给必须拒收（与 `patch_spec_section` 同一纪律）。定位复用已 import 的 `resolveSegmentIdFromNode`（`host-tools.ts:61`），**不造第二套分镜卡判据**。
- **结构性意见拒绝**：工具的 description 明写「拆屏 / 增删屏 / 换全片风格不调本工具，须重排段表，之前看过的画面都会变」。工具层能机械拒收的只有非法定位参数；自然语言里的结构性意图由 agent 按 description 拒绝——这是**能力边界**，别假装工具能判语义。
- **不新建 HTTP 路由、不新建 surface。**

## 3. 实现落点（行号基于 `d209cfa02b`）

1. **渲染复用**：`runShotRender(manifest, deps)`（`shot-render.ts:252`）。deps 构造必须与 `render_composition`（`host-tools.ts:3761`）**同源** —— 抽公共 `buildShotRenderDeps(...)`，两处调同一函数。**不复制 40 行注入代码**：复制必然在下次改 ffmpeg / 预览闸 / 缓存目录时漂移。
2. **manifest 来源**：`build/manifest.json`（`patch_spec_section` 的 `writeTo` 写这里）；缺失 / 坏 JSON 显式报错，不静默渲一份旧片。
3. **强制发段**：显式传 `publishSegments: true`，与第 1 批 draft 开关口径一致。
4. **回执 schema**：`resultSchema` 是 `additionalProperties: false`（`host-tools.ts:251` 注释：漏声明字段会被**静默剥掉**）。新字段 `projectId` / `ref` / `url` / `v` / `segments[]` 必须逐个显式声明，并保留 `text` 给 agent 读。
5. **客户端刷新**：`asset-capture.ts:443` 现判据是 `state.toolName === 'render_composition'`，新工具不会触发。改成常量集合 `RENDER_SETTLED_TOOLS = new Set(['render_composition', 'rerender_segment'])`；`client/index.ts:2283` 已发 `notifySegmentMediaRefresh(projectId)`，**不用改**。
6. **零写入承诺**：工具不写 `canvas.json`、不建画布节点、不进 undo；只写 `deliver/` / `assets/` / `build/manifest.json`。
7. **缓存**：段副本确定性名覆盖写；清单 `?v=mtimeMs` 自动换新版。只有目标段文件的 mtime 变，其余卡 URL 与 `v` 不变。

## 4. 耗时：先量再优化（§十 5）

现在直接复用 `runShotRender` 会连 concat 整片 + saveMerged + probe 一起做，端到端不会随单屏时长线性下降，R4 的时间判据暂时不满足。需求已定「实测前不做设计决策」：

- **第一步按本 plan 实现**，用探针量「说意见 → 卡上换画面」墙钟时间（含宿主是否每次重新 bundle）。
- **门槛**：若 ≈ 单屏渲染时间（≤ 2×）⇒ 到此为止；若明显被整片拼接拖住 ⇒ 再抽轻量 `renderSingleSegment`，共用 `planShotRender` / `getDirtySegments` / `publishSegmentArtifacts`，跳过 concat / saveMerged / probe，并补「单段产物与整片对应段逐字节一致」的同源断言。
- 不预先为没量过的数字加复杂度。
