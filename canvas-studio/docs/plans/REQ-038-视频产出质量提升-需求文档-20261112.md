## 2. 差距定位：为什么不是"CSR 能力差"

### 2.1 能力集与够用性

CSR 捕获路径**已能**表达：图层、仿射变换（x/y/scale/rotate/opacity/blur）、文本排版、位图/视频、音频与词级时间轴、group 子树、逐段关键帧链。

本次 1800 帧成片里，Ken Burns 推镜、group 汇聚、词级字幕、49 个 SFX 钉帧、12 镜头硬切节奏——**全部一次渲对**。

CSR 捕获路径**不能**表达（已被降级或绕开）：`backdrop-filter`、`mix-blend-mode`、CSS 多段渐变、逐帧 `perspective`、`letter-spacing`、圆角/描边、灰度、逐镜头暗角强度。

**结论**：能力集足够表达 90% 的动态图形；缺的是把 CSS 视觉词汇映射进来的那一层。

### 2.2 翻译链路的五个环节（缺口定位）

```
创意 brief
  ↓ ① 体裁骨架      src/remotion/recipes.ts 的 RECIPES（3 条）      ✅ 有，但缺「产品宣传片」体裁
  ↓ ② 镜头卡库      skills/code-driven-explainer/references/shot-cards.md（24 张）  ✅ 有，但全是 explainer 体裁
  ↓ ③ 内容规格      文案/数据/素材/相机/节奏（本次为手搓 lib/spec.mjs）  ❌ 缺 schema 化
  ↓ ④ 素材供给      「必须真 vs 可通用」无契约（本次 54/157/74）      ❌ 缺（本文 RQ-21）
  ↓ ⑤ manifest 生成  脚本生成（确定性）                              ✅ 有（本次 build-manifest.mjs 1187 行）
  ↓ ⑥ 像素对拍验收  落点/亮度/PSNR                                ❌ 缺，且现有工具只在 /tmp
  ↑ ★ 卡 → 配方 的可执行绑定                                       ❌ 缺（本文 RQ-10）
```

**★ 号那一环是断的**，证据：

- `src/remotion/recipes.ts:64-100`：每个段位都带 `card` 字段，取值 `'A2 标题逐字'` / `'B1 数据卡'` / `'C2 左右分栏'` / `'E1 素材推拉'` / `'A5 收尾落版'`；
- `skills/code-driven-explainer/references/shot-cards.md`：**这 5 个卡 id 全部存在**，且每张卡标了「用什么 DSL 原语」+「要什么素材」；
- 而 `src/remotion/recipes.ts:128` `planRecipe()` **不读 `card`**，只吐「每段一张文字卡」的占位轨（`bg` + `seg-*`）。

> **绑定键早就留好了，只是没人接。** 这就是"产品自己只产出 5.8KB / 16 轨"的直接原因——不是限制，是配方层空着。

### 2.3 「大 manifest 是能力密度，不是负担」

产品侧硬上限（已核实）：

| 上限 | 值 | 出处 | 与 200KB 的关系 |
| --- | --- | --- | --- |
| manifest 文件大小 | **8MB** | `src/host-tools.ts:3773` `MAX_MANIFEST_BYTES` | 200KB 只占 **2.5%** |
| manifest 内联提交体 | 16MB | `src/routes.ts:368` `MAX_BODY_BYTES` | — |
| 画布节点数 | 2000 | `src/routes.ts:373` `MAX_CANVAS_NODES` | 与 manifest 轨数不同域 |
| manifest 轨数 | **无上限** | `src/remotion/manifest.ts` 无 `MAX_TRACKS` | — |

密度对比（E10）：

| 产物 | 体积 | 轨 | 时长 | 密度 |
| --- | --- | --- | --- | --- |
| 产品自身 `sample-manifest.json` | 5.8KB | 16 | 13s | **0.04 轨/秒** |
| 本次 `playsout-manifest.json` | 134.4KB | 265 | 60s | **0.15 轨/秒** |

**论证**：如果产品自己生成同等观感、同时长的片子，产出的 JSON 会**比 134KB 还大**——因为我们的原语少（25 条缺口），同样观感要靠更多条轨去凑（Ken Burns 需 group+animate+asset；logo 墙 9 个元素即 9 个 group）。

> **所以「大 JSON」不是产品做不到，而是产品还没走到那一步。** JSON 体积应当被当作**能力密度的度量指标**，而不是负担（见 RQ-19）。

#### 2.3.1 这条论证的前提，以及它为什么必须被打破（2026-11-12 晚补）

上段论证成立的前提是「**原语不补**」：一个元素一条轨，于是同观感必然轨多、JSON 必然大。但实测的 265 轨构成显示，**这个前提是可以被打破的**：

| 类型 | 轨数 | 占比 | 性质 |
| --- | --- | --- | --- |
| `image`（素材摆放） | **129** | 48.7% | **纯摆放**（logo 墙 21 + 页面截图 16 + 海报/广告/媒体图 …） |
| `shape` | 59 | 22.3% | 几何 + 底板 |
| `textCard` | 51 | 19.2% | 文字 |
| `group` | 17 | 6.4% | 容器（Ken Burns 推镜） |
| `caption` | 9 | 3.4% | 字幕 |

**近一半的轨是「同一个原语反复摆放同构元素」** —— logo 墙 21 个 logo 是 21 条轨，页面截图墙 16 张是 16 条轨。这类内容**天然该由一个聚合型原语承担**（`logoWall` / `assetGrid` / `chipRow` / `codePanel`），而不是 N 条轨手工拼。

> **因此新增 RQ-22（聚合型原语）**：它既是「手写轨数」判据能成立的**唯一前提**，也是让「产品自产 JSON 小于 134KB」从**口号变成指标**的唯一路径。RQ-22 落地前，§5 的轨数目标只作参考值不作验收项；RQ-22 落地后才按 RQ-22 的实测重定。

### 2.4 别人的模板怎么用上：三层拆解

| 层 | 内容 | 能否直接用 |
| --- | --- | --- |
| **风格层** | 主题 token（`C.bg #07070F` / `C.text #ECECF2` / `C.peri #98A3FF` / `C.mute #6E6E86`）、字体族、运动语言（缓动、错峰时长） | ✅ 直接抄进主题配方——与渲染器无关 |
| **骨架层** | 镜头顺序、时长配比、节奏（logo 墙 → 字卡 → 推镜 → 数据 → 代码 → 汇聚 → 节点 → 目录 → 人群 → 落版） | ✅ 抄成体裁配方——纯时间轴，与原语无关 |
| **版式层** | 每镜头的具体摆法（哪张图、什么位置、推镜参数、CSS 渐变） | ❌ **必须用我们的原语重写**——依赖对方 CSS/Remotion |

playsout 之所以能被逐条翻译，是因为**我们恰好拿到了第三层**。若只有成片视频，第三层需靠视觉反推（场景切点检测 + 抽帧 + 版式聚类），精度会掉，**但第一、二层依然可用**。

> **关键区分：用模板 ≠ 复刻模板。**
> 复刻 = 拿到第三层源码 → 逐条翻译 → 像素级等价（本次，成本高、不可规模化）。
> 用模板 = 拿到第一、二层 → 换成**我们的**版式配方与内容 → 生成一条**新的**同风格片子（可规模化，是产品该有的形态）。

### R0 · 传输层（阻断级）

#### RQ-01（P0 · 阻断）渲染回执的元数据通道从 URL 查询串改为请求体

- **现象**：整片 60s / 265 轨的 manifest 在真机上**永远渲不出 mp4** —— 渲染本身 55s 全部跑完、进度 100%，但**回执被服务器拒收**，mp4 从未落盘。真机日志回执：`Error: 服务响应异常（HTTP 431），请稍后重试。工单：隐藏渲染窗口已渲染 55s，进度 100%`。
- **证据**：
  - `src/client/api.ts:1226-1230` —— `query.set('warnings', JSON.stringify([...warnings]))` + `query.set('metrics', JSON.stringify(report))` → `fetch('/canvas-studio/remotion/commit?' + query)`；
  - `src/routes.ts:3339-3340` —— `asRenderWarnings(requestUrl.searchParams.get('warnings'))` / `asRenderReport(requestUrl.searchParams.get('metrics'))`；成片字节走 body（`MAX_RENDER_BODY_BYTES = 256MB`，`src/routes.ts:372`）；
  - `@deepseek-ai/dsh-host-webserver/lib/index.js:412` —— `this.server = createServer(listener)`，**未传 `maxHeaderSize`** ⇒ Node 默认 **16,384B**；
  - 实测（E1/E2）：整片 query **16,239B**，越线 ≈ **287B**；用同样「裸 createServer」的 Node server 复现 ⇒ 连接被 EPIPE 断掉（Node 判定 header 超限即回 431 并断链）；
  - 反证：裁到 **40 轨**的版本**渲染成功**（52s / 1.2MB）⇒ 与 manifest 内容无关，与**回执体积**有关。
- **需求陈述**：回执元数据不得再进 URL。成片字节已在 body 内，故 body 需承载「元数据 + 字节」两段：建议用**长度前缀帧**（magic 头 + 4B 长度 + JSON + 字节），服务端按 magic 判定新老格式（老客户端的裸 mp4 body 继续兼容）。
- **验收标准**：
  1. 整片 265 轨 manifest 在真机一次 `render_composition` 出 mp4，**无 431**，且 `report.textFit` 完整回传（60 条一字不丢）；
  2. 老格式 body（裸 mp4）仍被正确接收（回归用例）；
  3. 回执体积不再受 Node header 上限约束（构造 200KB+ 元数据用例仍成功）。
- **成本**：小（客户端 + 路由各一处）｜**依赖**：无｜**风险**：低（服务端保留双格式兼容）

### R1 · 表达层：效果原语

> 这一组是"能力密度"的直接来源。**补完之后，本次这类宣传片不再需要任何预生成 PNG**（除玻璃拟态外），且 manifest 体积预计下降 30%+（同样画面用更少轨表达）。
>
> **本组另有两条补充（见 §3 R6 补充组）**：**RQ-22 聚合型原语**（把 N 个同构元素压成 1 轨 —— 是 RQ-11 轨数判据的前提）与 **RQ-23 多关键帧相机**（2D 轻量版，零新依赖）。

#### RQ-02（P0 · 极小）`textCard` 支持 `letterSpacing`

- **证据**：渲染器**不施加** letter-spacing（实测："The" @84px 墨迹 147.26px = HarfBuzz **无字距** advance 147px；源片 `TitleCard.tsx` 正文是 `-0.022em` 紧排）。度量与渲染同源改造点干净：`src/remotion/text-fit-plan.ts` 是唯一度量实现。
- **需求**：`textCard` 增加 `letterSpacing?: number`（px 或 em），**同时**进渲染与 `text-fit-plan` 度量口径。
- **验收**：源片 `-0.022em` 紧排可 1:1 复现；折行结果与渲染逐行一致；老 manifest（不写该字段）逐像素不变。

#### RQ-03（P0 · 极小）`textCard` 支持 `color`

- **证据**：源工程 `ui.tsx:6-34` 的 `Eyebrow` = 19px / weight 600 / `letterSpacing 0.22em` / 色 `C.mute #6E6E86`；而 `TextCardTrack`（`src/remotion/manifest.ts:493-514`）**只有 `accentColor`**，且 `title` 变体不生效 ⇒ 眉标表达不出来。
- **需求**：`textCard` 增加 `color?: string`（主文本色），与 `accentColor` 并存。
- **验收**：眉标可渲染为 19px/600/`#6E6E86`；老 manifest 不受影响。

#### RQ-04（P0 · 小）`shape` 支持 `radius` / `stroke` / `dash`

- **证据**：`shape` 白名单 = rect/circle/line/gradient/path/arrow/triangle/star/polygon/dotGrid，**无 radius**（`src/remotion/manifest.ts`）；本次药丸底板/代码面板/描边框/命中环 **4 类**全靠预生成 PNG 顶替。
- **需求**：`shape.rect` 增 `radius`；`shape.circle` 增 `stroke` / `dash` / `strokeWidth`。
- **验收**：上述 4 类可原生表达，预生成 PNG 数量下降 ≥4 张；老 manifest 逐像素不变。

     - **第二 brief 的来源（2026-11-12 拍板）**：先用**同一 brief 的换内容变体**（换产品名 + 换数据 + 换素材）跑通判据并标定阈值；最终验收口径仍以真实第二 brief 为准，**判据本身不变**。

  - **≥40dB = 同规格可复现**（同一份 spec 交给 P 卡，必须复现出手搓版 ⇒ 卡没偷工减料）；
  - **<25dB = 异规格不雷同**（换成另一个产品，不能只是「换字换图」）。
  - 二者夹逼出的才是真模板：**同一套骨架，换内容就换出另一支片**。
- **成本**：中（需设计 + 回归）｜**依赖**：RQ-02~RQ-09（部分原语）、**RQ-22（聚合原语 —— 轨数判据的前提）**、RQ-10（卡注册表）、RQ-12（spec schema）｜**风险**：中（判据 4 的第二 brief 暂用变体代，见 §8 SB-3）

- **现象**：agent 选完卡才知道缺素材，缺了就停下来问用户 —— 但**它并不知道哪些真的必须问**。不分类 ⇒ 要么把 286 个素材全问一遍（用户直接放弃），要么全自己生成（品牌/UI 造假 ⇒ 事故）。今天**没有任何字段**告诉 agent 这个区别。

  | --- | --- | --- | --- |
  | `user`（必须用户给 / 必须真实品牌） | **54** | 21 合作方 logo + 16 产品 UI 截图 + 1 自有品牌 icon + 7 展示字体 + 9 段 VO | ❌ 必须用户提供或走已授权库 |

  | `generated`（可生成 / 可预生成） | **74** | 15 游戏海报 + 12 广告图 + 21 灰阶 logo + 26 预生成 PNG | ✅ 可生成、可预生成 |

  2. **先出清单再动手**：选卡阶段先产出**素材需求清单**并按 `source` 三路派发（问用户 / 查资产库 / 走生成），清单齐了再生成 manifest；

  5. **不新增第二套登记**：复用现有故事板 §07 口径（`neededBy` + `source` + `status`），两边字段对齐。
- **验收**：
  1. 每张卡（现有 24 张 + 新增 P 类）都有可机读 `assets` 声明，**缺声明即校验失败**；
  2. 同一 brief 两次运行产出**同一份**素材需求清单（确定性）；
  3. 分流正确：`user` 类素材不出现在 `generated` 通道；品牌 / UI 类素材**零**次 AI 重画；
  4. 缺 user 素材时按 `fallback` 降级并出片（本次口径：54 条 user 素材缺 1 条 ⇒ 仍出片，且降级记录进交付报告）。
- **成本**：中（需设计 + 回归）｜**依赖**：RQ-10（卡注册表）、RQ-12（spec schema）｜**风险**：低

### R6 · 补充组（2026-11-12 晚增 · 原语补齐与能力对齐）

> 这三条是本文**自我纠错**的结果：§2.3 的密度论证与 §5 的轨数判据互相打架（原判据在现有原语下不可达成），
> 而 RQ-10~RQ-12 要真正跑通，还缺「聚合原语」「多关键帧」「截图采集」三块地基。
> 编号连续放在此处（而非插进 R1/R4 组内），便于进 `tracking.md` 派单；分组归属见每条的「归属」。

#### RQ-22（P0 · 中）聚合型原语：把 N 个同构元素压成 1 轨

- **归属**：R1 表达层（补 R1 的缺口）｜**优先级 P0**（RQ-11 轨数判据的**唯一前提**）
- **现象**：265 轨里 **129 轨是 `image`**（48.7%）—— logo 墙 21 个 logo 占 21 条轨、页面截图墙 16 张占 16 条轨、海报/广告/媒体图若干。这类内容**同构、天然该由一个原语承担**，现在是 N 条轨手工摆。
- **证据**（实测轨型分布）：

  | 类型 | 轨数 | 占比 | 聚合后应剩 |
  | --- | --- | --- | --- |
  | `image` | 129 | 48.7% | **≤20**（聚合为 2~4 条轨） |
  | `shape` | 59 | 22.3% | ≤35 |
  | `textCard` | 51 | 19.2% | ≤45 |
  | `group` | 17 | 6.4% | ≤17 |
  | `caption` | 9 | 3.4% | ≤9 |

- **需求**：新增**聚合型原语**（每种把一组同构元素压成 1 条轨，内部按参数展开）：
  | 原语 | 承担 | 参数（≥4 个可换参维度） |
  | --- | --- | --- |
  | `logoWall` | 合作方 logo 墙 | 列数 / 行数 / 间距 / 单体尺寸 / 圆角 / 灰度 / 入场错峰 |
  | `assetGrid` | 截图墙 / 海报墙 / 目录墙 | 列数 / 间距 / 尺寸 / 裁切模式 / 圆角 / 入场序 |
  | `chipRow` | 芯片条 / 标签行 | 排列方向 / 间距 / 药丸圆角 / 字号 / 配色 / 错峰 |
  | `codePanel` | 代码面板 | 底板色 / 圆角 / 行距 / 字号 / 高亮色 / 滚动速度 |
  | `ticker` | 无限滚动墙 / 跑马灯 | 方向 / 速度 / 密度 / 淡出宽度 / 字号 |
- **验收**：
  1. 用 `logoWall` 重生成 playsout 的 logo 墙（21 元素）⇒ **1 条轨**，且**关键帧像素对拍 ≥40dB**（与手搓版等价）；
  2. 用 `assetGrid` 重生成 16 张截图墙 ⇒ **1 条轨**，对拍 ≥40dB；
  3. 展开后总轨数从 **265 → ≤150**（RQ-11 判据 2 的前提达成）；
  4. **老 manifest 逐像素不变**（新原语是新增轨道类型，不影响既有 `image`/`group` 轨）。
- **成本**：中（需设计 + 回归）｜**依赖**：无（纯新增）｜**风险**：中（聚合后如果展开逻辑与手搓有细微差异 ⇒ 对拍不过 ⇒ 需逐个校准）

#### RQ-23（P1 · 中）多关键帧相机（2D 轻量版，零新依赖）

- **归属**：R1 表达层｜**优先级 P1**
- **现象**：我们的 `animate?: Animate | Animate[]`（`src/remotion/manifest.ts:202`）虽是数组，但每段只有 `from`/`to` 两点线性插值。playsout 的 3D 推镜只能用 `group` + 关键帧**近似**，README「已知偏差」已登记「透视弱于源片」。
- **证据**：开源方案 `PageCam.tsx` 用的是「整页截图 + 关键帧 `{frame, cx, cy, zoom, rotX/Y/Z, persp}` 插值」；其 `FlatPanel` 与 `helpers/camera` 依赖 `three` + `@react-three/fiber` + `@remotion/three` —— **这三个依赖我仓一个都没有**（`package.json` 无 `three` / `@react-three` / `@remotion/three`），引入 = 新增依赖族 + 破坏「零打包 +0MB」的路线前提（§2.3 表）。
- **需求**：新增**布局级多关键帧相机原语**，字段形如
  ```jsonc
  { "type": "image", "src": "...", "camera": {
      "keys": [ { "frame": 0, "x": 0, "y": 0, "zoom": 1, "rotX": 0, "rotY": 0, "rotZ": 0, "persp": 800 },
                { "frame": 120, "x": -12, "y": 4, "zoom": 1.35, "rotX": -4, "rotY": 6, "rotZ": 0, "persp": 900 } ],
      "easing": "easeInOut" } }
  ```
  - **2D 轻量版优先**：先用 `x/y/zoom/rotZ/opacity` + `persp` 伪 3D 覆盖 80% 需求，**零新依赖**；
  - **真 3D（three 栈）列为可选**：若实测伪 3D 不够，再单独立项并单独评估打包体积 —— **不在本条范围内**。
- **验收**：
  1. 多关键帧路径（≥3 个 key）可表达与渲染，且关键帧之间**平滑插值**（相邻帧位移差无突变）；
  2. **插值可复现**（同一 manifest 渲两次逐帧一致 —— 禁 `Date.now()`/`Math.random()`，伪随机固定种子）；
  3. 老的 from/to 两点 `animate` 路径**逐像素不变**（新字段缺省即旧行为）；
  4. 与 playsout 的 group+关键帧近似版**对拍**：新原语渲出的推镜与旧近似版**观感一致**（PSNR ≥35dB，允许透视强度差异）。
- **成本**：中（需设计 + 回归）｜**依赖**：无（纯新增字段）｜**风险**：中（伪 3D 与真 3D 观感上限不同，须在验收里说清"覆盖 80%"的口径）

#### RQ-24（P1 · 中）真实页面截图采集链（素材供给的上游）

- **归属**：R4 素材层（补 RQ-21 的上游）｜**优先级 P1**
- **现象**：我们只有**下游消费**（`layout_table` / `inspect_image` 能吃坐标表），**没有上游采集**。playsout 的 16 张 `textures-live-*`（真实页面截图）是我从源工程**拿现成的**，产品自己做不到 ⇒ 「复刻真实页面」这一整类镜头走不通。
- **证据**：原缺口条目 C1 在附录 B 里此前被标为「暂缓」—— 本条把它**升为正式需求**（见附录 B 的口径变更）。目标链路：起本地 dev server → 无头浏览器截全页 2x → 元素级抠图 → `layout.json` 坐标表。
- **需求**：提供一条**可复跑**的采集链：
  1. 输入：目标 URL / 本地 dev server 地址 + 元素选择器清单；
  2. 产出：全页 2x 纹理 PNG + 元素级裁切 PNG + `layout.json`（元素坐标 / 尺寸 / 层级 / 命中的选择器）；
  3. 产出直接可被 `image` / `assetGrid` / RQ-23 相机轨消费（**素材 URL 走同源资产路由**，与 RQ-21 的 `library` 通道对齐）；
  4. **合规闸**：采集前必须确认页面可采集（不含登录凭据 / 私有客户数据 / 未授权页面），敏感数据按 RQ-21 的 `user` 通道处理。
- **验收**：
  1. 对一个本地 demo 页跑一次采集 ⇒ 产出 PNG + `layout.json`，坐标与页面实测一致（抽样 5 个元素，偏差 ≤2px）；
  2. 产出的 `layout.json` 能直接被 `layout_table` 读取（下游零改动）；
  3. 采集链**可复跑**：同页面两次采集产出 sha256 一致（禁伪随机）；
  4. 采集脚本**不落盘任何凭据**，且对未授权页面拒绝执行。
- **成本**：中（需设计 + 回归）｜**依赖**：无｜**风险**：中（浏览器环境依赖；`three`/headless 工具链不得引入，采集走仓库既有 `playwright` 依赖）

## 6. 非目标（明确不做）

1. **不做 Remotion/TSX 路线**。我们走「manifest → CSR」；对方产出代码，我们产出数据。理由见 `docs/2026-11-12-remotion技术路线与开源对标.md` §1。
2. **不追求 1:1 复刻任意片子**。目标是把**一类**片子（产品宣传片）做扎实，不是通用视频引擎。
3. **不在 DSL 里引入 CSS 全家桶**。`backdrop-filter` / `mix-blend-mode` / 逐帧 `perspective` 走**预生成资产**顶替（RQ-16），不追 web-renderer 升级。
4. **不为了"能出片"而降低验收标准**。切段渲染是临时路径，M0 落地后应回收。
