## 三、v1/v2 完全未覆盖的问题（按严重度）

### A. 宿主 / 渲染器（P0）

**A1 `warm` 字段硬编码 false —— 诊断被自己的埋点骗了**
`src/client/remotion-render.ts:288` 直接写 `warm: false`。agent 在 13:28 用它得出"每次都要冷启动 40–60s"，而 14:13 那次 22.6ms/帧 同样报 `warm=false`。**坏字段比没字段更危险**。

**A2 超时后不 reset，形成"越失败越慢"的自锁**
证据链：① 11:31:38 一次 420s 超时之后，11:33 的 270 帧只花 23s；② 14:13:38 一次 420s 超时之后 19 秒，60 帧只花 1.4s；③ 而 12:20 / 13:19 / 13:27 三次 10 帧探针花了 45–60s。
→ 读法：**热态 22–85ms/帧，冷态固定开销 45–60s + 编码 20–30s ≥ 90s 预算下限**。一旦某次超时把窗口打冷，之后连 10 帧都卡在预算边缘，形成"小片段必然失败 → 再失败 → 一直冷"。这是能解释全部 39 次超时的唯一自洽模型，v1/v2 都没写出来。

**A3 报告缺"准备/挂载/认领"阶段，三字段对不上墙钟**
#3：报告 23.0s + encodeMs 21.8s = 44.8s，实测墙钟 **29.5s**。#7：55.6s + 28.8s = 84.4s，墙钟 **60.4s**。
→ 要么字段语义错（msPerFrame 用的是含编码的 totalMs），要么缺一段耗时。agent 13:42 发现了这个矛盾（bash #207）却没跟进；v2 反而把 encodeMs 当事实写进"固定开销"论据。

**A4 超时文案与工具描述互斥，直接误导了 3 小时**
- 工具描述：「渲染期间用户可以切走、最小化、甚至换到别的会话，都不影响」
- 超时错误文案（`src/errors/catalog.ts:331`）：「请确认画布页面**已打开且可见**」

agent 12:30–13:45 整段"可见性节流"论证，源头就是这句话。

**A5 两条渲染路径缺可观测性：`render-host` vs `client`**
`src/remotion/render-job.ts:47-50` 明确两条路：`render-host`（隐藏窗口，遮挡/最小化/切会话都照跑）与 `client`（用户画布页，**页面不可见 ⇒ rAF 停摆 ⇒ 挂到超时**）。
若是 `client` 路径，A4 的文案就是对的；若是 `render-host`，403/可见性理论全不成立。宿主日志里本有判据（`routes.ts:2998` 的 `滞留渲染工单 … 已改派隐藏渲染窗口`），**两份复盘都没去取宿主日志**，却下了 P0 根因结论。

**A6 探针渲染没有独立节点 / 没有 dryRun，污染了交付物**
6 次成功全部写入**同一个**画布节点 `4cd14a24-d582-482c-9ae0-503d3ee35f0e`（纳入段数 11→1→2→1→1→1）。也就是说：用户画布上最终的"成片"节点，内容最后一次被覆盖成 **10 帧 / 0.41s 的黑屏探针**。这是比"没出片"更糟的状态——用户看到的是一个假成片。

### B. 工具契约与描述失真（P0–P1）

**B1 `inspect_image` 的描述与能力严重不符（本次最大隐性成本）**
描述原文：「**这是唯一的像素真值来源**——不要再手写 PNG 解码脚本（node:zlib 手解 / 找 PIL / ffprobe 探像素都是弯路，本工具一次给全）」。
实测：`bbox-dark` 在 threshold=18 时返回 **x0-1279 / y0-735，w=100% h=100%，覆盖率 31.8%**；收紧到 threshold=8 仍 **w=97.3% h=100%**。原因是它只给**全图亮度包围盒**，没有区域扫描 / 连通域 / 多阈值 / 行剖面。
→ agent 在 09:27 明确说"inspect_image 只提供整幅图的包围盒，而我要的是屏幕区域"，随后写了 `screen_bbox.py / screen_bbox2.py / ascii.py / rows.py / prof.py / scan.py / vscan.py / screenfit.py / pnglib.py` **9 个脚本**，吃掉约 1.5 小时 + 多次 compaction。
**工具在说谎，agent 的"违规"是唯一正确解。**

**B2 渲染返回强制"先看这几张图"，但闭环根本不成立**
每次成功都附 4 张抽帧（合计 26 张）+「**先看这几张图再向用户汇报**」。而：
- 模型侧是文本模型（agent 自述"我是文本模型"）；
- `read_image` 全程只调 **1 次**，且因路径拼错（`build/../../../assets/…`）直接失败，之后**再没试过**；
- 最终只能自写 PNG 解码器 + ASCII 亮度图去"看"。
→ 26 张抽帧 0 次被真正消费。**"渲染→自检→修正"这条主链在工具层面是断的**，这才是"过度验证"的根因。

**B3 `image2vl` 精度不足以做像素定位**
唯一一次调用（09:24:00）回答"表盘宽约占画面宽度 35%、高 40%、中心 60%/50%"；像素实测为 **27.8% × 52.7%，中心 64.1%/50.3%**。宽度误差 7 个百分点——按它填轨道必然错位。agent 因此放弃 VLM 路线。

**B4 `bash` 300s 硬超时 + 输出被裁剪，且是同一条命令重跑就好**
11:13:36 一条**20 行的 print 循环**挂满 300s，返回「timed out after 300 seconds or experienced an OOM error」+ 输出被 scrollback 裁掉；agent 改成写 `.py` 文件后**立即成功**（11:18:51）。
→ 错误文案把"工具侧挂起"说成"OOM 或超时"，会误导排查；且缺"命令已在途/请改用文件"的提示。

**B5 大段 JSON 靠手写，中文引号直接炸**
09:17:01 `write_storyboard` 的 `sound` 段因引号未闭合被拒（`Expected ',' or '}' at position 98`），重发一次。凡是"参数是一大段 JSON 字符串"的工具都在赌模型不手滑。

**B6 `inspect_image` 只收 RGB PNG，抽帧是 RGBA**
12:10:56 `pnglib` 断言失败（colorType 6 不支持）→ 重写解码器。工具输出的抽帧格式与工具支持的输入格式不一致。

## 六、补：v2 漏掉的 8 条引擎契约（都是本次实读源码换来、可直接省掉下次重读）

1. `Transition` 包的是**整条轨道**，不能对单个元素做擦除；"一行一轨"的设计下只能改用 `exit` 淡出 + `fadeFrames` 淡入手工模拟。
2. `shape` 的 `box` **不能**被 `animate` 动画；`shapeTransform` 只有 `scale/rotate`，没有位移。
3. 但 `positionDeclared` 会覆盖 `box.x/y` —— 因此"以 box 定位 + 只动画 y"的滑入是可行的（第 2 条的例外）。
4. `bullets` 的行内打字用**全局连续帧号**且每行同起点 ⇒ 多行必须拆成独立轨道。
5. `bullets` 的圆点**没有开关**（始终渲染），只能靠深色 `accentColor` 隐藏；圆点占约 42px，居中换算必须带上这个偏移。
6. `fitted.fontSize` **只缩不放**（适配 900px 容器）；要放大标题只能靠 `transform.scale`。
7. `fx:"glow"` 固定冷蓝 `rgba(120,190,255,…)`，不可配。
8. `textCard` 的 `title` 变体带全屏蒙版、`subtitle` 固定底部居中 —— 左栏想左对齐只能用 `bullets`。

（v2 已有的 8 条不重复；其中"`circle` 的 `paddingBottom` 按父宽解析→真圆"应补半句：**直接给宽高不一致会渲染成椭圆**。）
