# 首屏 13 秒在干什么：会话时序拆解（2026-10-24）

> 对象：`session.v4.jsonl`（2026-10-24 20:38:22 创建，code- 3 项目，519 事件 / 90 步 / 109 次工具调用）
> 问题：**用户发出第一条消息到看到 agent 第一句话，中间那十几秒在做什么？**
> 方法：逐事件时间戳 + 模型 usage + 流式分块时间（`assistant/message.stream[].time`）。全部只读。

---

## 一、三句话结论

1. **首屏 13.1 秒里，9.8 秒花在"给会话起标题"上**——而标题在 1.0 秒时就已经有 fallback 可用，这 9.8 秒对用户**没有任何可见价值**。
2. 真正的生成只花了 **0.17 秒**（95 个 token）。剩下的是 **prefill 与排队**，不是"模型思考慢"。
3. 每个 step 还有一个 **≈6 秒的固定首 token 开销**（与输入大小几乎无关）。90 步 × 6s ≈ **9 分钟**，占整场 123 分钟的 7%。

---

## 二、首屏 13.1 秒的逐段账

| 时刻 | 事件 | 本段耗时 | 在做什么 |
|---|---|---|---|
| 0 ms | `session` | — | 会话对象创建 |
| 0 → 921ms | （静默） | **0.9s** | 应用侧：打开项目 → 建会话 → 注入 inbox |
| 921 → 1004ms | `turn/start` → `step/start` | 0.1s | 回合/步初始化 |
| 1004 → 1012ms | `system/message` + 3×`user/message` + `request/header` | 0.01s | 组上下文（system + 首条需求 + 运行时快照 + skill 说明） |
| **1018ms** | `session/title`（`source: fallback`） | — | **标题已经有了**（"使用技能「代码驱动科普成片…"） |
| **1021 → 10827ms** | `session/title-llm-request` → `session/title`（provider） | **9.8s** | 拿首条消息去问一次 LLM，把标题"升级"成"智能手表功能介绍视频" |
| 10827 → 12621ms | （主请求 prefill 完成） | 1.8s | 29,134 tokens 输入 → 首 token |
| 12621 → 12790ms | `assistant/message`（text + 2 个 `skill` 调用） | **0.17s** | 真正生成 95 个 token |

> 首 token 时间取自 `stream[0].time`（12,621ms），生成耗时取自 `text-chunks.dt` 之和（≈170ms）。

**关键对照**：三个会话（code- 系列全部 3 份 v4 转录）都是同一形态 —— 首 token 12–13s、标题返回 8–11s、首轮输入 28–29k tokens。不是偶发。

## 三、每步 ≈6s 的固定开销（推导过程）

把每步拆成 `TTFT + 生成`：生成按 80 tok/s 估，残差即 TTFT。

| step | 本步 ms | 未命中缓存输入 | 输出 tok | 残差(≈TTFT) | 残差/输入 |
|---|---|---|---|---|---|
| 1 | 12,088 | 29,134 | 95 | 10,901 | 0.37 ms/tok |
| 3 | 8,026 | **1,183** | 126 | **6,451** | 5.45 |
| 6 | 9,323 | **1,382** | 180 | **7,073** | 5.12 |
| 7 | 9,774 | **1,105** | 296 | **6,074** | 5.50 |
| 8 | 15,494 | **363** | 798 | **5,519** | 15.20 |
| 4 | 10,460 | 12,377 | 190 | 8,085 | 0.65 |

看 step 3/6/7/8：输入只有 363–1,382 token，TTFT 仍是 **5.5–7.1 秒**。
⇒ 存在 **≈6 秒的固定开销**，与输入长度无关。

再把这些固定开销减掉，剩下的与输入近似线性：
- step 1：(10.9s − 6s) / 29.1k ≈ **0.17 ms/token**
- step 4：(8.1s − 6s) / 12.4k ≈ **0.17 ms/token**

**成本模型**：`本步耗时 ≈ 6s + 0.17ms × 未命中缓存 token + 输出 tok / 80`

## 五、优化清单

| 优先 | 改什么 | 预期收益 | 落点 | 风险 |
|---|---|---|---|---|
| **P0** | **标题 LLM 请求移出关键路径**：有 fallback 就先让主请求走，标题结果回来再静默更新；或给它 1s 超时后放弃 | 若与主请求串行，**首屏 −8~10s**（每个新会话一次） | 会话标题特性（`session-title-first-prompt-llm`，在 harness 侧，不在 canvas-studio 仓） | 低：fallback 已存在，最坏只是标题朴素一点 |
| **P1** | **首轮注入瘦身 29k → ~12k**：两个 skill 正文按需加载（先读目录再读正文）、24 个工具描述压缩 | 首轮 **−2~3s**（一次性） | skill 加载策略 + 工具描述 | 中：描述压太狠会让模型用错工具 |
| **P2** | **减少步数**（90 → 55）：一次 `read` 多个文件、相邻 `bash` 探查合并、`skill` 一次载完 | **−3.5 min/场**（固定 6s × 少掉 35 步） | agent 纪律（SKILL.md）+ 工具支持多文件 | 低 |
| **不做** | 把大输出拆成多次写（如故事板分 5 次） | 负收益：每多一步 **+6s** | —— | —— |

### 关于"6s 固定开销"能不能修

它不在本仓：`canvas-studio/src/gateway.ts` 只有 171 行，只负责**发布凭据**，真正的代理在上游。
所以本仓能做的是 **少发请求**（P2），而不是让它更快。
要定性得量测上游：同一 prompt 连打 10 次看 TTFT 分布；若稳定 6s，那是服务端的排队/预热，需要上游优化。

### 标题到底有没有挡路（待一次实证）

现有数据两种解释都成立：串行（标题 9.8s 挡在前面）或并行（两者各自慢）。
**一次实证就能定死**：临时把标题请求关掉（或加 `titleLlm: false`）再开新会话 ——
首屏若从 13s 掉到 ~3s ⇒ 串行；仍在 12s ⇒ 并行，那 9.8s 只是"同时发生的另一件事"。
