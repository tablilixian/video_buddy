# 效果测试执行器

按 [docs/effect-tests/视频效果验证测试用例与轮次记录.md](长期用例文档) 的定义自动执行可自动化用例。你（agent）在同一会话里扮演两个角色：**先读本 skill 定流程，再按 `canvas-studio-creation` 规范真实执行创作**——测试的就是真实链路，不要走捷径（如直接编 prompt 而不调工具）。

## 可自动化用例总表

| 用例 | 内容 | 自动化范围 |
| --- | --- | --- |
| T1 | Ref2VA 基础烟雾（单镜直出） | 全自动：参数 + 六段式结构检查；画面质量留人工 |
| T1b | 固定参考图烟雾（跨轮可比性） | 全自动：固定锚点图上传 + Ref2VA 直出，结构与 T1 相同 |
| T2 | 六段式 prompt 质量检查 | 全自动（基于 T1 的产物，不单独生成） |
| T3 | 关键帧组合参考一致性 | 全自动：参数 + image2vl 逐帧比对 |
| T5 | FL2VA 首尾帧路由回归 | 全自动：路由 + 首行指令检查 |
| T6 | 单镜模式端到端 | 自动（auto 模式下测流程完整性）；confirm 门禁兼容项留人工 |
| T9 | **官方锚定 FL2VA（直出模式）** | 全自动：官方 keyframe + 官方金标准 prompt 逐字直出，与官方 `minimax-h3/assets/fl2va.mp4` 对比——不走创作 skill 流程 |
| T4 / T7 / T8 | AB 对比 / 降级路径 / 澄清序号 | **不自动化**（T4 需人工评分与版本切换；T7 需改名目录重建；T8 依赖逐步确认模式的提问顺序）——用户点名要求时提示需人工配合 |

每条用例的**固定输入（假数据）、预期清单、image2vl 比对 prompt** 见 `references/fixtures.md`，执行前必须先读它。

**直出模式（T9 专属）**：跳过第 2 步的 skill 加载与创作流程——直接 `upload_image` 官方素材 + 用 fixtures 里的官方 prompt 逐字调 video_generate。除采集产物外，还要把实际发送的 prompt 全文存档，供与金标准做逐字 diff。

## 前置检查（每轮开始时做一次，任一不满足即停下向用户说明，不要绕过）

1. **项目规范**：当前会话绑定的项目名必须形如 `效果验证-R<轮次>-<用例号>`（agent 不能创建项目——项目需用户在 UI 预先建好并进入其会话）。跑多条用例时用户需为每条建独立项目并切换。
2. **执行模式**：项目工作流必须是**放手跑（auto）**。若当前是逐步确认，请用户切工作流条后再继续（切到 auto 后继续即可，不要在 confirm 模式下硬跑——分镜审批会终止回合等人）。
3. **后端探活**：调一次轻量工具（如 `list_references`）确认后端可达；不可达则停止并提示检查 Drama Backend。

## 执行流程（每条用例）

1. **读 fixtures**：read 本 skill 资源目录下 `references/fixtures.md`，取该用例的固定需求文本与预期清单。
2. **加载创作规范**：若本会话尚未加载 `canvas-studio-creation`，先 `skill(name="canvas-studio-creation")`；随后严格按其标准工作流执行，需求以 fixtures 文本为准。
3. **无人值守约束**：全程**禁止调用 `ask_user_choice`**（fixtures 的预设答案即用户答案）；执行模式为放手跑，不等待任何审批。**上游风格 skill 自带的选项卡/确认提问（如品牌宣传片的成片时长、画面比例）一律不调 ask_user_choice**——按 fixtures 中该用例的预设答案直接推进，并在报告备注「跳过提问 N 次」。若发现工具结果出现超时结算（说明模型仍违规调用了提问），在报告中记为「约束失效」——这本身是有效的测试数据，不要掩盖。
4. **边跑边采**：记录每次 `image_generate` / `video_generate` / `video_composite` 的关键参数——`filenames`（张数与内容）、prompt 全文、`duration`、返回 url 与报错（如有）。**规范获取方式逐项记录**：每个用到的规范（canvas-studio-creation、h3-prompt-writing 及其 references 文件）注明获取途径——`skill 工具加载` / `直接 read 文件` / `未获取`，供长期观察路由指令服从率。同时记录有无加载失败（评分时要排除「skill 没加载」造成的干扰）。
5. **落盘交叉核对**：用例跑完后 read 当前项目目录的 `canvas.json`，核对新增节点数量、`toolName` 与运行中记录是否一致（Host 是事实源，以此为准）。
6. **关键帧自动评**（用例涉及关键帧时）：对每张关键帧按 fixtures 里的固定 prompt 调 `image2vl`，提取角色特征词（发型/服装/脸型）与场景特征词（地标/光位），跨镜比对并汇成特征词表。
7. **写报告**：把结果**追加**到当前项目目录的 `效果测试报告.md`（每轮一节，格式见下），然后串行进入下一条用例；全部跑完后在最终回复里完整输出报告 markdown，并附「轮次记录表待粘贴行」。

## 判定与报告格式

按 fixtures 每条用例的「预期清单」逐项判 ✅/❌；**不给 C/D 维度（表现力/节奏）打分**——那是人工评的，报告里只留待评项与产物路径。失败必须分类：`路由错`（该走 Ref2VA 走了 FL2VA 等参数级错误）/ `端点错`（后端 404/500）/ `效果差`（参数对但产物不符）/ `门禁拦截`（工具被拦）/ `skill 加载失败`。

报告节格式（写入 `效果测试报告.md`）：

```markdown
## R<轮次> · <用例号>（<日期> · SKILL commit <hash>）
- 判定：通过 / 失败（<分类>）
- 关键参数：video_composite filenames=N 张…（或 video_generate 单图）
- prompt 全文：（折叠存档，正文贴出）
- 自动评：六段式齐全度 N/6；image2vl 特征词表：…（如适用）
- 待人工评：C 表现力 __ / D 节奏 __；产物：<url 列表>
- 备注：skill 加载情况 / 异常
```

轮次记录表待粘贴行格式：`<轮次> | <日期> | <commit> | 新 | <用例号> | <通过/失败> | <关键发现一句话> | <产物目录>`

## 诚实边界

- 本执行器测**结构与一致性**（参数、六段式、跨镜特征词），测不了「惊艳感」——那是人工量表的事，两者互补，缺一不可。
- 多轮对比时每条用例只跑 1 次属抽样，结论标注「单轮抽样」；用户要求更可靠结论时同一用例跑 ≥2 次再比较。
- 产物与 prompt 存档属于测试证据，不要为「好看」而修剪失败记录——失败分类本身就是数据。
