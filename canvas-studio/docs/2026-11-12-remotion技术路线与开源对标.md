# Remotion 技术路线盘点与开源对标（2026-11-12）

> **本文定位**：把 Canvas Studio 当前**真实落地**的 Remotion 路线讲清楚（不是设计稿，也不是路线图），
> 再拿它去对照公开开源项目，回答「这条路线在世界上有多少人走」。
> **事实源**：`src/remotion/**`、`src/render-host/**`、`src/client/remotion-render.ts`、
> `src/remotion/render-job.ts`、`src/routes.ts`、`src/host-tools.ts`；
> 规格正本仍是 `docs/plans/remotion/remotion-integration-devdoc-2026-10-14.md`（v1.6+）。
> 本文只做**现状归纳 + 外部对标**，不引入新决策。

---

## 0. 一句话

> **LLM 只写声明式 JSON（`CompositionManifest`），不写 React 代码；一个固定的组件树解释这份 JSON；
> 真正的渲染发生在 Electron 渲染进程里（`@remotion/web-renderer` 的 WebCodecs 客户端渲染），
> 宿主与渲染端之间用一条 HTTP 工单桥连接；隐藏窗口当后台渲染 worker，画布页当兜底执行器。**

这条路线在 Remotion 官方术语里叫 **CSR（client-side rendering）**，对应包 `@remotion/web-renderer`；
它的对立面是官方主推的 **SSR**（`@remotion/renderer` + Chrome Headless Shell + webpack bundle）。

## 1. 六个技术决策（"是什么 / 不是什么"）

| # | 决策 | 我们的选择 | 明确**不是** |
|---|---|---|---|
| 1 | 渲染在哪执行 | `renderMediaOnWeb` / `renderStillOnWeb`，跑在 Electron 渲染进程（`@remotion/web-renderer@4.0.535`） | 不是 Node 侧 `renderMedia()`；不起 headless Chrome；不起 webpack |
| 2 | 谁来写视频 | 模型输出 **JSON manifest**（10 类轨道），宿主校验后渲染 | 不是「模型生成 .tsx 文件 → 打包 → 渲染」 |
| 3 | 组件树 | **一套固定组件**（`StudioComposition`），被预览、隐藏窗口、渲染三处共用 | 不是「每个片子一套 composition」 |
| 4 | 宿主与浏览器的关系 | **控制流反转**：工具在宿主建单 → 渲染端轮询取单 → 回写字节 | 不是宿主同步调用渲染函数 |
| 5 | 谁接单 | **隐藏渲染窗口优先**（`render-host`），画布页兜底；建单时钉死 | 不是「谁先来谁渲」，也不是每拍现算 |
| 6 | 渲染产物 | mp4 字节经 `octet-stream` 回写 → 宿主 `saveLocalAssetBytes` + `ffprobe` 探真值结算 | 不是「浏览器直接写用户磁盘」 |

**关键收益（也是选 CSR 的理由）**：包体 +0MB（不随包 210MB 的 headless-shell + compositor）、
没有 webpack 预构建/`staticFile()`/`publicDir` 那一整套、取消用标准 `AbortSignal`、
素材直接吃同源 URL（`/canvas-studio/assets/...`）不需要物化进 renderDir。

**关键代价**：拿不到 z-index / `object-position` / `mix-blend-mode` / `backdrop-filter` / inset 阴影，
`<OffthreadVideo>` 不可用（因此 `<Video>`/`<Audio>` 一律从 `@remotion/media` 导入，有机器守卫
`tests/csr-writing-guard.test.mjs` 盯着），编码走 WebCodecs（软编偏慢，见 §4）。

## 2. 五层结构（真实文件）

```
⑤ 编排层   skills/code-driven-explainer + 总纲第 10 步（compose_video vs render_composition 二择）
           src/remotion/{recipes,template-registry,template-compile}.ts
              │  模型只会产 JSON，不产代码
④ 契约层   src/remotion/manifest.ts（类型 + validateManifest）
           normalize-timing.ts / groups.ts / materialize.ts / manifest-lint.ts
           motion-lint.ts（ML-01~12 体检）/ slideshow-risk.ts（幻灯片六维评分）
              │  纯数据 + 纯函数，零 Remotion 依赖 → 可在 Node 单测
③ 组件层   src/remotion/components/*（Root/VideoClip/ImageClip/TextCard/Shape/Chart/
           Caption/Callout/AudioViz/AudioTrack/Transition/RevealShell/Group）
           Root.tsx = <Composition id="studio-composition"> + calculateMetadata（动态时长）
           三处消费方：@remotion/player 预览 / 隐藏窗口渲染 / capability-bench 取证
              │
② 渲染层   src/client/remotion-render.ts   ← renderMediaOnWeb 封装（质量三档 + 失败分类 + 有界重试）
           src/client/remotion-font-inject.ts（@font-face + document.fonts.load 8s 闸门）
           src/client/render-job-executor.ts（协议：渲染 → 抽帧回写 → 成片回写 → 失败撤单）
              │
① 工单桥   src/remotion/render-job.ts（内存工单表 + 队列 + 看门狗 + 滞留改派 + 结算）
           src/remotion/render-queue.ts（并发 1 / 上限 4 / 严格 FIFO / 进度只进不退）
           src/render-host/**（隐藏 BrowserWindow：page.ts 自举报错 → main.ts 心跳+轮询）
           src/routes.ts 上的 6 条回环路由
```

### 工单桥的 6 条路由（全部挂在 `/canvas-studio/remotion/` 下）

| 路由 | 方向 | 作用 |
|---|---|---|
| `GET /pending` | 渲染端 → 宿主 | 取单（返回 manifest / fps / quality / 真值时长 / 抽帧点 / `deadlineAt`） |
| `POST /progress` | 渲染端 → 宿主 | 进度（节流到 ~3% 一档） |
| `POST /sample` | 渲染端 → 宿主 | 抽帧回写（先图后片，让用户先看到画面） |
| `POST /commit` | 渲染端 → 宿主 | 成片字节（octet-stream）+ warnings + report |
| `POST /cancel` | 渲染端 → 宿主 | 撤单 / 失败原因 |
| `GET /jobs`、`GET /fonts/*`、`GET /sfx`、`GET /grain`、`GET /templates/*` | 宿主 → 端 | 观测 + 只读素材 |

宿主侧**不落文件**：Host 半与路由同进程，工单是模块级 `Map`。

## 3. 端到端时序（一次 `render_composition`）

```
模型 → render_composition(manifest | manifestPath, quality, probe, spotFrames, timingSegments)
  └─ 宿主：projectId 收口 → 审批门 → 结构校验 → 素材核对（缺失/外链硬失败）
     → video 轨按 ffprobe 真值校正帧号 → 建工单（钉死执行者）→ 排队（并发 1）
              ↓ 渲染端每秒轮询 GET /remotion/pending
      hidden window（主） / 画布页（兜底）
              ↓ 取到单
      draft（跳过预览闸门）｜ standard/high 先弹 @remotion/player 只读预览，用户点「开始渲染」
              ↓
      字体注入 → 素材预取（delayRender，8s 兜底）→ renderMediaOnWeb
              ↓ 每帧回调：节流进度 + 每 800ms 补一拍心跳
              ↓ 抽帧（4 张均匀 + 转场中点，上限 8）
      POST /sample ×N → POST /commit（mp4 字节）
  └─ 宿主：落盘 → ffprobe 探真值（时长/分辨率/音轨）→ LUFS → 编排体检 → 返回 url + frames + report
```

**异常路径都已建模**（这是这条路线最容易烂掉的部分）：
- 渲染窗口失联 → 看门狗按「最后一次活性证据」判死（不是按取单时刻）；
- 画布页单 15s 内从未被 claim 且窗口健康 → 隐藏窗口**滞留改派**（从头渲，代价可接受）；
- 渲染窗口「复用必挂」→ 一扇窗只渲一单，结算后回收并立即重建（实测重建 204–205ms）；
- 关窗口 = abort 当前单（`pagehide`），不等超时；
- 页面自己按 `deadlineAt` 主动 abort，避免「宿主超时但页面还在渲」把轮询卡死。

## 5. 这条路线对写法的硬约束（别当成风格偏好）

1. **层叠只靠 DOM 顺序**——CSR 不支持 `z-index`，所以 `Root.tsx` 的轨道顺序就是图层顺序，
   并有 `lintZOrder` 兜底。
2. **`<Video>` / `<Audio>` 只能来自 `@remotion/media`**——remotion 核心版在 web-renderer 下直接抛错，
   `tests/csr-writing-guard.test.mjs` 机器强制。
3. **`background-image: url()` 必须同文件配 preload + `delayRender`**——渲染器不等背景图加载
   （经典症状：本地有图、成片没图）。
4. **mask 只写 `linear-gradient` / `url()`**；`blend` / `perspective` / `backdrop-filter` 在 4.0.535
   整字段无效（能力基准 #08/#09 像素实证），等升级后按 `scripts/capability-bench/` 回归再放开。
5. **音频必须显式注册 WASM AAC**（`registerAacEncoder()`）——Chromium 的 WebCodecs AAC 声称支持
   但忽略 bitrate，实测请求 128kbps 产出 ~16kbps，整片响度塌 10 LU。

## 6. 开源对标

### 6.1 判定标准

我把「技术路线相同」拆成四个可验证的问题，按重合度分梯队：

| 判据 | 说明 |
|---|---|
| **A. 渲染位置** | 客户端 WebCodecs（`@remotion/web-renderer` / `@remotion/webcodecs` / 自研 mediabunny）还是 Node（`@remotion/renderer` + headless Chrome） |
| **B. 输入形态** | agent/用户产 **JSON/数据**（固定组件解释）还是产 **React 代码**（每片一套 composition） |
| **C. 宿主形态** | 桌面 App / 本地服务 / CLI / 云 |
| **D. 工单桥** | 是否有「建单 → 轮询/队列 → 回写」的异步渲染协议 |

### 6.2 第一梯队：**同渲染路线**（客户端 WebCodecs 出片）

> 方法：GitHub `topic:remotion` 按星标取前 100 个仓库，逐一读 `package.json`。
> **只有 1 个仓库声明了 `@remotion/web-renderer`**；另有 1 个用了上一代 `@remotion/webcodecs`。

| 项目 | ★ | A 渲染 | B 输入 | C 形态 | D 工单桥 | 与我们的关系 |
|---|---|---|---|---|---|---|
| **[0xsline/OpenChatCut](https://github.com/0xsline/OpenChatCut)** | 3.1k | ✅ `@remotion/web-renderer` 的 `renderMediaOnWeb`（`src/export/browserExport.ts`），**失败自动回退**服务端渲染 | ✅ 时间轴文档 JSON（`TimelineState` / `ProjectDoc`）→ 固定 `TimelineComposition`，agent 工具在 `src/agent/tools/` 里改这份文档 | ✅ Electron 桌面 + 本地服务 | ✅ `/export/job` + `renderJobClient` 轮询快照 | **最接近的一个**：同为「桌面 + agent + 声明式时间轴 + 浏览器出片」。差异有两点：① 它是**双引擎**（浏览器快导跑编辑器窗口 → 服务端 headless 兜底），我们**只有浏览器引擎**；② 我们多了一扇**专用隐藏窗口**当后台渲染 worker（编辑器窗口被遮挡/最小化也不影响），它是「导出时占着可见窗口 + 服务端兜底」 |
| **[ybouane/VideoFlow](https://github.com/ybouane/VideoFlow)** | 172 | ✅ 自研浏览器渲染器（WebCodecs + MediaBunny），**不是 Remotion** | ✅ 编译成可移植 JSON，DOM 预览 + 浏览器/服务端双渲染器 | 库 + React 编辑器 | — | 思路最像（一份 JSON、三种渲染器、其中一种是浏览器），但引擎自研，可当「JSON as IR」的架构参照 |
| **[Remocn/remocn-studio](https://github.com/Remocn/remocn-studio)** | 227 | ⚠️ `@remotion/webcodecs` + `@remotion/player`（浏览器转码，非 web-renderer） | 组件库 + 编辑器（自述 "Agent-native video editor"） | Web | — | 属于「浏览器侧编码」的同族，但它是素材转码/组合，不是逐帧合成 |
| **[mohyware/clip-js](https://github.com/mohyware/clip-js)** | 773 | ⚠️ `@remotion/player` 预览 + **ffmpeg.wasm** 编码 | 时间轴 | Next.js Web | — | 「浏览器内零服务端成本出片」的另一条实现（WASM 而非 WebCodecs） |
| **[openvideodev/react-video-editor](https://github.com/openvideodev/react-video-editor)**（原 DesignCombo） | 1.8k | ⚠️ 已从 Remotion 迁到 **PixiJS** + WebCodecs（`@openvideo/engine-pixi`） | 时间轴 | Next.js Web | — | 曾经的 Remotion 客户端编辑器标杆；**它离开 Remotion 这件事本身值得记住**（性能和 z-index/滤镜能力的硬约束） |

**结论**：`@remotion/web-renderer` 是 4.0 后期才补齐的能力，公开生态里几乎没人走——
上面 100 个 Remotion 主题仓库中只有 OpenChatCut 一条。这条路线的「孤独」是事实，不是错觉。

### 6.3 第二梯队：**同输入形态**（声明式 JSON / props → 固定 Remotion 组件树，但 Node 渲染）

| 项目 | ★ | A 渲染 | B 输入 | 说明 |

### 6.4 第三梯队：**同目的**（agent 驱动做视频，但走「生成代码」路线）

这一类是 2026 年最热的方向，也是我们和主流**分歧最大**的一类：它们的 agent 直接写 Remotion TSX。

| 项目 | ★ | 路线 |
|---|---|---|
| **[OpenMontageInc/OpenMontage](https://github.com/OpenMontageInc/OpenMontage)** | 79.7k | agentic 视频生产（Python 工具栈 + YAML 流水线 + HyperFrames/Remotion 双引擎）；我们的 `docs/plans/remotion/openmontage-adoption-analysis-2026-10-13.md` 就是对着它写的选型分析 |
| **[Vincentwei1021/video-shotcraft](https://github.com/Vincentwei1021/video-shotcraft)** | 18.8k | Claude Code / Codex skill：抓页 → 选镜头配方 → **用 Remotion 写动画** → 卡点 → 逐帧检查 |
| **[JuneYaooo/rea-video](https://github.com/JuneYaooo/rea-video)** | 7.1k | 逐镜拆解参考视频再生产（我们的「复刻线」借鉴过它） |
| **[Vincentwei1021/anything2explainer](https://github.com/Vincentwei1021/anything2explainer)** | 3.2k | 一个主题 → 旁白讲解片（skill 生成 Remotion 代码） |
| **[0xS4N4TG/kinetograph](https://github.com/0xS4N4TG/kinetograph)** | 498 | **反方向**：兼容 Remotion API，但用 Rust GPU 合成器，**不要浏览器**（速度路线） |
| **[dmtrKovalenko/fframes](https://github.com/dmtrKovalenko/fframes)** | 3.1k | Rust 重写的「视频 vibe coding」框架，主打比 Remotion 快 30×+ |

**这一类和我们最根本的差别**：它们的产物是一棵 React 组件树（要打包、要跑 webpack/esbuild、要能执行任意代码），
我们的产物是一份 JSON（可校验、可 lint、可 diff、可回放、能在宿主侧做纯函数体检）。
代价是我们必须预先造好 10 类轨道的能力边界；收益是**渲染链路完全确定**——没有「这次模型写的代码用了不支持的 CSS」这种不可穷举的失败面。

### 6.5 结论

| 组合维度 | 世界上有没有同款 |
|---|---|
| 桌面 + agent + 声明式 JSON + Remotion | 有（OpenChatCut、short-video-maker 各占一半） |
| 声明式 JSON + Remotion + **浏览器 WebCodecs 出片** | **几乎没有**（OpenChatCut 是唯一一个，且它是双引擎、服务端兜底） |
| 隐藏 BrowserWindow 当**专用渲染 worker** + HTTP 工单桥 + 滞留改派看门狗 | **没找到公开同款**（这是本项目的工程特色，也是最难复制的部分） |
| 渲染前 manifest 体检（ML-01~12 / 幻灯片六维评分 / 文本适配审计） | **没找到公开同款**（这是「让模型写 JSON」这条路的必要配套，别人走代码生成不需要它） |

> 检索方法与局限：GitHub repository search（`topic:remotion` 前 100 + 关键词组合）、逐个读 `package.json`
> 与关键源文件；未做全量代码搜索（GitHub code search 需鉴权，grep.app / Sourcegraph 在本机被拦截）。
> 因此只能说「**公开可检索的主流项目里没有**」，不能断言绝对不存在。

## 7. 可以回头看两眼的地方（不是待办，只是钩子）

1. **OpenChatCut 的双引擎降级**：`canRenderMediaOnWeb` 不通过 / 编码器拒绝时自动切服务端渲染。
   我们目前是「浏览器不行就报错」，若将来要覆盖老机器，这是现成的参考实现。
2. **VideoFlow 的「JSON 即 IR」分层**：`core`（编译）+ `renderer-dom`（预览）+ `renderer-browser`（出片）+
   `renderer-server`（云端）。我们把「预览」和「出片」已经共用组件了，但**没有独立的编译产物**；
   若将来要把 manifest 冻结成可归档的中间表示，这是可抄的形状。
3. **short-video-maker 的 zod 单源**：它用一份 zod schema 同时生成工具入参校验与 TS 类型。
   我们是手写 `validateManifest` + `gen-manifest-fields.mjs` 生成字段文档，两条链其实可以合并。
