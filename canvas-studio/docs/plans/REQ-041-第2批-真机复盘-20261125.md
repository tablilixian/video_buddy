## 1. 问题 ①：托盘不跟随 —— 根因链

### 1.1 事实

| 文件 | mtime | 大小 | 分辨率 | 内容 |
|---|---|---|---|---|
| `assets/seg-s2.mp4` | 21:20:59 | 579,860 | 960×540 | **旧文字卡**（「月亮走的是一条椭圆」+ 两条要点） |
| `build/shot-cache/a9dcd570c9928c75.mp4` | 20:01 | 579,860 | 960×540 | 同上 |
| `deliver/segments/s2.mp4` | 21:20:59 | 579,860 | — | 同上 |
| `deliver/final.mp4` | 21:21:00 | 29,058,713 | 1920×1080 | **新椭圆轨道动画** |

- `md5(assets/seg-s2.mp4) == md5(build/shot-cache/a9dcd570c9928c75.mp4) = fcc2313171e36de8…`
- 抽帧对比：`seg-s2.mp4 @4s` = 旧标题卡；`final.mp4 @14s`（帧 420） = 椭圆轨道 + 地球 + 月亮 + 近地点标注。
- 21:21 那次 high 整片渲染的回执原文：

```
ℹ️ 分镜渲染未启用：probe/spot 单或 manifest 含音频段（音频整轨后配 = Phase 1.5）
ℹ️ 段合声：9 段 / 0.5s（均 51ms，最长 79ms）
```

`段合声 9 段` 说明「合声」跑了 9 段，但**一段都没渲**——9 份段文件全是从缓存复制的。

### 1.2 代码路径（每一层都能对上）

1. `shot-render.ts:275` `allowShots: manifest.audio === undefined` —— **带旁白的片子永远不走分镜路径**。旁白是这个产品的主形态（本次全片 9 句旁白），所以这条等于「分镜渲染在这个项目从未启用」。
2. 走整片路径后，`host-tools.ts:4101` 进 P0-3 的补段：`fillMissingSegments` → `segment-render.ts:76 missingArtifacts`：

```ts
const index = cacheIndexByWindow(cacheDir)          // 键 = `${startFrame}:${endFrame}`
return artifacts.filter((a) => !index.has(segmentCacheKey(a)))
```

3. `segment-publish.ts:57 cacheIndexByWindow` 的键是**帧窗**，`meta.json` 里甚至存着 `hash` 字段（`"hash": "0ada401291b2521c"`），但索引根本不用它。
4. 于是：s2 的轨内容变了（旧 5 条单元轨 → 新增 7 条 `s2-*` 轨），**帧窗 324–638 没变** ⇒ 判定「已存在」⇒ 零补渲 ⇒ `publishSegmentPreview` → `publishSegmentsFromCache`（`segment-publish.ts:116`）把 20:01 的旧 mp4 又复制一遍。

### 1.3 后果是「永久陈旧」，不是一次性

下次整片重渲（quality 任意）→ 帧窗仍在 ⇒ 仍判命中 ⇒ 仍复制旧件。**除非有人显式 `rerender_segment(s2)`，托盘里这一屏永远是旧的。** 这次会话里没人调它（模型不知道托盘陈旧）。

### 1.4 顺带暴露的第二个洞：档位不跟随

| 段 | 分辨率 | 来源 |
|---|---|---|
| s3 / s5 | 1920×1080 | `rerender_segment(quality: high)` 21:26 / 21:33 |
| s1、s2、s4、s6–s9 | **960×540** | 20:01 的 draft 缓存被当命中复制 |

同一条托盘里 7 段 540p + 2 段 1080p。根因同上：帧窗键不看 `quality`，而 `segmentHash` 里 `quality` 是入参。

### 1.5 修法（P0，一处改完两个洞）

把「命中」的判据从**帧窗**换成 **期望 `segmentHash`**（`shot-cache.ts:89`，输入 = 段窗 + 段活跃轨 + quality + globals）：

- `missingArtifacts`：期望 hash 不在盘 ⇒ 缺 ⇒ 补渲（改内容、升档都自然命中「缺」）。
- `publishSegmentsFromCache`：按期望 hash 取件；取不到 ⇒ **不复制**，回执写「N 段缓存陈旧/缺失，未发布」。
- 收益：托盘与成片永远同源；副作用是升档首次整片渲染要多渲 7 段（≈+1× 时长），这是必要成本。

### 2.1 缺陷 A：spot 抽帧渲染 0/3 成功，规律极稳定

- 三次全部失败在 `进度 50%`，与 manifest 内容无关（改 s2 前后都卡）。
- 同一条素材整片渲染 **0 次失败**（draft 38.4s / standard 40.2s / high 40.2s，共 9 次全部成功）。
- 因此**不是**「渲染慢／预算不足／内容有问题」，是 spot 通道自身。

- 产品级短期缓解：`render_composition` 对 `spotFrames.length > 4` 直接拒收并建议「整片 draft 代替」，或让 spot 走帧范围渲染（同一渲染器，非逐帧 renderStill）。

| ③ 6 条测试用例 | 21:24:46–21:41:24 | 16m38s | 15.2s（1%） | 1209s（**99%**） |

### 3.2 阶段 ② 的 35m53s 花在哪（47 次调用）

| 环节 | 耗时 | 说明 |
|---|---|---|
| 读 skill 文档 + 探查 manifest/spec | ≈6m | 6 次 bash/read（`spec-capability` / `manifest-contract` / `motion-patterns` / `component-contract`） |
| 写改造脚本 + 4 轮校验返工 | ≈14m | 3 → 8 → 3 → 0 条 schema 错误（transition 指向已删轨、callout 缺 box、box 与 animate 冲突） |
| **spot 渲染两次失败** | **2m08s** | 缺陷 A，纯浪费 |
| draft 渲染 | 38.5s + 38.4s | 两次 |
| 抽帧核对 | ≈7m | 16 张 PNG + 2 次 vstack + inspect_image |
| high 渲染 | 40.2s | 最终成片 |

**渲染总耗时 245.2s，其中 128.1s 是失败的 spot 单**。真正的成片渲染只有 117s。

### 3.3 对照：单段重渲本身只要 5.2s

| 操作 | 实测 |
|---|---|
| `rerender_segment(s3, high)` | **5.1s**（223 帧 1080p） |
| `rerender_segment(s5, high)` | **5.2s**（223 帧 1080p） |
| 整片 draft 2400 帧 | 38.4s |
| 整片 high 2400 帧 | 40.2s |
| 段合声 9 段 | 0.4–0.5s（均 50–51ms） |

结论：**「调整分镜慢」不是渲染慢，是编排链路长**。用户的 6 分钟感知里，<10 秒是渲染，其余全是模型在「读文档 → 手写 31 段 animate 关键帧 → 被 schema 打回 → 重新数帧」。

## 5. 新挖出来的深层问题（按严重度）

### 5.1 P0 · 「改一屏表现」没有工具入口，改动必然丢

- spec 只能表达「卡 + 文案 + 格位」（`content-spec.ts` 的 section 字段），**表达不了沿路径运动 / 分段停顿 / 引线标注**。
- 于是模型只能手改 `build/manifest.json`（生成物）。模型自己在两个地方说清了这件事：
  - 「若用 `writeTo` 重编 manifest，会把第 2 屏手工编写的椭圆轨道重建成旧文字卡，所以我只改 spec 与对应的那一条轨道」
  - 「拆分要重新生成 spec 段表，这会覆盖 manifest，所以我会在重编后恢复第 2 屏的椭圆轨道和音频」
- 结论：**REQ-041「审阅 → 迭代」闭环缺一层持久化载体**。用户的真实诉求「这一屏效果不够，改成动画」在本产品里没有合法路径，只有「改生成物 + 祈祷不要重编」。
- 方向（下一期需求，非本批）：spec 增加 `section.extraTracks`（或用 `overrides` 声明「本段这层手工轨由 spec 携带」），让 scaffold 重编时把它们一起产出；或提供 `patch_segment_tracks` 工具把手工轨写进 spec 而不是 manifest。

### 5.2 P1 · 一次改一屏，缓存命中从 7/9 掉到 1/9（轨序敏感）

实测（同一份 `shot-cache` 目录，按 draft 档算期望 hash）：

| manifest | 轨数 | draft 命中 |
|---|---|---|
| `build/manifest-before-s2.json`（改 s2 前） | 160 | **7/9** |
| `build/manifest.json`（改 s2 后） | 157 | **1/9** |

原因不是「改了 9 屏」，而是 s2 改写脚本把 `tracks` 数组重排了（`filter(...)` + `push(...)` 把新轨放到末尾），而 `segmentHash` 的输入是 `tracks: segment.tracks`（**有序数组**，`shot-cache.ts:95`）。轨序在 Remotion 里承载 z 序，所以不能简单排序消掉——但它把「改一段」的缓存代价放大成「全片重渲」。

方向：给轨加显式 `zIndex`（语义层）后，hash 用 `(id, zIndex)` 稳定排序 + 其余字段；或在工具层保证编辑不重排。**不做这一步，P0 的 hash 命中改造会让每次改一屏都付整片重渲的钱。**

### 5.3 P1 · 目标时长三处不一致（每次交付都报红）

- `projects.json` 的 `plan.targetDuration = 15`（建项目时那次，从未更新）
- `storyboard.meta.targetDuration = 60`（`write_storyboard` 收的值）
- 成片 **80.02s**
- `deliver/card.json`：`durationCheck: { targetDurationSec: 15, deltaSec: 65, durationMismatch: true }`

`write_storyboard` 收了 60 却不回写 plan，交付卡取 plan ⇒ 每一版交付都带一条假红。

### 5.4 P1 · 会话中断留下 spec/manifest 分叉态（当前盘上就是这个状态）

```
spec.sections:     s1 s2 s3 s4 s5 s6 s6b s7 s8 s9   (10 屏)
manifest.meta.segments: s1..s9                       (9 段)
```

- 现在渲染安全（`resolveShotBoundaries` 优先用 manifest 声明段表，实测 `planSegmentTable` 仍出 9 段且 ref 对齐）。
- 但**下一次 `scaffold_manifest` 会变成 10 屏**，全片眉标 `0X / 09 → 0X / 10`、段表整体位移，而 s2 的手工轨道会丢。这是「用户看到的两件事都没生效」的隐藏原因。
- 建议：动手前先决定「拆屏到底做不做」，别让分叉态过夜。

### 5.5 P2 · 其他

- **版本号差一档（复发）**：`card.json` 写 `anchorVersion: 7`，而同秒落盘的快照是 `build/versions/v8.json`（21:21:00）。上一轮已报，未修。
- **「段」二义（复发）**：每轮回执都有 `段边界相对 v1 变了（33 段 → 26 段）`——这里的「段」是字幕卡轨数，与分镜 9 段重名。模型每次都要额外解释。
- **临时产物无约定**：`build/` 里留下 `make-orbit-s2.mjs`、`make-orbit-s2.cjs`、`manifest-before-s2.json`、`manifest-before-s5.json`、`manifest-before-split6.json`、`spec-before-*.json`、`manifest.json.pretty.json`、`check/`（16 张 PNG）。这些会被下一次 `list_references` / 磁盘统计带上。
- **spot 帧数越界**：t=1606 传了 9 帧，skill 写的是 1–8；`host-tools.ts` 只校验「是数组」，不校验上限。

### 8.2 F2 · 画序归一化 —— ✅ 已完成（2026-11-25 23:0x）

**做了什么**：`shot-cache.ts` 新增 `canonicalTracks`，`segmentHash` 前先归一。

- 规则：**只对时间不重叠的轨重排**（它们永远不同帧出现，顺序是纯噪声）；时间重叠的轨连边 `前→后` 保持原相对次序，在这个偏序上做确定性拓扑排序。
- 为什么不简单 `sort(by id)`：`Root.tsx:238` 按数组顺序 `<Sequence>` 渲染 ⇒ **数组顺序就是 z-order**，对重叠轨排序等于让两份不同画面算出同一个 hash。
- 归一化**只进 hash**，渲染仍用原始数组：存量项目画面零变化。`group` 容器的子轨递归处理。

**守卫**：不重叠换序 ⇒ 同 hash（s1 里必须有两条轨，否则用例无鉴别力 —— 第一版就因为两条轨分属两段而假绿）；重叠换序 ⇒ hash 必须不同；group 子轨同理；`canonicalTracks` 不许就地改入参；端到端「编辑脚本重排不重叠轨」⇒ 零渲染。

**反向变异**：天真全排序（无视重叠）⇒ 重叠换序用例红 + group 用例红。

**必须如实记的局限**：用本次真机会话的 `manifest-before-s2.json` vs `manifest.json` 实测，s4–s9 六段**轨内容完全相同**，但**重叠对的相对顺序翻转了 44 对**（例：`s3-u0-eyebrow` 从「在 vignette 之下」变成「在之上」）。那属于真的画序变化 ⇒ 这 6 段必须重渲，归一化**不会**也不该把它们算成命中。所以：

- F2 省下的是「跨段/跨阶段重排」这类噪声（编辑脚本 append / 重新归组）；
- 本次会话那种「整篇 manifest 被重写、同屏内部画序也变了」的成本，只能靠**不重写 manifest**（§5.1 的 F6 入口）解决，不能靠放宽缓存键。

### 8.3 F3 · spot 通道：一帧卡死不带走整批 —— ✅ 已完成（2026-11-25 23:3x）

**根因（这次拿到的是直接证据，不是推测）**

真机会话两次探针的报错原文（`session.v4.jsonl` seq 169 / 404 / 409）：

```
渲染窗口异常：隐藏窗口 31s 内既没有心跳也没有进度（渲染器被卡住），已中止本次渲染。请重试。
```

调用参数：`quality:"draft"`, `spotFrames:[150,480,750,990,1230,1470,1720,1970,2250]`（**9 帧**）。

1. 进度 50% ⇒ 8 帧里已渲出 4 张；第 5 帧（≈1230）把主线程按死 ⇒ 心跳与进度同时停；
2. `RENDER_HOST_STALE_MS = 30s` 看门狗判死**整张工单** ⇒ 已渲好的 4 张一起被丢弃，
   模型看到的只有「请重试」（3 次探针 = 0 张图）；
3. 9 帧 > 契约上限 8，`normalizeSpotFrames` 静默截断 ⇒ 模型以为 9 处都验过。

**改了什么**

| 位置 | 变化 |
|---|---|
| `src/spot-frame-budget.ts`（新） | `runSpotFramesWithTimeout`：**逐帧独立计预算**，超时/报错只丢这一帧，文案带帧号；超时会 abort 该帧的 signal 让 Remotion 尽量停掉。`SPOT_FRAME_TIMEOUT_MS = 25s`（必须 < 看门狗 30s）、`SPOT_FRAME_DELAYRENDER_TIMEOUT_MS = 20s`（Remotion 自己的 `delayRender` 闸门先响，干净释放） |

| `src/spot-upload-ledger.ts`（新） | 边渲边传的账本：一张一传、同帧去重、`settle` 等落地；纯逻辑可单测 |
