## 0. 结论先行

1. **价目表不是预估的前置条件，顺序恰好相反。** `POST /v1/generations/quote` 就是价目表的服务端实现，现在就能调，实测结果与真实扣费**一分不差**（21.1354 = 21.1354）。所以「预估积分」这件事**今天就能做完，不需要等价目表**。
2. **真正需要价目表的只有三件事**：明细行拆解、离线兜底、对外价格页。它们的共同点是「要在没有 quote 的情况下说出一个数」或者「要把一个总数拆成单项」。
3. **价目表的结构比预想的简单，且与「按分辨率分档」的直觉不符**：视频只有**时长**一维（6 积分/秒，480P 与 1080P **同价**），图片才按**像素面积**计价（2e-5 积分/px）。详见 §1.1。
4. **真实消耗只有一个来源**：`GET /v1/credits/ledger` 的 `commit` 条目（`amount` 为负数，带 `generation_id`）。生成快照里**没有金额字段**，参考工程也没做这件事——这块我们要自己造，没有现成答案可抄。

### 分层总览

| 层 | 内容 | 阻塞条件 | 可开工 |
|---|---|---|---|
| **A** | 预估接 quote、实扣回填、积分流水、价目采样脚本 | 无（后端接口全部就绪） | ✅ **现在** |
| **B** | 明细行拆解、离线兜底、价格页 | 需要一份可信价目表（可由 A 层采样产出） | 采样完成后即可 |
| **C** | 快照带金额、ledger 服务端按 generation 过滤、参考素材按个计价 | 需要后端补字段/参数 | ❌ 等后端 |

## 1. 事实基线（实测）

### 1.1 定价模型：10 个 operation 全覆盖

后端没有公开价目接口（`/v1/pricing`、`/v1/credits/pricing`、`/v1/billing/products` 全 404，2026-11-02 实测）。但用 quote 逐点采样可以把公式反推出来，**结果精确到小数点后 4 位无误差**：

| operation | 模型 | 计价公式 | 实测样本 |
|---|---|---|---|
| `txt2image` | `image.krea2` / `image.qwen-image-2.1` | **面积(px) × 0.00002** | 864×480=8.2944；768×1376=21.1354；1920×1088=41.7792；1024²=20.9715；512²=5.2429 |
| `image2image` | `image.qwen-image-2.1` | **面积 × 0.00002 × 1.25** | 10.368 / 26.4192 / 52.224（= 同尺寸 txt2image × 1.25） |
| `image2character` | `image.krea2` | **固定 30** | 30（不吃 width/height，prompt 有无同价） |
| `image2vl` | `image.qwen3-vl` | **固定 4** | 4 |
| `video2vl` | `video.qwen3-vl` | **固定 8** | 8 |
| `image2videofl2va` | `video.minimax_h3` | **秒数 × 6** | 4s=24；5s=30；6s=36；10s=60；15s=90 |
| `image2videoref2va` | `video.minimax_h3` | **秒数 × 6**（quote 层与参考数无关） | 5s=30 |
| `txt2audio` | `audio.yue2` | **秒数 × 1** | 5s=5；10s=10；15s=15；30s=30 |
| `txt2speech` | `audio.voxcpm2` | **固定 3** | 3（40 字与 100 字同价） |
| `asr2txt` | `audio.fast-whisper` | **固定 3** | 3 |

三条必须记住的结论：

1. **视频不看分辨率**。`megapixels` 取 0.4 / 1.0 / 2.0 三档，5s 视频一律 30 积分。⇒ **「一秒 480P 视频多少积分」与「一秒 1080P 视频多少积分」是同一个数：6。** 前端现在给清晰度加 6 / 14 分，是加了后端根本不存在的钱。
2. **图片按面积，不按档位**。同一面积跨模型同价（Krea2 与 Qwen 都是 21.1354）。⇒ 价目表里图片那一条应该是「积分/百万像素」，不是「720P = 25」。
3. **参考素材不按个计价**。`image2image` 是 operation 级的固定 ×1.25 系数，不是「每张图 +2」；视频 ref2va 在 quote 层与 fl2va 同价。前端那套「图×2 / 视频×6 / 音频×3 / 首帧2 / 尾帧3」在后端**没有对应实现**。

> ⚠️ **待验证项 V-1**：ref2va **真实带 9 张参考图**时，`commit` 金额是否仍是「秒数×6」。quote 不吃 `inputs`，所以报价层无法回答，只能真跑一次对照（见 §3.7 验收用例 A-9）。在这条验证出结论前，**UI 不得展示任何参考素材加价明细**。

### 1.2 三个接口的能力边界

| 接口 | 能给什么 | 局限（实测） |
|---|---|---|
| `POST /v1/generations/quote` | `estimated_credits`（4 位小数） | ① 请求体**只收 model/operation/input，不吃 `inputs`** ⇒ 参考素材无法单独报价；② 不建任务不冻结，失败可安全重试 |
| `GET /v1/generations/{id}` | `billing_status`：`none`/`held`/`committed`/`released` | **没有金额字段**。只有状态，拿不到实扣数 |
| `GET /v1/credits/ledger` | `entries[]`，`commit` 条目的 `amount` 为负数 = 真实消耗，带 `generation_id` | ① `?generation_id=` 过滤**无效**（实测被忽略，返回全量最新）；② `?entry_type=` 过滤**无效**；③ `limit` 上限 **200**（传 500 被夹到 200）；④ 倒序（最新在前）；⑤ `cursor` = 上一页最后一条的 `id`（exclusive） |

`ledger` 条目形状（实测样本）：

```json
{
  "id": 42310,
  "entry_type": "commit",
  "amount": -21.1354,
  "lot_id": "fc1485f9-…",
  "hold_id": "ce3c3adf-…",
  "generation_id": "ff2da005-…",
  "lot_balance_after": 798.9729,
  "metadata": { "committed_amount": 21.1354 },
  "created_at": "2026-11-24T11:18:46.716+08:00"
}
```

`hold` 条目额外带 `metadata.model_code` / `metadata.operation` / `metadata.frozen_amount` / `metadata.expires_at`（生成类）；LLM 类走 `llm_request_id` + `metadata.estimated_tokens`，**没有 `generation_id`** —— 所以按 `generation_id` 建索引时，LLM 条目天然被排除，不用额外过滤。

## 2. 分层判据

一条判据贯穿全文：

> **靠 quote + ledger 能不能直接得出答案？**
> 能 → **A 层**（现在做）
> 要「拆到单项」或「没有网络也要算」 → **B 层**（等价目表）
> 接口里根本没有这个字段 → **C 层**（等后端）

据此，用户设想的「一秒 480P 视频多少积分、一张 720P 图多少积分」这张价目表，**服务的是 B 层**，不是 A 层。A 层不需要知道单价，只需要会问。

## 3. A 层：现在就能做

### 3.1 数据管道（5 处 Host 改动）

**A1 · `src/contracts/account.ts` 新增流水契约**

```ts
/** 一条积分流水（`GET /v1/credits/ledger` 的 entries[]）。 */
export interface CreditLedgerEntry {
  readonly id: number
  /** 未知值原样保留（后端可能新增 grant/expire/adjust），不在类型里 switch 全集。 */
  readonly entry_type: string
  /** 带符号：commit 为负、release 为 0、grant 为正。 */
  readonly amount: number
  readonly lot_id: string
  readonly hold_id?: string
  /** 生成类条目才有；LLM 条目只有 llm_request_id。 */
  readonly generation_id?: string
  readonly llm_request_id?: string
  readonly lot_balance_after: number
  readonly metadata?: Record<string, unknown>
  readonly created_at: string
}

export interface CreditLedgerPage {
  readonly entries: readonly CreditLedgerEntry[]
  readonly next_cursor: string | null
}
```

**A2 · `src/drama-management.ts` 新增 `creditLedger()`**

紧贴 `creditBalance`（`:197`）放，保持协议层单一职责：

```ts
async creditLedger(
  token: string,
  options: { limit?: number; cursor?: string } = {},
): Promise<CreditLedgerPage> {
  const qs = new URLSearchParams()
  if (options.limit !== undefined) qs.set('limit', String(Math.min(200, options.limit)))
  if (options.cursor !== undefined) qs.set('cursor', options.cursor)
  const suffix = qs.size > 0 ? `?${qs.toString()}` : ''
  return this.#request<CreditLedgerPage>(token, `/v1/credits/ledger${suffix}`)
}
```

解析必须容忍未知字段（`entry_type` 不枚举校验，`metadata` 原样保留）——服务端加一种条目类型不该让整页变空。

**A3 · `src/account-state.ts` 扩出流水段**

与余额同一套纪律（TTL / 在飞去重 / 403 停手 / 失败留旧值），**不新写一份**。余额 TTL 30s、流水 TTL 建议 60s（流水变化比余额慢，且体量大）。

**A4 · `src/routes.ts` 新增读路由**

沿用现有命名：`GET /canvas-studio/account/ledger?limit=&cursor=`（对照 `ROUTE_ACCOUNT_CREDITS`，`:294`）。同样只读、405 拒写。

**A5 · 生成结束时绑定 `generation_id → credits`**

这是整个功能的关键一步，也是最容易做错的一步。两段绑定：

- **提交时**（`generate.ts:989-991`、`:2693-2695` 的 quote 分支）：记 `{ generationId?: 未知, estimated }`。此刻还没有 generationId（quote 在 create 之前），所以 **quote 值只用于 UI 的「预计」**，不进台账。
- **终态后**（`followGeneration` 返回 `final.id`）：把 `{ generationId: final.id, estimated }` 写入项目台账；`billing_status === 'committed'` 时再向 ledger 增量拉一次，补上 `actual`。

增量拉取的锚点用 **`lot_balance_after` 或本地最大 `id`**，不要用时间戳（服务端时间与本地时钟不同源）。

### 3.2 预估展示（4 处）

统一走一条新 Host 路由 `POST /canvas-studio/account/quote`（client 无 token，必须 Host 代调）。**client 侧只保留一个 hook**，不要在三个组件里各写一份 effect。

| # | 位置 | 文件:行 | 现状 | 改法 |
|---|---|---|---|---|
| 1 | 图片节点 chip | `client/canvas/NodeInputCard.tsx:1731` | `CREDIT_ESTIMATE[resolution]` | 走 hook，参数 `{operation:'txt2image', width, height}` |
| 2 | 视频节点 chip + 明细弹层 | `NodeInputCard.tsx:2047`、`:934-955` | `creditRows` 前端公式 | chip 走 hook；**明细弹层先只显示总数 + 一行「按服务端报价，明细逐项拆分待价目表」**（B 层再做拆解） |
| 3 | 音频节点 chip | `NodeInputCard.tsx:1858` | `creditCostOf` | 走 hook：TTS 传 `txt2speech`，音乐传 `txt2audio` + `duration` |
| 4 | 节点「重新生成一版」 | `client/canvas/NodeActionBar.tsx:116` | **零提示** | 直接把该节点的 generation 参数喂同一 hook，按钮旁显示 `✦ 21.14` |

统一 hook 的形状（**照抄参考工程的骨架**）：

```ts
// client/use-credit-quote.ts
// 三态：'idle' | 'loading' | 'ok' | 'failed'；参数变先清旧值；300ms 防抖；AbortController 取消在飞。
// 依赖只列计价参数指纹，不列 prompt 文本本身（prompt 不影响价格，改一个字不该重新报价）。
```

接口设计要点：
- **指纹缓存**：`model|operation|width|height|duration|megapixels` → 结果。同一指纹 5 分钟内命中缓存直接返回，不请求。
- **失败保留上一次成功值但标灰**，显示「约 N」（同时 `title` 挂原因）。quote 失败不阻断提交（与 Host 侧 fail-open 一致）。
- **预估与余额同屏**：把 `available_balance` 一起渲染成「预计 30 · 剩余 798」。参考工程这么做是对的——用户真正的决策依据是「花得起吗」。

模型选择必须复用 `src/model-route.ts` 的决策（纯函数、无 IO，client 可直接 import）：图片带可显示文字 → `image.qwen-image-2.1`，否则 `image.krea2`。否则 UI 报的价与实际走的模型不是同一条链。

展示口径（避免用户困惑）：
- **只显示 2 位小数**（用户 2026-11-02 已拍板「小数位只让人困惑」）：21.1354 → `21.14`。
- 三态文案必须区分：`冻结 21.14`（held）/ `消耗 21.14`（committed）/ `已释放`（released，失败退款）。
- **失败/取消不显示金额**，只显示「已释放」，避免用户以为钱没了。

### 3.4 积分流水页（1 处）

`client/BillingPage.tsx` 新增「积分流水」区块：

- 每条：时间 + 类型标签（生成/对话/充值/过期/调账）+ 金额（负数红、正数绿——按国内习惯反向？**这里用中性色**：金额是账务不是涨跌，`−21.14` 用常规前景色，只有正数加绿）+ 余额快照。
- **点条目能跳到画布节点**（有 `generation_id` 且在本地台账里命中时）。这是流水页真正的价值——不是记账，是「这笔钱花在哪了」。
- 分页：`cursor` 到底就用完，不做无限滚动，先给「加载更多」。

### 3.5 价目采样脚本（A 层最后一件，也是 B 层的原料）

`scripts/probe-pricing.mjs`：只读、幂等、不扣分（全走 quote）。

- 扫矩阵：图片尺寸 3 档 × 2 模型 × 2 operation；视频 6 个时长 × 2 operation × 3 megapixels；音频 4 个时长；固定价 5 项。
- 输出 `capabilities/pricing.json`，每项带 `sampled_at`。
- 断言：采样结果必须能被 §1.1 的公式复算到 4 位小数；对不上就告警（说明后端改价了）。

这个脚本让「价目表」从口头约定变成**可复现的产物**，也是 B 层的输入。

### 3.7 A 层风险

| 风险 | 处置 |
|---|---|
| quote 打太频繁（改一次参数 3 个请求） | 指纹缓存 + 300ms 防抖 + 在飞去重，三层都要 |

## 4. B 层：等价目表完善

### 4.1 价目表要什么形状

```ts
// 每条规则 = 一个 operation/model 的计价方式
export interface PriceRule {
  readonly operation: GenerationOperation
  readonly model: string            // 模型 code
  readonly basis: 'pixels' | 'seconds' | 'flat'
  readonly rate: number             // pixels: 积分/px；seconds: 积分/秒；flat: 固定积分
  readonly multiplier?: number      // 参考系数（如 image2image 的 1.25）
  readonly sampledAt: string        // 采样时间，缺一不可
}
```

按 §1.1 实测，这张表只有 10 条，且**只有两个维度**（面积、时长）。它不可能也不需要长成「一分钟 480P/720P/1080P 三行」那种形式——**视频不分分辨率**。

### 4.2 三个用处（对应三个可做项）

| # | 用处 | 依赖 | 为什么不能进 A 层 |
|---|---|---|---|
| B1 | 视频明细弹层逐行拆解（「时长 15s × 6 = 90」） | 价目表 | 后端只给总数，拆解必然要本地乘除 |
| B2 | quote 不可用时的离线兜底（显示「约 90」而不是「—」） | 价目表 | 没网络就没数，只能本地算 |
| B3 | 对外价格页（「1 秒视频 6 积分，百万像素图 20 积分」） | 价目表 + 定价决策 | 这是**商业决策**，不是技术实现 |

**B 层铁律**：价目表**永远只做兜底与拆解，绝不覆盖 quote**。展示优先级：`quote 结果` > `价目表推算（标注「约」）` > `—`。一张过期的表必须降级成「约」，不能伪装成精确值。

### 4.3 现在可以先立的接口（占位）

`src/price-table.ts` 先只写签名与「读 `capabilities/pricing.json` 并校验 `sampledAt` 新鲜度（建议 7 天）」的逻辑，`quote` 链路一行不碰。这样 B 层开工时不用再改 A 层的代码。

> **已落地（第 3 批）**：`src/price-table.ts` + `capabilities/pricing.json` + `scripts/probe-pricing.mjs`。
> 表结构相对上文的 `PriceRule` 有一处修正：**以 `operation` 为键，模型放进 `models` 数组**。
> 理由：「同 operation 同价」是实测事实（Krea2 与 Qwen 的 `txt2image` 都是 21.1354），
> 按 `(operation, model)` 分行会造出 11 条只能靠人工同步的重复规则；按 operation 归一条
> 之后，新增同价模型只需要一次采样。
