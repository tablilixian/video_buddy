# REQ-034 · 后台渲染方案（v2 · 2026-10-19）

> **v2 修订摘要**：v1 推荐「双通道（standard/high 走 SSR）」，前提是接受 +250MB 包体。你已明确 **D1 不接受** ⇒ SSR 出局。
> v2 另有一处**事实修正**：v1 写「隐藏窗口方案必须改 dsh shell」——**这是错的**。查证后确认零改动即可实现（见 §2）。
> 结果：v2 的主方案比 v1 更轻（零二进制、零 shell 改动），而且**比 SSR 快 7 倍**。

---

## 0. 结论先行

1. **ffmpeg 不承担渲染**（v1 结论不变）。它跑不了 React 组件、量不了字体、算不了缓动；能力边界在像素与流，位置永远是收尾（探真值、拼接、混音）。
2. **SSR 路线放弃**。它的唯一硬门槛是 headless Chromium 那 210MB，而「用系统 Chrome 顶替」不可控（用户机器不一定装、版本不一、`chrome-headless-shell` 的协议与开关也不保证兼容）。
3. **主方案 = RenderHost：一个专用隐藏 BrowserWindow 承载渲染**。
   - 包体增量：**0 个二进制**，只多一个几 MB 的 JS bundle；
   - 改 dsh：**不需要**（v1 的判断有误，论证见 §2）；
   - 速度：沿用 CSR 引擎，**13ms/帧**（20 秒片 ≈8s），比 SSR 的 ~90ms/帧快约 7 倍；
   - 预览 = 成片：同一套组件树、同一个引擎，天然一致。
4. **顺带解决两件事**：渲染不再依赖「画布页在前台」（连用户切走页面、切会话都不影响）；W6 的 `frames[]` / `report{}` 可以真正回到模型手里。

## 2. 为什么**不用**改 dsh（v1 判断的修正）

### 2.1 v1 为什么说要改

v1 的依据是：`dsh-plugin-desktop/src/window-options.ts:34` 的 `webPreferences` 里没有 `backgroundThrottling`，吃默认值 `true`；而那是 `BrowserWindowConstructorOptions`，看形态只能在建窗口的地方改 ⇒ 推断必须动 shell。

### 2.2 两条推翻它的证据

**证据 A：Canvas Studio 的 Host 与 Electron 主进程是同一个进程。**

`dsh-plugin-desktop/src/main.ts` 顶部就是 `import { app, crashReporter, shell } from 'electron'`，而 `:840` 的 `const ctx = await boot(...)` 在同一个文件、同一个进程里就地建起 Cordis root，随后 `hostCtx.provide(...)`、`hostCtx.plugin(DesktopActionsService, ...)`。
⇒ canvas-studio 的 Host 侧（`lib/index.js`，即 `registerStudioRoutes(ctx, ...)` 的调用方）**就运行在 Electron 主进程里**，`import('electron')` 拿得到 `BrowserWindow` / `powerSaveBlocker` / `app`。

**证据 B：Electron 43.4.0 提供运行时关节流的 API，不必在建窗口时决定。**

```
webContents.setBackgroundThrottling(allowed: boolean): void
```
（`electron.d.ts:18463`，Electron 43.4.0）
官方注释：*“Controls whether or not this WebContents will throttle animations and timers when the page becomes backgrounded. This also affects the Page Visibility API.”*

⇒ 即使窗口已经建好，也能在运行时关掉节流。**不需要重建窗口，更不需要改 shell。**

### 2.3 结论

| 原以为要改的地方 | 实际做法 | 是否碰 dsh |
|---|---|---|
| `window-options.ts` 加 `backgroundThrottling:false` | 运行时 `webContents.setBackgroundThrottling(false)` | ❌ |
| 主进程加 `powerSaveBlocker` | Host 侧 `powerSaveBlocker.start('prevent-app-suspension')` | ❌ |
| 主进程加 `disable-backgrounding-occluded-windows` 开关 | RenderHost 的 `webPreferences` 自带 `backgroundThrottling:false`（自己建的窗口，参数自己写） | ❌ |

**唯一残留风险**：`import('electron')` 在 plugin 的加载路径里能否解析（dsh 装了 `installProfilePackageResolver`，走的是自定义 module 解析）。这必须先 spike 验证。三条退化路径，见 §5.1。

> 这条修正的意义不只是"少改一处"：项目的红线是「不碰 dsh 本体」（`tests/host-boundary.test.mjs`）。v1 的方案会踩红线，v2 不会。

## 4. 主方案：RenderHost

### 4.1 形态

```
Host（Electron 主进程，canvas-studio 的 lib/index.js 就在这里）
 │
 ├─ 渲染请求（render_composition）
 │    ├─ 建工单（现有 pendingRenderJobFor / runRenderJob，单条串行，见 §4.4）
 │    ├─ powerSaveBlocker.start('prevent-app-suspension')
 │    └─ ensureRenderHost()  ←── 首次才建，复用已有
 │
 └─ RenderHost：new BrowserWindow({
        show: false,
        width: 1280, height: 736,
        webPreferences: {
          backgroundThrottling: false,     // 关键：隐藏也照跑
          nodeIntegration: false, contextIsolation: true, sandbox: true,
          partition: <与主窗口同一个>       // 复用本地资源访问
        }
      })
      └─ loadURL(`http://127.0.0.1:${ctx.webServer.port}/canvas-studio/render-host`)
           └─ 页面内：轮询 pending → renderManifestOnWeb() → 每秒 reportProgress → commit(字节, frames, report)
```

端口来源已确认现成：`routes.ts:641` 里就是 `const expectedPort = ctx.webServer.port`。

### 4.2 新增文件（4 个 + 3 处接线）

| 文件 | 职责 |
|---|---|
| `src/render-host/main.ts` | 页面入口：轮询工单 → 调 `renderManifestOnWeb` → 上报进度/抽帧/报告 → commit；`document.title` 暴露状态便于宿主观察 |
| `src/render-host/html.ts` | 返回那一个 HTML（一行 `<script type="module" src="/canvas-studio/render-host.js">`），由 `routes.ts` 以 `text/html` 输出 |
| `src/render-host/window.ts` | Host 侧：`ensureRenderHost()` / `disposeRenderHost()` / 空闲回收；`import('electron')` 的兜底逻辑都在这里（单点） |
| `src/render-host/power.ts` | `powerSaveBlocker` 的 start/stop，含"渲染中才持有"的引用计数 |

接线三处：`routes.ts`（两个新路由：HTML 页 + bundle）、`tsdown.config.ts`（第二个 browser entry）、`remotion/render-job.ts`（执行者从"客户端轮询"改成"Host 主动派发给 RenderHost"，并加心跳）。

### 4.3 与现有工单桥的关系

**保留工单，不改契约**：`PendingRenderJob` / `commitRenderJob` / `recordRenderSample` / `reportRenderJobProgress` 全部复用。只有"谁来取单"从**用户页面**换成 **RenderHost 页面**。

好处：客户端 `remotion-render.ts` 的渲染逻辑一行不用动（RenderHost 直接 import 同一份 `renderManifestOnWeb`），预览快渲（`render-preview.ts`）也照旧走用户页面。**两条执行者、一套实现。**

### 4.4 串行与进度（D3 的决定）

- 你选「单条串行 + 进度条」 ⇒ 现有模型正好够：`pendingRenderJobFor(projectId)` 单工单 + `activeRenderJobCount()` / `queuedRenderJobCount()` 已有计数。**不需要引入并发调度**。
- 进度条：RenderHost 每秒 `reportRenderJobProgress(jobId, 0..1)`；画布页挂载时读 `listRenderJobViews()` 显示「后台渲染中 62%」，用户切走再回来能接上。
- 「离开页面也能看到进度」需要一个常驻入口 —— 最小实现是画布页回来可见；可选增强是走 `dsh-client-ui-slots` 挂状态栏（复用现有 `SlateBar` 模式），**不进本期**。

### 4.5 三个必须处理的新风险

| 风险 | 处理 |
|---|---|
| RenderHost 崩了 / 白屏 ⇒ 又是静默挂死 | **心跳判活**：超过 30s 无进度上报 ⇒ 判失联、结束工单、给出「渲染窗口异常，已中止」；不靠 10 分钟超时兜 |
| 用户整个 App 关掉 | 无法避免，明确写进工具描述与文档：**关应用会中断渲染**（这是任意本地渲染器的边界，SSR 也一样） |
| 隐藏窗口吃内存（一个 renderer 进程 + remotion） | 空闲 5 分钟销毁；下次冷启约 1s。渲染期间常驻一个进程，可接受 |

### 5.2 S1 · RenderHost 骨架

- `src/render-host/{main,html,window,power}.ts`
- `tsdown.config.ts` 加第二个 entry（`platform: 'browser'`，把 `remotion` / `@remotion/*` / `react` 打进去）
- `routes.ts` 加 `/canvas-studio/render-host`（HTML）与 `/canvas-studio/render-host.js`（bundle），沿用 loopback 校验
- 验收：手动 `loadURL` 能看到页面自报"idle"

### 5.3 S2 · 把执行者换过去

- `runRenderJob` 里加 `dispatch()`：优先派给 RenderHost；RenderHost 不可用时**回退**到现有客户端轮询（保底，不破坏当前能力）
- 心跳：`reportRenderJobProgress` 里更新 `lastSeenAt`；`runRenderJob` 的等待循环改为「监听完成」而不是固定 sleep 轮询
- 超时：`clamp(帧数 × 200ms + 60s, 90s, 20min)`，替换 `RENDER_TIMEOUT_MIN_MS = 10min`
- 验收：渲染中把主窗口最小化 / 切到别的 Space / 切 dsh 内的别的会话，成片仍产出

### 5.4 S3 · 关掉主窗口节流（可选但便宜）

主窗口也 `setBackgroundThrottling(false)` **只在渲染期间**（引用计数），减少"用户就留在画布页、只是窗口被盖住"这类场景的浪费。渲染结束即恢复 —— 不做常开，避免长期影响其它 UI 的定时器行为。

### 5.5 S4 · 把 W6 闭环一起补掉（与后台化无关，但顺手）

`renderComposeResult`（`host-tools.ts:321-339`）把 `frames[]` 与 `report{}` 拼进结果文本；schema 里早就有，只是没渲染。这是上一轮评审的 P0-1。

## 8. 附：SSR / CSR 到底指什么

一句话：**同一份 React 组件，在哪台「浏览器」里被执行、被拍成帧。**

| | CSR（当前） | SSR（v1 曾推荐，现放弃） |
|---|---|---|
| 全称 | Client-Side Rendering | Server-Side Rendering |
| 谁来执行组件 | **用户正在看的那个页面**的 Chromium | 宿主另外起的**无头 Chromium**（`@remotion/renderer` + `chrome-headless-shell`） |
| 谁来编码成 mp4 | 页面的 `VideoEncoder`（WebCodecs） | `compositor` 原生二进制 + ffmpeg |
| 页面前台要求 | **要**（rAF / timer 被节流就停摆） | 不要 |
| 启动成本 | 0（页面已经在跑） | 一个浏览器进程（210MB 二进制 + 冷启） |
| 速度 | 13 ms/帧 | ~90 ms/帧 |

为什么 SSR 更适合"后台"：因为它的"浏览器"**没有可见性概念** —— 它天生是不可见的，没人能最小化它。
为什么 CSR 更快：没有跨进程取帧、没有 native 编码转交，帧直接从活动 DOM 光栅化后进 WebCodecs。

**RenderHost 的取巧之处**：它既享受 CSR 的速度（还是同一套 WebCodecs 路径），又拿到了 SSR 的"与用户窗口无关"（因为那个窗口是**我们自己的隐藏窗口**，用户看不见、也最小化不了它）。
