## 二、经验与教训（后续体裁直接继承）

### 做对了的（照做）

1. **先核实真缺口再动手**——缺口清单是快照不是事实，动手前读码核实（例：shot-cards 写「缺 rotate」，真缺口是 pivot 轴心）。
2. **三层 skill 架构 + 薄壳纪律**——总纲（路由/审批）→ 编排壳（≈4KB：定向/路由表/executor 指派/验收清单）→ executor（手法库）。壳只做「走哪条路」不做「怎么走」；结构预算等细则只在 executor 层写一份（唯一权威 + 壳内指针）。
3. **能力与编排并行**——能力批给 executor 供弹药，整片验收用一条提示词同时验多能力 + 结构纪律，验收成本摊薄。
4. **验收方式**——确定性提示词 + 逐条判据表 + 负例补刀（如 anchor 越界必须拒收）+ 会话实录回传做证据链核对。
5. **闸门先行**——反向变异（守卫关掉必须变红）、行数棘轮、字段文档机器生成门禁、快照深相等，每笔改动有守卫接住。

### 踩了的坑（避开）

1. **守卫吃编译产物**：改 `skill-catalog.ts` / `platform.yaml` 后必须先 `yarn build` 再跑测试，否则假红。
2. **文档腐化**：能力落地当天同步 shot-cards / manifest-contract / 字段文档（`gen:manifest-fields`），四处同步是硬成本。
3. **skill 措辞向真机行为对齐**：真机验证出的更优行为（如路由+定向合并提问）立即回写 SKILL.md，不坚持想象中的流程。
4. **上下文预算 = 耗时第一杠杆**（130min 会话实测 3 次 compaction）：references 按需读、bash 大输出落文件只回摘要、旁白先按 4–5 字/秒卡预算——已落 `explainer-patterns.md` §流程纪律，后续体裁 skill 同款照抄。
5. **体积贴线**：code-driven-explainer/SKILL.md 12206B / 闸 12288B（`ENTRY_LIMIT = 12*1024`，tests/skill-progressive-disclosure.test.mjs:43）。给现有 skill 加内容前先看余量，等量瘦身（砍重复指针）是标准手法。
6. **环境怪癖**：heredoc python 疑似双执行（以最终状态 grep 为准）、BSD grep 不支持 BRE `\|`、git index.lock 自愈残留。

## 四、新会话开工约定（必读）

1. **开工前**：读本文件 + `docs/STATUS.md` 头部与 §4 尾部（水位复核，不预领号）；`git log` 确认基线。
2. **每批改动**：`yarn check` 全绿才算完（typecheck + gen:manifest-fields 门禁 + build + verify:loader + smoke）；守卫必须反向变异验红。
3. **skill 新增**：照 explainer-format-director 模式三件套——SKILL.md（薄壳 ≤4KB 目标 / 硬闸 12288B）+ platform.yaml（category: `format`）+ skill-catalog.ts 快照同步；改 catalog/yaml 后先 `yarn build` 再跑测试。executor 层细则进 references（唯一权威），壳内只放指针。
4. **验收**：每体裁整片验收用「确定性提示词 + 逐条判据 + 负例补刀」，用户回传实录/成片后按转录核对；通过后才转正与登记。
5. **登记**：三层入库（STATUS §4 索引行 ≤400B/标题 ≤40 字符 + cv-details 条目 + changelog 一行）→ §0 水位与文件头 → `node scripts/status-summary.mjs` 重算 → `tests/status-shape.test.mjs` 闸验证。
6. **commit 纪律**：助手 commit、push 用户手动；未经用户批准不 commit。
