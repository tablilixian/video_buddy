## 2. 先说对的：三处我验过是对的

### 2.1 frameRange 闭区间换算（R11 的 P0 修复核心）

`node_modules/@remotion/web-renderer` 的 `getRealFrameRange`：

```js
if (resolved[0] < 0 || resolved[1] >= durationInFrames || resolved[0] > resolved[1]) throw ...
```

⇒ 半开窗 `[start, end)` 直传确实会：末段 `end === durationInFrames` 抛错、中间段多渲一帧。
`segmentRenderOptions` 传 `[start, end-1]` 是**唯一正确**写法，注释与实现一致，测试
（`req038-r11-segment-render.test.mjs`）把三个段窗的闭区间值逐条钉死。这条修得干净。

### 2.2 段 hash 的依赖传递语义

「改 s2 的 copy ⇒ s1 也脏」不是误伤，而是转场窗 `[b−10, b)` 归前段（D2）的必然后果。
测试把三种错误形态（全脏 / 只脏 s2 / 全复用）都写进注释，这个测试值钱。

### 2.3 非 autoStages 的边界派生

`boundariesFromSpec`（`shot-slice.ts:71-85`）与 `planRecipe`（`recipes.ts:177-195`）逐行对齐：
前 n−1 段 `round(w/total × totalFrames)` 累加、末段吃余数。**复刻是忠实的**，不会出现
「切在屏中间」导致的视觉问题。（即便漂几帧也只是缓存粒度变差，不影响成片。）

## 3. 需要修的问题

### P1-1 分镜路径丢抽帧与渲染报告（模型失去画面证据）

**证据链**：

| 位置 | 事实 |
|---|---|
| `host-tools.ts:4030-4038` | 合成 `shotOutcome`：`frames: []`、`report: undefined as unknown as RenderJobReport` |
| `remotion-render.ts:285` | `frameRange !== undefined ⇒ sampleFrames = []`（段渲染根本不抽帧） |
| `host-tools.ts:841-848` | `renderComposeResult` 的抽帧段是**唯一**给模型画面证据的入口（REQ-034 O-01 事故：8 张抽帧落盘、模型不知道） |
| `render-report-text.ts:83+` | `formatRenderVerdict` 全部判据来自 `report`，`{}` ⇒ 自检行基本空 |

**后果**：standard/high 主路径上，模型拿到的回执从「规格/文字溢出/音频/耗时 + N 张抽帧」
退化成「三段文字 + lint 计数」。skill 里「画面判据必须看图本身」的纪律在这条路上**不可执行**。

**建议**（成本递增，可只做前两条）：

1. concat 之后用宿主 ffmpeg 抽帧：`pickSampleFrames(renderManifest)` 给帧号，
   `video-frames.ts` 已有 `runFfmpeg` 全套，抽完 `saveLocalAssetBytes` + 填进 `frames`。
2. `report` 至少填宿主手里已有的字段（`width`/`height`/`quality`/`durationInFrames`），
   段落的 `textFit` 从各 `segOutcome.report.textFit` 汇总——现在 `segOutcome` 只取了
   `assetFile`，其余全丢，连 `warnings` 也丢（字体缺失告警在分镜路径静默了）。
3. 若暂不做，至少在回执里显式写「本次分段渲染无抽帧」，别让模型以为自己漏看了。

### P1-2 超时预算没按 frameRange 收窄

`render-job.ts:881`：

```ts
renderTimeoutMs(spotFrames.length > 0 ? spotFrames.length : manifest.meta.durationInFrames, jobQuality)
```

段工单的 manifest 由 `segmentManifest` 产出，**保留整片 `meta.durationInFrames = 600`**
（这是 frameRange 渲染的正确前提），于是每段都按 600 帧算预算：

- 每段 standard：`600×240ms + 60s = 204s`；实际只渲 200 帧，应给 `108s`；
- 3 段合计预算 `612s`，而整片一次只需 `204s`；
- 一个真卡死的段要白等 204s 才浮出（`render-budget.ts` 头注释专门写过「把最坏等待从
  10 分钟压到 1.5 分钟」，这里又回去了）。

**建议**：同一行加一个分支——`frameRange` 存在时按 `end - start + 1` 计帧数。
和 `spotFrames` 同一原则，源码里已有先例注释，属纯漏改。单测钉 `timeoutMs` 值即可。

### P1-3 分镜路径完全跳过 Q2 时序回核

`commitRenderJob` 里的 `verifyTeardown`（timingSegments 回核）、loudness 探测、
`recordTransientAsset` 全被绕过。用户传了 `timingSegments` 渲染，分镜路径下
`report.timingCheck` 永远缺失 —— 「表先回核、片渲完再回核」的第二半静默失效。
（`segmentRenderOptions` 也确实没透传 `timingSegments`，两头一致地没做。）

**建议**：concat 后在 merged 产物上补跑一次回核，或至少在 `allowShots` 里把
「传了 timingSegments」也算回退条件，别静默降级。

| 容器时长 | 6.698667（被音轨拉长），格式时长 ≠ 视频流时长 |
| 成片 `deliver/final.mp4` | `nb_frames=600`、`duration=20.066667`、`avg_frame_rate=9000/301`、另有 `aac 20.096s` |
| 帧时间戳 | 第 200 帧 `6.6333→6.7`（Δ0.0667）、第 400 帧 `13.3333→13.4`（Δ0.0667）；其余全部 Δ=1/30 |

**根因**（`remotion-render.ts:313`）：

```ts
audioCodec: options.muteAudio === true ? null : 'aac',
```

web-renderer 侧 `dist/esm/index.mjs:339` 是 `requestedCodec ?? getDefaultAudioCodecForContainer(container)`
—— **`null` 被 `??` 当成「没指定」**，回落到 mp4 的默认 `aac`，音轨照编。真正的关断开关是同文件
`:474` 的 `const muted = options.muted ?? false`（`if (!muted)` 才解析音频编码、`createAudioSampleSource`
返回 null ⇒ 不加音轨），而它就在公开选项里（`render-media-on-web.d.ts:70`）。

**后果**（按严重度）：

1. `concatShots` 的 `-c copy` 按**容器时长**累加偏移 ⇒ 每个段边界多出 0.0667s：转场轨
   （`trans-1-*` 190–200）正好跨在边界上，等于**每个转场中间顿一帧**；本条 3 段片共 2 处。
2. 成片 `duration 20.0667` / 音轨 `20.096`，而正确值 = 600/30 = **20.000**。`PROGRESS.md` 五个版本
   全写「20.10s」，`card.json` 的 `spec.durationSec=20.1` 也是它——**交付元数据被污染**，用户看到的
   「时长断言相差 5.1s」里混入了这 0.096s。
3. `avg_frame_rate=9000/301`（29.90fps）不是 30/1：要求 CFR 30 的平台会拒收或二次转码。
4. Phase 1.5 上音频时，段→整片会按容器时长错位 32ms/段，越拼越多。

**为什么测试没抓到**：`req038-r11-segment-render` 断言的是「options 里 `muteAudio === true`」这个**入参**，
不是「产物里没有 audio stream」；`shot-cache.ts:209` 注释「段视频不编码音轨」与现实相反。

**修法**：`muted: true`（1 行，与 `audioCodec: null` 可并存），并把该测试从「入参断言」改成
「产物断言」——ffprobe 段 mp4 的 `stream=codec_type` 只应出现 `video`。

### 6.2 P1-5（新，工作流）：一次不产帧的 probe 吃掉唯一的成片后批注额度

| step | 调用 | 结果 |
|---|---|---|
| 28 | `quality:"standard"` | 交付落地（`delivered=true`），回执带 `分镜渲染 0/3` |
| 41 | `probe:true`（无 quality） | 放行，**扣掉 annotations=1**；走整片路径，`sampleFrames=[]` ⇒ **零帧** |
| 43 | `spotFrames:[90,300,520]` | 拒收 `CS-RENDER-PROBE`：「成片后批注已用满 1 次…不要再逐帧试错」 |
| 45/50/55/60 | 全量交付档 | 模型只能盲改盲渲，4 次全量渲染（每次 11–29s） |

`probe` 的 `sampleFrames` 恒为 `[]`（`host-tools.ts:4071`），却与 `spotFrames` 同属 `isProbeCall`
（`render-probe-budget.ts:97`）——**消耗额度的那条路径不产帧，产帧的那条被它挤掉**。被拒后模型
按提示「把剩余问题写成未决项随片交付」，于是本会话的质检在 s2 只用肉眼看了一帧就结束了。

**修法**：`isProbeCall` 拆两档（`spotFrames` 记批注、`probe:true` 单独小额度或不计入），或在
probe 被允许时**同时给帧**（probe 本来就要落盘一次全片，抽帧成本可忽略）。

### 6.3 P1-1 被实锤（review 时是推演，现在是账单）

- **6 次渲染回执零帧**：整条会话 8 张图全部来自 `read_image`（step 33/34/47/52/57/62/65/67），
  没有一张来自 `render_composition`。
- **模型自建质检回路**：6 次 `ffmpeg -ss … -frames:v 1` + 8 次 `read_image` ≈ **14 步**（占 70 步
  的 20%），另有 6 步去读渲染器源码猜「文字为什么被裁」（`TextCard.tsx` / `cell-projection.ts`）。
- **硬代价**：自抽的是 1920×1080 PNG（250–400KB/张），base64 后撞 2MB 上限 ⇒
  **3 次请求失败**（step 63/66/68 `IMAGE_OFFLOAD_REQUIRED: … 1 more oldest occurrence(s) must be
  offloaded`），每次重发整请求，且最早两张图被驱逐出上下文 —— 质检证据链中途断裂。
- **无自检行**：分镜回执只有「3 段 / N 复用」一句，`formatRenderVerdict` 拿 `report=undefined`
  只能空转；整片 probe 那次（step 41）反而有完整告警列表。

### 6.4 缓存收益实测：3 屏片上接近零

### 6.6 P2-9（新）：格位多单元的「双底板 + 双眉标」

`s2` 在成片里看起来是**上下两张独立卡片**：各自一整块深色底板、各自眉标「02 / 03 · 气温」
「02 / 03 · 巡航高度」（同一屏出现两个「02 / 03」）。根因：56 张卡的生成器都吐
`sectionBase`（全屏 100%×100% 底）+ `decorVignette` + `eyebrow`，而格位投影只做**仿射重投影**
（`cell-projection.ts`）⇒ 每个单元把自己的全屏底缩成格位大小的底板，连带自己的暗角与眉标：
单元数 = 底板数 = 眉标数。模型为此花了 3 轮（v2→v3→v4）才发现「改不掉」，最后只能接受。

建议：`sectionBase` / `vignette` / `eyebrow` 在 unit 上下文里降级（`ctx.unit != null` 时不吐），
比在投影层维护 id 黑名单可靠；skill 的 `screen-plan.md` 里补一句「多单元 = 多底板」的警告。

## 7. 四个疑问的定位（同一会话追问，结论均已核实到产物/源码）

### 7.1 报错分五类，其中一处是「校验逼出假数据」

| 类型 | 实例 | 归因 | 处置 |
|---|---|---|---|
| 硬拒收 | step25 `scaffold_manifest`：`spec.sections[1].copy 必须是非空字符串` | s2 是 units 型 section（两个单元），没有屏级文案；schema 却要求每 section `copy` 非空 ⇒ 闸门与形态冲突 | **P1-6**：units 型 section 应允许 `copy` 缺省（或派生自 units），不能逼模型编一句 |
| 硬拒收 | step43 `render_composition`：批注已用满 | step41 的 `probe:true` 吃掉唯一额度（见 §6.2 P1-5） | 已记 |
| 请求失败 | step63/66/68 `IMAGE_OFFLOAD_REQUIRED`（3 次） | 渲染回执不返帧 ⇒ 模型自己 `ffmpeg` 抽 1920×1080 PNG，base64 累计超 2MB ⇒ 平台驱逐最旧图后重试（3 张图被丢，质检证据链断裂） | 根因是 §6.3 P1-1 |
| 常驻警告 | 时长差 5.1s / `dataSource` / `generatedBy` / 未决项为空 / 图文卡片型 | 分别对应 P2-12 基准错、P2-10 无处填、P2-11 白名单、P2-13 写入时序、形态提示（非错误） | 已记 |
| **静默不一致** | 产物数据卡是 **−64°C**，会话全程工具参数与交付说明都是 **−60°C** | 磁盘 `spec.json` / `manifest.json` 在 10:44 被改成 −64（mtime 与 step59 同刻，但该步参数只含路径）；`manifest` 的 `u0-s2-u0-data.data[0].v` 就是 −64 | **验收 blocker**：先定口径（用户原话 −60 为准），再查是谁写的 −64 |

P1-6 的因果值得单记：模型为了过 `copy` 非空这一关，往 s2 塞了一句拼合文案，顺手把 −60 写成 −64。
于是**一个纯格式校验，污染了成片里唯一的数值**——这比「报错」本身严重得多。

### 7.2 3 段 vs 6 个分镜：屏 / 段 / 镜是三个计数

| 计数 | 值 | 来源 |
|---|---|---|
| 屏 | 3 | `spec.sections` 三个；`planStages(20s)` → `round(20/6.5)=3`（`stage-plan.ts:177`） |
| 段 | 3 | 分镜渲染按屏边界切 `[0,200) [200,400) [400,600)`，与镜头无关 |
| 镜 | 6 | `write_storyboard` 每个 scene 写了 **两条**：Sh1 主镜 + `backup:true` 的 Sh2 备份拍 |

**根因**：`planSeedFromStoryboard` 遍历 `scene.shots` 时不过滤 `backup`（`storyboard-seed.ts:176-200`），
于是 3 张备份拍也落成画布卡；卡片标题只有「分镜 N · Sx-Shy · Static」，`shotCardText` 也不标备份
（`storyboard-seed.ts:81`）——画面上唯一的「备份：」前缀是模型自己写在 `visual` 里的，不是系统标注。
而 `storyboard-render.ts:113` 写得很清楚：**备份拍不是额外银幕时间，片长只累加非 backup**。
结果：画布 6 张 × 6.67s = 40s 声明时长，与 20s 片长自相矛盾（P2-12 的 40s 就是这么来的）。

⇒ 不是「少渲了 3 段」，是**多落了 3 张不该落的分镜卡**；spec 通道压根不读 `storyboard.shots`，
镜与段之间没有任何映射键。修法：seed 过滤 `backup`（或折叠进主镜卡作「备选拍法」文本）。

### 7.3 每段分镜为什么没有配一段视频：三层原因，三种方案

- **路线层**：这是知识型图文卡（零视频模型），skill 第 9 步（逐镜出片）整步跳过，
  成片由 `render_composition` 一次渲染 ⇒ **设计上就没有「逐镜视频」**。
- **数据层**：spec 与 storyboard 是两条平行数据（3 段 vs 6 镜），没有 `segment → shot` 映射。
- **产物层**：段视频**确实产出了 3 个**，但只在 `build/shot-cache/<hash>.mp4`：
  不进 `assets/history.json`、不进 `deliver/`、不挂画布节点 ⇒ 用户看不到，等于没有。

| 方案 | 做法 | 成本/风险 |
|---|---|---|
| **A1 段产物正式化**（推荐） | `deliver/segments/s1.mp4…`（可读名）+ `card.json pointers.segments` + 画布段节点；**前置**：先修 §6.1 P1-4（`muted:true`），否则每段带静音音轨 | 小；纯暴露与命名，不动渲染链路 |
| **A2 镜段对位**（推荐，与 7.2 同批） | seed 过滤 backup；主镜卡 `sbRef` 与 `spec.sections[].id` 建映射；渲染回执把 segmentId→shotRef 写回，段视频挂主镜卡右侧 | 中；需一条映射表 + 一次回执扩展 |
| **A3 段级抽帧** | 每段渲完抽 1 帧挂段节点，替代整片抽帧 | 小；顺带把 P1-1 的「模型自己抽帧」消掉 |
| B 真要 AI 镜头视频 | 走第 9 步 ref2va，与 spec 通道互斥，需产品层确认语义 | 大；不是本批范围 |
| C 直接把 shot-cache 当交付 | — | **不做**：hash 名 + 静音轨 + 回收策略都不合格 |

**2026-11-16 11:10 用户拍板（目标修正，覆盖上面的「暴露产物」措辞）**：

> 让视频跟随分镜展示，是为了让用户能调整每一段视频的效果，而不用每次都动全量产物；
> 修改范围集中、不影响其他分镜；UI 上直接改暂不支持，但「对着分镜跟 agent 聊」范围不容易误解。

⇒ 这不是「多几个视频文件」的需求，是**段级局部迭代**需求。判据只有一条：
**改一段的代价 = 1 段渲染 + 1 次确认，且不触碰其他段产物与其他分镜卡。**
R11 的价值因此不在「渲染提速」（3 屏片上实测收益≈0），而在段级隔离的地基。

### 7.4 信息密度低：主因是「输入即定稿」，不是创意太简单

**量化**：全片 ≈40 字 / 20s ≈ **2 字/秒**；3 屏 × 6.7s，每屏 1–2 个信息点。
卡容量其实很宽：A4 `bullets` 支持 6 条（`recipe-cards.ts:296`）只用了 1 条；
B1 `dataCard` 支持多行 `k:v` 只用了 1 行。

归因按权重：

1. **用户给的是定稿文案（4 句），不是素材清单**；agent 按「用户明说优先 + 事实不许编」逐字执行。
   纪律是对的，结果必然稀——它没有「把一句话撑成 20 秒」的合法手段（只能编）。
2. **autoStages 只按时间定屏**：`TARGET_STAGE_SEC=6.5`（`stage-plan.ts:27`），20s→3 屏，与信息量无关。
   知识型 20s 想密，应走 4s/屏（5 屏）或显式指定屏数。
3. **没有密度判据**：spec schema 只有 `copy/units`；质检 5 条（静态占比/运动密度/转场/镜头数/节奏）没有「文字密度」。
4. **版面冗余抵消密度**：A2/A5 的 `cornerMark` 把 `copy` 全文再放一次（`recipe-cards.ts:179`，s1 底部 y=92 重复标题 13 字）；
   s2 双底板双眉标（P2-9）⇒ 明明只有一句话，画面还重复两遍。

| 方案 | 落点 |
|---|---|
| 输入侧给「事实清单」 | brief 写 3–5 个点/屏：数值 + 对比 + 因果 + 反常识；数字带来源，模型才敢用 |
| 分屏按信息量 | 知识型 `targetStageSec=4`；或 spec 显式 `stages`；20s → 5 屏 |
| 加 `density` 体检 | 字/秒、信息点/屏、文本面积占比；低于阈值 warning（不阻断），进渲染回执 |
| 用满卡容量 | B1 多行 `k:v`、A4 3–6 条 bullet；删掉 `cornerMark` 的全文重复 |

> 本轮只定位与给方案，未改产品代码。正式顺序见 §8。

| # | 事项 | 为什么是 P0（判据 = 改一段不动全片） | 验收（可执行断言） |
|---|---|---|---|
| **O-1** | **镜–段–spec 三方同 id**：seed 过滤 `backup`；主镜卡携带 `segmentRef:'spec:s2'` + 段内 spec 摘要（card/copy/cell）；新增 `patch_spec_section`（只改指定 section/unit，回显 diff） | 用户「对着分镜说话」的前提是这张卡能唯一指向一段 spec。现在 3 张主卡指向模糊（正文与 spec 无字段对应），3 张备份卡指向空气 ⇒ **「范围不误解」这条产品承诺目前是零** | 对分镜 3 说「−60 改 −62」：patch 回执只 1 处 diff，只动 `s2.units[0].copy`；对备份卡说同样的话：工具明确拒绝并回「这是备份拍，无对应段」 |
| **O-2** | **段边界改为「转场归后段」**：段窗取各段底板起点 —— `[0,190) [190,390) [390,600)`（= stage 边界 200/400 减 10 帧预卷），段首自带入场转场，段内轨按窗裁剪 | C3 的直接原因。D2「转场窗归前段」让每段的末 10 帧包含下一段画面，改 s2 必然改 s1 的末段 ⇒ 用户看到「只改一段却重渲两段」，信任崩掉 | 改 s2 后回执 `2 复用 / 1 重渲`（s1、s3 复用）；成片总帧 600、帧时间戳无跳变、接缝无闪 |
| **O-3** | **段产物正式化 + 段级抽帧**（含 **`muted:true`** 前置）：`deliver/segments/<sectionId>.mp4`、`card.json pointers.segments[]`、画布段节点（挂主镜卡右侧）、每段抽 1 帧写 `build/qc/seg-*.png` | 没有可见产物，用户无从「调整每一段的效果」；段级抽帧同时替代整片抽帧，直接消掉 P1-1 那 20% 补偿步数 | 每段 mp4 `codec_type` 只有 video、`nb_frames` = 段窗帧数、`duration == frames/fps`；单独播放无黑屏；抽帧图能在节点上看到 |

> O-3 里的 `muted` 不是可选项：现在段文件带静音 AAC（`-91dB`），容器时长比视频流长 32ms，
> 单独播放每段都会有尾巴，拼接点各定格 40ms（§6.1）。先修它，再暴露产物，否则暴露的是坏件。

> **O-2 的落地形式**（否则实现会走偏）：`planFromSpec` 生成 manifest 时写入 `meta.segments[{id,startFrame,frames}]`（段表），
> `boundariesFromSpec` 直接读它；不再用 `stage.startFrame`（等分起点 200/400，含下一段 10 帧预卷），
> 也不靠轨 id 前缀（`s2-` / `u0-s2-`）猜归属。同一张段表同时喂给段渲染、段挂载、段级 patch —— C1 与 C3 共用一份真相。

### 8.3 P1：目标成立后，每轮都要付的利息

| # | 事项 | 理由（为什么不是 P0，但不能不做） |
|---|---|---|
| **O-4** | probe 与 spot 的批注配额分离（§6.2） | 段级迭代会让「渲一次」的频率涨 3–5 倍；现在一次 `probe:true` 就废掉唯一成片批注额度，迭代越多越容易踩 |
| **O-5** | units 型 section 允许 `copy` 缺省（§7.1 P1-6） | 段级编辑最常改的就是 unit；每次都要编一句假 copy，本次已因此把 −60 写成 −64 |
| **O-6** | 渲染回执返帧（§6.3 P1-1） | 段级迭代每轮都要模型自己 `ffmpeg` 抽 1080p PNG，3 次撞 2MB 上限、丢 3 张图；次数一多，成本线性放大 |
| **O-7** | 超时预算按 `frameRange` 收窄（§6.3 P1-2） | 段渲染次数变多，每段 204s（应 108s）的超时会累积成「白等十几分钟」 |

### 8.4 P2：卫生与内容质量（与段级闭环正交）

| # | 事项 | 备注 |
|---|---|---|
| O-8 | 密度体检（字/秒、信息点/屏）+ 知识型 `targetStageSec=4` | §7.4；解决「20s 只有 40 字」，不阻断渲染 |
| O-9 | `cornerMark` 去掉 `copy` 全文重复；多单元共用一块底板（P2-9） | 视觉重复会掩盖密度不足 |
| O-10 | `dataSource` 有处可填、`generatedBy` 白名单认 `spec:content-spec`、未决项真正写入 card.json、时长基准统一（P2-10~13） | 都是噪声/文档债，工作量小但会持续误导下一轮 |

### 8.5 最小切片：先做 O-1 + O-2 + O-3

三件合起来才形成闭环：**能定位（O-1）→ 改完只重渲这段（O-2）→ 看得见结果（O-3）**。
少任何一件，用户拿到的都是半成品：只做 O-1 是「能聊但改完全片重渲」；
只做 O-3 是「多 3 个文件但改一段还是渲两段」，反而更劝退。

### 8.6 现在不做（防止范围膨胀）

| 不做 | 原因 |
|---|---|
| 段级 UI 编辑器（拖拽调版式） | 你自己已说暂不支持；C1/C2 的契约没稳之前做 UI，等于把不稳定的 id 焊进界面 |
| 把 ref2va 镜头视频混进 spec 通道 | 两条链路的帧预算、素材纪律、审批门都不同；混了之后「一段」到底是卡还是视频说不清 |
| 直接把 `build/shot-cache` 当交付 | hash 名 + 静音轨 + 回收策略（过期即删）三条都不合格 |
| 给 spec 加 DSL / 模板语言 | 先证明段级闭环保值（用户真会按段改），再谈表达力 |

### 8.7 这次会话值得沉淀的三样东西

1. **产品判据**：C1–C5 五条，可当后续任何「分镜驱动」功能的验收模板——功能自称支持段级编辑时，逐条打勾。
2. **三条实测基线**（下批回归用，别再重新摸）：
   段渲染 11.8 / 11.3 / 12.4s（3 段全渲，无预热惩罚）；整片 probe 38.0s；3 屏片改一段命中 `1 复用 / 2 重渲`、改常驻轨 `0 / 3`。
3. **两条反面证据**：`shot-cache.ts:15` 注释「改 s2 只脏 s2」在带转场的 spec manifest 上不成立；
   `shot-cache.ts:209` 注释「段视频不编码音轨」与产物相反。注释与产物的偏差比代码 bug 更容易骗过下一轮 review。
