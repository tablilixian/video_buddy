# REQ-038 · R7 需求增补 · 版面层（屏表）

> 2026-11-13 增补。**为什么单独成篇**：REQ-038 正本的 24 条 RQ 全部落在「原语密度 / 卡 / 配方 / 验收」，
> 没有一条管**多屏版面编排**。而真机 5 分钟片与 45 秒片的单调，根因在这里（见 §1 证据）。
> 拆成增补篇而不改动 698 行正本，是为了让正本的证据索引不断裂（SB-D 已决）。

## 0. 一句话

`ContentSpec.sections[]` 已经是「屏」的形状，但一屏只允许一个单元、没有格位、没有常驻层，
且整条 spec 通道**没有工具入口** —— 补的是这三处，不是新建一层。

## 1. 证据基线（数字均可复算）

| 观测 | 手写版（60s） | 真机版（45s / 304s） | 出处 |
| --- | --- | --- | --- |
| 同屏非字幕元素 均值 / 峰值 | 5.88 / 12 | 2.21 / 4 · 1.71 / 4 | 对比报告 §2 |
| 平均停留 | 23.84s | 9.88s | 同上 |
| 内容像素占比 | 13.6% | 4.1% | 同上 |
| 常驻底板 | 9 块 | **0 块** | 同上 |
| 单元素帧占比 | — | **51%**（45s 版） | 流程推演 §2.5 |
| 屏长离散 | — | 3.4–12.7s（3.7×） | 流程推演 §2.5 |

**根因三条**（不修这三条，加任何原语都不改善观感）：

1. `ContentSpec.sections[]` 只有 `card` 一个单元字段 ⇒ 结构上**不可能**两元素同屏；
2. `cell`（格位）不存在 ⇒ 所有卡按 `100%×100%` 全屏铺，只能互斥替换；
3. `carry`（常驻层）不存在 ⇒ 渲染每帧重算，**跨屏不变的东西必须显式声明**，模型没处声明。

**可达性缺口（本次核查新发现）**：`planFromSpec` / `validateContentSpec` / `ContentSpec` 在
`src/host-tools*.ts` 与 `src/routes.ts` 中**零引用** ⇒ 模型在真机里根本看不见这条通道。
落地对照表 RQ-18 所述「`scaffold_manifest` 已有 recipe/spec 入口」与代码不符 —— 只有 recipe，没有 spec。
本条需求即修正该陈述（RQ-27）。

## 2. 需求条目

### RQ-25（P0 · 中）`sections[]` 支持格位与多单元

- **现象**：一屏一单元。真机 45s 片 23 秒整屏只有 1 个元素。
- **需求**：
  - `sections[].cell?: { x: number; y: number; w: number; h: number }`
    —— **中心点坐标**，与 `box` 同口径（`{x:50,y:50}` = 居中）；取值 `0–100`。
  - `sections[].units?: Array<{ card: string; copy: string; label?: string; cell?: CellRect; assetSlots?: Record<string,string>; accentColor?: string }>`
    —— 一屏 1–4 个单元。**与 `sections[].card` 互斥**（同时给报错）；`units` 缺省时行为与今天逐字一致。
  - 卡的几何走**仿射重投影**（不改 56 张卡内部写死的 `100%×100%` box）：
    `x' = cell.x + (x−50)·cell.w/100`，`y'` 同理，`w' = w·cell.w/100`，`h' = h·cell.h/100`。
  - **字号不在这一层管（2026-11-13 实施时修正）**：原设计打算用 `cell.fontScale` 乘字号，
    落地撞到事实 —— **`textCard` 白名单没有 `fontSize`**（`manifest.ts:1202`），字号由
    `planTextFit` 按「变体基准 + box 宽度」实时推（下限 `base × 0.55`）。所以格位缩窄 ⇒
    自动降号；硬塞 `fontSize` 只会被 `validateManifest` 判未知字段而拒收。
    保留 `fontScale` 字段但**校验期直接报「暂不生效」**，不留一个看起来能调的旋钮。
- **验收**：
  1. **旧行为**：任何不含 `cell` / `units` 的 spec，`planFromSpec` 产出与改动前**逐字段相等**（不是"看起来一样"）；
  2. **多单元**：一屏 3 单元 ⇒ 该屏 `tracks` 内非背景轨 ≥3，且各轨 `box` 落在各自 cell 的**半平面内**（几何断言）；
  3. **字号链路**：窄格位（w≤50%）的 textCard 轨 `box.w ≤50`，且**轨道上没有 `fontSize`**
     （证明字号仍由渲染期 `planTextFit` 推，没有被写死）；
  4. **反向变异**：把重投影公式改成恒等（`x'=x`）⇒ 第 2 条转红。

### RQ-26（P0 · 小）`carry[]` 常驻层

- **现象**：真机 0 块常驻底板，手写 9 块。模型想留也留不住 —— 没有跨屏声明。
- **需求**：顶层 `carry?: Array<{ id: string; box: CellRect; color: string; opacity?: number; fromSection: string; toSection: string; radius?: number }>`
  —— 编译成一条 `shape.rect`（或 `gradient`）轨，`startFrame` = `fromSection` 首帧，
  `durationInFrames` = 到 `toSection` 末帧；`fadeFrames: 0`（常驻层不该有入场动画，否则每屏开头都闪一次）。
- **验收**：
  1. 一段 6 屏、`carry` 覆盖第 1–6 屏 ⇒ 生成 1 条轨，帧区间恰好等于 6 屏并集；
  2. `fromSection` / `toSection` 指向不存在的 id ⇒ `validateContentSpec` 报 error（不静默丢）；
  3. 无 `carry` 的 spec 产出与改动前逐字段相等。

### RQ-27（P0 · 小）`scaffold_manifest` 增加 spec 起点（可达性修复）

- **现象**：spec 通道有代码、有 3 个测试文件，但**无工具入口**。模型在真机 223 次调用里 0 次碰到它，
  于是自己写了 29KB 的 `gen_specs.py`（7 个硬编码盒常量）。
- **需求**：`scaffold_manifest({ specPath, writeTo })` —— `specPath` 为项目内相对或绝对路径（≤8MB），
  读 → `validateContentSpec`（error 即拒收，warnings 原样回传）→ `planFromSpec` → 走既有落盘与校验。
  与 `templateId` / `recipe` / `title` 三者互斥（同时给报错）。
- **验收**：
  1. 45s 六屏 spec 一次调用出 manifest，`durationInFrames` 等于 spec 声明时长；
  2. spec 校验失败时**不落盘**、回传逐条 error；
  3. 与 `templateId` 同时传 ⇒ 报错文案列出三个互斥项。

### RQ-28（P0 · 小）ML-16 / ML-17 两条版面判据

- **现象**：ML-01…15 全查动画与字幕时序，**没有一条问「这屏有几个东西」**。
- **需求**（`motion-lint.ts`，纯函数，只产 warning —— 已拍板；**以下判定条件为实施后定稿版**）：
  - **ML-16**「单元素采样秒占比 > 25%」：按 `fps` 逐秒采样（不逐帧 —— 1500 帧 × 60 轨逐帧是 9 万次
    比较，而「整屏只有一个东西」是秒级现象），统计**内容轨**数 ≤1 的采样占比。内容轨 = 排除
    `transition` / `caption` / `audioViz` / `shape.gradient` / `shape.vignette` / `textCard.subtitle`。
    片长 <12s 不判（太短片没有编排可谈）。
  - **ML-17**「全片无常驻层」：不存在任何一条同时满足三条的 `shape` / `image` 轨 ——
    ① 时长 ≥ 全片 30%；② 入场动画 ≤ 自身时长 10%；③ 不是全屏（`w`/`h` 都 ≥99 的全屏底色
    每支片都有，判不出编排意图）。**第 ② 条不是 `fadeFrames === 0`**：300s 底板带 6 帧淡入
    仍然是常驻层，用「零入场」定义会把真常驻层误判掉（实施中改的，见 §8）。片长 <15s 不判。
- **必须同批处理的上限问题**：`MAX_ISSUES = 12` 会把新告警挤出（ML-02 曾累计 337 条）。
  ⇒ 两条新判据**各自独立计数、优先入列**（先 `push` 版面两条，再跑既有规则），否则「加了判据等于没加」。
- **验收**：
  1. 真机 45s manifest ⇒ ML-16 命中（实测 **51%**，23/45 秒）、ML-17 命中（0 块常驻）；
  2. **5 分钟整片版**（300s / 150 轨，每秒 4.4 个元素）⇒ ML-16 **不命中**（它不单调），
     但 ML-17 命中（确实没有跨屏底板）—— 两条判据语义正交，各自说各自的事；
  3. 一条已有 12 条其他告警的 manifest，版面两条仍在输出里（上限不吞）；
  4. 反向变异：把阈值 25% 改成 90% ⇒ 第 1 条转红。
- **注**：手写 60s 版是 TSX 直接渲染（`entry-hand.tsx` → `/tmp/hand-1800.mp4`），
  **没有 manifest 可 lint** —— 所以「手写版必不报」这条不能作为验收项，
  改为「按手写版形态构造的 manifest（多单元 + carry）必不报」，见单测第 14 条。

### RQ-29（P1 · 小）`template-gate` 把「整片时长」拆成两段

- **现象**：`template-gate.ts:128` 拿整片时长直比模板窗口 ⇒ 45s 片对 3–10s 的模板必然全灭（真机 `list_templates` 10/10 判死）。
- **需求**：判定拆成 `stageSeconds`（**必判**，= 该模板作为一屏时的时长）与 `totalSeconds`（**只提示**，
  用于估屏数 `round(total/stage)`）。`stageSeconds` 缺省 = 模板自身时长（即旧行为不变）。
- **验收**：
  1. 45s 需求 + `ink-open`(9s) ⇒ `stageSeconds=9` 通过，`totalSeconds=45` 只出 info；
  2. 45s 需求 + `three-cards`(36s) ⇒ 仍拒（真不适配不许放行）；
  3. 不传 `stageSeconds` 的既有调用 ⇒ 结论与今天逐字一致。

**实施中被推翻的三处设计**（记下来，避免下次又照着旧文档做）：

1. `cell.fontScale` —— `textCard` 白名单没有 `fontSize`，写了不生效还会被校验拒收。字号是渲染期产物。
2. 「手写 60s manifest 必不报」—— 手写版是 TSX 直接渲染，没有 manifest，这条验收不成立。
3. ML-17 的「`fadeFrames === 0`」—— 常驻层的定义是**跨屏存在**，不是**零入场**。
   手写 60s 版的 9 块底板里有带 6 帧淡入的，按旧定义会把它判掉。改为「入场 ≤ 自身时长 10%」。

**派生影响（必须记）**：新判据把 10 个整片模板里的 3 个判红 ——
`product/feature-walkthrough`、`report/data-summary`、`science/three-cards`，
它们的骨架本身就是「一屏一卡依次替换」（单元素 100%、零常驻层）。这不是误报，是如实：
**模板机制的粒度是整片单屏叙事，解决不了版面**。按既有 `lintSuppress` 约定在各自
`meta.json` 声明 `["ML-16","ML-17"]` + `lintSuppressNote` 写明设计意图，而不是放宽判据。
这条是「主力必须是卡 + 格位，模板只插 2–3 屏」的反证。

**新增测试**：`remotion-layout-lint`（10）+ `req038-r7-screen-plan`（14）+ `req038-r7-spec-entry`（6）= **30 条**。
**连带改动**：`param-guard.ts` 参数分类表补 `specPath`（否则 `param-guard` 门禁判红）；
`tests/remotion-template.test.mjs` 的「模板骨架零告警」断言靠上面 3 处 `lintSuppress` 恢复绿色。

### 11.1 B1 · 屏数原语 `planStages()`

**改了什么**

- 新文件 `src/remotion/stage-plan.ts`（纯函数，无 IO 无时钟）：
  `planStages({totalSeconds, fps, boundaries?, targetStageSec?, minStageSec?, maxStageSec?}) → {stages:[{index,startFrame,durationInFrames}], meta:{target,clamped,absorbedBy}}`。
  - 屏数 = `clamp(round(total/6.5), 2, 40)`，再拉进**单屏可行带** `[ceil(total/max), floor(total/min)]` ——
    越带即拉回。这是「不足合并、超出拆分」的等价确定性实现：先把屏数算对再等分，
    比贪心「等分→合并→拆分」少一轮震荡（贪心合并会造出拆不动的超长屏，20s + minStageSec 8 即触发）；
  - 等分后每个内部边界向 TTS 句起点（`boundaries`，帧号）±0.6s 吸附；从左到右处理，
    下界用已接受的左刀（两刀不会吸到同一点）、上界用未吸附的右邻（右刀不牵引左刀，行为可逐字段复算）；
  - guard 兜吸附残差：短屏并左邻（只剩两屏不再并 —— 屏数下限优先于屏长下限）、超长屏按「每段 ≤ 上限」拆分；
    拆不动或 guard 耗尽一律抛错，不交烂屏表（铁律 5）；
  - 值域硬边界：总时长 < 8s（2 屏 × 4s 下限）或 > 400s（40 屏 × 10s 上限）抛错，
    报错文案给出「更短/更长请关掉 autoStages 自己排或拆需求」的出路。
- `content-spec.ts`：`meta.autoStages?: boolean` + `meta.stageBoundarySec?: number[]`（秒，严格升序，
  来自 tts_narration 回执 `audio.voiceOver[].startSec`）。校验五条：autoStages 时 durationSec 必填、
  sections 不许带 durationSec/weight（节奏归工具）、**段数必须 == 算出的屏数**（两种意图打架即拒收）、
  stageBoundarySec 乱序/越界拒收、autoStages 非布尔拒收；只写 stageBoundarySec 不开 autoStages → warning「不生效」。
  `planFromSpec`：仅显式 `autoStages: true` 走屏窗分支（含未注册卡的占位轨重排），返回值带 `stagePlan`；
  false/缺省**连计算都不碰**（回归纪律）。
- `host-tools-spec.ts`：autoStages 时回执多一行「节奏：planStages 算出 N 屏（目标 X，屏长 A–Bs）」——
  工具替模型做的决定必须看得见。

**怎么验**（`tests/req038-r7-stage-plan.test.mjs`，21 条全绿）

- 45s → 7 屏 × 6.43s，离散 1.0×（对照真机 3.7×）；304s → 40 屏 + `clamped=true`（target 47）；
- 吸附：±0.6s 内拉过去（六句全部命中）、22 帧外不迁就；吸附致短屏 → 合并 + `absorbedBy` 原文记录；

- 非法入参 7 类全部抛错；Σ/单调不变量在 12/45/90/304s 成立；
- **反向变异**：断言 `TARGET_STAGE_SEC === 6.5`、45s target===7、304s target===47 && clamped ——
  常数若被改成 20，这四条断言转红；
- 回归守卫：无 autoStages spec → timeline 等权切分逐字段相等 + 输出**无** `stagePlan` 字段；
