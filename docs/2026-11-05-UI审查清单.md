### UI-01【高】四处破坏性操作用原生 `window.confirm`，与仓内 ConfirmDialog 双轨并存

**位置**：
- `canvas-studio/src/client/StudioFrame.tsx:1508`（画布节点批量删除——最高频的破坏性操作）
- `canvas-studio/src/client/ProjectRowMenu.tsx:131`（项目删除）
- `canvas-studio/src/client/ProjectList.tsx:500`（分组删除）
- `canvas-studio/src/client/SkillMarket.tsx:182`（用户技能删除）

**证据**（StudioFrame.tsx:1505-1509）：

```ts
    const message = referencing.length > 0
      ? `即将彻底删除（不可撤销）。以下 ${referencing.length} 个节点的参考将断链：${names}。确定删除？`
      : '彻底删除（不可撤销）？'
    if (!window.confirm(message)) return
```

而仓内已有专门承载「单条决策」的 `ConfirmDialog`（CV-196，ConfirmDialog.tsx），且 `ProjectRowMenu.tsx` 文件头 6-11 行自己论证过「原生控件由操作系统绘制，暗色壳上渲染成一块亮底浮块，且它不吃插件的任何令牌」——这正是当初把原生 `<select>` 换成自绘菜单的理由，但删除确认又走回了原生弹窗。

**触发场景**：任何删除操作。Electron 渲染进程里 `window.confirm` 会阻塞渲染进程（拖拽/轮询全部冻结），弹窗是系统样式，与整体暗色品牌壳割裂；多行 `\n` 文案在原生弹窗里的排版不可控。

**建议**：四处统一收敛到 `ConfirmDialog`（它已支持取消键自动聚焦 + Esc，语义比原生 confirm 更安全）。可先从 ProjectRowMenu / ProjectList 这两个纯前端调用点做起。

### UI-02【高】设置弹窗与导入向导的遮罩用 `onClick` 关闭，拖选文本松手即误关

**位置**：
- `canvas-studio/src/client/SettingsModal.tsx:875`：`<div className="csSettingsBackdrop" role="presentation" onClick={onClose}>`
- `canvas-studio/src/client/SkillImportWizard.tsx:157`：`<div className="csSkillImportBackdrop" onClick={onClose}>`

**证据**（对照正确实现，ConfirmDialog.tsx:50）：

```tsx
// ConfirmDialog —— 拖选安全：只在「按下起点就在遮罩上」时关闭
onMouseDown={(event) => { if (event.target === event.currentTarget) onCancel() }}

// SettingsModal / SkillImportWizard —— click 落在遮罩上就关
<div className="csSettingsBackdrop" role="presentation" onClick={onClose}>
```

click 事件的 target 是 mousedown 与 mouseup 目标的**公共祖先**：在弹窗里按住选中一段长文本、拖到遮罩上松手（或反向），click 落在遮罩上 ⇒ 弹窗立即关闭。设置弹窗里「复制凭据引用名」这类选择操作是常态。

**触发场景**：设置弹窗中拖选 Drama API 基址 / 存储路径等长文本，选区越过弹窗边界松手——弹窗当场关闭，正在浏览的分区丢失。

**建议**：统一改成 ConfirmDialog 的 `onMouseDown + target === currentTarget` 判定（同一套词汇抽成小组件或 hook，避免五种弹窗五种关闭语义）。

### UI-03【中】三处数字输入框不钳制越界值，键入即持久化

**位置**：
- `canvas-studio/src/client/SettingsModal.tsx:163-168`（视频时长上限，标注 1–15）
- `canvas-studio/src/client/SettingsModal.tsx:544-549`（最大并行数，标注 1–8）
- `canvas-studio/src/client/SettingsModal.tsx:615-620`（自动保存间隔，标注 5–600）

**证据**（SettingsModal.tsx:163-168）：

```ts
  const onSeconds = (v: string): void => {
    // CR-050：清空输入（'' → Number 为 0）跳过，不把 maxVideoSeconds 写成 0。
    if (v.trim().length === 0) return
    const n = Number(v)
    if (Number.isFinite(n)) void scope.set('maxVideoSeconds', n)
  }
```

HTML 的 `min/max` 只约束 spinner 按钮，键入 `0`、`-5`、`999` 都是 finite ⇒ 直接写进配置，无红字、无回弹。CR-050 只挡了「清空」，没挡「越界」。下游消费方是否兜底钳制是另一层，但 UI 层让非法值静默入库、读数与标签（「1–15」）矛盾。

**建议**：`scope.set` 前按标签范围 `Math.min/max` 钳制，或越界时给出行内错误态（现有 `.csFieldError` 通道现成）。

### UI-05【中】导入向导：忙时可无提示关闭，`overwrite` 跨选择残留

**位置**：`canvas-studio/src/client/SkillImportWizard.tsx:157`（遮罩点击）、`:169`（关闭按钮）、`:302`（上一步）、`:97`（overwrite state）

**证据**：

```tsx
// :157 遮罩点击无条件 onClose，busy 时也不拦
<div className="csSkillImportBackdrop" onClick={onClose}>
// :302 「上一步」只清 error，不清 overwrite
<button ... onClick={() => { setStep(1); setError(null) }}>
// :141 CS-SKILL-007 冲突时置 overwrite=true

```

两个独立问题：
1. **导入中（busy）点遮罩或「关闭」立即卸载向导**：`runImport` 的 await 继续跑，成功与否用户再也看不到（`onImported` 仍会触发列表刷新，但没有任何面向人的回执）。
2. **overwrite 残留**：第一次导入撞上同名（CS-SKILL-007）→ `overwrite` 置 true → 用户「上一步」换选另一个技能 → 新向导的覆盖勾选**默认已是勾上状态**，按钮文案直接是「覆盖并导入」，覆盖决定被跨选择继承。

**建议**：busy 时遮罩点击/关闭按钮要么禁用、要么弹「导入进行中，确定离开？」；`readFiles`（重新选择来源）与「上一步」时重置 `overwrite`。

### UI-10【中】弹窗焦点管理系统性缺失：无陷阱、不归还，`aria-modal="true"` 名不副实

**位置**（五处声明了 `aria-modal="true"` 的弹窗，全部无焦点陷阱）：
- ConfirmDialog.tsx:48、SettingsModal.tsx:879、SkillImportWizard.tsx:161、RenderPreviewOverlay.tsx:146、BillingPage（csBillOverlay）

**证据**（ConfirmDialog.tsx:9-13 文件头自认）：

```
1. **取消键自动聚焦**（不是确认键）……
2. **Esc = 取消**：useEffect 挂 window 级 keydown……
```

做了 autoFocus 与 Esc（这两点是好的），但：Tab 键会走出弹窗、聚焦到遮罩后面的画布/列表（对键盘用户，「模态」不成立）；关闭后焦点不归还触发元素（如从「⋯ 更多操作」打开的菜单，关闭后焦点掉到 body）。屏幕阅读器按 `aria-modal="true"` 会假设背景不可达——声明与实际行为矛盾。

**建议**：不必引依赖，写一个 ~30 行的 `useModalFocus`（打开时聚焦容器 + Tab 循环 + 关闭归还 `document.activeElement` 快照），五个弹窗统一挂。这是仓内 a11y 纪律（aria-pressed/aria-expanded 已成体系）缺的最后一块。

## 详情（补充）

### UI-15【中】图片查看器双轨：能力分叉 + 预览弹窗破图无兜底

**位置**：
- `canvas-studio/src/client/canvas/ImagePreviewModal.tsx:57-68`（双击画布图片节点 → contain 适配，无缩放；`<img>` 无 `onError` 分支）
- `canvas-studio/src/client/canvas/ImageZoomModal.tsx:196-217`（故事板样张 → 滚轮缩放/拖拽平移/双击适配/键盘 +−0；**有** `failed` 态「取不到图」）

**事实**：同一个「看大图」诉求，仓里有两套查看器：画布侧的预览浮层只能看不能缩放，加载失败时 stage 永远是破图图标 + 元信息条「— × —」；故事板侧的缩放浮层（CV-311）能力完整。两套都是 csModal 家族但体验不同档。

**建议**：合并——ImagePreviewModal 直接换成 ImageZoomModal 的能力（或让前者内部复用后者），失败态共用。双入口（画布双击 / 故事板点样张）保留。

### UI-16【中】视频播放浮层无加载失败态、无键盘控制

**位置**：`canvas-studio/src/client/canvas/VideoPlayerModal.tsx:126-152`

**证据**：`<video autoPlay>` 只处理了 play/pause/timeupdate/loadedmetadata；没有 `onError` / `onWaiting` / 加载中指示。源 404 或解码失败时用户看到的是永久黑屏 + 头部「时长 加载中…」。键盘方面 Space（播放/暂停）、←/→（±5s）都没有——图片缩放浮层有 +−0 键盘位，视频浮层反而全鼠标。

**建议**：补 `onError` 失败态（照 ImageZoomModal 的「取不到图」文案）与 buffering 指示；Space/←/→ 键盘位与图片缩放浮层对齐。

### UI-17【中】三个滑块拖动期间每个 tick 都触发一次全量画布持久化

**位置**：
- `canvas-studio/src/client/canvas/ReferenceTray.tsx:84-91`（参考强度滑块 `onChange` → `onUpdateNode`）
- `canvas-studio/src/client/canvas/NodeDetailDrawer.tsx:316-320`（不透明度 → `onSetOpacity`）、`:399-403`（参考强度 → `onUpdateNode`）
- 链路：`StudioFrame.tsx:1534-1536`（`handleUpdateNode` → `persistAfter` → `persist`）→ `index.ts:344`（`persistCanvasQueued` 排队串行）

**证据**：range input 的 `onChange` 在拖动过程中连续触发（每个步进 tick 一次），每次都走 `persistAfter(() => actions.updateNode(...))`，`persist` 立即发全量画布写（入队串行，无合并）。一次拖动手势 ≈ 20-60 次全量 POST。对照：视口保存有 400ms 防抖先例（`VIEW_SAVE_DEBOUNCE_MS`，StudioFrame.tsx:328），节点字段更新没有。

**建议**：滑块的中间态只写内存 store，`onPointerUp` / 防抖 400ms 后提交一次（与视口保存同款）。三处共用一个防抖提交工具。

### UI-18【中】整理布局不豁免锁定节点；auto 模式自动整理会反复冲掉手动摆放

**位置**：`canvas-studio/src/canvas-view.ts`（`arrangeCanvas` 全文 548-854，无一处读 `node.locked`）；对照 `StudioFrame.tsx:2133`（`handleMediaNatural` 明确尊重 `target.locked`）

**事实**：节点有 `locked` 字段（锁定/解锁按钮在图层与详情抽屉），媒体自愈明确「锁定节点只回填分辨率、不动框」；但「整理布局」（工具栏显式触发）与 auto 模式的到达自动整理（`scheduleAutoArrange`，StudioFrame.tsx:1009-1038）都给**所有**顶层单元重排坐标，锁定节点照搬。锁定语义被两条整理路径打破。

**建议**：先拍板 `locked` 的语义边界——若是「位置冻结」，arrangeCanvas 应跳过锁定单元；若只是「防误拖」，现状可接受但要在 UI 上说明。另外 auto 模式下用户在生成过程中手动摆好的位置，最多 3s 后就会被下一批产物的自动整理冲掉（`AUTO_ARRANGE_MAX_WAIT_MS`），建议自动整理只动**新到达批次**的落位，不做全量重排（或提供「锁定当前布局」开关）。

### UI-19【低】兜底泳道把手工便签/未分类节点归入「文案·成片」区

**位置**：`canvas-studio/src/canvas-view.ts:471-513`（`laneOfNode` 尾部 `return LANE_FILM`）

**事实**：用户手工加的便签/文本卡（无 toolName）、以及任何未分类节点都落到第 9 泳道「文案·成片」——agent 的文案与成片是流程终点区，手工杂件混进去会稀释「这一栏 = 交付物」的读感。整理布局后尤其明显（杂件整排出现在成片区）。

**建议**：手工件（`origin === 'manual'` 且无 toolName）归创意区（源素材），或开独立「杂项」栏；改动小，但要与现有验收截图口径对齐。

### UI-20【低】泳道宽度按「最挤的那一行」撑满，其余行留大片空白

**位置**：`canvas-studio/src/canvas-view.ts:705-713`（`laneWidths` = 该泳道最挤行的总宽；注释写明是为了治「节点突出去、每个区域不是矩形」）

**事实**：这是治突出问题的刻意取舍，但另一面是：某一行并排 4 张 1024px 关键帧时整栏被撑到 ~4200px，其余只有 1 张卡的行右侧留白 3000px+，画布横向被拉大、「适配视野」后整体缩得很小（触发「已按可读比例显示」toast）。

**建议**：短期不动（当前取舍有验收依据）；若后续优化，可考虑行内超过 N 张时换行成两行（行高补偿），把栏宽上限控制在 ~3 卡宽。
