# 故事板强约束 + 契约补齐：彻底方案（待评估，未落码）

> 输入（2026-10-25 拍板）：**① 不管存量**（老项目也要走故事板）｜**② auto 自动落地默认开**｜**③ G6 动画/素材语义必须补进契约**。
> 本文是方案，**不含代码改动**。评估通过后按第 5 节的顺序落。

---

## 1. 先定不变量（后面每条设计都为它服务）

| # | 不变量 | 怎么验 |
|---|---|---|
| **I1** | **任何产出类工具在「本项目故事板未落地」时都不可能成功执行** —— 与 `mode`（confirm/auto）、`state`、入口（对话/自动化/脚本）**全部无关** | 4 个工具 × 2 种 mode × 落地/未落地 = 8 条用例 |
| **I2** | **「已落地」只有一个事实源**：`storyboard.json.landed`。`workflow.state` 是**派生显示**，不参与放行判断 | 手工把 state 改回 `storyboarding`，工具仍应放行；反之 landed 为空时 state 写 `executing` 也不放行 |
| **I3** | **auto 模式也能走完整链路**：写故事板 → 校验完善 → **自动落地** → 继续出片，全程不需要用户点按钮 | auto 会话端到端跑一次，画布出现分镜卡 |
| **I4** | **不豁免存量**，但必须给**可执行的出路**（不是"你自己想办法"） | 老项目被拦时，报错里给出一条能走通的动作 |
| **I5** | 放行/拒绝是**声明式**的：新加一个产出类工具，只需要在工具定义里写一个字段，不需要记得去改 3 个地方 | 新增工具的守卫测试 |

## 2. 为什么"在每个工具里加 3 行"不算彻底

现状有 **3 处各自为政的判据**，它们必然漂移：

| # | 判据 | 位置 | 问题 |
|---|---|---|---|
| 1 | `mode !== 'confirm' → return null` | `approval-gate.ts:151` | **auto 全放行**（S1） |
| 2 | `state === 'storyboarding'` 时拦 `FORMAL_TOOLS` | `approval-gate.ts` | 只看 state，不看 landed（S3） |
| 3 | `landStoryboard()` 内部 `validateForSeed` | `storyboard-land.ts:191` | 只管"能不能落"，不管"能不能开工" |

再加第 4 处（在 4 个工具里各写一遍 `if (!landed) throw`），就是把 3 份判据变成 4 份 —— 下次
新增一个产出工具（比如"批量出图"）时，谁记得去加第 5 份？

**所以要引入"单一放行点"**。

## 3. 方案：五层

### L1 · 声明式前置 + 单一放行点（解决 S1 / S3 / I1 / I5）

**做法**：在 `host-tools.ts` 里加一个本地包装器，所有工具都从它出去：

```ts
// 概念示意，不是最终代码
studioTool({
  name: 'render_composition',
  gate: 'storyboard-landed',   // ← 新增的一个字段
  ...原有定义
})
```

包装器在 `execute` 前统一跑 `assertGate(gate, exec)`：

```ts
async function assertGate(gate, exec) {
  if (gate !== 'storyboard-landed') return
  const projectId = await resolveProjectId(registry, exec.agent?.session.header.cwd)
  const doc = await loadStoryboardOrFail(registry, projectId)   // 无文件 = 未落地
  if (doc.landed === null) throwError('CS-STORY-001', {...})
}
```

- **为什么改这里而不是 `DefineToolOptions`**：`@deepseek-ai/dsh-tools` 的 `DefineToolOptions` 是
  封闭 interface（读过 `.d.ts`，无 `additionalProperties` 位），加不了自定义字段。我们自己的包装器
  是唯一能在不 fork SDK 的前提下做到"声明式 + 单点"的地方。
- **与 mode/state 彻底解耦**：gate 只读 `landed`。`approval-gate.ts` 里的故事板分支**整段删除**
  （`STORYBOARDING_MESSAGE` 迁进 gate 的错误文案），保留 `keyframe_review` 那部分不动。
- **需要挂 `gate` 的工具**（产出类，共 8 个）：
  `render_composition` / `compose_video` / `video_generate` / `video_composite` /
  `tts_voiceover` / `music_generation` / `qc_shot` / `extract_last_frame`
  （= 现有 `FORMAL_TOOLS` 全集；`write_script` 也挂，规格同现状）
- **不挂的**：`image_generate` / `character_generate` / `look_card` 等 Look 阶段动作（现状就允许），
  以及所有读类/分析类工具。

> 这样 I1 成立：不经过 `approvalGateMessage`，也不再受 `mode` 影响。auto 与 confirm 走同一条。

### L2 · 单一事实源 + 自愈（解决 S3 / I2）

- **放行只读 `landed`**（L1 已实现）。
- `workflow.state` 降级为**派生显示**：`landFirstTime` / `resumeLanding` 已经会在落地后推
  `state='executing'`（`storyboard-land.ts:239/277`），保持不动。
- 新增**自愈**：`openProject` / 路由初始化时，若 `landed != null && state === 'storyboarding'`
  （历史数据不一致、或迁移时写坏），自动补推 `executing` 并记一条日志。**只修显示，不放行** —— 放行
  仍以 landed 为准，避免"自愈"变成后门。

### L3 · auto 自动落地（解决 S2 / I3）—— **必须最先落**

`write_storyboard` 的返回前，若同时满足：

1. `workflow.mode === 'auto'`
2. `validateForSeed` 的 `blockers` 为空（复用同一份判据；**`readyToLand` 不是现有字段**——`write_storyboard` 返回只有 `{ text }`，本期若要此名须新建。现成对称位：confirm 模式的 `concludedForLanding` = `awaitingLanding=true && blockers 空 → concludeTurn`）
3. 开关 `autoLandStoryboard` 开启（默认开）

→ Host 直接调 `landStoryboard(registry, projectId)`（`sourceVersion` 省略 = 落活副本，会自动补
「落地前固化」checkpoint），把结果写进返回文案：

```
已自动落地：生成 14 张分镜卡（版本 live），画布已可开工。
```

要处理的 4 个边界（都在 `landStoryboard` 里现成有语义，不用重写）：

| 情形 | 行为 |
|---|---|
| 已落地过 | `landStoryboard` 会抛"已落地，版本操作已冻结" ⇒ 捕获并忽略，返回"已落地"而不是失败 |
| 落了半截（有 landed 无种子锚点） | 走 `resumeLanding()` 自愈续做 |
| `blockers` 非空 | **不落**，照常返回阻断项让 agent 补 —— 这正是"先完善再落地" |
| 落盘异常（画布写失败） | 不吞错：把异常转成 `CS-USER-ERR` 并在文案里说明"故事板已保存、落地失败，可重试" |

> ⚠️ **顺序铁律**：**L3 必须先于 L1 上线**，双重理由：
> ① **现状（L1 未上线）已在漂移**：`skills/canvas-studio-creation/references/screenplay.md:21` 第 6 条
> 与 `host-tools.ts` 的 `concludedForLanding` 注释都已向 agent 承诺「auto 模式写完故事板由 Host
> 自动落地」，但实现不存在 ⇒ auto 跑完 `write_storyboard` 后 agent 按承诺继续、S1 门禁放行
> ⇒ **未落地的故事板直接出片（静默脱节）**。L3 上线即兑现既有承诺。
> ② **L1 上线后**：只上 L1 不上 L3 ⇒ auto 写完故事板没人落地又被 L1 拦住 ⇒ 死锁
> （agent 只能反复问用户，而 auto 模式下 `ask_user_choice` 是自动应答的，永远解不开）。

### L4 · 不豁免存量 ⇒ 必须给"出路"（解决 I4）

既然不开豁免，一个已有画布但**没有 `storyboard.json`** 的老项目，第一次调用产线工具就会被拦。
报错必须能把人送到终点，给出**三条**可执行路径：

1. **`write_storyboard` 手写**（agent 读画布节点反推 sections 后写）——已有能力，但费时；
2. **新增一次性迁移工具 `adopt_canvas_as_storyboard`**（建议做）：
   读画布节点（`seedStoryboardShot` / 镜位卡 / 文案卡）→ 反推 `§04 storyboard` + `§01 facts` +
   `§02 tokens` 的**骨架**，`meta` 从项目设置取（画幅/时长）；`blockers` 里会剩下需要人补的项，
   补齐后落地。**这是"不豁免"能落地的前提**，否则老项目真的没法继续。
3. **导出/重开项目**（最后手段）。

> 我的建议：**做 2**。不做的话，"不管存量"等于"老项目全废"，产品上不可接受。

### L5 · 契约补齐 G6（动画时序 + 素材挂载）

新增分册 `skills/code-driven-explainer/references/animation-and-assets.md`（约 3–4KB），写清 4 类语义
（都是本次会话**实际去读源码**才拿到的）：

| 主题 | 要写清的事 | 对应实现 |
|---|---|---|
| 逐字动画 | `textUnitProgress` 的帧语义（第 N 个字在第几帧出现、整卡 vs 逐行、`wordDelayFrames` 的叠加关系） | `TextCard.tsx` |
| 图片轨 | `fit` 三种模式的裁切规则、`kenBurns` 的运动包络、`ImageClip` 的尺寸来源 | `ImageClip.tsx` / `materialize.ts` |
| 素材可用性 | `asset-check` 判"可用/不可用"的依据（存在性、可解码、目录内）、失败时的降级 | `asset-check.ts` |
| 形状几何 | `shape-geometry` 的顶点算法与 `box` 百分比换算（star/polygon 的半径与边数关系） | `shape-geometry.ts` |

配套守卫：`tests/manifest-contract-doc.test.mjs` 已有的"文档断言 ↔ 源码正则"模式**照抄一份**
（新增 6–8 条），源码改了文档没跟就红。

## 5. 上线顺序（有硬依赖，不能乱）

```
① L3 auto 自动落地  ──→  ② L1 声明式前置（gate）  ──→  ③ L2 自愈  ──→  ④ L5 契约补齐
                                                     ↘ ⑤ L4 迁移工具（与①②同批，见下）
```

- **①②必须连着上**：只上①没风险（多做事）；只上②会死锁。
- **⑤ 必须与 ①② 同批上线**（硬约束，不是"建议"）：否则老项目在 L1 上线那一刻就停摆，且第 6 节 `CS-STORY-001` 文案会指路到尚不存在的 `adopt_canvas_as_storyboard`（CV-304 同类问题：文案不许指路到不存在的工具）。
- ④（契约）独立，可随时上。

**开关**（便于回滚）：
- `enforceStoryboardLanded`（默认 **开**）—— 关掉即退回今天的行为
- `autoLandStoryboard`（默认 **开**，你已拍板）

## 6. 错误文案（一次说清三条出路）

```
CS-STORY-001 · 本项目还没有落地故事板，产线工具暂不可用。

为什么拦你：故事板（storyboard.json）是全片规划的唯一事实源，落地后画布上的分镜卡
由它铸出来。跳过它直接出片，画布会与规划脱节，返工成本更高。

怎么继续（按推荐顺序）：
1) 写故事板：write_storyboard 补 §02 视觉规范 + §04 分镜（至少 1 scene、每 scene ≥1 shot），
   写完调 land_storyboard 落地（auto 模式会自动落地，无需用户点击）。
2) 老项目迁移：adopt_canvas_as_storyboard 从现有画布反推骨架，补齐后再落地。
3) 确认是纯素材拼接（没有分镜规划）：请明确告知用户需要在设置里切换项目类型。
```

> 注意：文案里**不出现"豁免/跳过"**——按你的决定，没有第四条路。

## 8. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| L1 上线即拦死老项目 | 高（核心流程不可用） | 与 L4 同批上线；开关可一键关 |
| auto 自动落地写出半截画布 | 中 | `landStoryboard` 是 WAL 先落料再写画布，且有 `resumeLanding()` 自愈 |
| auto 落地覆盖用户手动改过的画布 | 中 | 落的是"活副本"，已在首落时补 checkpoint；可用历史版本回看 |
| 删 `approval-gate` 故事板分支时误伤 keyframe 分支 | 中 | 两段独立，删前先跑 `render-host-executor` / `approval-*` 全量测试 |
| G6 文档写了但模型仍去读源码 | 中 | 用同样的"文档↔源码"守卫保证不漂移；但**不保证模型不看**——这条只能靠下次会话数据验证 |

## 10. 需要你确认的 3 个细节

1. **`write_script` 要不要一起挂 gate？** 现状它在 storyboarding 阶段被拦（`STORYBOARDING_EXTRA`）。
   我建议**挂**（保持现状语义），但它的产物是文案节点，与"产线"略有区别。
2. **`adopt_canvas_as_storyboard` 做不做？** 不做的话，"不管存量"没有任何出路（我建议做）。
3. **第 3 批（G6 契约）是否与第 1 批同批上？** 同批上的话一次会话就能验证两类改动，但 diff 会大一些。
