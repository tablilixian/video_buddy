## 0. 一页结论

| 问题 | 答案 |
|---|---|
| 渲染走哪条路 | **Route B / CSR**：`@remotion/web-renderer` 的 `renderMediaOnWeb`，跑在 Electron **渲染进程**。**不起 webpack bundle、不起 headless-shell**（生产链路里 `@remotion/bundler` / `@remotion/renderer` 只出现在取证脚本） |
| 最大瓶颈 | 4–6ms/帧（裸捕获）→ **209.2ms/帧**（产品 standard 档）这 **35–50 倍差距**，即全部优化空间 |
| 能不能提并发 | ❌ **不能**。web-renderer 包内 `onlyOneMediaRenderAtATimeQueue` 模块级串行（`render-operations-queue.d.ts:1-4`） |
| 分段渲染可行吗 | ✅ **API 层已打通**（`frameRange` 通到 `renderMediaOnWeb`），**但生产零调用方**，卡在 ffmpeg 拼接实验未做 |
| 分步渲染可行吗 | ✅ 已有雏形（三段式 + spot 不启编码器），可再推进「准备阶段前移」与「draft→standard 两阶段出片」 |
| 分层渲染可行吗 | ⚠️ **收益有条件**，等于「背景层栅格化成本 ÷ 总栅格化成本」。本项目背景是几个 `<AbsoluteFill>`，**不建议盲做**，需先测占比 |
| 三种切法省什么 | 分段省**超时与重试**、分步省**准备与无效编码**、分层省**重复栅格化** —— **三者都不省「每帧 209ms」本身** |

## 3. 分段 / 分步 / 分层：逐个回答

### 3.1 分段渲染（沿时间轴切）→ **可行，通道已打通一半**

**现状**：`frameRange` 从 `renderManifestOnWeb` 一路通到 `renderMediaOnWeb`，API 层完整可用：

```ts
frameRange?: FrameRange   // number | [number, number] | [number, null]
// remotion-render.ts:149（选项）/ :234（sampleFrames 旁路）/ :270（透传）
```

**但生产零调用方** —— `grep -rn frameRange src/host-tools.ts` 无匹配。REQ-034 明确判 ⛔：

- `:225` E5「分段重渲 + 拼接」⬜
- `:745` W5-6「⛔ 不做（本轮）……段拼接（ffmpeg concat + 边界关键帧对齐）按计划要先做 **20 次随机段拼接实验**，属独立批次」
- `:654` 风险：「段边界关键帧对齐、音频重采样接缝」

**收益边界（重要，别高估）**：

| | 说明 |
|---|---|
| ✅ 解决 | **超时风险** —— 单段恒 < cap，high 档 / 长片彻底解（P2-D 原始动机） |
| ✅ 解决 | **断点续渲** —— 段是最自然的检查点，失败只重做一段 |
| ✅ 解决 | **失败重试成本** —— 从全片降到单段 |
| ❌ 不解决 | **总渲染时间** —— 段串行渲，总帧数与每帧成本都不变 |
| ⚠️ 反而变差 | 每段付一次 `prepareMs`（**出处待 RP-16 拆解**；字体那部分只有 26–44ms，见 §7.5）+ 编码器初始化 + 建窗 204–684ms |

> **结论（2026-11-07 修订）**：原估「10 段多付 190s 字体费」**已证伪**（§7.5：字体
> 26–44ms/次，10 段合计 <0.5s）。分段的固定开销改成看 **RP-16 拆出来的真元凶** ——
> 若 `prepareMs` 主体是素材时长探测，每段重探就是真成本（需 `realDurations` 按段短路）；
> 若只是首帧前预取，分段反而能摊薄。
> **RP-08 的前置因此改为：RP-16（先定 `prepareMs` 出处）+ RP-09（建窗成本 / 挂死根因）。**

**拼接技术要点**：
1. **关键帧对齐** —— 段边界须为 IDR；可控 `keyframeIntervalInSeconds`，或 ffmpeg 后处理 `-force_key_frames`
2. **音频是最大难点** —— `audioCodec: 'aac'` 在 Remotion 内混音，分段会切成 N 段且接缝有重采样/编码延迟。
   **建议方案：视频分段 + 音频整轨单独渲**（段用 `muted: true` 出纯视频，音频走既有 ffmpeg 基建单路合成后 mux）
3. **基建已具备** —— `src/ffmpeg-run.ts:1-150`（随包二进制定位 / 超时强杀 / 信号中断 / probe）

### 3.2 分步渲染（沿管线阶段切）→ **已有雏形，可更激进**

**(a) 管线内部拆步** —— 已存在：
- `render-job-executor.ts:5-6` 三段式 `渲染 → 逐张回写抽帧 → 回写成片`
- 准备与渲染已分离计量（`remotion-render.ts:242-245` `prepareMs`）
- `realDurations` 让「探测」成为可跳过独立步

**可推进**：把 `prepareMs` 三件事（字体 / 时长探测 / 能力预检）**提到建单阶段预跑**，渲染单拿到的 manifest 直接「已就绪」（RP-03）。

**(b) 预览 / 成片两阶段** —— 已有 `spotFrames` 分支（`render-job-executor.ts:96-136`），每帧 `renderStillOnWeb` 不启编码器。`remotion-render.ts:330-339` 注释：「甜品复刻会话 46 次渲染里绝大多数只为看几个画面」。

**可再加一档**：`draft → standard` **两阶段出片** —— 先渲 draft（131.9ms/帧、scale 0.5）落画布，确认后再渲 standard 覆盖。比「直接渲 standard 然后发现要改」便宜得多。

### 3.3 分层渲染（把已渲染结果当素材）→ **可行，但收益有条件**

**技术上完全支持**：manifest track 支持 `type:'video'`，渲染出的 mp4 可作 `<Video>` 素材进新队列，消费路径 `VideoClip.tsx` 已有。

**收益模型**：

```
总成本 = 栅格化成本 + 编码成本

分层后：
  第1层（背景/静态）：渲 N 帧 + 编 N 帧
  第2层（动态前景）：渲 N 帧（背景不重画）+ 编 N 帧（但要解码第1层）
省下的：  第2层的背景栅格化 + React reconcile
没省的：  第2层仍要编 N 帧，且多了第1层解码开销
```

**收益 = 背景层成本 ÷ 总栅格化成本**：

| 场景 | 收益 | 建议 |
|---|---|---|
| 背景静态（纯色 + 颗粒 + 暗角），前景密集动画 | **低** —— 背景本来就是几个 `<AbsoluteFill>` | ❌ |
| 背景是复杂视频 / 图表 / 3D，前景是字幕 | **高** | ✅ |
| 多轨叠加，每轮只改一轨 | **高** | ✅ |

**本项目判断**：`Root.tsx:261-302` 是「每轨一个 Sequence 平铺」，暗角/颗粒是**逐帧确定的固定层**（`:281-292` 注释：整数偏移 + 固定 tile 保证不闪烁）⇒ 背景本身很便宜，**单纯为省背景而分层不划算**。但颗粒层若逐帧重画是可测的固定成本，值得单独测（RP-15）。

**三个陷阱**：
1. **重复编码质量损失** —— 每次分层合成都 re-encode，必须用中间格式（低 CRF / ProRes / 高码率 CQP），最终才 H.264
2. **与 H1 冲突** —— web-renderer 模块级串行，分层**串行**做 = 层数 × 全片时间，**必然更慢**。要快必须**多窗口并行**（不同 BrowserWindow 不共享那个 queue）
3. **对齐** —— 层间帧率 / 时长 / `startFrame` 必须严格对齐

### 3.4 三种切法的统一视角

| 切分维度 | 省什么 | 不省什么 |
|---|---|---|
| **分段**（时间轴） | 超时风险、重试成本、可断点 | **总时间** |
| **分步**（管线阶段） | 准备开销、无效编码 | **每帧成本** |
| **分层**（合成层级） | 重复栅格化 | **编码成本** |

> **三者都不省「每帧 209ms」本身。** 真正让每帧变便宜的只有 RP-04（硬编）、RP-05（去节流）、RP-02（去字体重复开销）。
> **RP-01 Q9 结果（§7.4）：温和可见性节流只有 1.21× ⇒ RP-05 这条路降级（⏸）**；
> 当前最有把握的"每帧变便宜"只剩 **RP-04（硬编）**；"整单变便宜"的抓手是 **`prepareMs`**
> ——但 §7.5 已证伪"字体 19s"，**必须先做 RP-16 拆解**才知道该优化哪一段（否则对着错误靶子写码）。

## 7. 归因实验（RP-01 · Q9 窗口节流；RP-02 前提 · 字体成本探针）

### 7.1 为什么这个实验是第一优先

项目里存在**两条看似冲突的记录**，此前从未被对账：

| 记录 | 口径 | 结论 |
|---|---|---|
| **A** `docs/cv-details.md:2000` / capability-bench **S2** | **合成 composition**（1920×1080 简单动画，无真实素材无字体），`hidden` vs `hidden-throttled` 窗口 | **「节流档不减速 ⇒ web-renderer 帧步进不依赖 rAF」** |
| **B** CV-447 真机实测 | **真实产品链路**（画布页 + 真实 manifest + 字体 + 工单桥） | **「healthy 209.2ms/帧 vs 节流 ≈445ms/帧」** |

**对账结论（本轮核实，两者并不真正矛盾）**：

1. **测的不是同一个东西**：A 测 `renderMediaOnWeb` 内部帧步进；B 测整条产品链路（含轮询 / 字体加载 / 素材预取 / 进度上报）
2. **A 只证明了「帧步进不依赖 rAF」这一条路径**，**不排除**其他节流机制（合成器降级、CPU 调度、`setInterval` 轮询被压）
3. 产品侧证据：`渲染全链路失败点与真机排查手册-20261029.md:102` 记 `render-job.ts:462-467` **实测「节流到几十秒一拍」**，且 `画布阶段提速方案.md:102` 把机制写成「Chromium 节流 rAF 与 `setInterval` 轮询」

⇒ **「节流是否为主放大器」此前只有 B 一条产品实测，没有独立归因实验。** 这正是 Q9 要补的。

> ⚠️ **注意**：CV-447 已落了 P0-A（渲染在飞时临时 `setBackgroundThrottling(false)`），所以 **Q9 测的是「若无该防护会怎样」的对照口径**，不是回归验证。别把 Q9 结果读成「CV-447 没用」。

画布页 209.2ms/帧（3.6×）**，而 Q9 已排除「窗口可见性」这一变量 ⇒ 这 3.6× 更可能来自
**页面本身**（画布重页的 React/栅格/绘制与渲染抢核，轻渲染页则没有）。
若成立，则「**保证工单走隐藏渲染窗、少回退到画布页**」的价值很高
（`executorFallbackReason` 正好能统计回退频率，可先取数再决定 RP-09 优先级）。

> **RP-01 补充实验（⬜ 未启动，可选）**：要直接归因 445，需在**产品侧**做同规格 A/B
> ——同一份真实 manifest × 画布页 `backgroundThrottling` 开/关，且复用真实中文字体
> （这样才测得到 `prepareMs`）。轻页 Q9 已排除窗口变量，下一次实验该换"重页 + 真素材"口径。

### 7.5 字体成本探针 —— **RP-02 的前提被证伪**（✅ 2026-11-07 实测）

**动机**：B2 的主攻项 RP-02 挂着「省 19s × 每次重渲」，但那 19s 是整段 `prepareMs`
（字体 + 时长探测 + 能力判定，`remotion-render.ts:242-245`）——**字体到底占多少从没单独测过**。
写码前先测。

**方法**：独立 Electron 探针（不进仓库，会话临时件）——同源小静态服务复刻产品字体路由
（`cache-control: public, max-age=31536000, immutable`，与 `routes.ts:3504` 一致），
在隐藏窗里分步计时 `document.fonts.load` / resource timing / 字形栅格化；
三态各跑 3 次（同页二次 / 同进程新窗 / **全新进程**）。

**数据**（随包 `noto-sans-sc-400.woff2` 997,160 B）：

| 阶段 | 冷进程（磁盘缓存空） | 新进程（磁盘缓存热） | 同页二次 |
|---|---:|---:|---:|
| `document.fonts.load` 400（取回 + 解析） | **43.8 ms** | 37.5 / 26 ms | **0 ms** |
| 字体传输（resource timing `transferSize`） | 997,460 B / 10 ms | **0 B（命中磁盘缓存）** | 0 |
| `document.fonts.ready` | 0 ms | 0 ms | 0 |
| 字形栅格化（50 次 `fillText` CJK） | **4.2 ms** | — | — |
| 服务端实际被请求次数 | 1 次（首个进程） | **0 次** | 0 |

**结论**：

1. **字体全程 ≈ 26–44 ms/次，不是 19s** —— 差 **两个数量级**。RP-02 原案
   「按字体 hash 缓存、省 19s×每次重渲」**前提不成立**：HTTP `immutable` 缓存
   **本来就已存在**（`routes.ts:3504`），跨进程也已命中（`transferSize=0`）。
2. **⇒ 真机 19s `prepareMs` 另有出处**，头号嫌疑是 `probeManifestDurations`
   （无 `realDurations` 时在浏览器里逐个加载素材取时长 —— 挂死取证里「26 个 `<video>`
   预取 + 首帧 ≈ 10.8–11.1s」与之同型），次嫌疑是能力判定与首帧前预取。
3. **B2 改道**：不写缓存代码，先做 **RP-16 `prepareMs` 三段拆解计量**
   （font / probe / capability 分段计时进回执）→ 真机取数 → 再定 RP-02/RP-03 怎么做。
   这与 [`2026-10-24-收口与后续路线图.md`](./2026-10-24-收口与后续路线图.md) 里
   **B5-1「先拿真机 `prepareMs` 基线」**是同一件事，当时判「等基线」，现在补上。
4. 顺带证伪项：`FONT_READY_TIMEOUT_MS=8000` 的等待闸门**没有被触发**
   （`fonts.ready` 0ms），字体不是超时风险源。

**caveat**：本机 loopback 探针，不含产品画布页的并发负载；真机若字体源不同
（manifest 自声明的同源 `src`）仍可能更慢 —— 但随包字体这条主路径已被排除。

## 9. RP-16 实施记录（2026-11-07，已落码 🟢）

### 9.1 动机与设计

§7.5 字体探针证伪了「19s 是字体」的假设 ⇒ 真机 `prepareMs` 的出处必须先测出来，才知道
RP-02 重定义 / RP-03 要不要做（= 10-24 路线图 B5-1「等真机基线」那件事）。

**口径**（加性遥测，不改任何现有字段与行为）：

| 字段 | 计时段 | 备注 |
|---|---|---|
| `prepareFontMs` | `applyManifestFonts`（注入 `@font-face` + 等字体就绪） | §7.5 预期 ≈26–44ms |

- **spot 路径三段与 `prepareMs` 一律 0**：spot 的字体 / 能力耗时已含在 `renderMs`（= `totalMs`）里，
  没有独立准备阶段；硬填会让「三段之和 ≈ prepareMs」这条口径在 spot 上失效。
- **文本只在三者至少一个是 number 时才加括号段**：老客户端 / spot 不上报时不冒出 `（- / - / -）`
  这种噪音（单测钉了正反两面）。

### 9.3 撞行数棘轮怎么解的（**没改白名单登记数**）

首版落码后 `test:smoke` 红：`host-tools.ts` 实测 5,022 > 登记 5,008、
