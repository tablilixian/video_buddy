## 二、现状的四个真问题（这就是必须重构的理由）

### 问题 1：`write_storyboard` 每次整体重写都打点 —— **与「分次写」直接冲突**

契约 §5 只规定 **3 个自动 checkpoint**：`首稿 → v1`、`落地前固化 → vN`、`落地冻结 → final`。
但实现里额外加了「每次整体重写，先把旧活副本打点」。而 skill 刚定下「分次写」（4 笔），于是**一次完整创作会刷出 4 条机械命名的版本**——正是实测里的 `重写前存档 v1/v2`。

这不是风格问题：版本列表是给用户做「里程碑选择」的，被自动噪音刷满就废了。

### 问题 2：`versions.current` 语义在「能看历史版本」之后就不成立了

现在 `current` 表示「活副本派生自哪一版」。但一旦 UI 允许**查看**任意历史版本，「current」立刻歧义：是「当前活副本的父版本」还是「当前正在看的版本」？

后者是**视图状态**，不该进数据。

### 问题 3：`final` 与 `sourceVersion` 塞在 `versions` 里，语义错位

`final` 不是「一个版本」，是**落地产物**（seed 的输入 + 一次性冻结）。它和「版本历史」生命周期完全不同，却共用一层。

### 问题 4：版本号铸造规则脆弱 —— `v{history.length + 1}`

任何未来的清理/裁剪都会撞号。开发阶段就该换成**单调计数器**。

## 三、目标语义（先定死，再谈实现）

### 3.1 三个概念必须分清

| 概念 | 是什么 | 可变？ |
|---|---|---|
| **活副本** `sections` | 正在编辑的内容（agent 分次写都落这里） | ✅ 持续变 |
| **版本** `versions.history[]` | **里程碑**快照（全量），只增不减 | ❌ 一旦写入不可改 |
| **落地产物** `landed` | 一次性冻结的 seed 输入 + 来源审计 | ❌ 落地即冻结 |

### 3.2 什么时刻产生一个版本（**这是本方案最重要的决定**）

只在这四个时刻打点：

| # | 时刻 | kind | label 默认 | 说明 |
|---|---|---|---|---|
| 1 | **首稿**（`write_storyboard` 第一次成功） | `auto` | `初稿` | 有意义的起点 |
| 2 | **用户点「存档为新版本」** | `manual` | `存档 N`（可改名） | 用户自己的里程碑 |
| 3 | **回退前**（活副本即将被覆盖） | `auto` | `回退前存档` | 保证「不丢数据」 |
| 4 | **落地固化** | `auto` | `落地前固化` | 落地的第一步 |

**明确不打点**：`write_storyboard` 的整体重写**不再**产生版本（撤销问题 1）。分次写 4 笔 → 只有首稿那一条。

> **与契约 §5 的差异**：契约说的 3 个 checkpoint 与本表 1/3/4 一致（本表多一条「用户手动存档」，那是契约 §5 本来就承诺的按钮）。**我上轮多加的「每次重写打点」是偏离契约的，本方案予以撤销。**

### 3.3 回退语义（需拍板，二选一）

| 选项 | 动作 | history 变化 | 我的评价 |
|---|---|---|---|
| **A（推荐）** | ① 先把当前活副本打点（保住「回退前」）② 活副本替换为所选版内容 ③ `baseline` = 所选版 | +1 条（回退前的状态） | 每条版本内容**互不相同**，语义清晰 |
| B（契约字面） | 新增一条版本，其内容 = 所选旧版内容；活副本 = 该内容 | +1 条（与旧版重复） | 会造出内容重复的条目，列表里两条一模一样 |

两者都满足「回退不删历史」。**我推荐 A**：它把「回退前」这个真正会丢的状态保住了，而 B 保住的是一份本来就还在的旧内容。

### 3.4 不变量（写进守卫测试，缺一即红）

1. `history` **只增不减**（整项目删除除外；本方案**不提供删除版本的接口**）
2. `history[].version` 唯一，且**单调递增**（`v{n}`，n 只增）
3. `history[].snapshot` 写入后**不被原地修改**（每次打点 = 新对象）
4. `baseline` 必须是 `history` 里存在的版本号，或 `null`
5. `landed` 一旦非 null，其 `sections` 与 `sourceVersion` 不再变
6. **落地后拒绝** `archive` / `restore`（单向终点）
7. **任何覆盖活副本的操作，必须先打点**（`restore` 是唯一会覆盖活副本的显式操作）
8. 版本快照是全量 `sections`（不存 delta）—— 体量小、`render(version)` 与 diff 都最省事

## 四、数据模型（schemaVersion 1 → 2）

开发阶段不考虑兼容，直接换形状。读到旧 `schemaVersion` **显式报错并提示让 agent 重写**（不静默丢弃、更不静默迁移）。

```jsonc
{
  "schemaVersion": 2,
  "projectId": "…",
  "title": "《初次接触》",
  "meta": { … },

  "sections": { … },            // ← 活副本（唯一可变处）

  "versions": {
    "seq": 3,                   // 单调计数器：下一个版本号是 v4
    "baseline": "v3",           // 活副本派生自哪一版；null = 尚无版本（还没首稿）
    "history": [
      { "version": "v1", "kind": "auto",   "label": "初稿",
        "createdAt": 1790…, "parent": null, "snapshot": { …全量 sections… } },
      { "version": "v2", "kind": "manual", "label": "黄昏版",
        "note": "把 S1 改成黄昏", "createdAt": 1790…, "parent": "v1", "snapshot": { … } }
      //    ↑ note 可选：用户存档时可写一句「这版是什么」
    ]
  },

  "landed": {                   // ← 从 versions 里搬出来，语义独立
    "at": 1790…,
    "sourceVersion": "v3",      // 落的是哪一版；活副本直接落时记 "live"
    "sections": { … }           // 落地所选内容的全量冻结
  },

  "bindings": { … },            // 语义 ID ↔ 画布 UUID（快照之外）
  "actuals":  { … }             // 执行期实况（快照之外）
}
```

**改动点**：`versions.current` → `versions.baseline`（语义改名）；新增 `versions.seq`；`history[]` 加 `kind` / `note`；`versions.final` + `versions.sourceVersion` → 顶层 `landed { at, sourceVersion, sections }`；`schemaVersion` → 2。

## 五、纯函数层（逻辑不散在路由里）

### 5.1 `src/storyboard-history.ts`（新增）

```ts
// 全部纯函数 + 可单测；路由与工具只做「读 → 调纯函数 → 写」
nextVersionId(versions): string            // `v{seq+1}`，只增不减
archive(versions, sections, { kind, label, note?, now }): versions
  // → seq+1、history 追加一条（snapshot = sections 的深拷贝）、baseline 指向新版本
restoreTo(versions, currentSections, target, { now }): { versions, sections }
  // 选项 A：先 archive 当前活副本（kind:auto / label:回退前存档）→ 返回 target.snapshot 作为新活副本
  //          baseline = target.version
versionById(versions, id): StoryboardVersion | undefined
latestOf(versions): StoryboardVersion | undefined
```

### 5.2 `src/storyboard-diff.ts`（新增）

字段级差异，**按语义路径逐字段比**（不是文本 diff —— 文本 diff 在 JSON 上只会给出一堆噪音）：

```ts
type DiffKind = 'added' | 'removed' | 'changed'
interface DiffEntry { path: string; kind: DiffKind; label: string; from?: string; to?: string }
diffSections(a: StoryboardSections, b: StoryboardSections): DiffEntry[]
```

路径示例：`04 分镜.S1.Sh1.duration`、`05 角色.C1.gen.lockedPrompt`、`08 硬约束[2]`。
**`label` 走人读中文**（复用渲染层已有的分节命名），因为它的唯一用途就是给人看。

## 六、路由 API（完整清单）

| 方法 | 路径 | 作用 | 鉴权 |
|---|---|---|---|
| `GET` | `/canvas-studio/storyboard/<projectId>.json` | **版本摘要**（不含快照）：`{ versions:[{version,label,kind,note,createdAt,parent,filled,isBaseline}], baseline, landed:{at,sourceVersion}\|null, liveFilled }` | loopback |
| `GET` | `/canvas-studio/storyboard/<projectId>.html?rev=<n>&version=<vN\|live>` | 渲染活副本或指定历史版本 | loopback |
| `POST` | `/canvas-studio/storyboard/archive` | `{ projectId, label?, note? }` → 打点 | 同源 |
| `POST` | `/canvas-studio/storyboard/restore` | `{ projectId, version }` → 回退 | 同源 |
| `POST` | `/canvas-studio/storyboard/rename` | `{ projectId, version, label }` → 改版本名（契约「可命名」） | 同源 |
| `POST` | `/canvas-studio/storyboard/land` | 已有 | 同源 |
| `GET` | `/canvas-studio/storyboard/<projectId>/diff?from=<vN\|live>&to=<vN\|live>` | 字段级差异 | loopback |

**`?rev=` 与 `?version=` 必须拆开**（关键修正）：现在 `?v=` 被当成**缓存破除号**（`write_storyboard` 结算时 bump，见 `client/storyboard-signal.ts`）。若继续用它传版本号，两个语义会撞车。拆分后：
- `rev` = 单调 rev，**只用来破缓存**
- `version` = `live` 或 `v3`，**决定渲染哪一版**

**不做**：`DELETE /version`（不变量 1：历史只增不减）。

## 七、UI 设计

### 7.1 控件放哪：**覆盖层头部（React），文档内只做只读展示**

理由：存档/回退要发 Host 请求，而故事板 HTML 是**刻意零 JS**（Host 纯函数渲染、iframe 同源加载）。把交互放外层 React，既不用给文档引入脚本，也不用 postMessage 通道。

覆盖层头部（从左到右）：

```
拍摄定稿  [活副本 ▾]                              [存档] [确认落地] [展开] [关闭]
```

点「活副本 ▾」弹**版本面板**：

```
┌────────────────────────────────────────┐
│ ● 活副本（未存档）        已填 6/9 节     │  ← 默认选中
│   v3  重写前存档 v2       10-11 08:57   │  ← 灰色小字是 kind=auto
│   v2  黄昏版 ✎            10-11 08:51   │  ← 用户命名的用正常色
│   v1  初稿                10-10 22:45   │
├────────────────────────────────────────┤
│ [以此版为准回退]   [与活副本对比]          │  ← 选中非活副本时出现
└────────────────────────────────────────┘
```

- 选任意项 → iframe 换 `version` 参数**只读回看**（文档 topbar 显示「拍摄定稿 · v2」）
- 「存档」→ 弹小框：名称（可空，默认「存档 N」）+ 备注（可空）
- 「回退」→ 二次确认（说明「回退前的当前内容会自动存为一版，不会丢」）
- 「对比」→ 进入对比模式：并排或叠加差异高亮（见 §7.3）

### 7.2 落地后的形态（单向终点）

- 头部：`[已落地 v3]` 徽标替代版本下拉的**存档/回退**入口；版本列表仍可打开**只读回看**
- 文档 topbar：已在显示「已落地 vN · 只读回看」
- 版本面板里所有写操作按钮消失（不是禁用，是不渲染）

### 7.3 对比模式

- 选两个版本（默认 = 活副本 vs 最近一个版本）
- 渲染目标版本，并在**差异字段旁加标记**：`▲ 改`（changed）/`＋ 增`（added）/`− 删`（removed）
- 顶部一条摘要：「共 N 处差异：分镜 3 · 角色 1 · 硬约束 2」，点摘要项跳到该节
- 未变部分正常显示（不隐藏），保持可读性优先

## 八、与其它机制的关系

| 机制 | 关系 |
|---|---|
| **落地** | 落地前 `archive(kind:auto, label:'落地前固化')` → 写 `landed` → seed。落地后拒绝 archive/restore |
| **L 类回写**（字段级改动） | **不升版本**（契约 §5）：直写 `sections`，`baseline` 不变。UI 上表现为「活副本（未存档）」持续有改动 |
| **`write_storyboard` 整体重写** | 只改 `sections`，**不打点**（问题 1 的修正）；`baseline` 不变 |
| **`render(version)`** | 已有能力，本方案只补入口（路由 `version` 参数 + UI） |
| **`?rev=`** | 与 `version` 解耦（§六） |
| **`revise_storyboard`** | **不在本方案**（另一块：落地后改结构 + delta re-seed） |

## 九、边界与错误处理

| 场景 | 行为 |
|---|---|
| `storyboard.json` 读坏 | 已有：留证 `<file>.corrupt` + 显式报错，绝不静默重置 |
| `schemaVersion` 是旧值（1） | **显式报错**：提示「schema 已升级，请让 agent 重写故事板」——不静默迁移、不静默丢弃 |
| `baseline` 指向不存在的版本 | 归一化时降级为 `null`（容错读，不崩） |
| 版本快照缺字段 | 复用 `normalizeStoryboardSections` 逐字段降级（与活副本同一条归一化路径） |
| 存档时活副本为空 | 允许（用户可能想留住「还没写」的状态）；但 `label` 无法从内容推断时用默认名 |
| 回退到与当前活副本内容相同的版本 | 允许，但仍先打点（不变量 7）；UI 提示「内容相同」避免困惑 |
| 并发存档/回退 | 走 `updateStoryboard` 的模块级串行队列（已有） |
