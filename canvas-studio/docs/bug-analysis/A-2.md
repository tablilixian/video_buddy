# A-2 ｜ 大画布（102 节点）拖拽卡顿 + 废弃素材开关 UI 大问题

> 优先级 P1（高频痛点）｜ 风险 T1→T2（分三步，逐步收益）｜ 依赖：无
> 截图要点：102 个节点、数百条半透明边纵横交错；拖动刷新卡顿；开「废弃素材」后 UI 大问题。

## 代码级原因（三个热点叠加，均已代码确证）
1. **全树重渲染 + memo 被击穿**：StudioFrame 订阅 `nodes`（StudioFrame.tsx:214）与 `view`（:265）→ 拖拽每帧 `moveNode`（project-store.ts:752-768）整树重渲染；`CanvasNode.tsx:833` 虽 memo，但 `CanvasSurface.tsx:560/627/644` 的手势回调是组件体内裸函数、每帧新引用，经 :1021-1031 传入 → 102 节点全部重渲染。`setGuides`（CanvasSurface.tsx:710/727）再叠加。
2. **边全量重算、无视口裁剪**：`CanvasEdges.tsx:73-153` 每次渲染遍历全部节点×sourceIds 重建 Map/path/chip；:181 的 memo 挡不住拖拽（visibleNodes 引用必变，CanvasSurface.tsx:807）。
3. **废弃素材开关触发全量重排**：开关本身只是布尔（CanvasToolbar.tsx:162-168），但 `StudioFrame.tsx:1699-1716` 切换即调 `actions.autoArrange(...)`（隐藏时 layoutOverVisible、显示时全量）+ fit——102 节点全部换坐标（project-store.ts:1056-1094，含 tidyGroupLayout 二次遍历）= 一次全量风暴。

## 修复方案（三步，风险从低到高）
1. **useCallback 保 memo**（低风险，先做先测）：CanvasSurface 的 onNodePointerDown/onResizePointerDown/onLinkPointerDown 用 useCallback 包裹，内部只读 ref 镜像（nodesRef/selectedNodeIdsRef/viewRef——注意 CV-169 旧选区教训，selectedNodeIds 也挂 ref）。预期拖拽时节点重渲染从 102 → 被拖的 1 个。
2. **边裁剪 + 按边 memo**：把可视区世界坐标框（含 margin）传给 CanvasEdges，循环里先粗剔除再建 path；每条边抽成 memo(Edge) 子组件（key=source->target）。低缩放下全画布在视口内、裁剪收益有限——根收益仍在第 1 步。
3. **废弃素材开关退化为纯过滤**：只改 hideRetired（:222-224 过滤已有），去掉自动 autoArrange 与 fit；「重排」做成独立菜单项显式触发。若必须保留自动重排，至少去同步 fit + 放 requestIdleCallback。**语义变化**：隐藏后留下的空洞不再自动回收（BUG-004 曾修的行为），需接受或做局部整理。

## 改动风险
- 第 1 步：依赖收窄不当会读到旧选区（CV-169）——ref 镜像是硬要求；纯客户端渲染层，不碰数据。
- 第 2 步：裁剪可能影响依赖全量边的功能——已核实 minimap 不走 CanvasEdges，无影响。
- 第 3 步：产品语义变化（不自动重排），建议桌面向用户确认一次观感。
- 量化收益需 profiling（本文档只保证方向正确）；建议每步独立提交 + 拖拽帧率实测。

## 验收
无头：无法测帧率，靠 React DevTools Profiler 断言重渲染计数（可选）。桌面：102 节点项目拖动单节点帧率对比；开/关废弃素材不再全卡。
