# B3-1 · 异步派发 + 进度轮询（设计稿 v1，待评审，未动码）

> 任务来源：路线图 §3 `B3-1`（F-19）。目标一句话：**把 130–260 秒的渲染从「工具调用阻塞」变成「提交即返回 + 可查进度 + 可取消」**。
>
> 本文只做设计，**不含代码改动**。评审通过后按第 5 节分期落。

---

## 1. 现状（实测数字）

| 事实 | 数值 | 来源 |
|---|---|---|
| CSR 真渲耗时 | **129–182s**（225 帧 @1280×720，≈13 ms/帧） | `remotion-spike-report-2026-10-15.md` |
| 单次工具调用阻塞 | 同上 + 建单/校验/素材物化 | 真机会话 |
| 超时预算 | `帧数 × 200ms + 60s`，clamp **90s–20min** | `host-tools.ts`（B2-1 守卫钉住） |
| 会话代价 | 一次渲染 ≈ 一次上下文压缩的触发量级（6 次压缩的会话里，渲染 0 次） | 会话 #5 诊断 |

**问题的本质不是"慢"，是"不可让出"**：这 2 分钟里 agent 不能做任何别的事，用户也拿不到中间状态；一旦超时，之前所有规划步骤的上下文还在，但产物没有。

## 2. 已经具备的地基（不要重写）

| 已有 | 位置 | 复用方式 |
|---|---|---|
| 渲染**工单**（建单 → 认领 → 结算） | `src/remotion/render-job.ts` / `render-queue.ts` | 异步模式只是"把等待挪到工单之外"，工单本身不动 |
| 认领 / 改派 / 看门狗 / `deadlineAt` | CV-363 | 直接复用；异步后改派逻辑完全不变 |
| 客户端轮询 `pollRenderJob` + 保活 | CV-359 | 不动（它本来就与工具调用解耦） |
| 任务落盘 + 重启续跑 | `jobs.json` + `startDramaJobResumeWatcher`（Drama 视频那套） | 渲染工单可照抄这个模式做"重启后继续等" |

> **结论：异步派发不需要新机制，只需要新的"结果回收路径"。** 这是本设计的关键判断。

---

## 3. 真正的难点（先解决它，否则别开工）

同步工具的结果会**直接回到模型上下文**；异步化之后，2 分钟后的产物怎么回到**同一轮对话**里？

三条可行路径，各有硬约束：

| 方案 | 做法 | 硬约束 / 风险 |
|---|---|---|
| **A. 轮询工具**（最保守） | `render_composition{async:true}` 立即返回 `jobId`；模型自己调 `render_status{jobId}` 查 | 模型会**反复轮询**烧步数（每步 ≈6s 固定 TTFT）；且"什么时候该查"没有判据 ⇒ 大概率出现「查 20 次都在渲」的会话 |
| **B. 宿主注入 system note**（体验最好） | 工单结算时宿主往会话注入一条系统消息（"渲染完成，产物已落画布"），触发模型续跑 | **未验证**：当前 `@deepseek-ai/dsh-tools` 是否有"延迟注入会话"的公开接口？`concludeTurn` 只能结束回合，不能事后补一条。这是本方案的**技术前提**，必须先做一次 spike |
| **C. 混合** | 提交时 `concludeTurn` + 结算后由宿主发起**新一轮**（等价于自动化的"继续"） | 需要宿主能主动起 turn（自动化机制已有先例），但要避免与用户正在说的话抢轮 |

**建议**：先做 **A 的受控版**（给模型明确的"别轮询"指令 + 宿主侧节流），同时**立刻 spike 方案 B 的接口可行性**。B 一旦通，A 降级为兜底。

## 4. 接口草案（若要落 A）

```jsonc
// 提交（新增 async 参数，缺省 false = 行为与今天完全一致）
{ "manifestPath": "/…/build/m.json", "async": true }
// → { text: "渲染已派发：jobId=…（预计 150s）。完成后产物会自动落画布；
//           **不要反复查**，我会在结算时告诉你。要中止用 cancel_render。" }

// 查（新模式，非新工具：避免工具数膨胀）
render_composition { "status": "jobId" }
// → { text: "渲染中 · 已用 62s / 预算 180s · 进度 84/225 帧 · 执行者：隐藏窗口" }
// → 或 "已完成 · 产物节点 <id> · 用时 141s"

// 取消
render_composition { "cancel": "jobId" }
```

**为什么塞进同一个工具而不是加两个新工具**：本仓工具数已被 `tests/tool-registry.test.mjs` 钉死（现 29），每加一个都要过 6 处登记门禁；而 `status`/`cancel` 语义上就是同一个能力的动作。

## 5. 分期与出口

| 期 | 内容 | 出口（可验） |
|---|---|---|
| **P1** | `async` 参数 + `status`/`cancel` 动作 + 宿主侧"结算后把结果写进工单文件"；SKILL 补一条"提交后不要轮询" | 真机：提交后 <2s 返回；跑完后 `status` 能查到产物；取消能在 5s 内停 |
| **P2** | **方案 B spike**：宿主在结算时注入系统消息（若接口不可用 ⇒ 记录结论、方案降级为 A 长期化） | spike 报告：可行 / 不可行 + 证据 |
| **P3** | 并行多渲染（同一会话提交 2 条，各自工单） | 两条片子互不干扰；改派/看门狗仍正确 |

## 6. 风险与不做清单

| 风险 | 缓解 |
|---|---|
| 模型不听话，仍然反复 `status` | ① `status` 返回值里带"距上次查询仅过 Xs，**不要连查**"；② SKILL 硬纪律；③ 宿主侧节流（同一 job 5s 内重复查直接返回缓存） |
| 异步后工单滞留无人看 | 已有 CV-363 的改派 + 看门狗，不需要新逻辑 |
| 用户以为"没反应" | 提交返回文案必须写清「预计 Xs，画布顶部会显示进度」；客户端顶条加一条工单进度 |
| 半途关掉 App | 已声明「关掉整个 App 会中断渲染」是既有边界（工具描述里钉着），异步不改变它 —— **但要在返回值里重申**，否则用户以为异步=后台常驻 |

**不做**：作业队列 / 消息中间件（本仓缺的是"让出"，不是吞吐）｜跨进程渲染｜分段渲染 + concat。
