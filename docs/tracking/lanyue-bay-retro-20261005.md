## 一、为什么生成了这么多废弃视频

### 1.1 现象

画布 21 个节点里有 **6 个视频节点**，其中 5 个带「已失效」灰显角标，只有 1 个是有效状态。用户看到的「一堆灰视频」就是这 5 条。

| # | 节点 | 标题 | 版本 | 状态 | 是否入片 |
|---|---|---|---|---|---|
| 1 | `f66b0d53` | 分镜 1 · 视频 | — | superseded | ❌ |
| 2 | `ca235781` | 分镜 2 · 视频 | v2 | superseded | ❌ |
| 3 | `279d2deb` | 分镜 3 · 视频 | v3 | superseded | ❌ |
| 4 | `3b5faf9c` | 分镜 1 · 视频 | v4 | superseded | ✅ |
| 5 | `60fa2981` | 分镜 2 · 视频 | v5 | superseded | ✅ |
| 6 | `fb3f3e03` | 分镜 3 · 视频 | v6 | **active** | ✅ |

注意最后三行：**真正入片的三条里有两条也带「已失效」角标**。角标与事实完全脱钩。

### 1.2 根因（代码级）

`src/shot-versions.ts:199-205` 的 CV-222 镜位级取代判定：

```ts
if (anchorCards.size > 0) {
  for (const node of nodes) {
    if (node.kind !== 'video' || node.toolName === 'compose') continue
    if (!isActiveShot(node) || ids.has(node.id)) continue
    if (node.sourceIds.some((id) => anchorCards.has(id))) ids.add(node.id)  // ← 交集判定
  }
}
```

判据是「**新旧血缘有任一分镜卡交集**就算同一镜位」。这个假设在本次会话被直接打破：

agent 每镜传 3 张参考图（符合 `shot-format.md` 第 9 步的「≥3 张」硬规矩）：

```
镜1: [分镜1关键帧, 分镜2关键帧, Look样张]   ← 引用了镜2的关键帧
镜2: [分镜2关键帧, 分镜1关键帧, Look样张]
镜3: [分镜3关键帧, 分镜1关键帧, Look样张]
```

而 `CV-031 关键帧继承`（`generate.ts:1505` `inheritShotCardIds`）会把每张参考图**各自挂着的分镜卡**全部继承进视频节点。于是：

```
镜1 视频 f66b0d53.sourceIds ⊇ {分镜卡1, 分镜卡2}
镜2 视频 ca235781.sourceIds ⊇ {分镜卡2, 分镜卡1}   → 与镜1 交集非空
镜3 视频 279d2deb.sourceIds ⊇ {分镜卡3, 分镜卡1}   → 与镜1 交集非空
```

**任何两条视频都至少共享「分镜卡1」** ⇒ 每提交一条新视频就把上一条标失效 ⇒ 6 条视频串成一条 v1→v6 的**全局单链**。

单元测试 `tests/shot-versions.test.mjs:130`「不同镜位互不误伤」用的是**每镜各自只挂一张卡**的干净形态，永远测不到多卡交叉。这条守卫给了虚假的安全感。

### 1.3 连带损失（三层）

**① 白烧 3 条视频。** agent 在 step 23 发现 `list_shots` 只剩 1 段，误判为「并行提交引发镜位竞争」，改串行重出。结果每条新视频又干掉上一条，链变成 v4→v5→v6，最终 3 条全部作废：

```
22:25  镜1 v1  194.7s  → 作废
22:28  镜2 v2  171.3s  → 作废
22:31  镜3 v3  167.9s  → 作废
22:36  镜1 v4  166.3s  → 作废（被 v5 顶掉）
22:40  镜2 v5  166.4s  → 作废（被 v6 顶掉）
22:44  镜3 v6  167.5s  → 有效
```

浪费 **8.5 分钟 GPU + 4.25 MB 磁盘**（3 条各 1.3~1.5 MB）。整个项目视频墙钟 21.8 分钟，接近 40% 是无效产出。

**② 默认合成路径彻底失效（未被察觉）。** `defaultComposeClips`（`host-tools.ts:499`）只收 `isShotClip` = 有效 + 非成片。实测当前画布状态：

```
默认合成会选的片段：fb3f3e03 一条，总时长 5.17s
```

也就是说：**用户在 UI 点「导出成片」，拿到的是 5.17 秒单镜残片，不是 15.51s 成片。** agent 是靠显式传 `clipIds` 三段 id 绕过的，UI 路径没有这个绕过口——它会自动得出错误结果。

**③ 废弃视频进了 GC 保护名单，永不自动清理。** 5 条作废片段全部登记在 `assets/history.json`（12 条记录）。按 CV-246 的设计，「未删除的历史条目 = GC 保护名单」，所以这 4.25 MB 永久留存，只能用户手动在历史面板删。

### 1.4 修复方向（三选一，推荐 A）

**A（推荐）· 判据从「交集」改为「锚点集包含」**
`shot-versions.ts:203` 改为：新节点的锚点集必须是旧节点锚点集的**超集或相等**（即旧节点不能有新节点没有的卡）。这样「引用了别镜关键帧」不再触发互取代，而「同镜位换参考组合重跑」（CV-222 的原始用例：卡相同、图不同）仍然命中。改动 1 行 + 补 1 条守卫测试。

**B · 锚点只认显式 `shotRefs`，血缘继承的卡不参与镜位判定**
语义更干净（镜位是显式声明的，不是推断的），但要改 `generate.ts:2572` 的派生逻辑，且 CV-031 继承的价值（漏传 shotRefs 不断链）会受影响。

**C · `list_shots` / 工具结果回执暴露「本次取代了哪些镜位」**
不修根因，但让 agent 能在第 1 次就发现「我取代了别人的镜」，不必烧 3 条视频去试。属于缓解措施。

无论选哪个，**测试都要补一条「多参考图跨镜」用例**——现有 16 条用例全部是单卡形态。
