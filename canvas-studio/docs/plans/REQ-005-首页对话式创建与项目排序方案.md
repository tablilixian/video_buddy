# REQ-005+ — 首页对话式创建（合并新建项目弹窗）与项目排序方案

> **需求来源**：产品讨论（2026-09-28）。把「新建项目弹窗」与「首页对话窗口」合并为**一个首页**：
> 用户在首页描述创意并回车，项目自动创建、首条消息自动发出，直接进入对话流。
> 覆盖 `docs/requirement-tracker.md` REQ-005 的未完成部分（项目按改动时间排序）。
> **文档性质**：交互 + 流程 + 技术方案，评审通过后进入开发。
> **已拍板决策**（产品确认，2026-09-28）：
> - D1 首条创意消息**自动发送**（创建项目 → 切入 → 消息自动进会话）；
> - D2 项目名称**自动生成**（创意摘要，不留手填输入框）；
> - D3 规格（画幅/时长/执行模式/分组）以**常驻一行 chips** 形式摆在输入框下方；
> - D4 旧弹窗**彻底删除**，新建入口唯一（首页）。
> **版本**：v1.1（2026-09-28，v1 评审后按全量代码核验修订）。
> **v1.1 修订点**：§2 回首页现状纠偏 + 补 `waitSessionBound` 积木；§4.1 会话就绪时序纠正（startSession 非 await）；§5.1 CSS 隐藏范围扩大到 `.csChat`；§5.4 send 失败二分法；§5.5 补 `mutationAllowed` 守卫与 touch 成本；§6 新增 E11 跨窗口撞名；§7 路径/契约勘误；§9 测试命令纠正（根 `yarn test` 不含 canvas-studio）。

## 1. 背景与目标

### 1.1 需求原文（产品讨论纪要）

> 能不能把新建窗口（图1）和第一个对话窗口（图2）结合起来，只保留图2。新的新建项目页面就是图2融合增加一些图1的信息。这样节省一个窗口，还能给 app 一个首页。

- **图1** = 新建项目弹窗（`ProjectList.tsx:529-702`，CV-092/099/196 迭代产物）：名称（必填）、所属分组、画幅、目标时长、执行模式。
- **图2** = lobby 首页（`StudioFrame.tsx:1311-1325` lobby 分支 + `LobbyHero.tsx`）：中栏居中的**宿主 conversation 槽**（大输入框，CSS 搬到中栏）+ 品牌条 + 推荐技能横滚。

### 1.2 现状痛点

| # | 痛点 | 证据 |
|---|---|---|
| P1 | **两条路径割裂**：开工必须先弹窗填表（名称必填），再切到对话里描述创意——同一个意图拆成两个窗口两步操作 | 弹窗入口三处：欢迎屏 `LobbyHero.tsx:48`、左栏 `ProjectList.tsx:377`、分组头 `:769` |
| P2 | **首页聊天发不出有用消息**：lobby 态无项目/工作区绑定，对话槽只是摆设；`LOBBY_COPY.hint` 却引导用户「在下面描述你的创意」 | `brand-copy.ts:49`；lobby 无 `createProject` 联动 |
| P3 | **名称必填在最先**：用户此刻往往没想好名字，表单是「开工前的一道墙」 | `ProjectList.tsx:256-257`（name 为空禁止提交） |
| P4 | **项目列表无时间排序**：`resolveVisibleSections` 分桶后保持 registry 创建顺序 | `project-sections.ts:39-70`；REQ-005 未完成项 |

### 1.3 目标

- **T1**：首页 = 唯一新建入口。输入创意回车 → 项目自动创建（摘要命名）→ 切入项目 → 首条消息自动发出 → 进入对话流。
- **T2**：图1 的规格信息不丢失——画幅/时长/执行模式/分组以常驻 chips 形式摆在首页输入框下方，默认「不锁定/跟随设置」。
- **T3**：旧弹窗删除，左栏「+ 新建项目」/分组头「+」改为跳首页并预选分组。
- **T4**（REQ-005 收口）：项目列表按 `updatedAt` 倒序；点品牌区回首页稳定可用。

## 4. 核心流程

### 4.1 创建时序（T1 主链路）

```
用户在 LobbyComposer 输入创意，回车
│
├─ ① 前端摘要命名（§5.2）：summarizeName(idea) → dedupeName(name, projects)
├─ ② createProject(name, groupId, plan, mode)         # index.ts:1236 现有
│     └ createStudioProject → refreshProjects → openProject
│         └ select → 绑定/建 workspace → 会话 clear → resume|startSession
│           → reloadCanvas → syncHasConversation
│           # ⚠️ 前后段均 await，唯独 startSession 是 fire-and-forget（见下）
├─ ③ 自动发送（先就绪等待 §5.4，复用 waitSessionBound）：
│     waitSessionBound(dir, 3000) → sessionId
│     sessionSvc.scope(sessionId).get('conversation').send(idea)
├─ ④ 首条 prompt ACCEPTED → blank 翻转 → hasConversation=true
│     → 布局自动 lobby-pending → work（CV-064 二期机制，零改动）
└─ ⑤ Composer 清空草稿、规格复位
```

- **就绪保障（关键，v1.1 纠正）**：`openProject` 内 workspace 绑定/rename、画布重载都已 await，但**会话切换没有**——`resumeLatestSession` 同步返回 boolean，`startSession(workspaceId)` 契约返回 void，内部 `connectWorkspace().then(...)` 异步执行、失败仅 `console.warn`（代码自身注释：「openProject 的 startSession 是 fire-and-forget」）。而新建项目在 1207 行刚 `sessionSvc.clear()`，必然走 `startSession` 分支——**`openProject` resolve 时 `sessions.current` 极可能仍为 `undefined`**。
  因此 §5.4 的就绪等待不是「保险」而是**主链路必需步骤**：发送前必须等待会话绑定（复用 `waitSessionBound`，`index.ts:1351-1360`，超时 3s），超时走降级（§5.4 / E5）。
- **blank 翻转自动切 work** 是既有机制（`index.ts:1035-1039` 订阅、判据在 `syncHasConversation` `:614-624`），本方案零改动。

### 4.2 交互细节

- **输入为空**：发送按钮禁用、Enter 无效（与弹窗 `createName.trim()` 同规则）。
- **创建中**：`creating` 态下 Composer 输入与 chips 禁用，按钮显示「开工中…」。
- **发送失败降级**（失败分类见 §5.4）：项目已建但会话超时未就绪 / `send` reject → toast「项目已创建，创意未能自动发送」+ 文本注入对话输入框（`insertReferenceToken` 能力，`StudioFrame.tsx:867-896`）+ 布局停在 lobby-pending，用户回车即发。
- **ESC / 点外部**：Composer 是常驻页面不是弹窗，无关闭语义；草稿保留在本地 state（lobby 态切走再回来不丢——组件保持挂载即可，不需要 localStorage）。

## 5. 技术设计

### 5.1 LobbyComposer 与对话槽共存

- `StudioFrame` lobby 分支（`:1311-1325`）改为渲染 `<LobbyComposer …>`；`<LobbyHero>` 收缩为顶部品牌区（删双 CTA 里的新建按钮）。
- styles.ts 改动（**v1.1 扩大范围**）：不能只加一条 `.csConversation { display: none }`——lobby 态现有规则（`styles.ts:89-157`）会把整个 `.csChat`（含 `.csConversation` + `ChatStrip`）搬到中栏居中展示（`:115-141`）。需在 `data-mode="lobby"` 下**隐藏整个 `.csChat`**（否则留下 ChatStrip 残条与空壳聊天卡），并新增 `.csLobbyComposer` 布局段（居中、最大宽度约 720px，对齐宿主输入卡视觉）。lobby-pending / work 的 `.csChat` 规则不动。
- `renderSlot('conversation')` 的 JSX 位置**不动**（`:1806-1808`），仅靠 data-mode 切换可见性。

### 5.2 自动命名（D2）

新纯函数（放 `src/` 根，可单测，Host/Client 两侧无关）：

```ts
// src/project-naming.ts（新）
summarizeName(idea: string): string
// 1. 折叠空白（换行/制表 → 单空格）、去掉控制字符与 / \（validateProjectName 的黑名单，projects.ts:94）
// 2. trim 后取前 20 个码元（≤80 上限留重名后缀余量）
// 3. 结果为空 → 兜底「未命名项目」

dedupeProjectName(name: string, taken: readonly string[]): string
// 大小写不敏感比对（对齐 projects.ts:440 的 toLowerCase 口径）；

```

- **去重的责任在客户端**：store 里已有全量 `projects`，`createProjectFromIdea` 调 `createProject` 前先 dedupe。Host 的重名校验（`:440-442`）保持不变，作为最后防线。
- **不采用的替代**：Host `create` 加「自动命名模式」跳过校验——改动 Host 契约、且重名语义变成隐式，收益不成比例。

### 5.3 回首页的稳定性（goHome 抑制）

现状有**两层缺口**（v1.1 纠正 v1「机制已存在」的说法）：

1. **入口不存在**：品牌区 LogoMark 目前不是按钮，全仓无任何用户可达的「回首页」动作（`index.ts:1441` 的 `select(null)` 只在 `deleteProject` 内部）。入口要新建。
2. **裸用 `select(null)` 会被踢回**：`workspaces.list` / `sessions.list` 任何变化都会触发 `syncActiveProject`（函数体 `index.ts:598-607`，订阅点 `:1027/:1035`）→ `resolveActiveProjectId()`（`:263`）从最近 workspace 解析出项目 → **重新 select，把用户踢回 work 态**。

方案：新增品牌区点击 → `goHome()`；store 增加瞬时标志 `homePinned: boolean`（不持久化）：

```
goHome(): actions.setHomePinned(true) + actions.select(null)
syncActiveProject 开头：if (snapshot.homePinned) return
openProject / createProject 成功路径：actions.setHomePinned(false)
```

- 入口：品牌区点击（work / lobby-pending 态均可点，lobby 态点击为 no-op）、左栏「+ 新建项目」、分组头「+」都走 `goHome()`；**品牌区点击本身也是本次新建的接线**（当前 LogoMark 非按钮）。
- 回首页时**不清当前会话**（用户可能马上点回项目继续聊）。
- 短路范围只在 `syncActiveProject` 即可：`syncHasConversation`（`:614-624`）虽也用 `resolveActiveProjectId()`，但只写 `hasConversation[id]`、不触发 select，homePinned 下无害；`alignStartupSession`（`:632-647`）只动 session 选择（`sessionSvc.open`），不 select 项目，也不会绕过短路。
- 解除时机兜底：除 `openProject`/`createProject` 成功路径外，`actions.select(非null)`（用户点项目行、`deleteProject` 选下一个）也应视为离开首页、清掉 homePinned——建议直接在 `select` action 内实现「projectId !== null 即解除」，避免散落各处漏清。

### 5.4 自动发送的就绪等待与失败二分

```ts
async function sendFirstMessage(idea: string): Promise<boolean> {
  // ① 就绪等待（必需，见 §4.1）：复用 waitSessionBound（index.ts:1351-1360）
  //    等价实现——轮询 sessions.list 直到 current 就位且 scope 可取，超时 3s
  // ② 失败二分，处理方式完全不同：
  //    a. scope/get 取不到（sessionSvc.scope(id) undefined / get('conversation') undefined）
  //       = 会话未就绪 → 继续重试，直到 3s 超时 → 返回 false 走降级
  //    b. conversation.send(text) 的 promise reject = prompt 业务失败
  //       （上游 ConversationController.send 业务失败必 reject 并落 promptError）
  //       → 立即返回 false 走降级，不重试
}
```

- **不要照抄 `wakeAgent` 的 `.catch(() => {})`**（`index.ts:783`）：它把 a、b 两类失败一律吞掉，降级路径永远不会触发。正确做法：a 类在等待循环里消化，b 类显式捕获。
- **复用 `waitSessionBound` 的两个注意**（v1.1 补）：① 它超时抛 `CS-EFFECT-001`（效果测试专用错误码）、轮询粒度 1.5s——`sendFirstMessage` 必须 catch 并转降级，或改为等价的本地轮询（不共用错误码），避免效果测试错误码泄漏进创建链路；② 它只验 `cwd` 匹配，返回后仍要按 ②a 再确认 `scope(id).get('conversation')` 可取。
- 成功：静默（首条 prompt ACCEPTED 后 blank 翻转走既有机制切 work）。
- 降级（返回 false）：toast + 文本注入输入框（§4.2），**项目不回滚**（建好的项目是资产，不是垃圾）。
- 降级后布局停在 lobby-pending：此时宿主对话槽可见（§3.2），注入的文本可直接回车发送。

### 5.5 REQ-005 排序收口（T4）

- **比较器**：`resolveVisibleSections` 内分桶后，每桶按 `updatedAt` 倒序，不可解析的记录排最后。模块注释「排序口径只有一处」由此延续。**（v1.2 实现偏差）** 比较用 `Date.parse` 数值比较而不是 v1.1 写的 `localeCompare`：ISO 8601 里 `Z` 与 `+08:00` 能表示同一时刻，字典序会把它们排成两个顺序；也只有解析过才分得出「不可解析垫底」与「两者皆坏走稳定序」两个分支。
- **写回点补齐**：
  - 打开项目写回 `updatedAt`（语义：「最近在用」正是列表要回答的问题）。Host 新增 `touchProject(projectId)`（registry 单字段 patch，复用 `updateWorkflow` 的落盘模式 `projects.ts:622-635`），`openProject` 成功路径调用。
