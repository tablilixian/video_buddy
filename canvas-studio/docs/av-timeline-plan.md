## 0. 一句话结论

**目前没有统一时间轴。** 只有 5 个分散机制，其中 4 个互不闭环、1 个（成片真实时长）拿到时已经晚了。

这条路线的死结：**BGM 时长必须等于成片时长，而成片真实时长在合成前不可知** ——
现在只能拿「分镜表声明的时长之和」去估，模型一旦不守时或某镜重做，音乐与画面对齐全错位。

### 1.1 关键发现：视频生成后从不探测真实时长

`parseFfmpegDuration` 在全仓只被 4 处调用：`compose.ts:330`（BGM 探测）、`compose.ts:351`（成片探测）、
`video-frames.ts:102`、`video-style.ts:147`（抽帧/风格归纳）。

→ **生成主路径（`generate.ts`）完全没有时长探测**。节点上写的、画布上显示的、`list_shots` 回报的
`duration`，全都是**请求值**。若模型产出与请求不符，我们**不知道**，而且会一直显示错的数字。

## 3. 死结与两条解法

```
现在：目标总时长(软) → 分镜表文字(软) → 逐镜 duration(请求值,未验证) → 合成 → 真实时长(才出现)
                                                                        ↑
                                             BGM 在合成之前就要定长 ─────┘  ← 死结
```

### 路线 A：声明值驱动（先规划后生成）

结构化时间轴（每镜 declared duration）→ 逐镜按轴生成 → BGM `duration` = 各镜声明之和。

- ✅ 一次成型，无额外合成；时间轴成为单一事实源（时间线 UI / 分镜表 / BGM 全读它）
- ❌ **成败全押在「模型是否遵守 duration」上**（= 未验证的断点 2）

### 路线 B：真实值驱动（先合成后配乐）

先合成**无声**成片 → 探测真实时长（能力已具备）→ 生成**等长** BGM → 二次合成混音。

- ✅ **数据硬对齐**，完全不依赖模型守时；BGM 时长必然正确
- ✅ 零件全都有，只缺流程编排 + 一个时长守卫
- ❌ 多一次合成（ffmpeg 本地 concat，秒级，且会多产出一个成片节点，需处理）

### 推荐：B 为主、A 为辅

A 负责「尽量一次到位」（时间轴指导生成，减少返工）；**B 负责「最后一定对齐」**（真实值兜底）。
即便 A 完全失效，B 仍能保证音画对齐 —— 这是当前路线能给出的最强保证。

## 4. 第一步必须先验证的前提 —— **已完成初测（2026-09-10）**

### 4.1 实测方法

新增探针脚本 `scripts/h3-duration-probe.mjs`：按**生产同款口径**直连后端
（`POST /api/v1/generate/image2videofl2va`，body `{ prompt, aspect:'16:9', megapixels:0.4, duration }`，
与 `src/providers/drama.ts` 的 `submit` 逐字段一致），固定 prompt、只变 `duration`；
产物下载后本地 `ffprobe` 量真实时长、帧数与帧率（`ffprobe` 而非 `parseFfmpegDuration`，
后者只解析 ffmpeg 日志文本，拿不到帧数）。

用法：`node scripts/h3-duration-probe.mjs --durations 5,8,10`；
带首帧图（生产逐镜路径）加 `--with-image`。

> ⚠️ **本机 Bash 沙箱会拦截到 `117.50.108.73:8082` 的连接**（表现为 HTTP 超时 / 零字节返回，
> 极易误判成「后端挂了」）。实测：沙箱内 20s 超时，沙箱外 59ms 返回 200（`server: uvicorn`）。
> 探针必须在沙箱外运行。

> **10s / 12s 未取到数据 = 采样时点问题，不是 H3 不守时** —— 用户确认（2026-09-10 下午）

> **生成耗时（仅供参考，采样期含后台测试占用）**：5s→139/144s、8s→246/214s、10s→>301s、12s→>301s。
> 换算斜率约 **30s 推理 / 1s 视频**（≈30× 实时），即 **10s 视频约需 5 分钟** —— 但该组数据是在
> **后台同时被测试占用**的窗口内采到的，**不代表后端空闲时的真实速度**，需空闲时复测。
> 生产侧 `DRAMA_TIMEOUT_MS.video = 600_000`（`generate.ts:203`）——对 10s 视频余量约 2×。

### 4.3 结论

1. **H3 遵守 `duration`，最大绝对偏差 0.167s < 0.2s 阈值 → 路线 A（声明值驱动）可信。**
2. **偏差是确定性的、且与模式无关**：同一 duration 在「纯文生」与「带首帧图」下产出
   **完全相同的帧数**（5s→124 帧、8s→192 帧），两次独立运行结果一致
   → 不是随机抖动，而是**帧数量化**（可预测、可补偿）。
3. **偏差只多不少（正偏）**：5s 的 0.167s 恰是 24fps 下 4 帧。意味着按声明值生成 BGM 会**略短**于画面
   （单镜 5s 时 3.34%；60s 成片被摊薄到可忽略）。
4. **帧数落点疑似有 4 帧网格**：124 = 4×31、192 = 4×48，都是 4 的倍数 —— 符合视频 VAE
   常见的时间压缩比 4×。但 n=2 不足以定式（8s 恰好精确、5s 多 4 帧），需补测 6 / 10 / 12s 才能拟合。
5. **可操作推论**：时间轴对齐应**以帧为准（24fps）而非以秒为准** —— `declaredDuration` 落盘时
   同时记 `declaredFrames`，把对齐误差压到 0。这条直接改写 P2 的数据结构设计。
6. **用户已确认（2026-09-10）：时长就是按时长与帧率算出来的，可以信赖。**
   → 这不是「统计上偏差小」，而是**确定性的可计算量**：产出帧数由请求时长按帧率推导，
     不存在随机漂移。因此：
   - **路线 A（声明值驱动）已确认可用**，结构化时间轴值得做，且**不需要为「模型不守时」留后路**；
   - `declaredFrames` 应作为**一等字段**与 `declaredDuration` 一起落盘（不是补偿手段，而是权威值）；
   - BGM 时长依赖「声明值之和」是**安全**的 —— 唯一残余误差是已知且可算的那 ≤4 帧量化。

### 4.4 `duration=10` / `12s` 失败结案：**后台在测试（主因）+ 客户端有 300s 隐形上限**

> 本节三次改写：① 「`duration=10` 疑似打挂后端」→ ② 「探针自身 300s 超时」→
> ③ **最终真相**（用户澄清 + 本地实证）。三次修正的过程有方法论价值，保留。

**结论**：两个因素叠加，**没有一个是后端能力问题**：

| 因素 | 说明 | 证据 |
|---|---|---|
| **① 采样时点**（主因） | 那段时间**后台正在测试**，请求未被及时响应 → 响应头迟迟不到 | 用户确认（2026-09-10 下午） |
| **② 客户端 300s 隐形上限** | 响应头晚于 **300s** 到达时，**Node 内置 fetch（undici）先掐断**，与我们设的超时**无关** | 错误码 + 耗时 + 本地复现（见下） |

**② 的机制（关键，且直接波及生产）**：Node 的全局 `fetch` 由 undici 提供，其 dispatcher 的
`headersTimeout` / `bodyTimeout` **默认 300s**（官方文档：`Defaults to 300 seconds`），
而它**先于 `AbortSignal` 触发**：

- 探针里 `AbortSignal.timeout(TIMEOUT_MS)` 的 `TIMEOUT_MS = 900_000`（15 分钟）
  —— **根本没机会触发**。实测三次失败 `wallMs` 精确 = **301.0 / 301.1 / 301.2s**，
  错误码 **`UND_ERR_HEADERS_TIMEOUT`**（这是 undici 的 headersTimeout，**不是** AbortError）。
- **本地复现**（起一个「只接不回响应头」的服务器）：`AbortSignal.timeout(2000)` 抛的是
  「The operation was aborted due to timeout」且**无任何 `UND_ERR_*` 错误码**
  → 证实那 300s 一刀来自 undici，**与我们的信号无关**。
- **复现脚本（已固化进仓库）**：`scripts/undici-timeout-repro.mjs` —— 起「只接不回响应头」的
  本地服务器，分别用 900s（看 undici 何时掐）与 2s（看 AbortSignal 自己的错误形态）跑一遍。
  约 5 分钟，**不要放进 CI**，需要时手动执行。
- **实证结果（2026-09-10 实测，已跑完）**：传 `AbortSignal.timeout(900_000)` 仍于
  **301.166s** 被掐断，`cause.name = HeadersTimeoutError`、`cause.code = UND_ERR_HEADERS_TIMEOUT`
  → **900s 形同虚设，实际上限 = undici 的 300s**，与探针实测的 301.0/301.1/301.2s 完全吻合。

**撤回**：我曾据此推断「后端单通道串行 + 客户端超时不取消任务 → 假死 20 分钟」——
**正式撤回**。`/health` 长时间不响应归因于**后台测试占用**。
**教训**：本地观测只能证明「我方行为」；在推断「对方内部机制」前，先排除
「环境被占用」这个最朴素的解释。

**当时观测到的耗时（含后台测试占用，不是空闲基线）**：

```
5s  → 139 / 144s    换算斜率约 30s 推理 / 1s 视频
8s  → 246 / 214s    （在后台测试占用窗口内测得，不代表空闲时的真实速度）
10s → >301s         被 undici 的 300s 上限掐断（不是我们放弃等待）
12s → >301s         同上
```

**⚠️ 由此发现的真实生产问题（已立为 P0，见 §5）**：

`DRAMA_TIMEOUT_MS = { image: 360_000, video: 600_000, text: 180_000 }`（`generate.ts:203`）里，
**image(360s) 与 video(600s) 都超过了 undici 的 300s 上限** →

- **实际有效上限 = `min(配置值, 300s)` = 300s，配置里的 600s 是不可达的**（配置失效）；
- `dramaPost` 失败后还会**自动重试一次**（`generate.ts:359-377`）→ 一个请求最坏要
  **300s + 300s = 10 分钟**才最终失败，且报错文案是「Drama Backend 连接失败（已重试一次）」
  —— 会把排查方向误导到「后端不可达」；
- **注意 `video_composite` 的默认时长正是 10s**（`host-tools.ts:947`），
  而 10s 推理在负载期已 >301s → **这是当前最可能的「随机失败」来源**。

**结案四条**：

1. **10s / 12s 是「没测到」，不是「H3 不守时」** —— §4.3 的结论（含用户确认的时长可信）
   **完全不受影响**。
2. **补测姿势已修正**：脚本生成请求**改走 `node:http`**（`postJson`），因为**调大
   `AbortSignal` 对 300s 上限无效**；并**选后端空闲时段**跑。
3. **「后端单通道串行」推断撤回**，降级为待观察（原 P0″ 撤回，见 §5）；日后若需确认，
   在后端空闲时用**并发请求**直接实测。
4. **新增 P0：修掉 undici 300s 隐形上限对生产的影响**（超时配置失效 + 重试放大失败时长，见 §5）。

**✅ 已修复（CV-135，2026-09-10 晚）—— 取「按请求 dispatcher」方案，上限 900s**

三选一的取舍（用户拍板：「尽量干净、上限 900s」）：

| 候选 | 结论 |
|---|---|
| ① 引入 `undici` 依赖自建 Agent | ❌ 会被打进 Electron 插件产物，代价最大 |
| ② 全仓改走 `node:http` | ❌ **fetch 同时是测试缝**（10 个测试文件打桩 `globalThis.fetch`），替换即集体失效 |
| ③ **按请求注入 dispatcher**（选定） | ✅ 零依赖、不动全局、**仍走 `globalThis.fetch`** → 现有打桩测试零改动 |

落地：新增 `src/long-request.ts`（`LONG_REQUEST_TIMEOUT_MS = 900_000`）——Node 不暴露
undici 模块（`import('undici')` → `ERR_MODULE_NOT_FOUND`），但 fetch 使用的全局 dispatcher
挂在 well-known symbol 上，借它的 Agent 构造器造一个 `headersTimeout/bodyTimeout = 900s`
的**请求级**实例，只在 `dramaPost` 那一次请求上注入；取不到就防御式退回默认（300s）并
告警一次，**绝不阻断生成**。**顺带修掉「重试放大」**：本地超时不再触发「失败重试一次」
（video 档最坏 20 分钟 → 收敛到单档上限），改报「N 秒内未返回结果（已放弃重试）」；
502/503/504 的一次性重试保持不变。

实证（已固化为测试 `tests/long-request.test.mjs`，不碰真实后端）：本机 loopback 起一个
「2s 后才发响应头」的服务器 —— 传收紧到 500ms 的 dispatcher 时请求在 ~0.5s 被掐断
（`UND_ERR_HEADERS_TIMEOUT`），同一端点**不传** dispatcher 的对照请求正常成功
→ 证明该参数确实决定上限，且未污染进程内其它请求。

## 6. 与「音乐先行」的关系

- 音乐先行（CV-126）**已降级**：它需要后端提供长音频能力与统一音轨方案（当前 `txt2audio`
  只暴露 7 参数），后台暂无时间支持。方案文档保留（`music-first-workflow-plan.md`），待后端就绪再启。

- 两条路线不冲突：音乐先行是「音轨定调、视频对齐音乐」；本路线是「视频定形、音轨对齐视频」。
  后者是前者的真子集前置条件 —— **先有可靠的时间轴，才谈得上音乐先行**。
