## 1. 问题：为什么必须新建「模板」这个容器

「只改内容和参数就能还原效果」要求模板**同时携带六样东西**。逐样对照本仓现状：

| 模板必须携带 | 本仓现状 | 差距 |
|---|---|---|
| ① 版式参数（字号/对齐/圆角/配色/坐标） | 散落在**组件源码**里（84px 写死、居中写死、直角写死、62% 黑底写死） | 参数化不了 |
| ② 编排时序（段长/错峰/缓动/相机） | `recipes.ts` 只固化「段序列 + 卡片编号 + 素材需求」；`shot-cards.md` 是可粘 JSON 片段 | 没有一个东西同时带时序**和**版式 |
| ③ 出入场与转场 | **能力全有**（`exit` / `reveal.out` / `transition` 11 式） | 能力在，没被任何模板固化 |
| ④ 槽位合同（能填什么/多长/必填） | **零** | 无 → 静默裁切 |
| ⑤ 声音事件表 | **零** | 无 → 静音 |
| ⑥ 装饰构件层 | **零**（`themes.ts` 只给颜色 token） | 无 → GT 是「一帧设计」，我们是「元素流」 |

⇒ **不是缺某个能力，是缺「模板」这个容器。** 现在的 `recipes.ts` + `shot-cards.md` + `themes.ts` + `manifest-spec.json` 是四块碎片，谁都没把它们装进一个可复用、可参数化、可校验的对象里。

### 1.1 MotionGit 的解法（结构可直接抄）

```
.mmotion/
  motion.json            # 身份 + 运行 profile + 输出声明
  params.schema.json     # ① 可替换内容合同（每字段 maxLength）
  content.schema.json    # ④ 槽位合同（469 槽，每槽 maxChars/format/required/source 行号）
  core/catalog.json      # 内容单元表（分组 / 时间窗 / 字段集 / 素材位）
  core/audio-events.json # ⑤ 音效事件表（t / type / gain / pan）
  core/lib.js            # ② 动效原语（EZ 缓动集 / place() / cam()）
  core/style.css         # ① 视觉风格 + ⑥ 装饰构件
  core/scenes/*.js       # ② 场景实现
  guide.json             # 给 AI 的使用指南
  examples/*.json        # 示例填充值
```

**六样东西全部有独立文件、都是声明式、都有机器可校验的合同。**


### 3.2 `slots.json`

```jsonc
{
  "slots": [
    {
      "id": "b1-keyword",
      "label": "主标题",
      "type": "string",          // string | string[] | number | asset
      "required": true,
      "maxChars": 8,
      "maxLines": 1,
      "maxCharsPerLine": 8,
      "semantic": "主标题，四到八个汉字，能独立成立",
      "styleRole": "title",      // ← 模板声明这个槽用哪个版式角色（见 §6）
      "example": "从想法开始",
      "onOverflow": "reject"     // reject | truncate（reject = 编译期拒绝并给建议）
    },
    {
      "id": "b1-body",
      "label": "正文",
      "type": "string",
      "required": true,
      "maxChars": 40,
      "maxLines": 2,
      "maxCharsPerLine": 20,
      "semantic": "两行以内，每行不超过二十字",
      "styleRole": "body",
      "example": "把你的想法\n变成清晰的视觉故事"
    }
  ]
}
```

> ⚠️ **数组 vs 字符串必须分开判**（实测踩过的坑）：
> - **`type: "string[]"` = 作者显式分行** ⇒ 校验**数组长度 ≤ maxLines** + **每行 ≤ maxCharsPerLine**。
> - **`type: "string"` = 整块** ⇒ 校验**总字数 ≤ maxChars** + **内含 `\n` 的行数 ≤ maxLines**。
>
> 真实项目里**有意两行标题**是存在的（`hook-title` = `["四季","是因为离太阳远近吗？"]`、`s6-title` = `["不是距离","而是倾斜"]`）⇒ 数组形式**不因为「看起来长」就拒收**，只按 `maxLines` 判。

## 4. 编译器（纯函数，可单测）

**新建 `src/remotion/template-compile.ts`**

```ts
export interface TemplateBundle {
  template: TemplateMeta
  spec: ManifestSpec            // = manifest-spec.json 的形状
  slots: SlotContract[]
  furniture: FurnitureSpec[]
  audio: ManifestSfx[]
  limits?: LimitsContract
}

export interface CompileInput {
  bundle: TemplateBundle
  /** 本期内容：slot id → 值。 */
  values: Record<string, unknown>
  /** 画布尺寸（默认取 spec 的 aspect/fps）。 */
  canvasWidth: number
  canvasHeight: number
}

export interface CompileResult {
  ok: boolean
  manifest: CompositionManifest | null
  /** 槽位校验问题（每条都带可执行建议）。 */
  issues: SlotIssue[]
  /** 成功时附带的音效轨。 */
  audio?: ManifestSfx[]
}

/** 纯函数：模板 + 内容 → manifest。不碰 IO。 */
export function compileTemplate(input: CompileInput): CompileResult
```

**编译链**：

```
template.spec ─┐
template.slots ─┼─→ [ compileTemplate ]─→ manifest ─→ [ validateManifest ]─→ render ─→ 成片
values ─────────┘                        ↑
template.furniture ─→ expandFurniture ────┘   （任务包 1C）
template.audio ────────────────────────┘         （任务包 0A）
limits ──→ 槽位容量校验（编译期拦截）
```

### 4.1 槽位校验（编译期，**必须在渲染前拦下**）

| 检查 | 规则 | 级别 | 建议文案 |
|---|---|---|---|
| 必填缺失 | `required: true` 且值缺失 | error | 「槽位 `b1-keyword`（主标题）必填」 |
| 类型不符 | `type` 与值类型不符 | error | 「槽位 `b1-body` 应为 string」 |
| 字数超限 | 整块总字数 > `maxChars` | error | 「正文超了 N 字，请改到 M 字以内」 |
| 行数超限 | `\n` 行数 > `maxLines` | error | 「正文有 K 行，最多 maxLines 行」 |
| 数组长度超限 | 数组长度 > `maxLines` | error | 同上 |
| 单行超限 | 每行 > `maxCharsPerLine` | error | 「第 K 行有 N 字，最多 M 字」 |
| 多余槽位 | 传了模板里没有的 id | warning | 「模板没有槽位 `xxx`，已忽略」 |
| 素材缺失 | `type: "asset"` 的值不存在 | error | 「槽位 `xxx` 需要的素材不存在」 |

**错误文案必须能直接指导下一步改什么**（这是「准确」的一部分）。

> 这套校验已在配套原型里验证过：合成套件 **8/8**、真实四季 spec **7/7**、全库 4 个真实 `manifest-spec.json` 回归 **4/4**。实现参考 `原型-spec-limits-validate.mjs`。

## 5. `limits` 的落点：**spec 层，不是 manifest 层**

**重要决策**：容量合同的权威声明层是 **`manifest-spec.json` 的 `limits` 层**。

**理由**：真实生产里 `manifest.json` 是**由脚本生成**的（`generatedBy: "gen-v5.mjs"`），manifest 是产物、spec 才是声明。**把合同挂在 manifest 上 ⇒ 生成脚本也得改，等于合同没有单一事实源。**

```jsonc
// spec.json（= manifest-spec.json 形状）的 limits 层
{
  "title": "动能科技 · 要点三卡",
  "fps": 60,
  "aspect": "16:9",
  "filmFrames": 1080,
  "limits": {
    "defaults": { "maxChars": 60, "maxLines": 3 },
    "byVariant": {
      "title":   { "maxChars": 12, "maxLines": 1, "maxCharsPerLine": 12 },
      "subtitle":{ "maxChars": 40, "maxLines": 2, "maxCharsPerLine": 20 },
      "bullets": { "maxChars": 80, "maxLines": 6, "maxCharsPerLine": 20 }
    },
    "captions": { "maxCharsPerLine": 18, "maxLines": 2 }
  },
  "captions": [],
  "visuals": [],
  "audio": {}
}
```

**容量按 variant 声明，不按字段逐个声明** —— 因为我们的内容角色由 `textCard.variant` 决定。

## 6. 工具

### 6.1 `list_templates`（新工具）

**这是 LLM 能「快速准确选对模板」的前提。**

返回（数组，每项）：
```
id / name / summary / suitableFor / notSuitableFor /
durationInFrames / fps / aspect /
furniture[]（用了哪些构件） /
slotSummary[]（id / label / required / maxChars / maxLines / semantic） /
previewFrame（样片首帧 URL） / referenceFrameCount /
requiredAssets[]
```

**不返回**完整 spec / slots（太大，会吃掉上下文）⇒ 用 `describe_template` 取。

### 6.2 `describe_template`（新工具）

入参 `templateId` ⇒ 返回该模板的完整 `template.json` + `spec.json` 的**精简版** + `slots.json` + `furniture.json` + `audio.json` + 参考帧清单。

> 精简版的 spec 要**去掉逐轨的冗余**（只给结构与参数），因为 LLM 不该手写 spec —— 它只该填 slots。

### 6.3 `render_composition` 加 `templateId` + `slots` 通道

**现有入参全部保留**（`manifest` / `manifestPath` / `projectId` / `quality` / `probe` / `spotFrames` / `timingSegments`），**新增两条**：

```jsonc
{
  "templateId": "motiongit/kinetic-b1b2",
  "slots": { "b1-keyword": "从想法开始", "b1-body": "把你的想法\n变成清晰的视觉故事" }
}
```

**互斥规则**：`templateId` 与 `manifest` / `manifestPath` **互斥**（同时给 ⇒ 报错，和现有 `manifest` vs `manifestPath` 互斥同一风格）。

**执行流程**：
```
templateId + slots
  → 查模板目录（宿主侧读盘）
  → compileTemplate（槽位校验 + 容量合同 + 家具展开 + 音效事件表注入）
  → validateManifest
  → 走现有渲染链路（复用 renderMediaOnWeb / 队列 / 落盘）
  → spot-check：渲参考帧 → 与模板 frames/ 比对
  → 返回：url + frames[] + 校验结论 + **与参考帧的差异结论**
```

### 6.4 参考帧基线 + spot-check 自动比对（「准确」的落点）

**模板自带参考帧**（`frames/`，帧号 → PNG）。渲染后：
1. 按模板声明的 `referenceFrames`（帧号列表）渲出这些帧（复用现有 `spotFrames` 机制）
2. 与模板参考帧比对 ⇒ 产出**可读结论**

**比对维度**（按成本从低到高，先做前两个）：
| 维度 | 算法 | 成本 |
|---|---|---|
| **整体像素差** | 平均绝对差 / 最大差 / 差异像素占比 | 低（canvas 2D 逐像素） |
| **元素位置差** | 关键锚点（标题/卡片的中心点）的像素位置偏移 | 中（需先定位，v1 可先只做亮度剖面） |
| 文本内容比对 | OCR 太贵 ⇒ **跳过**（内容一致性由槽位校验保证） | — |

**结论格式**（写进 `report.templateCheck` + `warnings`）：
```
[模板比对] 参考帧 3/6 一致；差异帧：frame 540（像素差 8.3%，最大差 62%）
            frame 546（像素差 7.9%，最大差 58%）—— 疑似卡片入场时机偏移
```

**阈值**：像素差 ≤ 3% 算「一致」；3–10% 「可接受差异」；> 10% 「超出阈值，请检查槽位内容或参数」。

> ⚠️ **参考帧必须在同源可访问**（浏览器里的 canvas 才能加载）⇒ `frames/` 要随模板落到可访问的 URL（项目资产目录），`template.json` 里存 URL 而不是相对路径。

- ❌ 不做模板编辑 UI（先让 LLM 能用）

## 10. 已知的坑

1. **`render_composition` 的 `manifest` 与 `manifestPath` 已互斥** ⇒ 加 `templateId` 时要**三方互斥**（`manifest` / `manifestPath` / `templateId`），且错误文案要说清「只能选一种」。
2. **`report` schema 是 `additionalProperties: false`** ⇒ 只改组装不改 schema，字段会被静默剥掉。
3. **模板 spec 的 `visuals[]` 里有大量冗余**（`at` / `fromTrackId` / `toTrackId` / `baseline` 等是制作期元数据）⇒ `describe_template` 返回前要**裁剪**，否则吃掉 LLM 上下文。
4. **参考帧必须是同源 URL** ⇒ 不能在 `template.json` 里写相对路径。
5. **spot-check 的比对要有容差**：字体渲染、亚像素、抗锯齿都会造成差异 ⇒ 阈值不能设成 0。
6. **模板里的 `contractVersion` 不被渲染器认识时必须明确拒绝**（不要静默降级）—— 否则会出现「模板要求的能力没有，但渲出来了」的假成功。
7. **模板自身要能被 `validateManifest` 过** ⇒ 第一个模板的 spec 要真的过校验（配套的 `manifest-b1b2.json` 已验证 0 error 0 warning，可作起点）。
8. **`themes.ts` 与模板的关系**：主题是「视觉 token」，模板是「一整支片」。**模板引用主题，不是替代主题。**
