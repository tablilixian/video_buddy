# 后台服务需求 ｜ ASR 词级转写服务（2026-11-02）

> 提出方：Canvas Studio 前端（桌面端）。本文档自包含，供后台团队独立评审。
> 用途：前端「爆款视频复刻」拆解流程需要参考视频口播的**词级时间轴**；前端已有词级字幕渲染能力（TTS 能量谷推导），缺「任意音频/视频 → 词级时间戳」的转写服务。

## 一、目标

提供 HTTP 转写服务：输入音频或视频文件，输出**带词级时间戳**（中文为字级）的结构化 JSON。核心质量指标是时间戳精度，不是转写正确率——前端用它做音画对齐。

## 二、接口设计

### 2.1 同步接口（短音频，≤60s）

```
POST /v1/asr/transcribe
Content-Type: multipart/form-data

file:          必填，音频或视频文件（mp4/mov/m4a/mp3/wav/webm）
language:      可选，zh / en / auto（默认 auto）
prompt_hint:   可选，字符串；品牌名/生词提示（提升专有名词识别，类似 whisper initial_prompt）
```

成功响应 `200`：

```json
{
  "duration": 18.42,
  "language": "zh",
  "segments": [
    {
      "id": 0,
      "start": 0.0,
      "end": 3.2,
      "text": "家人们谁懂啊，这个价格真的离谱",
      "words": [
        { "t": "家", "start": 0.00, "end": 0.18 },
        { "t": "们", "start": 0.18, "end": 0.30 }
      ]
    }
  ]
}
```

### 2.2 异步接口（长音频，>60s）

```
POST /v1/asr/tasks        → { "task_id": "..." }        （入参同 2.1）
GET  /v1/asr/tasks/{id}   → { "status": "queued|running|succeeded|failed", "result": <同 2.1>, "error": {...} }
```

前端以轮询消费（间隔 2s），`result` 结构与同步接口完全一致。

### 2.3 输出契约（关键约束）

- **时间单位**：秒，浮点，相对文件起点；单调不减。
- **切分粒度**：中文按**字**切 token；英文按词；每 token 必带 `start/end`。
- **标点**：不进 `words`（避免污染对齐），仅在 `text` 中保留。
- **无时间戳兜底**：个别词对齐失败时，允许该词 `start/end` 为句内插值，但 `words` 数组不允许缺项。
- **说话人**：`speaker` 字段预留（v1 可不实现；v2 若做说话人分离，按 `"S1"/"S2"` 填在 segment 级）。

## 三、交付形态与实现模式（后台任选其一，前端只认契约）

### 3.1 交付物定义

后台交付**一个自建 HTTP API**（契约见 §二）。前端只对接该 API，**不直连任何第三方 ASR**；key 管理、计费、限流、格式差异全部收敛在后台。至于该 API 内部怎么实现，后台按实现成本自行选择以下任一模式，**验收只看 §2.3 输出契约 + §五精度指标，不锁定实现**。

### 3.2 模式 A：自建推理服务

后台部署开源 ASR 并封装成本服务。

| 子选型 | 说明 | 优势 | 注意点 |
| --- | --- | --- | --- |
| A-1 WhisperX | faster-whisper 识别 + 对齐模型强制对齐 | 词级时间戳精度最高（开源同类最佳） | GPU 需求；python 服务化 |
| A-2 FunASR (Paraformer) | 达摩院开源，中文效果好，原生时间戳预测 | 中文精度好、部署简单 | 英文混说场景需验证 |

### 3.3 模式 B：代理第三方云厂商 API

后台不跑模型，代理火山/阿里/腾讯等云厂商 ASR 文件识别接口。

- 后台职责：key 托管、计费统计、限流、**契约归一化**——把云厂商返回格式转换为 §2.3 统一契约（时间单位秒、中文按字、`words` 无缺项、标点不进 words）。
- 关键前置确认：所选云厂商必须返回**字级时间戳**（火山/阿里/腾讯的文件识别接口均支持）；仅句级时间戳的接口不满足本需求，不可选。
- 优势：零模型运维、落地最快。注意点：按量成本、第三方 SLA 依赖。

### 3.4 模式 C：混合路由（可选）

如短音频走自建推理、长音频走云厂商 API（或按语言路由）。对外仍是同一个 §二 契约，路由细节对前端透明。

### 3.5 模式对比速览

| | A 自建推理 | B 代理云厂商 | C 混合 |
| --- | --- | --- | --- |
| 落地速度 | 慢（部署+调优） | **最快** | 中 |
| 运维成本 | 高（GPU/服务化） | 低 | 中 |
| 单次边际成本 | 低（量大了划算） | 按量付费 | 视路由 |
| 精度上限 | 最高（可调优） | 取决于厂商（需确认字级） | — |

**给后台的建议**：追求最快上线选 B（先确认厂商字级能力）；预期调用量大、有 GPU 资源选 A-2（中文场景）；不确定先 B 后 A 也可以，契约不变前端无感。

## 四、非功能需求

| 项 | 要求 |
| --- | --- |
| 文件上限 | 200MB / 2 小时 |
| 同步接口时限 | 60s 音频 P95 ≤ 15s（GPU）/ ≤ 60s（CPU），超出建议直接走异步 |
| 并发 | 起步 10 并发，429 附 Retry-After |
| 幂等 | 同一文件重复提交允许（前端有重试场景），不做去重要求 |
| 数据保留 | 音频与转写结果保留 ≤ 24h 后删除；**用户内容不用于模型训练**（需在服务条款层面确认） |
| 错误码 | `INVALID_FILE`（损坏/无法解码）/ `UNSUPPORTED_LANGUAGE` / `NO_SPEECH`（成功响应内标记而非报错）/ `FILE_TOO_LARGE` / `TIMEOUT` |

## 五、验收标准

- **AC1 精度**：中文 15s 口播样片（安静环境），随机抽 10 个字，字级时间戳与人工标注误差 ≤ 100ms。
- **AC2 嘈杂**：带 BGM/音效的口播样片，句子边界完整，字级时间戳误差 ≤ 200ms；完全无法对齐的段允许整段回退句级（不崩）。
- **AC3 混说**：中文夹英文品牌词（如「iPhone」「GPT」），不崩；生词允许拼写偏差，但必须有合理时间窗口。
- **AC4 性能**：60s 音频同步接口达到 §四时限。
- **AC5 契约**：`words` 无缺项、时间单调、单位秒——前端会用 schema 校验器做硬校验，字段缺失视为不合格。

## 六、前端对接（另立任务，供参考）

前端将封装 `transcribe_media` 宿主工具消费本服务（传 `transcriptPath` 给证据网格工具叠加台词标注）。前端不直接暴露本服务给终端用户，鉴权走现有网关。

## 七、待后台反馈的问题

1. **实现模式选型**（§三）：A 自建推理 / B 代理云厂商 / C 混合，后台按实现成本自行定夺，只需告知结论与预计排期。
2. 若选 B：拟用云厂商的**字级时间戳**能力确认（这是模式 B 的前置硬条件）。
3. 若选 A：GPU 资源情况（决定 A-1/A-2 取舍与 §四同步时限承诺）。
