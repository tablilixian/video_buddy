# Canvas Studio 全功能验收测试用例集

> 版本：2026-08-29（对应批次 0 + 1 + 2 首批全部落地后的代码状态，测试 116/116）
> 用途：桌面端手动回归的完整用例清单。每条用例给出**操作步骤**与**正常表现**（预期结果）；
> 「正常表现」之外的任何稳定复现现象都算缺陷，回填到 §十二 缺陷记录表。
> 用例编号规则：`模块-序号`，标注关联 backlog 条目（CV-xxx / HITL-x）方便追溯。

---

## 〇、验收前准备

1. 构建 + 重启桌面（**每次代码变更后必须重建**，桌面只加载 `lib/` 编译产物）：
   ```bash
   corepack yarn workspace canvas-studio build && corepack yarn dev
   ```
2. 打开一个已有内容的项目（含生成节点、参考图、血缘边的项目最理想）；没有就先跑一遍 §八 M 组造数据。
3. 记录桌面版本与分支提交号，缺陷记录需附带。

判定总原则：
- **通过** = 表现与用例「正常表现」列一致，且不引入新异常。
- **有条件通过** = 功能生效但有轻微瑕疵（如动画缺失），记录不阻塞。
- **不通过** = 功能不生效 / 报错 / 产生错误数据。

## 一、A 组：项目管理

| 编号 | 前置 | 步骤 | 正常表现 |
| --- | --- | --- | --- |
| A-1 | 无 | 新建项目 | 项目出现在列表并自动选中；画布为空但网格/工具栏正常渲染；无报错 toast |
| A-2 | 已有 2 个以上项目 | 点击列表另一项目 | 画布切换为该项目内容；当前会话跟随切换；左右栏不残留上一项目的选中态 |
| A-3 | 项目甲存在 | 删除项目甲 → 再新建同名项目 | 新建成功，**不报** `workspace rename failed: workspace-name-conflict`（CV-033） |
| A-4 | 有历史残留孤儿 workspace 的旧环境 | 重启桌面，观察画布映射 | 「对话有内容 ⇒ 画布跟随当前会话」「列表选中项与画布一致」，三者不互相矛盾（CV-034） |
| A-5 | 任一项目 | 重启桌面后打开 | 上次的项目与画布状态恢复；对话与画布对应关系正确 |
| A-6 | 两个 DSH 实例共享同一 home（可跳过，单实例环境验证不了） | 两边各新建一个项目 → 各自刷新项目列表 | 两个项目都在 `projects.json` 里（旧版后写方会拿内存副本整表覆盖、先建的项目从列表消失，CV-046）；删掉其中一个后，另一个实例再做任何操作都不会把它「复活」（墓碑） |

## 四、D 组：节点右键菜单（CV-037 修复回归，逐项必点）

前置：右键任一节点，菜单弹出。**通用关闭行为**（每条用例都隐含验证）：
- 点菜单项 → 菜单先关闭、动作**真正执行**（修复点：此前 14 项全部点击无效）；
- 按 Escape → 关闭；点菜单外任意处 → 关闭；右键另一节点 → 旧菜单关闭新菜单打开。

| 编号 | 菜单项 | 步骤 | 正常表现 |
| --- | --- | --- | --- |
| D-1 | 重命名 | 点击 | 出现改名入口（详情面板/行内编辑），改名生效 |
| D-2 | 复制 | 点击 | 副本出现；随后右键空白「粘贴」能粘贴该副本 |
| D-2a | 查看详情 | 点击 | 打开该节点的详情 / 编辑面板（媒体类节点双击已改为预览，详情查看走此入口，CV-045） |
| D-3 | 引用到对话 | 点击 | 对话输入框光标处插入 `@ref` 引用标记；失败时回退为复制（不静默丢失） |
| D-4 | 下载资产 | 右键**带图片/视频 url** 的节点 → 点击 | 触发浏览器下载，文件名为清洗后的节点标题 + 正确扩展名（CV-020） |
| D-5 | 下载资产（置灰） | 右键无资产的节点（便签/文本） | 菜单中**不出现**该项（`canDownloadNode` 为 false 时直接不渲染） |
| D-6 | 锁定 / 解锁 | 点击锁定 | 节点不可拖动、方向键微调跳过它；再点解锁恢复 |
| D-7 | 隐藏 / 显示 | 点击隐藏 | 节点从画布消失（图层面板仍有记录）；再点显示恢复 |
| D-8 | 置顶 / 置底 | 与相邻节点重叠后点击 | 层级立即变化，视觉遮挡关系正确 |
| D-9 | 上移一层 / 下移一层 | 同上 | 每点一次只动一层 |
| D-10 | 解组 | 右键 group 节点 | 子节点散开为独立节点；非 group 节点**不出现**该项 |
| D-11 | 打断 | 右键生成中（isLoading）节点 | 生成任务取消，loading 遮罩消失；非 loading 节点**不出现**该项 |
| D-12 | 重试（同参数重新生成） | 右键 agent 生成且有提示词的非 loading 节点 | 节点回到生成中态并重新生成；**双击/快速连点只触发一次**（防重复生成守卫） |
| D-13 | 修改提示词 | 右键 agent 生成节点 | 打开提示词编辑入口（steer），提交后生效 |
| D-14 | 删除 | 点击（红色危险项） | 节点删除且相关边消失；undo 可恢复 |

## 七、G 组：节点详情（CV-194 起 = 就近工具条 + 底部抽屉）

> G-1~G-5 是原「详情面板」时代的用例（内容仍然有效，只是打开方式改由工具条 / 右键进入）；
> G-6~G-11 是 CV-194（2026-09-17 验收通过）新增的交互用例。

| 编号 | 前置 | 步骤 | 正常表现 |
| --- | --- | --- | --- |
| G-1 | 打开生成节点详情 | 观察参数区 | 提示词单独成段可复制；参考图缩略图正确反查显示；参数为一行摘要；原始 JSON 折叠可展开（CV-012） |
| G-2 | 生成节点 | 点工具条「改提示词」 | 抽屉打开且提示词**预填当前值**（不用自己从 JSON 抠），光标落在编辑区 |
| G-3 | 上传的图片节点 | 查看分辨率 | 显示真实宽高（落卡前已探测），不是「未知」（CV-013） |
| G-4 | 媒体节点详情 | 点底部「下载资产」 | 与右键下载行为一致（CV-020） |
| G-5 | 失败的生成节点 | 打开详情 | 可见错误信息；有重放参数时提供重试入口 |
| G-6 | 画布上任一可操作节点 | **单击**它（不拖动） | 节点上方贴近处出现小工具条（重试 / 改提示词 / 引用到对话），抽屉**不**自动打开；多选、或正在拖动时工具条消失（CV-194） |
| G-7 | 把节点拖到画布最上缘 | 观察工具条 | 上方装不下时自动翻到节点**下方**；工具条始终贴在节点旁边（CV-194） |
| G-8 | 打开抽屉后缩放到 0.4× | 看工具条与抽屉里的字 | 工具条尺寸与 1× 时**逐像素相同**（不随缩放变形）；抽屉里的字号也不变（CV-194） |
| G-9 | 打开抽屉 | 看四条边 | 底边与时间轴顶边齐平、左右与画布等宽、**不覆盖**宿主右栏对话区；抽屉打开时工具条被夹在抽屉上缘之上（CV-194） |
| G-10 | 抽屉打开 | 拖上缘那条 6px 抓取带改高度 | 高度跟手变化；关掉再开、乃至重启桌面后**仍是上次的高度**；拖到最小仍看得见提示词区，画布另一侧至少留出可点区域（CV-194） |
| G-11 | 任一含提示词的节点 | ① 点提示词正文；② 点「展开」；③ 点「聚焦」 | ① 原位变自增高编辑框，**失焦即保存**；② 编辑器占满右栏并出现「保存 / 取消」；③ 居中大窗左「已保存」右「编辑」并排。三档中 Esc 均取消、Cmd/Ctrl+Enter 均提交；**保存不会触发重新生成**（提示语明说「改完再点重试」）（CV-194） |
| G-12 | 音频（BGM）/ 四视图（character_sheet）/ 抽帧 节点 | 打开工具条与右键菜单 | **出现「重试」**（CV-195 补齐了这三类的重放链路）；「改提示词」只对有自由文本提示词的节点出现——**只有 BGM 有**（音乐描述 / 歌词两个框），四视图与抽帧没有可改的自由文本，故不出现（CV-194/195） |
| G-13 | 同上三类节点 | 点「重试」 | **原地换一版**：节点 id / 位置 / 血缘 / 编组全不动，不新增节点。BGM：新音频落在同一张卡上（标题仍「BGM」、时长角标更新为实测值）；四视图：资产卡不新增（仍是同一张卡、冻结描述不变）；抽帧：末帧换成新图，仍指向同一源视频。过程中画布出现 loading 遮罩，失败时错误写回该节点（CV-195） |
| G-14 | BGM 节点 | 在抽屉里改「歌词」→ 点重试 | 新一版音频的歌词就是刚改的那份（参数来自节点自己保存的 `generationPrompt`，不是对话里的临时覆盖）；纯器乐留空时卡片显示「纯器乐」（CV-194/195） |
| G-15 | 四视图节点 | 手工删掉它的资产卡（或换成别的锚点）→ 点重试 | 明确报错「资产卡已不存在…无法重试」，**不会**悄悄新建第二张卡（CV-195） |

## 八、H 组：Agent 工作流 / HITL（造数据用，也是回归用例）

| 编号 | 前置 | 步骤 | 正常表现 |
| --- | --- | --- | --- |
| H-1 | 新会话输入一条创意 | 发送首条真人消息 | 画布原点自动出现「创意」节点（toolName=user_brief）；每项目至多一个，重复发消息不重复落（CV-023）；旧项目打开时经历史重放自动补落 |
| H-2 | 有创意节点 | 让 agent 提交分镜表 | 分镜**逐镜拆卡**（「分镜 N · 景别」），每行 3 卡横向排列，血缘指向创意节点并排其右侧；解析失败回退整表单节点（CV-024/025/026） |
| H-2b | H-2 的分镜已提交 | 点「驳回，继续修改」写点意见 → agent 重新提交（**连做两轮**） | 画布上**仍是每镜一张卡**（打回两次不会变成三套同名卡）；同镜号的卡 **id 与位置原地不动**、只有文案/时长更新；新镜号新建卡且不压在旧卡上；被删掉的旧镜号卡**保留**（不静默删，避免下游断链），工具结果里会写明「新建 N 张 / 复用 M 张」（CV-050） |
| H-3 | 分镜卡存在 | 让 agent 生成关键帧/视频，指定所属分镜 | 新节点连到分镜卡与素材来源，落位在来源右侧一列（重叠自动避让）；即使模型漏传 shotRefs，视频也继承分镜卡血缘（CV-027/031） |
| H-4 | HITL 逐步确认模式 | 分镜提交后 | 出现批准/驳回 UI；批准走分镜门禁；**已知现状：批准后 agent 不自动苏醒，需手打「继续」**（O1/HITL-B 未实施）——记录表现，不算新缺陷 |
| H-5 | agent 提问（allowFreeText） | 遇到开放性问题（如品牌名） | 点选卡片出现自由输入框 + 提交按钮；答案走同一通道；提交后锁定防重复提交（CV-002） |

## 十一、K 组：内置 ffmpeg（装机即全功能，CV-201）

> **必须在没装过 ffmpeg 的机器上验**（干净机器或新用户账户，`which ffmpeg` 为空）。开发机上装过 brew ffmpeg 的**验不出这条链路** —— 解析链会命中系统 PATH 上的 ffmpeg，现象与「随包生效」无法区分。
> 验前自检一条命令：`ls "/Applications/VideoBuddy.app/Contents/Resources/ffmpeg"` 应列出 `darwin-arm64` / `darwin-x64` 两个目录，且每个目录里有 `ffmpeg` 与 `LICENSE`。
>
> ⚠️ **K 组只证明「功能可用」，不证明「可以对外发」**：随包二进制实测带 `--enable-nonfree`（configure 行含 `--enable-gpl --enable-version3 --enable-nonfree`），触发 FFmpeg 随包 LICENSE 的 *"unredistributable"* 明文 ⇒ **内测 / 自用不受限，对外发布前必须换成 LGPL 构建**（详见 [STATUS.md](./STATUS.md) §7 B2 与 [plans/bundled-ffmpeg.md](./plans/bundled-ffmpeg.md) §8）。因此 K 组通过后状态是**「功能已就绪、发布前需换构建」**，不是「可直接发布」。
>
> 另注：出包命令 `dist:mac-smoke` 自身不设镜像变量，无 VPN 环境下会挂在 GitHub 下载上（单请求 600s 超时）。复跑前先导出 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` 与 `ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/`。
> **拿包通道（本地构建跑不动时用这条）**：手工触发 GitHub Actions 的 `CI`（`workflow_dispatch`，分支选 `dev`）—— `desktop-macos` 任务产出 artifact `VideoBuddy-macOS-<sha>`（smoke DMG），`desktop-windows` 任务产出 `VideoBuddy-Windows-<sha>`（`Setup.exe` + `Portable.zip`）。⚠️ 都是**未签名**测试包：DMG 经浏览器下载会带 quarantine，装到 `/Applications` 后需 `xattr -dr com.apple.quarantine /Applications/VideoBuddy.app`（或右键「打开」）才能起。
>
> **转包给别人时的三条铁律**：① **下载 artifact 必须登录 GitHub**（匿名请求实测 401）⇒ **Actions 链接不能当公开下载口**，转发时先把包下到本地再走网盘/共享盘（Windows artifact 解压后是 `VideoBuddy-2.0.4-x64-Setup.exe` + `VideoBuddy-2.0.4-x64-Portable.zip`，单文件过大，微信类 IM 通常发不出去）；② 收包人第一次运行 Windows 包会被 **SmartScreen** 拦（未签名）⇒「更多信息 → 仍要运行」，浏览器下载可能需在下载列表选「保留」；③ **分发范围：仅限内部/自用** —— 包内 ffmpeg 含 `--enable-nonfree`（上游明文 *unredistributable*），而本仓是 public 仓库，**建公开 Release 等于对外分发**，换 LGPL 构建前不要做（见下方 K 组 ⚠️ 与 [STATUS.md](./STATUS.md) §7 B2）。

## 十五、L 组：后端单任务纪律与上传超时（CV-215）

> 本批要验两件事：① **模型是否知道「后端同刻只跑一个」并逐个调用**（传达纪律的唯一目的）；② 上传路径不再是「裸 fetch」（收口 CV-135 漏网）。①只能靠真实对话观察（**不能**只看「没报错」），②可用故障注入或弱网验。
>
> ⚠️ **L-1/L-2 必须看「模型怎么发」，不能只看「有没有乱并发」**：串行**在平台层已被默认兜住** —— 24 个工具都未声明 `isConcurrencySafe`，而 dsh-tools 是 fail-closed 语义（「只有精确 `true` 才 parallel」）⇒ 同回合多 tool_call **本就**被排成 exclusive 串行 + 排序屏障。所以「没有并发事故」**不能单独证明纪律生效**（那是兜底的功劳）。真正的判据是：模型**主动**逐个发（分回合 / 每条等结果再发下一条）。若模型仍试图批量提交、只是被平台挡住，属**「纪律未生效但被兜底」**，需回头加强描述用词。

## 十六、M 组：放手跑卡片降级与结算文案（CV-216）

> 本批要验的是**卡片的有无由谁决定**。修前：由「模型调没调 `ask_user_choice`」决定 ⇒ 放手跑下照样弹出一张没人能答的卡片。修后：由「Host 的结果文本里有没有放手跑标记」决定。
>
> ⚠️ 两个容易看错的点：
> ① **窄条不是「消失」** —— 它保留一行说明，整条隐藏反而是错的（那会丢掉「这里本该提问、但放手跑替你定了」的唯一痕迹）；
> ② **见到「已结算」就是 bug 复现** —— 修前**所有**卡片底部都显示它，包括用户正常作答之后（`extractResultNote` 读错层级、恒回退兜底文案）。

| 编号 | 前置 | 步骤 | 正常表现 |
| --- | --- | --- | --- |
| M-1 | 放手跑模式 + 只给一句话创意的项目 | 发一条创意，看模型进澄清阶段时画布上出现什么 | 出现的是**不可交互窄条**：「（放手跑）本回合未提问，已按默认值取「…」」；**不出现**选项 chips / 确认按钮 / 自由输入框 |
| M-2 | 同上 | 点击窄条、或在它上面回车 | **没有任何反应**（它不是按钮）；不报错、不触发「当前没有待回答的问题」 |
| M-3 | 同上 | 读窄条文案 | 能看出**取了哪个默认值**（带出选项名，如「多镜头叙事短片」），不是泛泛一句「已结算」 |
| M-4 | 逐步确认模式 + 同项目 | 发同样的创意 | 卡片**照常可交互**（chips 可点、确认按钮可用、自由输入框可用）—— 双向守卫：不要把 confirm 一起降级掉 |
| M-5 | 逐步确认模式 | 点一个选项并确认，等结果回流 | 卡片底部显示**真实答案文本**（如「用户的选择：16:9 横屏」）。**若显示「已结算」，即 CV-216 的层级读错 bug 复现** |
| M-6 | 放手跑模式 | 全程跑完一轮，随后查会话转录里有没有 `ask_user_choice` 的 `tool/call` | **理想是零次**（skill 层短路生效，模型根本不该问）。若仍有调用、但画布显示为窄条 ⇒ **客户端修好了、skill 层没生效**，属半通过，需回头加强 `clarification.md` 开头的力度 |
| M-7 | 一台**今天之前**的放手跑旧会话 | 打开它，看历史卡片 | 仍渲染为窄条 —— 判定按**调用粒度**生效（读那次调用的结果文本），不随「当前模式」漂移 |

## 十七、N 组：占位节点（CV-217）

> **背景**：模型会把「先落个占位节点、稍后回填」当成做法，而 `write_script` **每次调用都新建节点** ⇒ 占位那张卡永远没人替换它。实测两次独立复现（北京书市 / 测试分辨率拆分），画布上留下正文只有「占位」二字的「文案」卡。

| 编号 | 前置 | 步骤 | 正常表现 |

| N-1 | 全新项目 | 走完整流程（到成片），期间不要干预 | 画布上**始终没有**正文是「占位 / 待补充 / TODO」的「文案」或「剧本」卡。**有 ⇒ 写入侧守卫没生效** |

## 十八、O 组：image2fix 自动修复的 prompt 形态（CV-218）

> **背景**：`image_generate` 出图含非 ASCII 引号文字时会自动挂一次 `image_fix`。修复 prompt 的**形态**决定成败：只喂「字符清单」会丢位置锚点 ⇒ 模型按形近字猜（真机实测把「武仔」修成「武传」**仍错**，并凭空多出两处文字 + 曝光漂移）；喂「**原 prompt 的文字规格段 + 逐字约束段**」则 8 处错字全对、排版零漂移（先例取证 `api-probe/image2fix-20260920-text-spec/`）。
>
> **判据（最容易看的一条）**：修复节点的标题就是 fix prompt 的**首句**。首句是**带位置的规格句**（如「前景是一处武侠书专摊：…摊后竹架上挂一面写着毛笔字 "武侠" 二字的红色竖幡；」）⇒ 新形态生效；首句是「确保画面中以下文字字符正确渲染…」⇒ **退回旧形态了**。

| 编号 | 前置 | 步骤 | 正常表现 |
| --- | --- | --- | --- |
| O-1 | 任意项目 | 出一张**含中文文字**的图（prompt 里用引号锁字，如招牌「老张面馆」） | 出图后**自动**多出一个 `image_fix` 节点（原图被 `replaces` 标失效）；**该节点标题是文字规格句、不是「确保画面中以下文字字符正确渲染」** |
| O-2 | 同 O-1 | 打开该修复节点的详情 / 重放，看 prompt 全文 | 含**位置 + 字体 + 字号/颜色**等描述（「写在xxx处」「粗黑体」「墨黑」…）；末尾是逐字约束句（「每一个汉字都必须逐字准确还原…不得替换、增删、乱码或自造汉字」）。**全文不得出现 `- "xxx" —— 保持原字体、字号、颜色、位置不变` 这种 bullet 清单** |
| O-3 | 同 O-1 | 对比原图与修复图 | 错字被改对；**不新增任何文字**；版式/元素**不增删**（可能允许轻微质感差异 —— image2fix 是整图重绘） |
| O-4 | 任意项目 | prompt 里只把风格词放引号且带否定，例如 `画一张海报，不要"水墨"风格` | **不触发** `image_fix`（无修复节点、无 CV-212/218 warning）。这是 CV-218 收紧的误触发 |
| O-5 | 任意项目 | 否定句 + 正常文字句并存，如 `不要「水墨」风格，标题用「春山一盏」` | **仍触发**，且修复 prompt 是那句**带位置的原句**（反向对照：别把正常路径一起挡掉） |
| O-6 | 任意项目 | 出一张**无文字的纯风景图** | **不触发**（引号文本不存在） |
| O-7 | 任意项目 | 显式传 `autoFixText: false` 出含文字的图 | **不触发**，画布只有原图 |
| O-8 | 任意项目（造数据） | 写一个**没写逐字约束**的含文字 prompt，如 `画面中央写「限时特惠」四个字` | 仍触发；修复图末尾**补上**兜底约束句（原文没写不代表可以不约束） |
| O-9 | 后端 `upload` 恢复后 | 跑 `node scripts/probe-image2fix-ab.mjs --out docs/api-probe/image2fix-20260921-ab`（可加 `--handle <名>` 复用句柄跳过 17s 上传、`--tag -rN` 跑第 N 轮） | 同一张真实原图 + 同一句柄，A（旧清单）/ B（新规格段）各出图一张并落盘；**看图判定**。**2026-09-21 已跑完（第 1 轮 A/B 齐、第 2 轮 B 被他人 5 个并发提交挤到 420s 超时）**：判据要按**「有没有凭空增字」**看，**不要**按「主字修没修对」——两版都能修对（旧模板第 2 轮把摊前不可读伪字整块写成「武侠」＝增字）。逐处结论与放大裁剪见 `api-probe/image2fix-20260921-ab/analysis.md` + `crops/` |

## 十九、P 组：health 探针分层与「忙/闲」双态（CV-219）

> **背景**：`ensureDramaReachable` 原判据是 `ok = response.ok` —— health 一返 500 就把**所有**打后端的操作报成「不可达」（2026-09-20 实测正是这个形状：`/api/v1/health` 稳定 500 而 `/view` 返 422，服务本身活着）。现已分层：**收到任何 HTTP 响应即算活着**，只在**拿不到响应（连接失败 / 超时）**时才报「不可达」。
>
> **判据**：本组看的是**报错文案的精度**，不是「成不成功」。最难自然复现的是 P-1/P-2（要后端恰好坏掉），所以主要靠单测；桌面端只需跑 P-3~P-5。

| 编号 | 前置 | 步骤 | 正常表现 |
| --- | --- | --- | --- |
| P-1 | 后端 health 异常（4xx/5xx）、业务端点正常 | 正常出一张图 | **照常出图**。**不得**出现「Drama Backend 不可达，请检查服务是否已启动后再试」。旧版本在这里会把图挡下 —— 见到该文案即为回归 |
| P-2 | 后端**整个不可用**（进程停掉） | 出一张图 | 秒级报「Drama Backend 不可达，请检查服务是否已启动后再试」，**不**吃满 6 分钟超时。这是 P-1 的反向对照，改完必须两边都对 |
| P-3 | 后端空闲（`curl :8082/api/v1/health` 看 `queue_task_count` 为 0） | 出一张图 | 结果里**没有**任何排队提示（空闲不该报警） |
| P-4 | 后端有活在跑（先在前端/`api-playground` 提交一个长任务，`queue_task_count` ≥ 1） | 立刻再出一张图 | 结果里出现提示「Drama 后端同步单任务：本次提交时已有 **N** 个任务在执行，本请求排在其后」（N 与 health 读数一致）。**注意 N=1 也要报警**（该计数含正在执行的那个） |
| P-5 | 任意项目 | 造一次本地超时（如选明显超出该档上限的时长，或断网后调视频） | 报错文案含**实时**队列深度三选一：「后端当前有 N 个任务在执行」/「后端当前空闲」/「后端队列深度未知」。**不得**再是含糊的「后端可能繁忙」 |

## 二十、Q 组：宿主侧生成队列（CV-220）

> **背景**：Drama 后端**同步单任务**（并发只排队、墙钟不变），而客户端占位截止 `PENDING_TIMEOUT_MS = 660_000` 是从**占位落卡那一刻**起算的，视频档 `DRAMA_TIMEOUT_MS.video = 600_000` ⇒ **只剩 60s 余量**。只要与任何东西重叠（本端重试 / 重出 / 模型同回合多调用 / 后端被别人占满），**排在后面的那个请求「还没轮到」就被判「生成超时」**。⇒ 宿主现在有一条**显式单通道队列**，且**排队时间不计入截止**。历史实测：CV-218 B 轮 `queue_task_count = 5`（被别人占满）时本人的请求就是这样被误判的。
>
> **判据**：本组看的是**「排队期间会不会被误判超时」与「位次提示对不对」**，**不是**「出图快不快」——队列不会让墙钟变快，它只是把误判消掉。**Q-3 / Q-6 是反向对照，改完必须两边都对。**

| 编号 | 前置 | 步骤 | 正常表现 |
| --- | --- | --- | --- |
| Q-1 | 任意项目，后端可用 | 让**两个请求重叠**：在画布上连点两个节点各自重试（或一个重试 + 立刻在对话区让它再出一张） | 两个请求**都不被判「生成超时」**、先后各自完成；画布上出现窄条提示「**生成队列：<标签> · 等待 1 个**」（标签随请求类型变：视频生成 / 图片生成 / 图内文字修复…） |
| Q-2 | 同 Q-1 | 重叠期间盯住第二个卡片的占位计时 | 排队期间**不**弹「生成超时」（排队被显式延期）；只有**真正轮到自己开始生成**并超过该档上限才报超时。旧版本在这里就会误报 —— 见到「生成超时」而两个请求其实都出了图即为回归 |
| Q-3 | 任意项目 | **只发一个**请求，不制造任何重叠 | **不出现**任何队列提示（无等待 ⇒ 不渲染窄条）。这是反向对照：若空闲时也恒显示窄条，说明状态派生写成「只要在生成就忙」了 |
| Q-4 | 任意项目 | 重叠状态下去**取消**其中一个（取消重试 / 关掉该项目 / 断网） | 被取消的等待条目**出队且不占坑**：紧接着的单发请求**立刻开始**（不卡在空槽上）——「取消了但槽位没释放」是这里最容易出的错 |
| Q-5 | `curl http://127.0.0.1:<端口>/canvas-studio/generate-queue`（端口取桌面实际占用） | 空闲时 GET；再试非 GET / 跨源 | GET → `200 {"active":null,"waiting":[]}`；**非 GET → 405**；**跨源/非回环 → 403**（这是**只读**路由，不走写权限那一档） |
| Q-6 | 任意项目（造数据） | 故意让一次生成**出错**（如断网后调一次） | 队列**释放槽位**：出错后紧接着的请求**立刻开始**，不会被永久排在后面（错误不得让队列锁死）。与 Q-4 一起构成「两类异常出口都要放行」的反向对照 |

## 二十一、R 组：统一错误处理系统（CV-233）

> **背景**：过去「错误」是一堆裸 `throw new Error('中文文案')` + `console.warn`，谁该看见、看见了该怎么办全靠下游猜文案。本系统给每条错误一个 `CS-<模块>-<序号>` 码，在 `src/errors/catalog.ts` 集中登记**受众**（`user`/`agent`/`developer`）、**可恢复性**（`auto`/`guided`/`fatal`）、**展示通道**（D1–D5）、**UI 三级处置**（`uiKind`），再由纯函数 `routeError()` 决定处置。

> **判据**：本组看的**不是「有没有报错」，而是「该看见的看见了、不该看见的看不见」**。R-3 / R-7 是一对**反向对照**（隐藏过头 = 真故障消失），两边都必须对。

## 二十二、S 组：错误可见性「诊断开关」（CV-234）

## 二十三、T 组：工具入参「占位值」守卫（CV-235）

> **背景**：模型在**一次规划多个工具调用**时，会给「还没取到的」素材句柄先填一个占位串顶上，打算回头再补。实测（2026-09-23 一次真实会话，**12 条报错里 7 条源于此**）：`upload_image {"imageUrl":"placeholder2"}`（一直到 `placeholder5`）、`character_sheet {"filename":"placeholder-will-retry"}`、`video_composite {"prompt":"placeholder"}`。
>
> 这些串的麻烦之处在于**长得像合法取值**（像个文件名、像个地址），于是每一层校验都放它过去，直到某个与「这是个占位词」毫无关系的地方才失败 —— `upload_image` 报的是「**下载地址不安全或不在允许范围内**」（下载地址安全校验），而真因是「模型压根没去取真实值」。用户读到文不对题的报错，模型得到**误导性纠正信号**（它会去改地址，而不是去取真实值），白烧一轮。
>
> **判据**：本组看的**不是「报不报错」，而是「错得准不准 + 有没有副作用」** —— 被拒的那次调用**必须什么都没发生**（不建节点、不落卡、不发起生成），且报出来的要说清是「入参填的是占位值」，**不是**「地址不安全」。**T-3 是 T-1 的反向对照，改完必须两边都对**：拦得太宽会把合法调用一起挡掉。
>
> **位置**：拦截发生在工具 `execute` **之前**，挂在宿主全部工具的唯一包装点（`wrapStudioToolDefinition`）。因此**任何**工具（含占位工具）都受同一份守卫覆盖。

## 二十四、U 组：H3 预检 R7「素材标签编号不连续」降级为提示（CV-236）

> **背景**：H3-Context-IR 预检（CV-119 / CV-196）里有一条规则 **R7「素材标签编号」**。它原先要求 `<Picture N>` 的编号**从 1 连续**，跳号即 ERROR、直接抛 `CS-H3IR-001`、**不发后端**。2026-09-24 用户报障：一次 4 张参考图的 `video_composite` 被这句 `- [R7] <Picture N> 编号不连续：1, 2, 4` **掐断**（后端零调用），用户拍板「**这个报错，降级成一个提示性的语句**」。
>
> **为什么降级而不是删检查**：`<Picture N>` 的 N **就是 `video_composite.filenames` 的位次**（第 N 张 = 第 N 个输入）⇒ **跳号指向的图仍然是对的、简报自洽**，它属「有一张输入素材没被引用」的**记账不齐**，不是路由错误。真正的矛盾是「**引用了不存在的素材**」（`<Picture 999>` 而只传了 4 张）—— 那一条**仍然是 ERROR**。
>
> **判据**：本组看的是**「同一份简报、两种编号错误的处置必须相反」** —— 不连续只提示、不阻断；越界仍拦截。**U-2 是 U-1 的反向对照，两边都要对**：只把 `err` 改成 `warn` 而没分清两者，就是「把真矛盾也放过去了」。
>
> ⚠️ **降级后最容易出的问题是「静默」而不是「报错」**：预检原本只把 WARN 拼在**有 ERROR 时**的报错文本里，一次**通过**的调用里 WARN 整批丢弃 ⇒ 若只改 `err`→`warn` 就收工，用户与模型**都看不到任何痕迹**（比原来报错更糟）。所以本批把 `assertH3IrPrompt` 的返回值改成 `string[]`，由两个视频工具并进 `result.warnings` —— **U-3 专测这条接线**。
>
> ⚠️ **对话流里那行红字（仅 U-2 会看到）是宿主 L0 固定渲染**，受众判定够不到，属**已知限制**（同 S 组横幅）。

| U-3 | 同 U-1 | 看**模型/用户这一侧**是否真的收到了那条提示 | 提示必须出现在**工具结果的 warnings 通道**里（结果文本 / 结果呈现可见），**不得只落日志**。若 U-1 的生成正常但**哪儿都看不到提示** ⇒ `assertH3IrPrompt` 的返回值被丢掉了（`irNotes` 没并进 `result.warnings`），这正是本批最该防的「静默」失败模式 |
| U-4 | 同 U-1 | 正常路径复核：写一份编号**连续**的合规简报（4 张图 ⇒ `<Picture 1>…<Picture 4>`）跑 `video_composite` | 生成正常，且**不出现任何 R7 提示**、结果里不夹带无意义的 warnings 噪音（确认降级没有把提示变成常驻） |
| U-5 | `canvas-studio/` | 看**事前纪律**（用户要求「把前面的提示词和用法部分写好」）：查 `video_composite` 的 `filenames` 参数描述与工具描述、以及技能分册 `skills/h3-prompt-writing/references/format-ref2va.md` | 三处都写清了两件事：**「每一张参考图都应在简报里出现一次」**（单独立 `<Picture N>` 条目，或在 `<Subject N>` 里 inline 注明出处），以及**「素材标签编号不连续只出提示、不阻断生成」**。⚠️ 只有报错时才有这份说明 = 事前纪律缺失：**模型没犯错时读不到用法，就还会照旧漏引** |

### 24.1 已知限制与取舍（刻意为之，勿提单）

| 项 | 说明 |
| --- | --- |
| 落选的处置：**降级而不是自动补号** | 有人会问「为什么不让 Host 自动把 1,2,4 补成 1,2,3」。因为 `<Picture N>` 的 N **是位次不是序号标签** —— 补号会让标签指向**另一张图**，那是改内容、不是改格式，违反预检「只修格式不动语义」的既有边界（CV-119 / CV-196）。所以只提示，让模型自己决定是补引用还是去掉那张输入。 |
| 「越界」与「不连续」必须分开 | 二者都在 R7 这一段里、都源自「编号」这一件事，但语义相反：不连续 = 有一张没被引用（可继续），越界 = 引用不存在的素材（真矛盾）。**回归信号**：U-2 变成「照常生成」即说明两条被一起降级了。 |
| WARN 必须带出调用点 | `assertH3IrPrompt` 的返回值是「要转达的提示文案」。**改回 `: void` 或调用方丢掉返回值，表现是静默**（用户与模型都看不到），比原来报错更糟 —— U-3 与 U-0 的第 ④ 条就是为这条设的。 |
| 技能分册与本守卫口径已对齐 | 分册本就允许某张图不单独立条目（在 `<Subject N>` 里 inline 注明出处），而旧守卫要求「每一号都单独立条目」⇒ **原拦截比我们教给模型的规则更严**。本批把守卫放宽到与分册一致，不是新加纪律。 |
