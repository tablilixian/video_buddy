## 一、一句话结论

**工单基本没走隐藏渲染窗口，而是走了"用户画布页"那条路；而那条路既没有看门狗、也没有快速失败，一旦卡住就只能干等到 `CS-RENDER-TIMEOUT`。**

三条硬事实支撑：

| # | 事实 | 怎么读出来的 |
|---|---|---|
| 1 | 全天 **0 次** `滞留渲染工单 … 已改派隐藏渲染窗口` | `routes.ts:2997` 的 `onTakeover` 是唯一出口，命中必打 warn。grep 全文 0 命中 |
| 2 | 日志里的 `CS-RENDER-TIMEOUT` **恰好 39 条**，与会话里 39 次超时逐一对应 | 交叉验证日志完整、无遗漏 |
| 3 | `RenderHost 已创建` 8 次、`RenderHost 销毁（idle）` 7 次，**每次销毁都在"那段时间一次成功渲染都没有"之后 5 分钟** | `RENDER_HOST_IDLE_MS = 5min` 且「忙时不回收」（`lifecycle.ts:15,116-126`）⇒ 销毁只能由 `touchRenderHost()` 起算，而它只在 host **取到单**时调用（`routes.ts:3002`） |

第 3 条是关键推论：**空闲回收的正常节奏证明"那几分钟里窗口从未取到过任何单"**。

## 三、源码链条（为什么会这样）

派单闸只有一处，两条路共用它：

```
建单  runRenderJob
  └─ pickExecutor()                      render-job.ts:387-401
       ├─ warmRenderHost()  → 拉起隐藏窗口
       ├─ 最多等 3000ms 的 renderHostReady()
       └─ 等不到 ⇒ executor = 'client'   ← 首单几乎必中这一条

取单  GET /remotion/pending?owner=host    routes.ts:2985-2993
  └─ claimRenderJobFor(null, 'render-host')
       ├─ 先按 executor 过滤              render-job.ts:224
       └─ 扑空才尝试改派                  render-job.ts:238-254
            └─ takeoverOrphanedClientJob
                 ├─ if (!renderHostReady(now)) return null   ← 闸门二
                 └─ if (job.clientClaimedAt !== undefined) continue  ← 闸门三
```

`renderHostReady()` 的判据（`status.ts:108-112`）只有一条：**页面自报在 30s 内且状态 ∈ {idle, rendering}**。

于是有三个互相叠加的死角：

### D-1 派单闸与改派闸是同一个闸

`renderHostReady()` 为 false 时：新单派给 `client`，**同时**改派也被禁止。也就是"你越忙/越可疑，越不给你单，也越不许别人接你甩掉的单"。这是结构性死锁，不需要额外触发条件。

### D-2 "看过一眼"= 永久归客户端

`claimRenderJobFor` 在 client 取单时打点 `clientClaimedAt`（`render-job.ts:227`），而改派条件是 `clientClaimedAt !== undefined → continue`（`:295`）。

**claim ≠ 正在渲染**。画布页取到单、然后卡住/崩溃/被切走，这张单就永远回不到隐藏窗口——哪怕窗口此时完全空闲。而日志里 0 次改派，正说明大量单停在了"已被画布页取走"这一格。

### D-3 client 单没有看门狗

`armHostWatchdog` 只给 `render-host` 单装（`render-job.ts:413`，注释也写明"在 armTimeout 只给建单时就归窗口的单装"）。client 单的唯一结局是等工具的固定超时（90–420s）。

### D-4 冷启 3 秒竞态

`pickExecutor` 只等 3s（`render-job.ts:389`）。窗口要「创建 → loadURL → 下载 bundle → 自检 → 首次自报」，实测远不止 3s。所以**每个新会话的首单几乎必然走 client**，偏偏那是用户最没耐心、最容易切窗口的时刻。

### D-5 超时后不 abort，页面把自己锁死

页面 `pollOnce` 有 `if (polling || currentJobId !== null) return`（`main.ts:156`）。工具超时只是宿主放弃等待，**不会通知页面**；若画布页那次渲染仍在跑（`pageResponsiveness:'disabled'` 会把主线程按住几十秒到几分钟），`currentJobId` 一直非空 ⇒ 页面从此不再取单 ⇒ **后续每一单都必然超时**，直到那次渲染自己结束。

这条能解释"越试越死"和"420s 之后连续超时"。

## 四、日志里两个可复现的模式

**P1「成功之后必有一挂」**：4 次干净样本，成功结束 → 15/15/19/27 秒 → 下一单超时。

| 成功 | 结束 | 下一单 | 间隔 | 结果 |
|---|---|---|---|---|
| 12:20:07 | 12:21:07 | 12:21:26 | 19s | 90s 超时 |
| 12:25:25 | 12:26:04 | 12:26:31 | 27s | 90s 超时 |
| 13:27:36 | 13:28:39 | 13:28:54 | 15s | 96s 超时 |
| 14:13:57 | 14:14:33 | 14:14:48 | 15s | 420s 超时 |

与 D-1/D-2 相符：渲染刚结束的窗口自报最"不新鲜"，此刻最容易被判 not ready → 派给 client → 被 claim 后锁死。

**P2「重启有时管用」**：13:19:12 用户重启后 13:19:25 一单成功。重启清空了页面的 `currentJobId`，解开了 D-5 的自锁——但下一单照样挂，因为 D-1/D-2 没动。

## 五、仍然未知（一条，必须靠 F-01 定死）

日志没有 **claim 级打点**，所以无法区分：

- **情形甲**：画布页从未取单（比如用户把窗口切到别的项目 / 首页），工单空转到超时；
- **情形乙**：画布页取走了单（`clientClaimedAt` 打点）但没结算，改派被 D-2 永久挡住。

两者修法不同（甲=补快速失败和改派；乙=补看门狗和 claim 语义），**所以 F-01 是必须的前置**。

**怎么最省事地定死**：F-01 落地后跑一次真机复现，看返回体里：

- `claimedBy === null` ⇒ 甲；
- `claimedBy === 'client'` 且 `firstFrameAt === null` ⇒ 乙（取单了但一帧没出）；
- `firstFrameAt !== null` ⇒ 真在渲，问题在结算。

## 六、对修复清单的影响

Phase 0 把原计划里的"待证"收敛成"可改"，并新增两条排在 F-01 之前的**立即修复项**：

| 新 ID | 修什么 | 依据 | 规模 |
|---|---|---|---|
| **F-02a** | 改派闸与派单闸解耦：改派不再要求 `renderHostReady()`，改为要求「窗口存活（`alive`）」，允许 `booting/error` 之外的任何状态接管 | D-1 | S |
| **F-02b** | `clientClaimedAt` 语义改为「**取单即计时**」：claim 后 N 秒（建议 20s）无首帧 ⇒ 允许改派，不再"看过一眼就永久归它" | D-2 | S–M |
| **F-02c** | 给 client 单也装看门狗（判据用首帧/进度上报，与 host 同口径） | D-3 | S |
| **F-02d** | 冷启预算从 3s 提到 8s，且窗口 `booting` 时**排队等**而不是直接判 client | D-4 | S |
| **F-02e** | 工具超时时向页面下发 abort（或页面自带「宿主超时」判定），清 `currentJobId` | D-5 | S–M |

这五条都在同一个模块（`render-job.ts` + `render-host/main.ts`），可以一次做完，**规模合计 M**，比原计划的 F-02 更省也更根本。
