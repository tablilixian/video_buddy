## 5. 上下文能否主动调整（用户第 2 问）

### 5.1 硬约束：插件层不能「删除」历史消息

- 故事板 skill 的分册全文是经 `skill` / `read` / `bash` 的 **`tool/result` 进入历史**的，不是常驻系统提示（系统提示里只有 `active-skills-prompt.ts:137` 生成的**装载清单摘要**，很小）。
- `agent/inbox/spliced` 是 **log-only 事件**（`deepseek-harness/docs/persistence-catalog.zh.md:173`），`target: next-turn` 只管待发消息，不是删历史 API。
- 宿主确有改写 surface 的能力：`compaction-tool-result-pruner/src/index.ts:160-171` 用 `session.append(..., {surfaceOp:'replace'})` 替换 `tool/result` 节点；但它由 `compaction-basic/src/index.ts:296,324` 在**压缩流程内**调用，且带 shadow-price 事件与 tool pairing 平衡。插件自己照抄去删阶段历史 = **改历史数据 + 跨宿主边界**，违反项目铁律「只修产生数据的路径，不动历史数据」与「不碰 dsh 本体」。**别做。**
- 结论：**不能按字面「剔除」，能做到的是「不再重发 + 在阶段边界用宿主已有能力收敛」。**

### 5.5 实测探测结果（12:4x，已跑完，结论确定）

**方法**：显式 `DRAMA_API_BASE=http://117.50.108.73`，凭据取自 `~/.videobuddy/.credentials.yaml`（只放请求头、未落盘/未打印），`max_tokens=16/64`、`stream:false`，共 23 次最小请求，模型费用可忽略。真实 POST 路由是 **`/v1/llm/chat/completions`**（`gatewayProfile()` 的 baseURL `/v1/llm` 由 pi-ai 追加 `/chat/completions`；直接 POST `/v1/llm` 返 404）。服务端实际模型 `deepseek-v4.1-flash`。

**静态判定（比探测更硬）**：`llm-pi-ai/src/adapter.ts:183-195` 注释明写 —— hand-declared 模型被 pi-ai 报为只支持 `off`，而 `off` 被翻译成**省略 reasoning 选项，与不填字节级相同**，"a provider whose own default is to think would keep thinking with `off` selected"；`models.ts:61` 对 `reasoning:false` 模型只返回 `['off']`。⇒ **设置页填 `off` 必然无效**；填 `none` 还会被 `adapter.ts:176-180` 判 `UNSUPPORTED_REASONING_EFFORT`（`THINKING_LEVELS` 见 `catalog.ts:75-86`，没有 `none`）。

**动态实测**（问题 `17*23`，答案全对 `391`）：

| 请求参数 | reasoning_tokens | message keys | 判定 |
|---|---:|---|---|
| baseline（无额外字段） | 18 | 含 `reasoning` / `reasoning_content` | 思考 |
| **`foo=bar`（未知字段对照）** | 17 | 含 reasoning | **排除「带任意额外字段就换路由」的假象** |
| `reasoning_effort:'off'` | 18 | 含 reasoning | **无效**（设置页能填的正是这个） |
| `reasoning_effort:'low'` / `enable_thinking:true` / `enable_thinking:false`（顶层） | 19–23 | 含 reasoning | 无效 |
| **`reasoning_effort:'none'`** | **0** | 仅 `role,content` | ✅ **有效** |
| **`thinking:{type:'disabled'}`** | **0** | 仅 `role,content` | ✅ 有效（等价拼写） |
| **`chat_template_kwargs:{enable_thinking:false}`** | **0** | 仅 `role,content` | ✅ 有效（等价拼写） |
| **`reasoning:{effort:'none'}`** | **0** | 仅 `role,content` | ✅ 有效（等价拼写） |

**所以当前产品没有可用开关**：设置页只能填 `off`（无效）或非法值（抛错），`none` 发不出去。

**最小改动方向（初稿已作废，正确实现见 §5.6）**：初稿写「`reasoningEfforts: { off: 'none', low: 'low' }` + 设置页选 `off`」是**错的** —— `llm-pi-ai/src/adapter.ts:132` 对 `effort === 'off'` 直接省略 reasoning 选项，`thinkingLevelMap.off` 的 wire 值根本到不了请求。必须把「关闭思考」挂在一个**非 off** 档位上（`minimal` → `none`）。

**未验证的风险**：本次只测了 `17*23` 这类单步题，**没有验证写 manifest 的多步规划质量**。关 reasoning 后可能步数更多 / 产物更差。默认关闭前必须 A/B：同 prompt 开 / 关各跑一条 45s 片，比步数、reasoning 字符、compaction 次数、成片是否落地。

### 12.3 Q1 · 那张「跟项目完全无关的图片」是模型从全局缓存里捞错的旧附件

**不是生成的，也不是画布节点**（`image_generate` / `attach_storyboard_image` 全程 0 次）。链路：

1. 用户贴图后，客户端只注入一行**纯文本**：`（1 个附件已暂存、尚未落画布：image.png …）`（#662 / #668；代码 `src/client/index.ts:632-641`）——**没有路径、没有 id、没有 image block**。
2. 模型说「先看一下你发的截图」(#669)，用 bash 去 `~/.videobuddy/cache/attachments/request-images/` 翻：`find -newermt "-15 minutes" -name "*.png"` **返回空**（#671 只有 `---` 和三个目录名）。
3. 找不到就放宽：`ls -t` + `stat` 按 mtime 排序取第一个（#675 / #680），捞到 `2f/2f36b7…`（85878 bytes，webp 1052×1802）。注意 #681 的时间戳 `21:37:28` 与本次会话 14:35–15:35 对不上，**是历史会话遗留文件**。
4. `read_image` 读出来是「穿白裙的女士 + 10cm 字样」(#686)，模型自己都写「这张图和我正在做的科普片完全无关…可能是误传，也可能来自其他会话」(#689)。

**根因**：附件注入只给名字不给定位信息 + 缓存是全局目录（不按项目/会话隔离） + 模型「找不到就猜」的启发式。为这张图白烧了 4 步（s27–s30）。**修法**：注入文本带上 `requestId` 或已落盘的相对路径/节点 id；若未落卡就明确「不要去缓存目录找」，并在 Host 侧给附件缓存按会话分桶。

### 12.4 Q2 · 贴图不自动落画布是产品决策（REQ-037 / CV-407），不是 bug

`src/client/index.ts:629-641` 注释原话：「2026-11-03 拍板，**反转 2026-09-05 附件自动标参考落卡**」——项目内附件发送时登记进 `lobbyStash` 暂存，用户点画布上方「待落画布」条的「落进画布」才落（`StudioFrame.tsx:2759-2779` / `LOBBY_LAND_STASH_EVENT`）。正文追加占位说明的目的写得很直白：「agent 必须知道附件存在但未落卡，产线要用时先提醒用户点击，不要假装可用」。

首页态不同：`LobbyStashBar.tsx:145` 写着「发送第一句话后自动落进画布」。**两种语义并存**，用户容易混淆。

这次的真实后果：`list_references` 0 次 ⇒ 模型从没查过画布节点，即使你点了「落进画布」它也读不到；而 Q1 的那张图是它绕过正规链路自己猜的。设计意图没错，**接口缺口是「注入文本不给定位信息」**（Q1 根因同源）。

### 13.2 根因（三条叠加，不是单一 bug）

1. **终态业务错误被当成可重试错误**：`CS-USER-ERR` 是通用用户错误码，`recoverability:'guided'`、无 `uiKind` ⇒ 一律回落 `retryable`。但「已落地 / 版本操作冻结」是**一次性终态**，按提示重试没有意义，正确处置是「知道了，去看版本列表」，不是「重试」。
2. **三态错误卡没有 dismiss 出口**：组件从设计上就只有「重试 / 打开设置」两类主行动，缺一个「关闭 / 忽略」。任何非配置类错误都只能靠点一个不该点的按钮来消卡。
3. **全局错误槽被十几个不相关操作共用**：落地、读版本列表、对比、模式切换、画布保存都写同一个 `phase='error'`，错误卡无法知道「我该不该自己消失」，也没有局部提示的通道。

**为什么点「重试」也不算解决**：它只是刷项目列表把 store 清干净，用户以为在重试落地；只要再点一次落地/版本操作（或刷新本身再失败），同一张卡立刻回来。用户要的「关掉」始终不存在。

### 15.2 bash 300s 超时的真根因：`!word` 触发交互 shell 历史展开

`printf 开始标记; eval -- $'…命令…'; …; printf 结束标记`。这个 shell 是 PTY 上的**交互式**
bash，历史展开在**读行时**生效，于是命令体里的 `!m` / `!he` / `!t.fadeFrames` 抛
`event not found`，**整行（含两个标记）被丢弃** ⇒ 工具永远等不到结束标记 ⇒ 到 deadline
超时 + shell 重置，且文件根本没生成。

用真 pty 复现（同一条 397 字节命令，`stty -echo` 前置）：

| 场景 | 开始标记 | 结束标记 | 文件落盘 |
|---|---|---|---|
| 默认（历史展开开） | ✗ | ✗ | ✗ |
| 先 `set +H` | ✓ | ✓ | ✓ |

统计佐证：16 次超时命令**全部**含 `!`+字母；只含 `!==` 的 4 条全部 0.2–0.4s 正常返回。
**与 heredoc 无关** —— 上一条 skill 文案把锅记在 heredoc 上是错的，已改正（§15.3 末尾）。

落地三件：

1. `patches/dsh-tool-bash-persistent@0.2.1-rc.2.patch`：`text: "stty -echo"` →
   `text: "stty -echo; set +H"`（一行）；
2. 根 `package.json` 的 `resolutions` 加该包的 `patch:` 条目（与既有 12 个 dsh 补丁同机制）；
3. `cordis.patch.yml` 的 bash 描述加一条纪律：禁止在命令里写裸 `!word`，改写成
   `x === false` / `x !== true`（**只为兜底**，真修是 1）。

⚠️ 本机 `yarn install` 在 **Fetch 步被沙箱拦死**：
`Brokered host rename source refused by file policy`（补丁包要写全局缓存）⇒ 锁文件未更新、
补丁未自动落位。已把这一行**就地**打进 `dsh-plugin-desktop/node_modules/.../lib/index.js`
（幂等，`yarn install` 成功后由补丁接管），因此**重启即生效**；锁文件更新留给你跑一次
`yarn install`。

## 16. 2026-11-06 19:5x 执行记录：启动链路修通（锁文件 + 启动脚本）

### 16.1 现象

用户跑 `bash start-canvas-studio.sh`，停在「安装 workspace 依赖」：

```
➤ YN0028: The lockfile would have been modified by this install, which is explicitly forbidden.
➤ YN0000: · Failed with errors in 0s 224ms
```

前置的 Resolution 步是**成功的**（打出了 `@deepseek-ai/dsh-tool-bash-persistent@patch:…hash=84dc19`），
所以这不是补丁写错、也不是网络问题。

### 16.2 两个原因，都是真缺陷

1. **锁文件缺 patch entry**。往根 `package.json` 的 `resolutions` 里加一条 patch 后，
   yarn 必须往 `yarn.lock` 补一条 `@patch:` entry（`resolution` + `checksum`，与已有的
   `dsh-token-meter` / `dsh-agent-loop` 等 9 条同形）。`--immutable` 禁止 install 写锁，
   于是校验完直接失败。
2. **启动脚本自相矛盾**（更根本）。脚本进入 install 分支的判据是「清单/锁比安装标记新」，
   而 `--immutable` 又禁止 install 改锁 ⇒ **只有真需要改锁的时候才会走进这个分支，走进来
   就必然失败**，且报错文本完全看不出是锁过期。对一个「一键启动」的开发脚本，这个组合是错的。

### 16.3 修法

- `start-canvas-studio.sh`：`corepack yarn install --immutable` → **`corepack yarn install`**，
  并在原处留注释写明「不能加 `--immutable`」及其后果（锁一致性由 CI 的
  `yarn install --immutable` 把关，开发脚本的职责是自愈）。
- `yarn.lock`：由一次**正常可写安装**重建，+17 行（`@deepseek-ai/dsh-tool-bash-persistent@patch:…
  hash=84dc19…` 的 resolution + checksum）。**不是手抄**：checksum 只能在 Fetch 步算出，
  手写锁无法凭空得出。
- 上一轮 §15 的应急（把 `set +H` 直接打进 `node_modules`）**已被正品取代**，见 16.4 的
  「删目录重建」。
