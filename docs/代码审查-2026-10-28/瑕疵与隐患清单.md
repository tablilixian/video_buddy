### 1.1 安全（P0/P1）

#### CR-01【P0】资产 URL 分支无文件名白名单，可读任意本地文件并上传到外部服务器

- **位置**：`canvas-studio/src/generate.ts:714-716`（解析）、`generate.ts:737-744`（消费）
```ts

  const m = source.match(/\/canvas-studio\/assets\/([^/]+)\/(.+?)(?:\?.*)?$/)
  return m ? { projectId: m[1]!, file: m[2]! } : null
}
...
  const localPath = join(registry.assetsDir(asset.projectId), asset.file)
  if (existsSync(localPath)) {
    const ext = extname(asset.file).replace(/^\./, '') || 'png'
```

- **判断**：`asset.file` 是 `(.+?)` 裸捕获，未经任何字符集/穿越校验——`join()` 会折叠 `..` 段，`/canvas-studio/assets/x/../../../Users/<name>/.ssh/id_rsa` 这样的字符串会逃出资产目录。该字节的直接去向是 `uploadBytesToDrama` → 外部服务器 117.50.108.73，即**本机任意文件外泄**。对照组在同一文件里：`assetKeyFromUrl`（generate.ts:864-867）对同一形态 URL 明确做了 `[A-Za-z0-9._-]+` 白名单并拒绝 `..`；分支 2（绝对路径）有 CR-011 白名单、分支 3（外链）有 SSRF 防护——唯独分支 1 漏配，属于「防护有清单但旁路缺口」。
- **触发**：`upload_image` 的 `imageUrl` 是 agent 可控裸字符串（LLM 误行或被提示词注入诱导即可），无需用户交互。
- **修复**：`parseCanvasAsset` 命中后对 `asset.file` 复用 `assetKeyFromUrl` 同款白名单，或 `resolve` 后强制 `startsWith(base + sep)`。一处改动收口全部分支 1 的调用方。

#### CR-02【P0】`readLocalAssetBytes` 无穿越防护，fal 通道可把任意本地文件 base64 外传

- **位置**：`canvas-studio/src/providers/reference.ts:17-27`
```ts

  registry: ProjectRegistry, projectId: string, file: string,
): Promise<{ bytes: Uint8Array; ext: string }> {
  const localPath = join(registry.assetsDir(projectId), file)
  if (!existsSync(localPath)) throwError('CS-USER-ERR', { message: `本地资产不存在: ${file}` })
  const buffer = await readFile(localPath)
```
- **判断**：`file` 直接进 `join(assetsDir, file)` 读盘，无白名单。上游链路已核实：`resolveRefValue`（host-tools.ts:1277 附近）对非 `@ref`、非 `lib:`、非节点 id 形态的裸值**原样透传**；`video_composite` 传 `filenames: ["../../secret.png"]` 且 provider=fal 时，字节经 `toFalDataUri` base64 内联发往公网 fal 队列。同文件 `promoteAssetFile`（generate.ts:996-998 附近）有 `^[A-Za-z0-9._-]+$` 白名单，此处没有。该函数是 Drama / fal 两条通道共用的读取单点，单点修复即可覆盖全部调用方（generate.ts:2100/2132/2471）。
- **修复**：在 `readLocalAssetBytes` 内做与 `promoteAssetFile` 相同的白名单校验。

#### CR-03【P1】Drama 轮询对 401/403/429 立即硬失败，与「瞬时容忍」契约相反

- **位置**：`canvas-studio/src/providers/drama.ts:264-273`；对照 `canvas-studio/src/generate.ts:417-421`（`dramaJobRequest` 注释）
```ts
      const status = jobStatusOf(snapshot.json)
      if (status === null) {
        if (snapshot.status >= 500 || snapshot.status === 0) return { done: false, stage: '状态查询失败，稍后重试' }
        throwError('CS-NET-010')
      }
```
- **判断**：`dramaJobRequest` 注释明确写「401 会随 status 返回、按既有瞬时错误容忍处理——轮询下一轮自会拿到 client 刷新后重推的新 token」。但 401/403/429 响应体是错误信封（无任务 `status` 字段）→ `jobStatusOf` 返回 null → 不满足 `>=500 || ===0` → 直接抛 `CS-NET-010`，整单判死。且 `markJobAbandoned` 会把台账落成 `cancelled`，而后端任务还在跑——孤儿任务继续占用后端队列/计费，用户产物丢失。注释与实现各自成立、合在一起矛盾，是典型的「两处各写一份必然漂移」。
- **触发**：40 分钟轮询窗口内撞上一次 token 刷新空档（Supabase access token 有效期约 1 小时，属正常时序，非异常场景）。
- **修复**：把 401/403/429 与 5xx/0 同列「本轮未完成」；只有 404 与确定终态才立即失败。

#### CR-04【P1】PNG 解码只限像素不限字节，小文件可把 Host 进程打 OOM

- **位置**：`canvas-studio/src/inspect-image.ts:131-133`（尺寸上限）、`:157-171`（逐行拷贝）、`:181`（RGBA 分配）
```ts
  if (width <= 0 || height <= 0 || width > 20000 || height > 20000) { throwError(...) }
...
    lines.push(line)                       // line = raw.slice(...)，逐行再复制一份
...
  const rgba = new Uint8Array(width * height * 4)
```
- **判断**：只限制像素尺寸（20000×20000），不限解码后字节数。RGBA8 下 `rgba` 即 1.6GB，`lines` 经 `raw.slice` 又是一份，加 inflate 出的 raw ≈ 3GB+。PNG zlib 对纯色行压缩比可达约 1000:1，一个约 2MB 的 PNG（远低于 16MB 上传限额）即可通过全部现有校验后在解码阶段耗尽内存——Host 是单进程承载全部项目的，OOM 波及所有会话。
- **触发**：上传/引入一张高压缩比大尺寸 PNG 后调用 `inspect_image` 或任何走 `decodePng` 的分析。
- **修复**：IHDR 解析后按 `width*height*4` 设解码上限（如 256MB）直接拒收；`lines` 改存 `raw` 的子视图而非 slice 拷贝。

#### CR-06【P1·桌面】更新安装包无签名/哈希校验，下载即执行

- **位置**：`dsh-plugin-desktop/src/update-download.ts:419-451`（仅魔数校验）；执行点 `electron-runtime.ts:753-762`

#### CR-07【P2】素材核对 fail-closed 只覆盖 video/image 轨，音频/字体缺失静默出片

- **位置**：`canvas-studio/src/remotion/asset-check.ts:144-152`

#### CR-33 Look 预算 check-then-charge 非原子

#### CR-35 波形音频白名单缺 `.opus`

`waveform-host.ts:40` 的 `AUDIO_EXTENSIONS` 与 `media-extension.ts:33` 的统一上传白名单脱节：`.opus` 能入库、能播放，波形接口按自己的白名单拒绝 → 客户端静默退回确定性假波形。`asset-history.ts:70` 的 kind 表同样缺 `.opus`。改由 `MEDIA_EXTENSIONS.audio` 派生（单点事实源）。

#### CR-36 分组展开残留 `group: undefined` 键，触发伪「契约外字段」告警

`remotion/groups.ts:121,126`：`{ ...track, group: undefined }` 保留键名；`warnUnknownKeys` 按 `Object.keys` 扫描不看值。宿主管线先 expand 后 validate，于是每份用分组的 manifest 都收到「含契约外字段 groups/group（已忽略）」——而分组实际已生效，模型会误判能力失效反复改写。改用 `delete` 摘键（normalize-timing.ts:152-153 对 `startAfter` 就是这么做的）。

#### CR-37 asset-gc 模块头注释与实现漂移，在途生成竞态失去免疫

`asset-gc.ts:5-13` 头注释仍完整描述两段式 trash 及其「undo / 粘贴共享 / 生成中引用三个竞态全部免疫」；实现（`:92-104`）按 BUG-005 拍板（2026-10-03 批 F）已改物理删除，仅靠保存时刻的引用集合判定。用户删节点与 agent 对同源产物做节点级重试并发时，文件被先删、随后落盘的节点 URL 悬空。至少更新头注释；对在途生成可按 history 未删条目暂缓物理删一拍。

#### CR-38 `text-fix-trigger.ts` 是生产无人 import 的第二份实现

`text-fix-trigger.ts` 头注自称「skill 文档与 host-tools 侧自动触发共用」，但 host-tools 实际 import 的是 `./text-detection.js`（全 src 检索确认无引用）。两份 `shouldAutoFixText` 算法不同（配对引号+否定词豁免 vs 任意引号字符集正则），同一 prompt 两边判定可不同。删除或明确降级 deprecated 并互指。

#### CR-39 OAuth loopback 无 Host 校验、无 state；`/auth/pending` 轮询即消费

`auth-loopback.ts:74-86`：回调 handler 只认路径不认 Host 头；端到端无 `state` 校验（PKCE 兜住了账号置换，但没兜住 DoS 与本机信任面）：本机任意进程/页面可向 `/callback?error=...` 注入失败掐断登录，或直接 GET `/auth/pending`（routes.ts:3408-3411，无 `mutationAllowed` 校验）抢走含授权码的回调 URL；多窗口场景第二个窗口也会取走第一个窗口的回调。修复：授权请求带随机 `state` 并校验；handler 校验 Host 必须为 `127.0.0.1:<port>`；pending 回调绑定一次性 token。

#### CR-40 余额卡登出竞态：旧账号余额写回视图

`client/credits-store.ts:51-66` 与 `:85-92`：`resetCredits()` 清视图但不取消/作废在飞请求；登出后请求返回时 `emit({ view, ... })` 用旧账号余额覆盖刚清空的 state，在「登出 → 未重新登录」窗口内显示上一账号的钱，与 Host 侧 `notifyAuthCleared` 的隐私注释相悖。模块级 epoch 计数，emit 前比对丢弃过期结果。

#### CR-41 bootstrap 在飞时静默丢弃新 token 推送

`account-state.ts:180`：`if (bootstrapInFlight !== null) return` 与注释「进行中复用同一 Promise」不符——实际是直接 return，在飞期间推来的 TOKEN_REFRESHED 新 token 既不发布网关凭据也不记录；若那是最后一次推送，Host 持旧 token 打 Drama 直到 401 自愈链再次触发。在飞时记 pending token，bootstrap 结束后补跑。

#### CR-42 覆盖导入「先 trash 后写」，新写失败时活动目录里 skill 已消失

`user-skills.ts:280-299`：覆盖路径先把旧版 rename 进 `.trash`，再写 incoming、再 rename 落位；第二步之后任何失败只清 incoming，旧版留在回收站而活动目录里这个 skill 已不存在，UI 无恢复引导。失败分支把 `.trash` 旧版 rename 回来；或改成「先写 incoming 成功后再 trash + rename」。

#### CR-43 导出面转义缺口：`detail` 不转义 + `fact.source` 无 scheme 白名单

`storyboard-render.ts:952-956`：通用提示页 `<p>${detail}</p>` 未转义（为 corrupt 页的 `<br/><code>` 留的口子，当前调用点安全，但这是 export 的通用入口，无护栏）；`:247-250`：`fact.source`（agent 可控）直接入 `href`，escapeHtml 拦不住危险 scheme。修法：拆 `detailHtml`/`detail` 两个明确参数；source 校验 `http(s)://` 前缀否则只渲染纯文本。

#### CR-44 auto 模式「绑镜出图」不受拦（代码自认已知边界，无补偿闸）

`approval-gate.ts:152-153,167-171`：`mode !== 'confirm'` 短路放行在先，绑镜出图的旁路拦截在其后——auto 模式 + 故事板未落地时 `image_generate` 带 `shotRefs` 不会被拦。注释明写「彻底收敛属下一批」但至今未收。把这条旁路拦截迁进 `withStoryboardGate`（那里已有 toolName 名单，可对 image 家族加 shotBound 参数探测）。

## 二、dsh-plugin-desktop（桌面壳）

P0/P1/P2 级见 CR-06/CR-19~22/CR-45 等（CR-06 更新签名、CR-19~20 LAN 面、CR-21 重定向、CR-22 进程树）。以下为 P3。

#### CR-45 更新检查/下载失败完全静默

`update-lifecycle.ts:205-209`：`catch {}` 注释自述「deliberately silent」。用户点「检查更新」→确认下载→保存对话框之后任何失败（断网、磁盘满）都无提示无日志，感知为「点了没反应」。至少 `adapter.notify` 一条失败通知 + `logger.error`。

#### CR-46 LAN 地址取第一个非内部 IPv4，可能绑到 VPN/虚拟网卡

`desktop-network.ts:85-94`：按 OS 枚举顺序取 `addresses[0]`；开 VPN/虚拟化（Tailscale/WSL/Hyper-V）时可能绑到不可达或不应暴露的接口，「局域网地址」打不开或服务暴露到 VPN 网段。按默认路由接口优选，或 UI 展示所选 IP 让用户确认。

#### CR-47 `writeHeader` 不经过 maskSecrets

`log-files.ts:99-105`：`write()` 逐行打码而 `writeHeader()` 直写。当前唯一调用点内容是版本/平台/时间戳（非现行漏洞），但这是文件日志公共入口，未来传动态串会绕过全部脱敏。一行修复：同样调用 `maskSecrets`。

#### CR-48 ui-locale 未验证枚举即 `as DesktopLocale` 透传

`index.ts:374-377`：settings.yaml（用户可编辑、且被纳入 checkpoint）里任意字符串都会成为 `runtime.currentLocale`；同文件对 shell mode 有显式校验的先例，此处缺失。加 `'zh' | 'en'` 白名单过滤。

#### CR-49 被信号杀死返回裸 128

`bin.ts:97-99`：`resolveExit(code ?? (signal === null ? 1 : 128))`——惯例是 `128 + 信号编号`，裸 128 吞掉具体信号，影响外层包装脚本的退出码判断。`128 + Os.constants.Signals[signal]`。

#### CR-50 checkpoint restore 原样写回 manifest 中的 mode

`profile-checkpoint.ts:495-500` 与 `:659`：manifest 只校验 `0 <= mode <= 0o777`，未排除退化值；损坏/被篡改的 manifest 可把 `settings.yaml` 恢复成 0o000，之后所有槽位读失败，恢复机制自锁（userData 0700 之下无攻击面，属自愈能力缺陷）。restore 时仅保留 owner 位并强制最低 0o600。

#### CR-51 端口重试依赖对上游私有字段的结构猜测

`webserver.ts:19-27`：`closeFailedServer` 通过 `(instance as { server?: ... })?.server` 访问上游 WebServer 私有字段；上游一旦重命名即静默变 no-op，绑定失败旧 server 占住原端口，32 次重试的端口选择从此失真。在上游暴露受保护的 close 句柄或改用显式 unref 方案。

#### CR-52【P2】无键抓取通道明示不做私网/SSRF 防护，可把本机数据读进模型上下文

- **位置**：`dsh-web-search-hybrid/src/provider.ts:170-176`
```ts
 * Keyless HTTP(S) retrieval. Compact port of the upstream `web-fetch-http`
 * provider: http(s) URLs only, same-origin redirects under a hop cap, one
 * combined timeout, byte-capped body read, and html/text classification.
 * Requests carry no browser cookies or ambient credentials; private-network and
 * SSRF protection is not implemented, matching the upstream provider's stance.
```
- **判断**：`httpFetch` 是注册进 `ctx.web`、模型可直接调用的抓取工具，允许 `http:`，注释自述「private-network and SSRF protection is not implemented」。同仓 canvas-studio 的 `assertSafeDownloadUrl`（generate.ts:490 起）已有现成的 BlockList 防护（环回/私网/链路本地/云元数据），这里没有——同一仓库两套纪律。具体后果：agent（或被注入的提示词）可让 Host 抓 `http://127.0.0.1:<webserver-port>/...` 读会话/资产数据（GET 路由对 loopback 可读），或抓 `http://169.254.169.254/...` 云元数据，结果直接进模型上下文。抓取结果体量有 5MB 上限，但上限不是防护。

- **位置**：`AGENTS.md`（「dsh-community-market/ … Until its runtime is implemented, it remains a private documentation scaffold and must not declare loadable DSH or package entry points」）；对照 `dsh-community-market/src/index.ts:19-23` 与 `dsh-plugin-desktop/src/desktop-market.ts:28-39`

## 复核为「做得对」的方面（抽样）

审查不是只挑刺，以下防护点经查确实成立，后续改动不应回退：

- **资产服务路由的穿越防护**（routes.ts:1132-1135）：段数校验 + `startsWith(base + sep)` 双重挡住 `..` 与编码变体——与 CR-01/CR-02 的两个未设防入口是不同代码路径。
- **preload 暴露面**（preload.ts）：仅 `getPathForFile`，无 ipcRenderer 透传；窗口全部 sandbox + contextIsolation + nodeIntegration:false。
- **私有路由三重校验**：settings 类路由 Host + Origin + socket loopback 三重校验（CR-20 指出的是两条未对齐的路由）。
- **keyed-queue 防重入死锁**（keyed-queue.ts）：AsyncLocalStorage 检出同 key 重入并抛错；生成队列「等待中取消必须出队 + finally 释放 + pump 推进」语义完整。
- **SSRF / 下载纪律主体到位**：`assertSafeDownloadUrl` 覆盖环回/私网/链路本地/云元数据；`downloadBytes` 有超时+字节上限（缺口在旁路，见 CR-17/CR-25）。
- **日志脱敏**（mask-secrets.ts）对 URL/Cookie/Authorization/命名密钥/长 token 覆盖良好（缺口仅 CR-47）。
