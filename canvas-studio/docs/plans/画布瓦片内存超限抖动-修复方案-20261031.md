# 画布瓦片内存超限抖动 · 修复方案（2026-10-31）

> 议题来源：真机日志 `ERROR:cc/tiles/tile_manager.cc:1013 WARNING: tile memory limits exceeded,
> some content may not draw`——节点较多时拖动/缩放刷屏（成对出现、间隔 ≈16ms），画布同步抖动。
>
> 状态：**已拍板（2026-10-31），可开工**。全部根因结论已对照代码逐条验证（file:line 可点）；
> D-01 ~ D-06 六条已按建议项拍定（§八），开工前置清单见 §七 开头。

---

## 一、结论（先看这段）

1. **这条日志不是 bug，是 Chromium 合成器的瓦片光栅内存预算告警。** Chromium 把每个合成层
   切成 256×256 瓦片（tile）在 GPU 上光栅化，每帧有一个内存预算（按视口 / DPR / 可用 GPU
   内存动态算出）。当前帧需要光栅化的瓦片总量超过预算时，多余的瓦片被丢弃——"some content
   may not draw" 就是字面意思：这一帧有些内容不画了，等下一轮补画。**画布上内容一块块闪没
   又闪现，就是"抖动"的全部来源。**
2. **日志成对、间隔 ≈16ms** = pending 树与 active 树每帧各报一次 ⇒ 拖缩期间**每一帧都在
   超限**。这是持续性光栅抖动（thrash：这帧挤掉的瓦片下帧又要），不是偶发。
3. 代码侧是**四个结构选择叠加**，全部已在代码里验证：
   - ① **每个节点一个常驻合成层**（双重强制：`.csNode { will-change: transform }` +
     节点定位用 `translate3d`）——节点多时就是 N 个层，每层各带一套瓦片；
   - ② **节点无视口裁剪 + 媒体原图直出**——所有节点全部挂载，`<img>` 直接吃生成产物原图；
   - ③ **拖拽/缩放每帧重设 transform，且 pointermove 无 rAF 合并**——缩放时每个可见节点层
     的光栅刻度（raster scale）都变了，每帧全员重光栅；触控板 pointermove 频率可高于帧率，
     每次都写 store + 重渲一遍；
   - ④ **Retina 2x + 缩放上限 5**——瓦片像素量 ×4，放大到 5x 时同样视口要光栅 25 倍像素。
4. **缩放比拖动更凶的机制**：平移只是"视口扫过新瓦片"；缩放是"全员重光栅"——每个可见
   节点层都要按新刻度重新光栅一遍，而旧刻度的瓦片还没释放，瞬时内存需求近似翻倍。

## 二、机制（Chromium 侧，30 秒版）

```
合成层（composited layer） ──切成──▶ 瓦片（256×256） ──光栅化──▶ GPU 纹理
                                                        ▲
                              每帧预算（视口×DPR×GPU 策略）┘
超预算 → 丢瓦片 → 该处内容本帧空白（checkerboard）→ 补画 → 闪现 = 抖动
```

- 瓦片只在需要时光栅化：初次可见、或层内容/刻度变化后。**拖动** = 视口边缘持续要新瓦片；
  **缩放** = 所有可见层的理想光栅刻度变化 → 全员重光栅。
- 预算是动态的（GPU 内存管理器按可见性/遮挡分账），但量级有限。按 1512×982 @2x 估算：
  一个满视口层的一套瓦片 ≈ 3024×1964×4B ≈ **24 MB**。200 个节点层即使每层只光栅可见部分，
  叠加缩放期"新刻度 + 旧刻度"两套并存，轻松越过几十~一两百 MB 量级的预算
  （此为量级估算，真机以 §六探针实测为准，不作为验收数值）。
- 被丢的瓦片按优先级补画 ⇒ 内容"块状闪现"，视觉上 = 抖动/闪烁；若同时触发主线程光栅
  兜底，还会叠加掉帧。

## 四、修法（按性价比排序）

> 总原则：**把"每节点一个层"收敛成"世界层一个层"**，把"全员常挂"收敛成"视口内才参与"，
> 把"每 move 一渲"收敛成"每帧一渲"。不换渲染架构（不上 Canvas2D/WebGL），不动数据模型，
> 不动 Host API。

### P0-1 节点去常驻合成层，拖拽中才提升（收益最大）

- **改法**：
  1. `styles.ts:2016` 删除 `.csNode { will-change: transform }`（净 -1 行，棘轮只减不增）；
  2. `CanvasNode.tsx:624` 静态定位 `translate3d(x, y, 0)` → `translate(x, y)`
     （2D transform 不强制提升层，节点画进世界层的瓦片里）；
  3. 新增拖拽态类 `.csNodeDragging { will-change: transform }`（新 CSS 进新文件
     `src/client/styles-canvas-perf.ts`——`styles.ts` 棘轮 10731 只准减，先例
     `styles-audio.ts`）；被拖节点（`primaryDragId` / `spotDragIds`，CanvasSurface.tsx:433/441
     已有现成手势态）在拖拽期间挂该类，松手摘除。拖拽中该节点独立成层、逐帧只动自己；
     **接线约束：拖拽类只挂被拖节点**（与 `csNodePrimary` 同语义）。CV-186 的历史教训
     要守住：禁止画布级 `data-dragging` 全员压暗那类写法（styles.ts:2289 历史注释已废该路，
     压暗只走血缘聚光档位）；
  4. 例外核实：resize / 多选 / 托盘代理 / 瀑布流只读手势走同一类。
- **为什么不是只删 `will-change`**：见 §三.1b——`translate3d` 本身就强制提升，两个都要动。
- **预期收益**：合成层数 N+1 → ≈2；缩放重光栅从"每个可见节点层各一套"降到"世界层一套
  视口瓦片"。
- **风险**：CR-081 的回归面——静态位移（snap 吸附、瀑布流重排、撤销回放）从合成路径回到
  普通绘制路径，位移面积小、paint 代价可控，但必须在 §六.T3 回归清单里逐项过。
- **回滚**：纯样式 + 一处 transform 写法，单 commit revert。

### P0-2 手势事件 rAF 合并

- **改法**：`CanvasSurface.tsx` 四个 pointermove 分支（node-drag / resize / pan / link）+
  wheel 缩放，事件坐标先落 `pendingRef`，`requestAnimationFrame` 每帧最多消费一次
  （合并不是节流：最后一帧的坐标必须入账，松手前 flush 一次）。
- **预期收益**：触控板高频 move 下 store 写与重渲次数从 >60/s 收敛到每帧 ≤1 次；
  与 P0-1 叠加后，拖缩期间的每帧工作量稳定可见。
- **风险**：低。语义不变（只合并时序）；需守卫"松手最后一帧坐标不丢"（§六.T1 反向变异）。
- **回滚**：单 commit revert。

### P0-3 节点视口裁剪（主案 A，兜底 B）

- **主案 A：`content-visibility: auto`**——`.csNode` 加
  `content-visibility: auto; contain-intrinsic-size: <width> <height>`（inline style 已有
  `node.width/height`，CanvasNode.tsx:626-627，精确值直填）。DOM/选中态/媒体状态不丢，
  浏览器自动跳过离屏渲染与光栅。
- **兜底 B：React 条件挂载**——若 A 在 transform 缩放容器内实测异常（**已登记为风险**，
  content-visibility 的可见性判定与合成器交互存在实现差异），则复用连线裁剪口径
  （`EDGE_CULL_MARGIN_PX`，CanvasSurface.tsx:1229-1241）做视口 ± margin 挂载，视口外挂
  占位骨架。B 的代价：img 重载闪现、框选/连线跨视口语义需适配——所以 A 可用时不用 B。
- **裁剪矩形计算抽纯函数**进 `canvas-math.ts`（先例：`canvas-math.ts` 即纯函数 + 单测形态），
  供单测与 T1 守卫。
- **预期收益**：视口外节点完全不参与光栅调度；配合 P0-1，预算消耗 ≈ 视口内容一份。
- **回滚**：A 是一行 CSS 属性；B 是条件渲染，revert 即回全量挂载。

### P1-4 媒体缩略图（**先不做，看 P0 探针数据再拍板**——D-03）

- 现状：节点按自然像素显示（CV-284 是拍过的产品决策），缩略图必然引入 zoom ≥ 1 的画质
  损失；且 Chromium 本身有 decode-to-scale（按绘制尺寸降采样解码），缩小视图下原图解码
  成本已被部分缓解。
- 结论：**P0 三件套之后大概率不再需要**。若探针数据显示纹理内存仍是瓶颈（放大到高倍 +
  视口内大图很多时），再启动：生成侧出长边 ≤2048 缩略图、节点卡吃缩略图、原图留给
  `ImageZoomModal`（`ImageZoomModal.tsx:208` 已有全分辨率查看链路）。

### P2-5 背景网格重绘收敛（可选，顺手做）

- `CanvasSurface.tsx:1400-1403` 的 `backgroundPosition/backgroundSize` 每帧变 ⇒ 视口背景
  每帧重绘。点阵网格绘制便宜，收益小；若做完 P0 后探针显示 paint 仍高频，把网格改画进
  世界层或 Canvas 再说。不单独立项。

### P2-6 Electron GPU 内存开关（诊断实验先行，是否落包拍板——D-04）

- `app.commandLine.appendSwitch('force-gpu-mem-available-mb', '1024')` 抬高 GPU 内存管理器
  预算。**只用于诊断**：真机实验时若加了开关告警即消失，则实锤"预算超限"机制；
  是否落包影响全客户端 GPU 策略（超出 canvas-studio 边界，涉及 `dsh-plugin-desktop` 主进程），
  现有代码无任何 `appendSwitch` 先例（已核实），**不建议默认落包**。

## 六、验收方法（三层）

### T1 自动门禁（每批必过）

1. 既有链路全绿：`yarn run check`（typecheck 双 tsconfig + build + verify:loader + test:smoke），
   门禁 0 新增红。
2. 新增守卫测试（`tests/`，走 `node --test`）：
   - **G1 静态守卫**：断言 `styles.ts` 与 `styles-canvas-perf.ts` 中不存在作用于 `.csNode`
     的无条件 `will-change`（防止回填）；存在即红。
   - **G2 裁剪纯函数单测**：视口矩形反算（world = (screen − view)/scale）、margin 换算
     （`MARGIN_PX / scale`）、节点相交判定——边界用例：恰好在 margin 边缘、scale 极小
     （0.1）时 margin 膨胀、空画布。
   - **G3 rAF 合并时序单测**：模拟 N 次 move + 1 次 rAF tick ⇒ 恰好消费 1 次、坐标 = 最后
     一次；松手 flush ⇒ 最后坐标入账（反向变异 M1：拆掉 flush ⇒ 红）。
3. 反向变异 ≥2 条（仓库惯例）：M1 = 把 `.csNode` 的 `will-change` 加回去 ⇒ G1 红；
   M2 = 拆掉裁剪矩形的 margin ⇒ G2 红。

## 十、复现方式（改前基线）

1. 真机起客户端，画布铺 ≥100 节点（含大量图片节点，用真实产物图）；
2. 缩放到 0.3x 左右，按住触控板连续拖拽平移 / 双指缩放 10~30s；
3. 终端日志出现成对刷屏的 `tile memory limits exceeded`，画布出现块状闪现（抖动）；
4. `grep -c "tile memory limits exceeded"` 记为改前基线（T2 对比用）。

### 批 2（同日真机迭代，2026-10-31）

### 批 3（真机迭代：10% 边界抖动定性，2026-10-31）

**现象**：拖动已好；缩到 10%（MIN_VIEW_SCALE）附近抖动严重，**画布外的壳层（顶栏/左侧竖条）一起抖**；放大过 ~10.5% 即停（0.100~0.105 标签四舍五入恒显 10%，纯显示口径）。**定性**：瓦片预算页面共享，10% 时整个世界可见、世界层光栅需求最大，壳层瓦片被连坐逐出 = 壳层抖动——世界层在低倍率下需求爆炸是主因。

**头号嫌疑与本批修法**：`.csCanvasLayer` 的 `will-change: transform` 会被 cc 当「随时可能启动动画」的信号，低倍率下光栅刻度钉在高处（本应 0.2）→ 瓦片需求爆炸。批 3 把世界层提升通道改走 **translate3d**（3D 变换同样强制成层，平移仍是纯合成更新），will-change 通道关死；G1-② 改写钉住。**这是实验性修法（假设明确、零风险、可逆）**——若批 3 后 10% 仍抖，嫌疑顺延：D-04 预算开关 → D-03 缩略图 → P2-5 背景网格。棘轮 10734 / 1752（func 1371）。
