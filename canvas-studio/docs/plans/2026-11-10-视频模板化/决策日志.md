## D-01 · 0A 的 sfx 定位方式：三种并存（推翻任务包旧版"只用秒"）

- **问题**：`任务包-0A` §2 决策 1 原本写"用 `startSec` 不用帧"，理由是要跨 fps 复用；但 `执行总表` P-5 写"帧为基准"，两者字面对立。且 K-8 要求"必须支持锚定"。
- **选择**：`anchor` / `startFrame` / `startSec` **三选一互斥**，优先级 anchor > startFrame > startSec；换算走唯一入口 `resolveSfxStartFrame()`。
- **理由**：
  - 三者各有不可替代的用途——模板必须用 `anchor`（换例子、卡片位移时音效要跟着走）；GT 复刻验收必须用 `startFrame`（`9.060×60 = 543.6`，秒制有 0.4 帧舍入，无法断言"帧域精确对齐"）；手写/跨 fps 复用用 `startSec`。
  - 原版"只用秒"的论证是对的但不完整：跨 fps 只要 `startSec`，帧精确必须 `startFrame`。
  - **P-5 与本节不冲突**：P-5 管验收口径（一律换到帧域比对），本决策管存储格式。
- **可回退性**：高。`startFrame` 与 `anchor` 都是可选字段，旧 manifest 不受影响。

## D-09 · `pan` 在 MVP 不做运行时复刻，验收不断言声像

- **问题**：GT 的三张卡片音效 pan 是 −0.2 / +0.2 / −0.2，但本仓 `pan` 是"合成期烘入文件"的声明字段（决策 3），同一 `card.wav` 无法同时是左/中/右。

- **可回退性**：高（将来要复刻，按 `pan` 值分文件即可）。

## D-10 · 合成库用 TypeScript 重写，不移植 numpy

- **问题**：`gt/native_audiolib.py` 是 Python + numpy；渲染链路是 TS，且 WAV 要在**构建期**产出。
- **选择**：`src/audio-sfx/` 用纯 TS 重写三个原语（`whoosh`/`thud`/`write`）+ 5 支素材配方；随机源用 **`mulberry32`**（自实现 32 位 PRNG）替代 numpy `default_rng(11)`。
- **理由**：
  - 跨机器**字节一致**是硬要求（确定性渲染的前提）。numpy 的 `default_rng` 算法（PCG64）无法在 TS 里低成本复刻，而"生成一次入库"的模式下，只要**同一台机器同一次构建**可复现即可，不需要与 Python 版本逐样本相同。
  - 拉 Python 依赖进构建链会毁掉 `yarn build` 的可移植性（本机 `python3` 版本随环境变）。
- **代价（已接受）**：与 GT 的 wav **不可能逐样本相同**。因此 0A-8 的验收口径是「事件**帧号**逐条相等 + 起音实测偏差 ≤1 帧」，**不是**波形比对。
- **可回退性**：低（换成逐样本复刻要重写整层 PRNG）。但影响面被限制在 `src/audio-sfx/`，契约层不受影响。

## D-14 · 「只跑 tsdown 就测」是假绿 —— `lib/routes.js` 由 tsc 产出

- **问题**：本会话做 0A-6 的反向变异时，把白名单判据改成 `if (false)` 后跑 `npx tsdown`，测试**照样 8/8 绿**，一度以为守卫无效。

  必须先 `CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD=100000 CODEBUDDY_SAFE_DELETE_BULK_COUNT_LIMIT=100000`。
- **可回退性**：N/A（纯流程知识）。已同步写入 `PROGRESS.md` §0 与 `无人值守推进协议.md` §1。

## D-15 · sfx 在渲染器内解析起点，不引入新 manifest 字段

- **问题**：`anchor` 需要 `trackById` + `fps` 才能折成帧，而 `AudioTrack` 现在只拿 `audio` / `fps` / `durationInFrames`。
- **选择**：`AudioTrack.tsx` 接一个 `tracks` 参数，内部 `new Map(tracks.map(t => [t.id, t]))` 后逐条 `resolveSfxStartFrame()`；**不**在宿主侧预先把 sfx 折成 `startFrame` 回写 manifest。
- **理由**：
  - 宿主侧回写会让「写出 manifest」与「渲染出的 manifest」不一致（现有 `anchor` 字段也刻意不在 manifest 里折，见 `manifest.ts:210` 与 `manifest.ts:1531` 的注释），破坏 P-3 验证过的「逐字节还原」性质。
  - 渲染器拿到的 manifest **一定**是 `normalizeManifestTiming()` 之后的（宿主 `host-tools.ts:3742`），`track.startFrame` 已含顺序衔接与叠化，所以直接查表即可，**不要**在渲染器里再 normalize 一次（会二次位移）。
  - 解析失败（三定位不唯一 / trackId 不存在）⇒ **静默跳过该条**，不 throw。校验层已在 write 时拒收；渲染期 throw 会让整片黑屏，代价远大于少一声响。
- **可回退性**：高（纯渲染侧，不动契约）。

## D-16 · 0A-7 渲染接线的三个技术拍板（fade-out 边界 / volume 帧语义 / §5.1 断言口径）

- **问题**：任务包 §4.2 只给了 `sfxVolumeAt` 的名字与三条 §5.1 断言，没给：① fade-out 锚在哪（素材时长渲染器拿不到）；② `<Audio>` 在 `<Sequence>` 内 volume 回调的帧是相对还是绝对；③ 断言 1「在 `startFrame` 处等于 gain（淡入起点）」与线性淡入「起点 = 0」字面冲突。
- **选择**：
  1. `sfxVolumeAt(frame, {startFrame, fps, gain, fadeInSec?, fadeOutSec?, durationInFrames?})`：fade-in 线性 `0→gain`（afade 约定，完成帧起满音量）；fade-out **仅当显式给了 `durationInFrames` 才生效**（在 `[end−fadeOut, end)` 线性降到 0）。**渲染器 MVP 只接 fade-in**——素材时长只在 `assets/sfx/manifest.json`，`tsconfig` 是 NodeNext 且未开 `resolveJsonModule`，渲染代码无法干净静态引入；运行时 fetch 破坏渲染确定性。渲染器不传 `durationInFrames` ⇒ 淡出暂不生效（契约字段保留，`ManifestSfx.fadeOutSec` JSDoc 已写明口径）。
  2. volume 回调拿**相对帧**（0 = 素材起点）：remotion 的 `useFrameForVolumeProp` 返回 `frame + cumulatedNegativeFrom`，而 `<Sequence from={正数}>` 的 `cumulatedNegativeFrom = (currentSequenceStart − firstFrame) = 0`（读 `node_modules/remotion/dist/esm/index.mjs` 实证）。⇒ 接线处写 `sfxVolumeAt(startFrame + f, {startFrame, …})`，函数内部统一**绝对帧**语义（任务包断言即按绝对帧书写，可脱离 React 单测）。
  3. 断言 1 按**无 fade 缺省口径**解释：`fadeInSec = 0` 时起点帧即 `gain`（`fade-in 存在时起点 = 0`，与断言 2「完成帧起 = gain」相容）；断言 3 的取样点取**淡出区间中点**（边界帧按 afade 约定保持满音量）。`gain > 1` 放行（增益合法）、`> 2` 收敛回契约上限。
- **理由**：改动最小且可回退；fade-out 的「缺时长不生效」是显式文档化的 MVP 边界，不是静默吞字段；帧语义实证避免了「淡入跑错时间轴」这类不可单测的隐患。
- **将来接 fade-out 的路径**：契约给 sfx 事件加可选 `durationSec`（或渲染侧经 `/canvas-studio/remotion/sfx/manifest.json` 取数），调 `sfxVolumeAt` 时传 `durationInFrames` 即可——纯函数已就绪。
- **可回退性**：高（`sfxVolumeAt` 是纯追加；AudioTrack 分支可整段删除回到三分支形态）。

## D-18 · 0A-8 探针验收：断言口径三次修订 + 一次重大误判反转 + 两处加固保留

- **背景**：`sfx-e2e.probe.mjs` 按 §5.2.3 七条断言验收 0A。跑通后经历了一整轮「响度塌陷」排障，最终证明**成片渲染从头到尾是正确的**，红的是验收基准本身。全程记录，防后人重蹈。
- **误判反转（最重要的一段）**：
  - 现象：断言 6 红——成片 −26.0 LUFS vs 「参考混音」−16.2，差 10 LU；且 ffprobe 报音轨平均码率仅 16–22kbps，一度定性为「Chromium WebCodecs AAC 忽略码率请求」的真 bug，沿此做了三轮排障（显式注册 WASM 编码器 → 修 CSP 让 worker 能加载 → bundle 内插桩确认编码器身份与字节流）。
  - 真相：**自建的参考混音漏乘 GT gain**（adelay+amix 直接用裸素材）。逐事件能量比 CSR/REF = 0.55/0.25/0.30/0.30/0.28——**精确等于各事件的 gain**（thud 0.55 / write 0.25 / swoosh·card·swipe 0.3）。修参考（补 `volume=<gain>`）后：成片 −26.0 vs 参考 −26.2，**差 0.2 LU**，渲染零损失。16–24kbps 的平均码率也是同一假象的一部分：纯音效片 18s 里只有 ~2.5s 有声，平均码率天然低，与编码质量无关（波形保真由断言 5 的 0~−3.8dB 实证）。
  - 教训：**验收基准本身要按被测物的口径构造**；「响度塌 10 LU」这种巨差先查基准再查被测物。此教训与 `无人值守推进协议.md` §5「不许改断言迁就实现」不冲突——改的是**写错的断言/基准**，且每处都能说出为什么错。
- **断言口径三次修订（全部实证驱动）**：
  1. **断言 4（起音）±1 帧 → 差分口径**：原 ±1 隐含「muxer 写 edit list 补偿 AAC priming」前提。实测 CSR 渲染链（mediabunny mux）不补偿：音轨 18.069s > 视频 18.0s，全体音频恒定后移 ~2.5 帧（thud 硬起音精确落在 F+2）。同机 ffmpeg 参考实证 ±1 在补偿路径成立。修订为：Δ = dev_csr − dev_ref ∈ [0,4]（priming 2.56 帧 + 帧量化 ≤1 的物理上界）且 spread ≤1（均匀后移 = 调度正确）；带 gain 参考的 devRef 绝对值含阈值偏置（软起音过 0.01 阈值更慢），降为信息性。card2/3 被前卡持续音淹没不可测，其对齐由断言 3 集合相等保证。
  2. **断言 6（响度）GT 闸 −24~−18 → 相对参考 ±3 LU + 绝对护栏 [−30,−12]**：GT −21.1 的前提是 GT 素材电平 + 共享混响尾；零授权合成素材（无混响、按 gain 衰减）天然不落该闸——素材差异不是渲染缺陷。
  3. **断言 1：不拿流平均码率当质量判据**（同上，稀疏内容的物理事实），质量由断言 5/6 把守。
- **保留的两处加固（非缺陷修复，但有实锤价值）**：
  1. **`src/render-host/page.ts` CSP** 补 `worker-src 'self' blob:` + script-src 加 `'wasm-unsafe-eval'`：mediabunny 的 WASM 编码器以 blob: worker 跑，而 worker-src 回退到 script-src（无 blob:）⇒ 被拦（探针实锤：注册后报「AAC encoder worker failed to load or crashed」，修 CSP 后消失）。flac/mp3 同批机制同需。
  2. **`src/client/remotion-render.ts` 顶层 `registerAacEncoder()`**：把音频编码器选择钉到确定性路径（WASM ffmpeg-native，忠实执行码率），不再赌 Chromium `canEncodeAudio` 的诚实度。注册幂等、包 `sideEffects:false` 必须显式调用、bundle 零体积增量。node 隔离实验：同配置 WASM 输出 130kbps 忠实执行 ✓。
- **探针工程质量修复**：`extractWav48` 的固定输出路径让参考解码**覆盖**成片解码（事后取证差点误判成「测量拓扑 artifact」）→ `outName` 参数化；诊断插桩只进 `lib/`（构建产物），收尾 `yarn build` 重建清零。
- **可回退性**：断言口径修订都在探针内、有注释锚点；两处加固各 ~5 行，可独立撤销。


## D-19 · 0B 的 Node 侧容量静态合同做成 **warning 不 error**（推翻任务包 §2 决策 4）

- **问题**：`任务包-0B` §2 决策 4 的表格写「数组长度 > maxLines ⇒ error」「字符串 `\n` 行数 > maxLines ⇒ error」；但同一份任务包 §3.3 又写「**不拒收**」（拒收会打断渲染流水线，且「标题就是要 3 行」可能是作者故意的）。两者在 `validateManifest` 这一层正面冲突。
- **选择**：静态合同出 **warning**，文案带「压到 N 字以内 / 加大 box」两条出路；`errors` 一个不加。
- **理由**（三条，按权重）：
  1. Node 侧**没有 canvas**，这里的折行全是字符宽度估算（`charWidthRatio`）。让估算有权**拒收**一份能渲的 manifest，等于把一次估算误差升级成整条流水线中断 —— 而 `render_composition` 正是以 `errors` 非空为拒收判据（`host-tools.ts:3759`）。
  2. 协议 §4 的默认规则：「宁可 warning 不 error，除非会静默出错」。溢出会静默裁字 ⇒ 必须**上报**（0B 的整个目的），但上报 ≠ 拒收：`report.textFit` + `warnings` 已经让「有人知道」成立。
  3. 真实例证：`hook-title` = `["四季","是因为离太阳远近吗？"]` 是有意两行；把「数组 3 条 > title 2 行」做成 error 会误杀这类设计。
- **代价**：校验期不会拦住溢出片。已接受 —— 渲染前实测（`report.textFit`，浏览器真字形）是硬结论，校验期只是早提醒。
- **可回退性**：高（`warnings.push` 改 `errors.push` 一行即可，两处）。

## D-21 · 体检口径的三个定义（`dataCard` 的 maxLines / `caption` 的软上限 / 报告字段集）

- **问题**：任务包只给了 `subtitle` / `title` / `bullets` 的预算表；`dataCard` 与 `caption` 没有可比对的 `maxLines` 判据，硬造会产噪声。
- **选择**：
  1. **`dataCard`**：`maxLines` = **作者声明的行数**（`dataCardDesignHeight` 就是按它算设计高度的）。折行数超过它 ⇒ 卡片被盒上下裁（这条是真缺陷，不是噪声），此时 `fontPx` 仍等于基准号（数据卡不缩号，字号由 `dataCardMetrics` 的缩放系数决定）。
  2. **`caption`**：`maxLines` = **3**（`CAPTION_SOFT_MAX_LINES`，常量；文案明确写「不会裁字，但会顶到画面下沿，建议拆句」）。它是**软上限**：词级字幕没有自动缩号，也没有硬行数契约，硬判会天天误报。
  3. **报告字段**：`id / variant / fontPx / baseFontPx / maxLines / lines / overflow / atMinFont / maxWidthPx` —— `maxWidthPx` 保留（判断「是不是盒太窄」的唯一依据），`renderText` 不报（它是渲染输入，不是诊断信息，且会让报告体积翻倍）。
- **为什么不在 `prepareMs` 里单独切一段 `prepareTextFitMs`**：体检是同步的 `measureText`，11 条轨 <1ms（实测在 `原型-manifest-b1b2.json` 上 11 条全量对账无感），单独计时只会让 `RenderJobReport` 多一个恒为 0 的字段（`warm` 字段的教训）。
- **可回退性**：高（全是常量与字段选择）。

## D-23 · 构件轨统一 `fx-` 前缀，并给 ML-05（机械感）加定向豁免

- **问题**：1C 的构件展开器产出的是**普通 shape 轨**（这是刻意的：渲染器零契约扩展）。但底部进度条的游标必须**匀速**从左走到右 —— 否则进度条会「一顿一顿」。`motion-lint.ts` 的 ML-05 规则恰好把「位移/缩放 + `easing:'linear'`」判为机械感并上报，实测在科学模板上报了 `fx-progress-cursor`。
- **选择**：构件轨 id 一律以 `fx-` 开头（`expandFurniture` 内生成，模板作者不可改），`motion-lint.ts` 对 `fx-` 前缀的轨**跳过 ML-05**。
- **理由**：
  1. 匀速是**刻意的设计意图**（进度条时间的视觉映射），不是「作者偷懒没给缓动」—— 规则与意图在这里本来就不冲突，误报而已。
  2. 豁免粒度用**前缀**而不是「白色名单 / 轨 id 数组」：构件是编译期生成的，id 不在模板作者手里，前缀是唯一稳定的判据；也不给作者留「把自己写的轨命名成 fx- 来绕过体检」的口子（`fx-` 只由 `expandFurniture` 产出，手工写 `fx-` 轨会在下一条规则里被 `FURNITURE_ID_CONFLICT` 拦住）。
- **代价**：作者若手写 `fx-` 开头的轨，会被构件 id 冲突检查拒收（这是想要的：前缀是构件的命名空间）。
- **可回退性**：高（`motion-lint.ts` 一个 `isFurnitureTrack()` 判据）。
- **连带**：ML-10（运动时长占比 <10% 判幻灯片）在科学模板上报了告警（运动只占 4%）—— 这一条**没加豁免**，而是给骨架各文字轨补了 `anim`（`maskReveal` / `fadeUp` / `wordStagger`）。理由：ML-10 说的是实话，模板本来就不该是一叠静态文字。

## D-24 · `contractVersion` 不符 ⇒ 编译期**拒绝**，不是 warning

- **落点**：`template-registry.ts` 的 `contractOk` + `template-compile.ts` 的顶部校验 + `tests/remotion-template.test.mjs` 的「契约版本不符即拒收」用例。

## D-25 · 模板产物的 manifest id 用**内容哈希**，禁任何时间成分

- **问题**：`scaffold_manifest` 的旧实现用 `Date.now()` 之类的时间戳拼 id（便于每次生成不撞车）。模板编译器如果照抄，就违反「同输入两次编译逐字节相同」，画布上同一次会话反复编译会堆出多张卡片。
- **选择**：`id = 'comp-tpl-' + fnv1a(stableStringify({ template: meta.id, values: resolved }))`（8 位十六进制）。**不含**时间、不含随机。
- **理由**：
  1. 模板编译是纯函数（骨架 + 槽位值 → manifest），id 是它的函数值的自然延伸；同内容同 id 才能在画布上去重。
  2. 逐字节确定性是 Remotion 渲染一切断言的地基（像素哈希、缓存、差分验收）。id 里掺时间会让「同一份 manifest 渲两次」变成「两个 manifest」。
- **反向变异实测（重要教训）**：把 id 改成 `...-${Date.now()}` 后，**23/23 全绿** —— 因为 `Date.now()` 的分辨率是 1ms，连续两次编译常常落在同一毫秒里，「两次编译字节相同」这条守卫抓不到。⇒ 已在测试里补**形状断言**：`assert.match(id, /^comp-tpl-[0-9a-f]{8}$/)`。补完后同一变异**精确变红 1 条**。
  - 教训写进 `无人值守推进协议` 的口径里：**「比字节」不足以证明「无时间成分」，必须同时钉形状**。
- **可回退性**：高（一个函数）。

## D-26 · 占位符替换的两条口径：整串 ⇒ 原值；内嵌 ⇒ 字符串化

- **问题**：`{{slot}}` 有两种出现方式：① 整个字符串就是一个占位符（`"text": "{{title}}"`）；② 嵌在长文本里（`"text": "第 {{n}} 步：{{action}}"`）。槽位类型有 `string` / `string[]` / `number` 三种。要不要为了「统一」把数组一律拍平成字符串？
- **选择**：
  1. **整串占位符** ⇒ 替换成**原值**（`string[]` 保数组、`number` 保数字）。作者的数组分行意图是**显式设计**（`textCard` 的数组 = 多行），拍平就毁了这个意图。
  2. **嵌在长文本里** ⇒ 字符串化（数组按 `\n` 拼，数字走 `String()`）。此时作者写的是「一句话里插个值」，语义本来就只能是文本。
  3. 未在 `slots.json` 声明的 `{{xxx}}` ⇒ 编译期 `SLOT_UNKNOWN` 错误（不是静默留空）。
- **理由**：`text` 字段的校验只要求「非空字符串 / 非空字符串数组」，两种形态都合法 ⇒ 保结构是**零成本**的；而拍平是**不可逆的信息损失**。
- **可回退性**：中（口径写死在 `replacePlaceholders`，改则影响所有模板；但模板只有 3 个，改完重跑编译测试即可）。

- **问题**：要证明「构件真的上了屏」，最直接的办法是渲一帧然后看四角/底部有没有构件颜色。但实测不可行：

  - 换成「与去构件成片的区域**平均差**」也不行：110×110 的方框里只占 ~70 个像素，均值被面积稀释到 **0.19–0.35**，和编码噪声同档（实测第一版断言就是这个原因误红：tl 0.214 / tr 0.325 / bl 0.353，只有 br 1.916 因为混进了游标）。
- **选择**：判据改成**差分像素数**（任一通道差 > 12 的像素个数），且**必须**有对照成片：
  - 对照构造成立的前提是「同 values、同骨架，只把 `furniture` 换成 `[]`」—— 这样两份成片**只有构件不同**，差分像素就是构件本身，天然抗压缩；
  - 实测：四角 **71 / 72 / 107 / 294**（br 多出的是进度条游标）、底部带 **1948**、画面中心 **7**（纯编码噪声）、全画面 2127；阈值取 30 / 200 / 40（中心上限）/ 800。
- **为什么不用「渲一张只有构件的纯色片」**：那验的是 `expandFurniture` 的几何（已由 `remotion-furniture.test.mjs` 的 `★几何` 用例覆盖），验不到「构件与真实内容的层叠关系」——而层叠关系（括线不被卡片盖住、进度条不压字幕）才是模板里最容易错的地方。
- **顺带修的两个探针工程问题**：
  1. 假宿主没调 `recordRenderHostReport()` ⇒ 窗口层 8s 后打**假**告警「从未收到任何自报，本单回退画布页」。探针日志一旦有假告警，后面所有断言的公信力都要打折 —— 已照真实宿主（`routes.ts` 的 status 处理）补上，现在那句话变成「仍在自报（state=rendering，最近一拍 0.8s 前）」。
  2. `assertStep` 原本同步调用断言体，**async 断言体里的 throw 会变成无人处理的 rejection**，探针会「假绿」。已改为 `await fn()`。
- **实测结论（6/6 绿）**：三支样片 h264 / 1920×1080 / 18.03·24.02·20.03s（偏差 = muxer priming 的既有属性，0A-8 已记录）；音效峰 0.315 / 0.293 / 0.284，有声帧 39 / 32 / 12；`report.textFit` 6 / 6 / 3 条全 `overflow=false`（**0B 当时留给人工的那一环，现在有机器证据了**）；同 manifest 重渲帧 **0 字节差异**。
- **可回退性**：高（探针不进产物，阈值都在脚本里带注释）。

## D-34 · `meta.family` 是**可选新字段**，不动 `MANIFEST_CONTRACT_VERSION`

- **问题**：P-7 要求「G2 不开工，但 `meta.family` 本期必须写」。落地时有个岔路：加字段算不算破契约？要不要把 `MANIFEST_CONTRACT_VERSION` 从 `'1'` 升到 `'2'`？

## D-35 · 模板配乐位只存**参数+提示**，音频由模型现场生成（不内置曲库）

- **问题**：真机会话（`session.v4.jsonl`）里模型想出带 BGM 的片子，模板给不了它任何入口 —— `TemplateBundle.audio` 只能声明 `ManifestSfx[]`，`bgmUrl` / `mix` 无处可写。模型最后 `node -e` 手改 JSON 4 次，`mix.bgmVolume` 靠试。
- **两条路**：(A) 每个模板内置一条免版税 BGM（+3–5MB、授权审计进发布流程、换风格要重新配）；(B) 模板只声明「要什么样的曲子」（提示词 / 时长 / 建议音量 / 淡入淡出），音频由模型**现场生成**后经 `scaffold_manifest({ bgmUrl })` 编进产物。
- **用户拍板**：选 **B** ——「模型自己生成即可，这个消耗时间比较短，可以接受」。
- **实现边界**：
  1. `TemplateBundle.audio` 从 `ManifestSfx[]` 升为 `{ sfx?, bgm? }`；注册表**两种形状都认**（裸数组 = 旧的音效表，包成 `{ sfx }`），老模板不用改文件；
  2. `compileTemplate(bundle, values, { bgmUrl })` —— 编译仍是**纯函数**（不读盘 / 不联网 / 不取时间），所以生成必须在编译器之外；
  3. 模板建议的 `volume` / `fadeInSeconds` / `fadeOutSeconds` **只在真接了 BGM 时**写入 `audio`（没接就留空，避免出现「孤立的 mix」让人以为配乐丢了）；
  4. 声明了但没给 `bgmUrl` ⇒ 编译**不报错**（无 BGM 是合法成片），但 `CompileOutput.bgmRequest` 原样回传，`scaffold` 回执把它改写成三条可执行指令（生成 → 回传 → 重编）；
  5. `bgmUrl` 进 `HANDLE_PARAMS`（与 `imageUrl` / `videoUrl` 同类：合法值只能来自音乐生成工具的产物）。
- **代价（接受）**：每条带配乐的片子多 1 次生成 + 1 次重编（会话成本 +2 次工具调用），换来 0 体积、0 授权风险、风格可随内容变。
- **可回退性**：高（`audio` 联合形状 + 编译器一个 `if`；不传 `bgmUrl` 时行为与 CV-463 完全一致）。
