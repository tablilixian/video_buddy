Canvas Studio Skill 系统设计评审

这是一个「文档纪律驱动 + CI 兜底」的 skill 系统，工程成熟度高于多数团队。但它存在一个结构性判断错误—— 把 skill 系统当「内容工程」治理，没当「检索问题」治理。

基线 dev @ 8fc99b4905 对象 23 个 skill 门禁 10 文件 / 61 test 方法 全量静态核查 + 实测统计 产物 只读评审，未改源码
01

核心判断：四个「看起来在管，实际已经不管」的机制

这是本文最重要的一节。它们有共同的特征——断言的形式还在，约束的意图已经丢了。

可维护性 ★★★★★
★★★★★
  • 单一事实源 + 5 道防回弹守卫
  • 负向验证意识（注入假条目证明断言有效）
  • 约束全部编译成会红的测试
可路由性 ★★☆☆☆
★★☆☆☆
  • 无任何度量：没有路由准确率、没有误加载率
  • 无结构收敛：23 条候选、零可见性控制
  • 靠 system prompt 硬指令撑着（SK-01）
一句话

所有产出物都是内容侧的，没有一个产品侧的。团队选择了治理「内容质量」并做到了优秀，却跳过了「检索质量」——而后者才是 skill 系统区别于「一组 markdown 文档」的本质。

这不是执行不力，是议题选择。

真正「在管」的机制长什么样——单一事实源守卫：有迁移史、有 6 个 test、有 stripComments 防「只删注释」式假修复、有反直觉的职责边界。它不会在内容增长时自动退让。这就是四个失效机制与它的差别。

06

建议：按投入产出排序

全部是「填已存在的洞」，不是新建机制。P0 是唯一能治本的一项。

P0
接上 invocation.modelInvocable

8 个技术类 skill 设 modelInvocable: false，创作总纲改由 system prompt 直接加载；配合上游 scope 分层，让用户的 activeSkills 成为真 gate。catalog 从 23 条降到典型 3–6 条。

依据 index.ts:48-53 接口已就位 · 成本约 20 行
P1
用 whenToUse 承接负向路由语

description 压回 ~200 字符（说「这是什么」），负向路由语（Not for…）移入 whenToUse（说「什么时候别用」）。10 字符的雷解除。

依据 index.ts:62 · 无长度上限
P2
把「>10KB 必拆 references/」写成测试

会立刻点出 5 个违规 skill（32KB / 23KB / 21KB / 16KB / 14KB），强制处置。写进护栏清单等于没写——这一点已被实测证明。

现状 10/23 refs=0 · 5 个 >10KB 违规
P3
CV-121 体积上限冻结，或换指标

不要再上调 21KB。改为双指标：(a) 骨架绝对上限冻结；(b) 新增「分册覆盖率」要求（细则类内容占比 < X%）。

三次上调已证明 绝对值上限无效
P4
清理无活跃消费者的重复 skill

z-image-prompt-writing、qwen-image-edit-writing 的运行时路由早已改指 krea2 系列（CV-189/192），却仍占 description 预算、投歧义候选、造重复卡片。

catalog 内 summary 逐字重复
P5
给「安全底线不参与优先级反转」加测试守护

这是风格 skill 与总纲重叠 80% 之后，唯一支撑整套安全模型的条款。目前仅有 prompt 一处声明，零断言检查它未被侵蚀。

依据 skill-system-optimization.md:109
P6
建 skill 质量回归（长期）

把 effect-test-runner 从 1 个 skill 扩到覆盖所有 preview 与主力风格 skill；或建「skill 契约测试」——每个 skill 声明其必须产出的结构（如 bible-story-director 声明九节 storyboard.json），由结构断言兜底。当前 23 个 skill 中只有 1 个有真实执行回归（4.3%）。

依据 placeholder-tools.ts:14 · Pilot scope = 3d-animation-short-generator
07

必须说清楚：它不是做得差

问题不是执行不力，是议题选择。

单一事实源
历史上是双源（submodule 同步 + skills-local/ 覆盖合并），必然产生「我该改哪个」的漂移。2026-09-17 一次性收敛
5 道守卫 + stripComments 防「只删注释」式假修复——这种考虑通常出现在做过一次真实回退的团队里
在管
负向验证
「往 catalog 注入假条目 → 测试变红 → 还原 → 8/8 绿（断言确实有效，非空转）」
写测试和验证测试有效是两件事——这个仓库明确区分了它们
在管
诚实边界
占位工具不假装成功，返回三条可执行替代路径；music_generation（CV-125）、tts_voiceover（CV-271）逐个转正并从注册表移除
从 3 个占位收敛到 1 个（subtitle_burn）——「占位是负债，转正是目标」的正确姿态
在管
零配置注册
目录成员即注册，23 个 skill 由一个函数注册（minimax-skills.ts:165-173），新增 skill 不改一行注册代码
实测三方严格 1:1：skills/ 目录 = 注册数 = catalog 条目 = 23，frontmatter.name 零偏差
在管
为什么 SK-01 只能靠硬指令

routing-prompt.ts:9-11 自己写明了原因：「catalog 摘要只是技能广告位，模型是否优先读它取决于自身策略」。

把软性祈使句升级为 system prompt 常驻硬指令，是务实的正确补救（背景是 CV-094 的一次真实复盘：模型自行追问三轮才加载总纲）。但为什么需要它？因为 catalog 本身不提供任何收敛能力——23 条、8,818 字符、零优先级、零可见性。团队只能靠提示词纪律，去补结构能力的缺口。
