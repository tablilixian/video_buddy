canvas-studio-creation 怎么写才撑得住用户上传 skill

总纲 131 KB，骨架 21 KB。目标不是"更短"，是让总纲停止知道具体 skill 的名字—— 这样用户上传多少个 skill，它都不用改。

这次讨论新增的约束

后续放开用户上传 skill 以后，不可能随时修改总纲。

这一条把设计目标从「怎么写得更简练」改成了「怎么写才不会因为新增 skill 而过期」。简练只是结果，不是目的——因为一条冗长的、枚举了具体 skill 名的规则，它必然会随 skill 增长而腐烂。

一条判据决定每句话该写在哪

整份蓝图只有一个判断标准。它可以直接拿来审任何一条总纲文字。

Q：这条规则会不会因为「多了一个 skill」而变？
会 → 不能写死在总纲（要移出去或改成槽位）。不会 → 可以写死。

能写死 · 多一个 skill 不影响

  • 11 步流程顺序与阶段边界
  • 审批语义（门禁拦截 / 提交停手 / 放手跑）
  • 工具契约（两类 filename / 16:9 / 同步异步）
  • 安全底线四条
  • 能力边界（无视觉能力 / 附件处理）
  • 用户 skill 安全协议（新）
这些是产品定义的稳定面，用户行为改不了它们。

不能写死 · 多一个 skill 就过期

  • 必须先加载 h3-prompt-writing
  • 必须先加载 krea2-turbo-writing
  • 风格预设清单（11 类）
  • 决策型 skill 的路由规则
  • 工具手册细节（toolchain）
  • 单步细则（shot-format 等分册）
现在这 6 项有 5 项在骨架里——这是总纲会随用户 skill 增长而腐烂的根本原因。

为什么 5 道现有门禁一个都没抓到

5 道 skill 门禁（目录成员即注册 / 引用完整性 / kebab-case+description 长度 / 截断哨兵 / catalog 双向断言）全部是结构门禁。引用一个不存在的工具名，在结构上"references/ 下的文件存在"这一条就通过了；"三个 submit 工具"数量不对，没有任何断言会数工具个数。

缺的是一条语义门禁：扫所有 skill 正文的 snake_case 工具名候选，与实际注册的工具表对账。约 30 行，和现有 5 道同一个模式，团队已经熟悉。它是唯一能把「下次又写错」变成「这次就红」的改动。

这条改动的直接效果

① 内置 skill 换实现，总纲不动。今天 h3 写得不好、明天换一个新模型 —— 改绑定表一行，总纲照旧。

② 用户上传 skill 可以填补或竞争这些槽位，总纲不动。用户 skill 在 frontmatter 声明 role: knowledge + slot: video-prompt 即可参与；是否让它顶替内置实现，是绑定策略问题，不是总纲问题。

③ 骨架里第 54–55 行那两条硬编码 skill 名，是整个问题里最该先动的地方——它们只有 2 行 753 字节，但正是"总纲会随 skill 增长而腐烂"的那个点。

务实提醒：槽位不一定要宿主侧实现

真正的槽位机制需要宿主支持（绑定表 + 加载逻辑）。如果暂时不想动宿主，有一个零改动的退路：把绑定表放进 references/toolchain.md，骨架只写「第 9 步需要 video-prompt 槽位，见 toolchain.md 槽位表」。

这样也能拿到 90% 的效果——总纲不再枚举 skill 名，绑定关系集中在一本分册里而不是散在总纲各节。分步做的话，先做这个退路，未来要升级成宿主侧槽位也是平滑的。

风险与前提

瘦身后骨架薄了 58%，这些是必须一起回答的

R1

骨架变薄，模型可能不读分册

21 KB 骨架的好处是「所有关键规则都在上下文里」。降到 8.9 KB 后，很多规则只在读到分册时生效。缓解：骨架里把「必读分册」按步骤写死 4 本（澄清前读 clarification、写剧本前读 screenplay、分镜前读 shot-format、写提示词前读 prompt-writing），其余 4 本标注「按需」。

R2

峰值上下文会不会反而变大？

不会，按数字算：现在骨架 21.3K + 分册按需 1–3 本（10–40K）≈ 峰值 30–60K；之后骨架 8.9K + 同样按需 ≈ 峰值 20–45K。骨架常驻部分降 3.2 倍，峰值不升反降。所以「瘦身后执行力下降」这个担忧，现有设计里本来就存在，不是新增风险。

R3

用户 skill 质量不可控

槽位机制只解决"能不能接"，不解决"好不好"。需要配两件事：①槽位冲突策略（内置优先，建议默认）；② 结构契约——每个决策型 skill 声明它必须产出什么（如 bible-story-director 声明九节 storyboard.json），由结构断言兜底。这是当前 4.3% 端到端回归覆盖率的直接解法。

R4

决策型 skill 的候选集从哪来

总纲不写清单，但模型需要一个候选集。候选集不是总纲的内容，是 UI 层的输入——用户激活集 + 平台可见集 + 按大类的收敛结果。总纲只需要规定「怎么选、什么时候必须问用户、什么时候不许自己选」，不需要规定「有哪些」。
