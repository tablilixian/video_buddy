> 需求来源：2026-10-05 用户讨论（「在 app 内点一个测试按钮，自动建项目、输入对话、引用资源到画布、在合适的时机停止/继续对话，模仿用户使用 app 的过程」）。
> **拍板结论（2026-10-05，用户逐条确认）**：
> ① 测试项目命名沿用 `效果验证-R#` 前缀（吃到既有启动清扫）；② 机器断言报告落在**测试项目目录内**（`test-report.md`，验收方直接读盘）；③ 第一个固定场景 = **《山谷晨光》15s 版**；④ 设置开关只控制「按钮可见」，跑不跑、何时跑永远由用户手点，**不做任何定时/自动触发**。
> 状态：**已实现·待桌面验收（2026-10-05，D1/D2/D3 三批全绿）**。落地映射见 requirement-tracker **REQ-021**（含两处实现偏差说明：纯函数模块落 src/ 根、E-3 带秒口径校正）；铁律口径 STATUS 不登记（验收通过后才落）。
> 实现备注：设计文档 §四.5 的数据源「fetchStudioGenerateQueue」快照只含 active/waiting/resumedJobs（无逐任务 executionError）——检查点 8 按可核对口径实现（队列全清 + 无缺 URL 残缺节点），后端失败证据由检查点 4/11（视频数与成片来源）兜住。

## 一、需求与目标

给 app 加一个「测试模式」：设置里打开开关 → 界面出现「▶ 自动测试」浮窗 → 点开始后，app **自己扮演用户**：创建项目、发送剧本对话、等 agent 干活、跑完对产物做机器断言、生成一份自包含的评估报告。固定场景可反复执行，形成回归；**内容质量**（画面好不好、中文逐字对不对）由用户自己或喂给其他大模型评估——自动化只负责「驱动 + 客观检查点」，不负责审美判断。

**被否方案的备忘（勿重新讨论）**：沙箱第二实例 / 外部 Playwright / headless 编排（2026-10-05 讨论过，用户明确要「app 内按钮 + 不新开环境」——真实链路本身就是被测对象，污染面用命名前缀 + 清理按钮压制）。

## 二、现有地基（实现前必读，能省一半工作量）

`src/client/index.ts:1873-1960` 的**一键效果测试**（2026-09-02，effect-test-runner skill 的驱动器）已经实现了本功能最难的四件事：

| 既有件 | 位置 | 作用 |
|---|---|---|
| `runEffectTests(round, cases)` | client/index.ts:1911 | 编排骨架：建项目 → refreshProjects → openProject → 切放手跑 → 程序化发送 → 等回合空闲 → 进度回写 |
| `waitSessionBound(projectDir)` | :1883 | 等 openProject 的 fire-and-forget startSession 真正把会话 cwd 绑到项目目录 |
| `waitAgentTurn(sessionId)` | :1894 | **回合空闲判据**：先等 `summary.running===true`（回合已启动），再等 `running===false && pendingInteraction===undefined` 连续两拍。超时错误码 CS-EFFECT-001/002/003 |
| 程序化发送 | :1929-1932 | `sessionSvc.scope(sessionId).get('conversation').send(text)` —— 官方发送入口（首页认领、附件改道等包装都在其下游） |

其它既有件：`效果验证-R#` 前缀被 `refreshProjects` 的启动清扫识别（`projects` 空项目 10 分钟保护期后回收，client/index.ts:941-971）；「效果测试报告.md」由 skill 侧落盘的先例 + `scripts/collect-effect-tests.mjs` 归档器；`store.effectTest` 进度切片 + 其 UI 消费。

**已知边界（写进了既有注释，沿用）**：approval 类弹窗没有客户端 API 可自动批准——放手跑（auto）模式下 submit 门自动放行（揽月湾真机复盘验证），`ask_user_choice` 被 studio-defaults 自动取值拦截；若仍出现 pendingInteraction 阻塞，`waitAgentTurn` 超时即记失败，人工接管。

## 三、方案总设计

```
设置「测试模式」开关（默认关）
   └─ 开 → 首页 + 画布顶栏出现「▶ 自动测试」浮窗
        └─ 浮窗：场景列表（一期 1 个）+ 开始/停止 + 步骤日志 + 上次报告入口
              + 「清理历史测试项目」按钮
        └─ 点开始 → 场景执行器（复用既有 driver 骨架）：
             ① createStudioProject(`效果验证-R<n>-山谷晨光`)
             ② openProject + waitSessionBound + setWorkflowMode(auto)
             ③ conversation.send(《山谷晨光》15s 剧本)
             ④ waitAgentTurn（上限 50 分钟，复用既有常量口径）
             ⑤ 机器检查点（断言库，见 §五）
             ⑥ conversation.send(追加指令：改孙女形象) + waitAgentTurn + 检查点
             ⑦ 生成 test-report.md → POST 落到测试项目目录
             ⑧ 浮窗展示结果摘要 + 报告入口
```

**原则**：场景执行器**不经过 LLM**（驱动与断言都是确定性代码，agent 在回合内自己调度）；开关只管按钮可见性；运行期间不改任何真实设置。

## 四、技术设计（逐锚点）

### 4.1 抽取共用驱动模块（本批的重构点，铁律「同一规则只准一份实现」）

把 `waitAgentTurn` / `waitSessionBound` / `effectTestPoll` / 超时常量从 `client/index.ts` 抽到新模块 **`src/client/test-driver.ts`**，签名保持不变；`runEffectTests` 改为 import 共用件，**行为逐字节不变**（既有 effect-test 流程与 `store.effectTest` UI 消费不得受影响，抽完后相关测试 + 全量 smoke 必须原样绿）。场景执行器基于同一模块搭建，防止两份「回合空闲判据」漂移（CS-UNC-000 教训）。

### 4.2 设置项

`src/host-config.ts` 的 canvas-studio 分区新增 `testMode: boolean`（默认 `false`，描述注明「显示应用内自动测试入口，日常使用保持关闭」）。`SettingsModal.tsx` 的 canvas-studio 卡片加开关行（照 assetDir 行的样子）。客户端读设置快照控制浮窗可见（client 设置作用域只有 subscribe 无推送，见 client/index.ts:1274 注释——浮窗组件订阅设置快照即可）。

### 4.3 浮窗 UI

新组件 `src/client/AutoTestPanel.tsx`（浮窗，右下角，类似既有 effectTest 进度条的形态）。**新增独立 store 切片 `autoTest`**（scenario 列表 / running / 当前步骤日志 / 上次报告路径），**不动 `effectTest` 切片**（它有既有消费者）。挂载点：`StudioFrame` + Lobby 共同的客户端外壳（跟 effectTest 进度条同层）。运行中在浮窗显著位置提示「测试运行中，请勿操作当前项目」，结束后提供「返回原项目」（记住进入前 `selectedProjectId`，`store.actions.select` 回去）。

### 4.4 场景定义（固定脚本，版本化）

新文件 `src/client/auto-test-scenarios.ts`，导出常量数组。每个场景：

```ts
interface AutoTestScenario {
  id: string                      // 'shangu-chenruang-v1'
  label: string                   // '《山谷晨光》15s 全链'
  scriptTurns: readonly [string, ...readonly string[]]  // 第一条 = 创意剧本；其后 = 追加指令（逐条发送、逐条等回合）
  checkpoints: readonly Checkpoint[]  // 按 turn 序号分组，见 §五
}
```

一期一个场景（§六）。`scriptTurns` 的第一条文本直接内嵌 15s 剧本全文（用户已拍板的《山谷晨光》，见 §六）。

### 4.5 检查点断言库（纯函数，必须可单测）

新文件 `src/client/auto-test-checkpoints.ts`：每个检查点 = 纯函数 `(snapshots) => { pass, evidence }`，输入是**持久化状态快照**，不触网：

| 数据源（全部现成 client api） | 拿到什么 |
|---|---|
| `loadStudioCanvas(projectId)` | 节点表：kind/toolName/supersededBy/sourceIds/宽高/title/auxiliary |
| `getStudioAssetHistory(projectId)` | 产物登记：filename 前缀（路由断言）、label、deletedAt |
| `fetchStudioGenerateQueue()` | jobs 状态（全 settled） |
| `listStudioProjects()` | 项目目录名（E-3 带秒）、createdAt |

**一期检查点清单**（对应《山谷晨光》，逐条给出断言）：
1. 项目创建成功且目录名匹配 `效果验证-R\d+-.*` 且带秒（E-3）；
2. 分镜卡（`STORYBOARD_NODE_TOOL`）数量 = 3；
3. 关键帧节点存在且挂对应分镜卡（sourceIds 含分镜卡 id）；
4. **视频节点 = 3 且全部 active（零 `supersededBy`）——BUG-011 回归断言（本功能的立项动机）**；
5. 海报产物 filename 前缀 = `Qwen_image_2.1_`（R-P1-03 路由：含引号片名文字 → Qwen）；
6. 概念图产物 filename 前缀 = `krea2_`（无字 → Krea2）;
7. 全部产物宽高 = 480p 档（对照 `config.ts OUTPUT_SIZE` 的 16:9 档位值，C-8）;
8. jobs 全 settled 且 `executionError` 为空；
9. history 登记数 ≥ 预期下限（2 定妆 + 3 关键帧 + 3 视频 + 1 音乐 + 1 海报 + 1 成片，下限写宽防止合理重试）；
10. 旁白（tts_voiceover）节点 generationPrompt 中 refaudio 全部一致（C-5）；
11. 成片节点存在且来源 sourceIds ≥ 3 段（compose 选片未被残片化，M-3 侧证）；
12. 追加指令后：旧孙女四视图节点 `supersededBy` 非空 + 下游视频 Picture 槽 sourceIds 已改写为新句柄（批F supersede 改写链）。

**刻意不做进一期的**（会话流内才可见，留给验收方事后做）：warnings 文案断言、逐字正确性、画面质量。

### 4.6 报告落盘

Host 路由新增 `POST /canvas-studio/test-report`（`routes.ts`，照 draft-landing 路由的形态）：入参 `{ projectId, markdown }`，校验项目存在后写 `<projectDir>/test-report.md`（覆盖写，增量更新靠客户端每检查点后重发全量）。client `api.ts` 加 `saveTestReport()`。**报告结构**：

```
# 自动测试报告 · 《山谷晨光》15s（scenario v1）
- 运行：时间 / 耗时 / 场景版本 / app 构建版本
- 本次生效设置：分辨率 / 供应商 / 模型 / 画幅（只读快照，不改设置）
- 机器断言：12 条逐条 pass/fail + 证据（节点 id / filename / 数值）
- 产物索引：成片 URL / 海报 URL / 关键帧 URL 列表（可直接点开）
- 创作过程留档：分镜表全文 / 旁白全文 / 每次生成的 prompt 原文（取自节点 generationPrompt）
- 内容评估指引：把本文件交给人工或外部大模型，评估「逐字正确 / 节奏 / 美感 / 纪律遵守」
```

### 4.7 清理按钮

浮窗「清理历史测试项目」：列出所有名字匹配 `/^效果验证-R\d+/` 的项目（含**有内容的**——既有清扫只回收空的），逐个 `deleteStudioProject`（其内建的删除语义：列引用方确认不需要——测试项目无用户数据，但**沿用删除语义的全部既有代码路径**，不另写删除逻辑），完成后 refreshProjects。删除前列数量让用户确认一次。

## 六、边界与不做清单

| 不做 | 理由 |
|---|---|
| 定时/自动触发、批量队列 | 拍板④：开关只控制可见性，跑由用户点 |
| 沙箱第二实例 / DSH_HOME 编排 | 被否方案（§一备忘） |
| 修改真实设置来「保证环境一致」 | 改真实设置才是污染；报告记录生效设置即可 |
| warnings / 逐字正确 / 画面质量断言 | 会话流内或主观判断，留给报告的「内容评估」环节 |
| 退役 effect-test-runner skill | 一期不动；场景执行器不依赖 skill（固定剧本直发）。后续可把 skill 用例迁移成场景，另行立项 |
| 打字级 UI 模拟（逐键输入） | 脆弱且覆盖增量小；走 `conversation.send` 官方入口 |

## 七、实现顺序与工作量（合计约 2.5 天）

1. **D1**：抽 `test-driver.ts` 共用模块（runEffectTests 行为不变，全量 smoke 原样绿）+ `testMode` 设置项 + SettingsModal 开关 + `AutoTestPanel` 骨架（含 `autoTest` store 切片）。

## 八、验收标准

- **无头**：全量门禁绿；checkpoint 单测绿 + 反向变异可红；`runEffectTests` 既有行为零回归（其测试原样绿）。
- **桌面**：① 开关关 → 无浮窗；② 开 → 浮窗出现；③ 跑《山谷晨光》15s → 项目创建、放手跑全链、12 条断言逐条出结果、`test-report.md` 落在测试项目目录；④ 追加指令触发改写链且断言 12 通过；⑤ 清理按钮删净 `效果验证-` 项目；⑥ 关开关浮窗消失；⑦ 全程真实项目列表中除测试项目外无任何新增/修改。
- **真实跑一轮后**：把项目目录与会话交给验收方（同揽月湾复盘方式）做产物级复核。

## 九、风险

1. **真实后端抖动导致场景偶红**：检查点把「后端 5xx / 超时重试」与「真断言失败」分开标记（jobs 的 executionError 与 CS-GEN-* 错误码可区分）；偶红允许重跑，连续红才算回归。
2. **waitAgentTurn 对长回合的超时**：50 分钟上限沿用既有常量口径；15s 场景实测后如有富余可收紧到 30 分钟（改常量需过测试）。
3. **「效果验证-」清扫与场景项目的交互**：场景项目有内容不会被自动清扫（清扫只删空项目）——这是期望行为（报告要留存），靠清理按钮显式回收。
4. **测试与用户并发操作**：浮窗提示 + 「返回原项目」；同一时刻只允许一个场景在跑（`autoTest.running` 防重入，同 runEffectTests 的守卫）。
