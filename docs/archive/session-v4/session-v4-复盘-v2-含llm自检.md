## 五、最有价值的新内容：agent 自己的受控实验（自检）

### 5.1 被逐一证伪的假设（都有实验支撑，不要再重复踩）

| 假设 | 验证方式 | 结果 |
|---|---|---|
| 全屏 `blur(3px)` 图层太慢 | 把光晕烘焙成静态 PNG，去掉 3 个模糊层 | 仍超时 → **排除** |
| ECG 长 `path` / `draw` / `strokeWidth` 慢 | 单独渲染 2 轨 30 帧 path，去 `draw`、改 `strokeWidth` | 仍超时 → **排除** |
| 手表图太大（2.4MB / 1920×1080） | 缩到 1280×720、再缩到 21KB | 仍超时 → **排除文件大小** |
| 轨道数太多触发逐帧重算 | 3 轨/60 帧超时；57 轨/60 帧超时；但 1 轨/60 帧 1.4s | 高轨数相关，但不是唯一因子（见 5.2 矛盾） |
| 素材路由 403 是根因 | `curl` 拿 `/canvas-studio/assets/*` 得 403 | **误判**：403 是 `desktopBrowserAccess` 对"非受信浏览器"的正常拦截（curl 无 Electron token），渲染窗口在 Electron 内应被放行；agent 自己纠正了这一点 |

### 5.2 被确认的硬事实（可直接用于修复与监控）

1. **超时预算公式**：`timeout = 帧数 × 200ms + 60s`，上限 20min。1800 帧 = 420s；450 帧只有 150s；小片段下限 90s。
2. **固定开销极大且与帧数无关**：`encodeMs` 稳定在 **18–34s**（10 帧 24s、270 帧 21.8s）；冷启动 **40–60s**；每次渲染 `warm=false`（从不复用预热）。
   → 这直接击穿了短片段预算：10 帧也要 40–60s 启动+编码，90s 下限根本不够，于是 10 帧探针"有时过（45–60s）有时挂（90s）"——是**预算余量**问题，不是内容。
3. **渲染器本身健康**：早期 S1 = 85ms/帧（接近源码注释的真机 58ms/帧）；14:14 纯背景 60 帧 = 1.4s（22.6ms/帧）。说明硬件/代码没问题，**故障是状态性的**。
4. **任何 image / video / audio 轨道都会让渲染器挂死**，纯 shape / textCard 轨道正常。agent 推断是图片预取在 `delayRender` 中挂起、8s 超时后仍不释放。

### 5.3 未决真因（自检收敛到的点）

agent 的最终诊断表（14:57）暴露了核心矛盾：

| 场景 | 轨数 | 帧数 | 结果 |
|---|---|---|---|
| 纯背景 | 1 | 60 | ✅ 1.4s |
| 纯背景 | 1 | 10 | ✅ 45–60s（同一内容，耗时差 40 倍） |
| S1 完整（早期） | 11 | 270 | ✅ 23s |
| **S1 完整（现在，同一份内容）** | 8 | 270 | ❌ 超时 |
| 背景 + 21KB 小图 | 2 | 10 | ❌ 超时 |
| shape-only 全片 | 57 | 1800 | ❌ 超时 |

**结论**：既不是内容、也不是复杂度；是渲染器的**运行时状态**在会话中持续劣化——（a）每次都冷启动（从不 warm）、（b）素材预取通道死锁（image/video/audio 全挂）、（c）叠加非确定性节流。三者合起来让全片永远过不了超时线。

## 六、对当前项目有用的信息

### 6.1 引擎契约事实（已验证，建议直接沉淀进 skill 文档 + 守卫测试，省掉下次重读源码与写像素脚本的 5 次 compaction 开销）
- `durationInFrames` 必须等于 `max(track.startFrame + durationInFrames)`。
- `textCard` 全居中；只有 `bullets` 左对齐（圆点+文本同行、固定 900px 宽容器居中）→ 左栏须按像素 `translate(x-50%)` 定位。
- 打字机 = `anim:"typewriter"` + `animOptions`；`useCurrentFrame()` 是**轨内相对帧**。
- `boxStyle.h` 是**百分比**不是像素；`circle` 的 `paddingBottom` 按父宽解析→真圆；`path` 坐标是画布百分比（真圆需 rx/ry 校正）；`line.x` 是**左缘**；`look.temperature>0` 走 `hue-rotate(-12deg)` 偏暖，冷调须用负值。
- `bullets` 文字色硬编码 `#e6edf3`，`accentColor` 只改圆点色。
- `animateStateAt` 按维度独立选段（只动画 y 时 x 保持 `transform.x`）。
- `exit.durationInFrames` 必须 ≤ 轨道时长（校验器硬规则）。
- `render_composition` **绝不传 projectId**；长 manifest 走 `manifestPath` 绝对路径（内联截断触发 tail-integrity 拒收）。
- 本机无 PIL/numpy；ffmpeg 在 `/Applications/Jellyfin.app/Contents/MacOS/ffmpeg`。

### 6.2 宿主侧代码线索（给 canvas-studio / dsh-plugin-desktop 团队的 actionable leads）
1. **渲染器冷启动 / `warm=false` 从不复用**：每次渲染都重付 40–60s 冷启动 + 20–34s 编码。应研究渲染窗口/Remotion bundle 的预热与复用机制，避免每单都冷启。
2. **素材预取死锁**：image/video/audio 轨道让 `delayRender` 永不释放（疑似 `fetch(cache:'force-cache')` 对 `/canvas-studio/assets/*` 挂起）。需排查渲染窗口的 asset 路由鉴权——`desktopBrowserAccess` / `ordinaryBrowserEnabled` 关闭时，隐藏渲染窗口是否被正确带上 Electron 信任 token；以及 `delayRender` 是否缺超时兜底与失败释放。
3. **超时预算公式对短片段失真**：`frames×200ms+60s` 的下限 90s 远小于真实固定开销（~60–94s），导致 10–40 帧小渲染必然失败。应让预算 = 固定开销基线 + 帧数×单价，或改为**异步派发 + 进度回报轮询**而非固定窗口傻等（用户已两次指出"进度在走"）。
4. **渲染窗口状态劣化/不可恢复**：失败的渲染似乎留下"上一单未清干净"的隐藏窗口状态，需 reset/心跳保活机制。
5. **客户端重启清空用户资产目录**：`watch-hero.png` 被删，应改为惰性重新物化、保留引用。
