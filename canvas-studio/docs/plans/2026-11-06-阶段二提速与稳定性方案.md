## 2. 问题清单

### P2-01 · 交付档渲染预算不足，靠跨次续渲碰运气出片 【T2】

**证据**（turn3）：

| step | quality | 耗时 | 回执 |
|---|---|---:|---|
| s46 | `high` | 338.1s | 超时（330 秒内未完成），进度 **55%** |
| s47 | `standard` | 338.1s | 超时，进度 **82%** |
| s48 | `standard` | 338.1s | 超时，进度 **88%** |
| s49 | `standard` | 313.3s | **成功** 1280×720 / 45.08s |

`src/remotion/timing.ts:1423-1446`：`renderTimeoutMs = clamp(帧数×200ms + 60s, 90s, 20min)`；45.08s / 1352 帧 ⇒ **330s**。注释依据「真机实测 standard ~58ms/帧，200ms 给到 3.4× 余量」（**改动前基线；工作树已有 CV-447 改为 240ms + 分档系数，见 §9**）。`render-job.ts:902` 探针按 `spotFrames.length` 计、交付档按 `meta.durationInFrames` 计。

**但本次所有渲染都比文档基准慢 6–8 倍**：`verification.md:9` 写「探针 1.5s / 全片 draft 24–29s」，实测探针 **8.6–10s**（turn2 均值 14.8s）、640×360 draft **187.7s**；首跑 330s 才 55% ⇒ 完整约需 600s，对比 58ms/帧预期 78s **差 ~7.7×**。

**根因判断**：不是某一份 manifest 太重，而是**每帧成本整体抬升**，最可能是画布页 `rAF + paint` 被后台节流（已知铁律：CSR 渲染依赖画布页可见，Electron 未设 `backgroundThrottling:false`；`errors.md` 也提示「后台会被节流」）。`src/remotion/` 全仓**无跨次帧缓存 / 断点续渲契约**，55→82→88→100% 的进度累积是浏览器侧隐式行为，产品未正式化，等于「重试四次碰运气」。

**影响**：22.1min；high 档 55% 即超时，07:27 的高清档请求按现状必然重演。关联 REQ-034 后台渲染 v2、评审 P1-5。

### P2-02 · 阶段二无轮次上限，自检循环 120 步 / ~80min 【T1】

turn2 从 s15 首次探针到 s134 共 **120 步 / 80min**，17 次渲染中 **17 次都是 probe/spot**；s99–s132 只反复探年份轴标签两帧就烧掉 6 次渲染；s134 才自述「按纪律已用探针超过 2 轮」，**晚了 119 步**。turn3 s1/s3 两度声明「不再继续做探针测试」，s5 之后又看了 15 张图、渲 4 次。

代价几乎全是 LLM 往返：turn2 135 步 × 平均 38s 推理 + 314,238 字符 reasoning，工具只占 502.5s。`verification.md:19` 甚至已记录过同类事故「静默探针→看图→改坐标循环约 50 分钟才被用户叫停」——**同一事故原样重演，且更贵**。

阶段一方案 B1\* 的「≤5 步」预算**只约束需求澄清 → 拍摄定稿**，对阶段二完全无效。

### P2-03 · 图片撑爆上下文，39 次请求被拒重发 【T1】

55 次 `read_image` → 39 次 `IMAGE_OFFLOAD_REQUIRED`（2MiB base64 上限）+ 2 次 compaction；`verification.md:78` 已把 compaction 次数列为健康度指标，同样没被当闸用。每次只卸载最老的 1–4 张就重发，形成「看图 → 被拒 → 重发 → 再看图」的固定税。⚠️ 该卸载机制属于 **dsh 本体**，插件层改不了（红线），只能在**流程侧少送图**。

### P2-04 · 401 让 95min 零交付，且无断点恢复 【T3】

22:17:21 `AUTH` / `401 unauthenticated invalid access token` 打断 turn2 s135；此前 95.3min 的工作没有形成可交付产物，也没有可续跑的断点，直到 8h21m 后用户重新登录说「继续」。**这是可靠性问题，不是性能问题**，但单次代价最大。日志判不出是 token 自然过期还是网关固定 TTL。

### P2-05 · `words` 未透传：词级卡拉OK 字幕必然全暗 【T0】

- 契约支持：`src/remotion/manifest.ts:691`（`words?: {text,from,to}[]`）、`:939`（caption 白名单含 `words`）、`:1759`（消费 `track.words`）；
- 产生路径丢失：`skills/code-driven-explainer/assets/manifest-builder.mjs:64-90` 的 `buildSegments` 只构造 `{id, text, frames, src?}`，**整个文件 `words` 出现 0 次**；
- 后果：字幕只能靠 `useEnvelope(src)` 音频包络兜底，包络一失败即整句 dim 0.28（用户看到「字幕全暗」）。agent 本次花 turn3 s30–s43 共 **14 步 / ~7min** 查出根因，改的却是**项目内一次性脚本** `<projectDir>/build/manifest-builder.mjs` 的 `CAPTION_STYLE_KEYS`，**没回写 skill asset ⇒ 下一条片按标准流程做必重现**。

典型的「只修产生路径」缺口，改动最小、收益确定。

### P2-06 · 验收指令与 skill 纪律冲突，缺裁决与终止条件 【T0 规则 + T1 闸】

首轮 prompt 明确要求「首轮就用 `spotFrames` 探针取代表帧，逐张 `read_image` 看**成片像素**后对照判据表逐条打勾」「画面类结论禁拿 manifest 字段自证」「交付前复述未决项」；`verification.md:20` 却要求「静默自检 ≤2 轮就必须出完整草稿落画布」。**两条上位指令对「看多少张图」给出相反要求，且没有裁决序、没有机器可判的终止条件** ⇒ agent 选择严格遵守用户验收，循环到 401。

不能简单砍掉看图：20:57 用户插话「字幕太大了，会遮挡其他内容」正是逐张看图之后才有的**唯一有信息增益的反馈**。正确做法是给上限 + 一次批注出口，不是取消验收。阈值已由 **§8 D5** 定为 probe ≤3 次 / 每次 ≤8 帧 + 成片后 1 次批注。

### P2-07 · 错误处置指引与唯一可行路径冲突 【T2】

`errors.md:8`「不要原样重试」、`:16`「不要反复提交同一份 manifest」；07:26:04 宿主还注入 `You are repeating the exact same tool call with identical arguments` 守卫。**但本次四次相同参数重试是唯一能出片的路径**（帧缓存跨次累积），agent 全部无视。⇒ 该修产品（让续渲成为显式契约、带 `resume` 语义而非「相同参数重复」），不是再加禁令；重复调用守卫的拦截文案若一刀切，会与正当续渲冲突。

### P2-08 · 规范数字失真，误导所有预算判断 【T0】

| 文档 | 写的 | 实测（本次） | 偏差 |
|---|---|---:|---:|
| `verification.md:9` | 探针 1.5s / 全片 draft 24–29s | 探针 8.6–14.8s / draft **187.7s** | 6–8× |
| `timing.ts:1426` 注释 | standard ~58ms/帧 | 首跑 330s 仅 55% ⇒ ~440ms/帧 | ~7.7× |

数字一失真，`renderTimeoutMs` 的 3.4× 余量实际变成 0.4×，agent 按文档做的「探针快、draft 便宜」判断也全错。

### P2-09 · 越界调试产品代码 + 自检未收口 【T1】

turn3 后半段 bash 全在 `grep/sed` 运行时 checkout 的 `Caption.tsx` / `audio-envelope.ts` / `word-timing.ts`（P2-05 的根因），**超出「生成一片」的职责**，且没有「记录未决项 → 降级交付 → 上报」的固定出口，于是一直不结案：s50 宣布成片已生成，s51 发现第 0 帧全空，s52 发现第 222 帧双地球，s53 起新步后转录结束，**没有 `turn/end`**。

### P2-10 · HITL 时机错配 【T0/T1】

阶段一 5 次 `ask_user_choice` 用户**全选「（推荐）」**，零信息增益；全会话真正有效的两次人工反馈都在成片之后（20:57 字幕太大、07:27 高清档要求）。符合阶段一方案「一次性意图卡」的判断，但阶段二还缺一个**成片后一次性批注**的出口，否则用户只能看着 agent 逐帧自检。

### 明确降级 / 不做

- `generate-queue.ts` 单槽并发拆分：阶段二生成类工具仅 160.8s，实测无关；只对成片合成阶段可能有效。
- LLM 规划与媒体渲染彻底解耦 + 本地 DAG 调度器：超出本范围，动 dsh 编排边界，单独评估。
- 自研蒸馏 / 量化：API 调用方碰不到。

## 3. 分析：因果链与共同放大器

```
用户严格验收指令（首轮 prompt）
        ×  verification.md「≤2 轮」但无闸（§8 D5 改 3 轮 + 硬闸） ×  阶段二无轮次预算
        ↓
   probe → read_image → 改坐标 → 再 probe   （turn2 120 步 / 80min）
        ↓
   55 张图进上下文 → 39 次 offload + 2 次 compaction → 每轮 prefill 更贵
        ↓
   401（95min 零交付）→ 8h21m 空窗 → 重新登录
        ↓
   turn3：成片已落画布，但字幕全暗（words 丢失）→ 越界读 Remotion 源码排障 14 步
        ↓
   交付档 4 次撞 330s（预算基于失真基准 + 画布页节流）→ 22.1min 靠隐式续渲出片
        ↓
   s51/s52 又发现两处缺陷 → 无终止条件 → 无 turn/end
```

**三个共同放大器**：① 所有「上限」都是文本规则、没有机器可判的闸；② 上下文随看图线性膨胀、每轮重发；③ 文档基准失真 6–8×，导致所有时间判断系统性乐观。

**为什么阶段一方案不够**：B0/B1\*/B1 把 turn1 从 35 步压到 ≤5 步，方向正确，但只覆盖活跃时长 **13.9%**；turn2+3 占 **86.1%** 且未跑完。即使阶段一全兑现，本次总时长几乎不变。
