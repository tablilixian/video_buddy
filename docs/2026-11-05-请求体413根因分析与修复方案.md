# 请求体 413「request body is too large」根因分析与修复方案

- 日期：2026-11-05
- 现象来源：真机会话截图（成片检查阶段，连续三轮 `本轮运行失败 413: INVALID_REQUEST`，点「继续」重试仍 413）
- 影响：会话在读图后彻底卡死，任何重试都失败，只能开新会话
- 结论一句话：**会话历史累积的内联 base64 图片把 DramaServer `/v1/llm` 的请求体撑爆；harness 的两道本地防线（spill-policy 截断、图片 offload）在这条链路上都没生效，而 413 又被归类为「重发也不会成功」的终态错误，于是无限失败。**

## 1. 现象与错误体

```
本轮运行失败 413: INVALID_REQUEST
{"code":"invalid_argument","message":"request body is too large"}
```

- `{"code":"invalid_argument", ...}` 是 **DramaServer 网关**的错误信封格式（与 2026-10-23 压缩 400 事故同款，见 §6 先例）。
- 413 → `INVALID_REQUEST` 的归类发生在
  `deepseek-harness/packages/llm/llm-pi-ai/src/stream.ts:48`：

  ```ts
  // A rejected request body (gateway or provider size cap): resending the
  // same request cannot succeed, so it is invalid, not transient.
  if (/\b413\b|...|request body too large/i.test(message)) return 'INVALID_REQUEST'
  ```

  语义是「重发同样的请求也不会成功」——所以 UI 上点「继续」必然再失败，与截图三连败吻合。

## 2. 请求链路

```
会话 (VideoBuddy 桌面)
  → llm-pi-ai 适配器（openai-completions 协议）
  → provider 路由 canvas-studio-gateway（canvas-studio/src/gateway.ts:95 gatewayProfile()）
  → baseURL = <businessApiBase>/v1/llm（DramaServer）
  → 413 {"code":"invalid_argument","message":"request body is too large"}
```

网关行由 `canvas-studio/src/index.ts:227 applyGatewayConfig()` 在每次启动/会话推送时
通过 `settings.mutate` 整体写入（deep-strict 比较，形状变了就重写）——**这也是 P0
修复能生效的原因**（见 §4.1）。

## 3. 根因链（每一环都有证据）

### 3.1 图片全部内联进历史，只增不减

会话在成片检查阶段连续 `read_image` 读了十几张图（`check/` 下 contact sheet +
抽帧，单张 21–101 KB）。每张图作为 tool result 的 image block 以 base64 内联进
请求体，并**永久留在会话历史里**，每次后续请求都整包重发。单张不大，累积 + 文本
历史（工具 schema、system prompt、命令输出）就超过网关请求体上限。

> 参考：单张 `final_contact.jpg` 仅 89,117 字节；`check/` 目录共 20+ 张 jpg。

### 3.2 第一道防线失效：spill-policy 拿不到图片定价器，放弃截断

VideoBuddy 日志（`~/Library/Application Support/VideoBuddy/logs/dsh-2026-11-05.error.log`）
从 14:38 起反复出现：

```
spill-policy: Error: the current model has no image token calculator; keeping the inline content
```

机制（`deepseek-harness/packages/spill/spill-policy/src/index.ts`）：

1. spill-policy 要按 token 预算截断超限的工具结果，带图结果必须先给图片定价：
   `ctx.get('llm').imageRequestPricing(provider, model)`（`:65`）。
2. 拿不到定价器就 `throw`（`:66`），被 `:127-130` 的 catch 吞掉，只打告警，
   **原样保留带图内容**（`keeping the inline content`）。
3. 为什么拿不到：`imageRequestPricing` 是 `LlmAdapter` 的可选能力
   （`llm/src/index.ts:236`，基类默认返回 `undefined`）。**`llm-pi-ai` 适配器没有
   override 它**（`llm-pi-ai/src/adapter.ts` 只 override 了 `imageRequestTarget`，
  在 `:238`；全包 grep `imageRequestPricing` 零命中）。只有 `llm-deepseek`
  实现了（`llm-deepseek/src/adapter.ts:42`）。
4. 结果：**网关路由上的带图工具结果永不截断**，spill-policy 的
   `maxInlineTokens: 12500`（base bundle `cordis.patch.yml:417`）对图片完全失效。

> 这条告警在日志里刷屏（14:38 / 14:46 / 14:58 / 15:00 / 15:03 / 15:06 / 15:08 /
> 15:30 / 15:45 …），**是本事故最直接的可观测前兆**。

### 3.3 第二道防线阈值错位：本地 20 MiB 图片预算 vs 网关整体请求体上限

`llm-pi-ai` 自带图片预算 `maxRequestImageBytes`（`llm-pi-ai/src/config.ts:58`，
默认 **20 MiB**，provider profile 级字段 `:173`）。超预算时在
`llm-pi-ai/src/context.ts:343-355` 抛 `IMAGE_OFFLOAD_REQUIRED`，由
`compaction-image-offload`（base bundle `cordis.patch.yml:434` 已挂载）把最老的图片
替换成占位文本并**自动重试**——这是设计好的自愈路径。

但两处错位让它永远触发不了：

| | 本地预算 | 网关 413 |
|---|---|---|
| 计数对象 | 仅 base64 **图片**字节 | **整个**请求体（图 + 文本 + schema） |
| 默认阈值 | 20 MiB | **实测精确 4 MiB（4,194,304 B）**，2026-11-05 已探测确认（见 §4.1 步骤 2） |

于是：本地检查通过 → 请求发出 → 网关拒收 413。**自愈路径在错误发生前没机会触发，
错误发生后又不归它管。**

### 3.4 413 不触发任何恢复

`IMAGE_OFFLOAD_REQUIRED` 才走 offload 重试（`compaction-image-offload/src/index.ts:28`
只认这个 code）。413 被归为 `INVALID_REQUEST`，被视为终态 → 重试发的是同样大小的
请求体 → 再 413。三连败、无法自拔。

### 3.5 因果总图

```
read_image × N（历史只增不减）
   ├─ 3.2 spill-policy 无图片定价 → 不截断（日志告警刷屏）
   └─ 3.3 pi-ai 预算按「图片字节 20MiB」算 > 网关按「整体请求体」算
          ↓
      请求体超过 DramaServer 上限
          ↓
      413 → INVALID_REQUEST（stream.ts:48，终态、不可重试）
          ↓
      image-offload 不接管（只认 IMAGE_OFFLOAD_REQUIRED）→ 三连败
```

## 4. 修复方案

### 分层原则（务必先读）

- `deepseek-harness/` 是**钉死的上游子模块，禁止在桌面特性分支里改**
  （根 `AGENTS.md`）。凡涉及 `llm-pi-ai` / `spill-policy` / `stream.ts` 的改动都属
  上游轨道，单独走「子模块 pin 更新与桌面行为变更分离」的流程。
- **可立即落码的编辑区**只有两处：`canvas-studio/`（网关行）与
  `dsh-plugin-desktop/cordis.patch.yml`。
- 编号纪律：给本条修复取 CV 号前，**先 grep 整个 `canvas-studio/docs/` 取最大号+1**
  （撞号踩过三次）。

---

### 4.1 【P0 · 立即止血 · 编辑区内】给网关 profile 显式设置 `maxRequestImageBytes`

**原理**：把「图片字节预算」压到**网关整体请求体上限之下**，让
`IMAGE_OFFLOAD_REQUIRED` 在网关 413 **之前**触发，从而进入
`compaction-image-offload` 的自愈路径（自动用占位文本替换最老图片并重试）。
这不修根因，但把「永久卡死」变成「自动降级继续跑」。

**改动位置**：`canvas-studio/src/gateway.ts`

```ts
// 与 GATEWAY_MAX_OUTPUT_TOKENS 同一先例：本地预算必须对齐网关真实上限。
// DramaServer /v1/llm 的整体请求体上限低于 harness 默认的 20 MiB 图片预算
// （2026-11-05 真机 413 事故：图片未达 20 MiB 但整包已超网关上限）。
// 注意：该字段只约束 base64 图片字节，不含文本历史——留出文本头部空间。
export const GATEWAY_MAX_REQUEST_IMAGE_BYTES = 2 * 1024 * 1024  // 初值，按步骤 2 实测校准

export interface GatewayProviderProfile {
  displayName: string
  apiKeyEnv: string
  api: string
  baseURL: string
  /** llm-pi-ai provider 级字段：超出即抛 IMAGE_OFFLOAD_REQUIRED 触发自动 offload。 */
  maxRequestImageBytes?: number
  models: { id: string; name: string; contextWindow: number; maxTokens: number; input: GatewayInputModality[] }[]
}

export function gatewayProfile(gateway: GatewayRow): GatewayProviderProfile {
  return {
    displayName: 'DramaServer',
    apiKeyEnv: GATEWAY_CREDENTIAL_REF,
    api: 'openai-completions',
    baseURL: `${gateway.apiBaseUrl.replace(/\/+$/, '')}/v1/llm`,
    maxRequestImageBytes: GATEWAY_MAX_REQUEST_IMAGE_BYTES,
    models: gateway.models.map(/* 不变 */),
  }
}
```

同时把常量纳入指纹，保证**不重启也能被 reconcile 重写**（`gatewayFingerprint`
当前只比 catalog 行，profile 形状变化只有启动恢复路径
`src/index.ts:318` 的 deep-strict 比较能发现；把常量加进指纹 JSON 后，下一次
`reconcileGateway` 就会命中 `applyGatewayConfig` 的形状差异并重写）：

```ts
export function gatewayFingerprint(gateway: GatewayRow | null): string {
  if (gateway === null) return ''
  return JSON.stringify({
    apiBaseUrl: gateway.apiBaseUrl,
    maxRequestImageBytes: GATEWAY_MAX_REQUEST_IMAGE_BYTES,   // 新增
    models: gateway.models.map((model) => [model.code, model.displayName, model.input]),
  })
}
```

**字段合法性**：`llm-pi-ai/src/config.ts:345` 的 provider schema 已声明
`maxRequestImageBytes`（默认 20 MiB），无需动子模块。

**步骤 2：校准初值（✅ 2026-11-05 已探测完成）**

**实测结果**：DramaServer `/v1/llm` 请求体上限 = **精确 4194304 B（4 MiB）**。

- 探测方法（零模型费用）：裸 socket POST 非法 JSON body（`"x" * N`）——未超限时应用层返回
  400 解析错误（不进模型），超限返回 413；带 token 二分。
- `content-length ≤ 4194304` → `HTTP/1.1 400`（应用层处理）
- `content-length = 4194305` → `HTTP/1.1 413 {"error":{"code":"invalid_argument","message":"request body is too large"}}`
  （外层多一层 `error` 包裹，内层信封与会话事故逐字节一致）
- `> ~4.004 MiB` → 服务端直接 reset 连接（连 413 都不回）

**取值结论**：`GATEWAY_MAX_REQUEST_IMAGE_BYTES = 2 MiB`（已落码）——必须 < 4 MiB，
且给文本历史（system prompt / 工具 schema / 会话文本）留 ≥2 MiB 头部空间。
若后续 P2 放大服务端上限，按 `实测上限 − 文本历史余量（≥2 MiB）` 重新校准本常量。

**验收**：
1. 单测 `canvas-studio/tests/gateway.test.mjs` 新增断言：
   `gatewayProfile(row).maxRequestImageBytes === GATEWAY_MAX_REQUEST_IMAGE_BYTES`；
   `gatewayFingerprint` 含该字段。
2. 走 canvas-studio 验证链（铁律顺序）：
   `corepack yarn typecheck && corepack yarn build && corepack yarn verify:loader && corepack yarn test:smoke`
3. 真机复现路径：新会话连续 `read_image` 15+ 张 → 预期**不再 413**，而是日志出现
   `image/offload` 事件、最老图片变成占位文本、会话继续。
4. 收尾四件套：STATUS.md 状态列 + §8 变更记录、canvas-ux-backlog、tracking.md
   （涉 BUG 时）、带 CV 号提交。

**回滚**：删除该字段与指纹行，重启即恢复 20 MiB 默认。

### 4.2 【P1 · 根因 · 上游子模块轨道】让带图工具结果能被截断

两条可选路线，**二选一**，都在 `deepseek-harness/`，需走子模块独立提交 + pin 更新：

- **路线 A（推荐，改动收敛在 spill-policy）**：
  `spill-policy/src/index.ts:66` 在 `calculator === undefined` 时不再直接抛错，
  改用中性估算器兜底（按图片像素/字节估 token，`token-meter/estimate` 已有文本
  估算器可参考）。`LlmAdapter.imageRequestPricing` 的 JSDoc 本身承诺
  「基类返回 undefined 时消费方回落到自己的中性估算」（`llm/src/index.ts:227-235`），
  spill-policy 目前没有兑现这个回落。
- **路线 B（能力对齐）**：给 `PiAiAdapter` 补 `imageRequestPricing` override，
  返回按 `imageRequestTarget`（`adapter.ts:238`）投影尺寸的估算定价，语义对齐
  `llm-deepseek/src/request-pricing.ts:90 deepSeekImageRequestPricing`。

**验收**：带图工具结果超过 `maxInlineTokens: 12500` 时被截断为「路径描述 + 省略
通知」；日志中 `no image token calculator` 告警归零；上游单测 +
`pnpm run test && pnpm run build` 全绿。

**收益**：历史里图片不再无限堆积 → 从源头消除 413 的燃料，P0 的预算只是第二保险。

---

### 4.3 【P2 · 服务端】放大 DramaServer `/v1/llm` 请求体上限

向 DramaServer 侧反馈：`/v1/llm` 的请求体上限过低，且 413 错误体建议带上
`limit` 字段（如 `{"code":"invalid_argument","message":"request body is too large","limit":4194304}`），
便于客户端对齐预算。服务端放宽后，§4.1 的初值可以相应调大。

### 4.4 【用户侧临时绕行 · 无需落码】

在修复发布前给用户的话术：

1. **开新会话**（或先手动 `/compact`），旧会话的历史图片已无法清除；
2. 少逐张读图，优先用 contact sheet 一次看多帧；
3. 「继续」按钮对 413 无效，不要反复点。

## 5. 明确不做的事

- **不要**通过关掉 `read_image` 或调低 `spill-policy.maxInlineTokens` 来「修」——
  前者砍能力，后者对图片无效（定价器缺失在 cap 判断之前就抛了，见 §3.2）。
- **不要**在桌面特性分支直接改 `deepseek-harness/`。
- **不要**把 413 当成可重试错误去加重试次数——同样的请求体重发必然同样失败。
